用語集

CADLおよび周辺の研究プログラムで用いる作業語彙をまとめる。 用語は分野別にまとめている。 リンク先は各用語を詳しく導入している章である。 必要に応じて，項目の末尾に具体例を添えている。

コア言語​

  • CADL — Contract Architecture Description Language。 System of Systems の Institution / Protocol / Algorithm の三層を， 検証可能な単一ドキュメントで記述するDSLである。 仕様書イントロダクション を参照。例：家庭の家事分担ルールから大規模な都市交通システムのガバナンスまで，幅広い制度を記述対象とする。
  • Institution 層 — 誰がどの規則のもとで参加するかを記述する層。 actors:，contracts:，および transitions:（運用モードを切り替える条件） からなる。2.2節と 付録AのA.4節も 同じ定義を用いる。リファレンス実装のIRでは，institution がアクターと契約を保持し， 遷移はトップレベルの別のリストになる。各契約は，当事者， assume / guarantee，authority，information， responsibilities，incentives，violation を記述し， ガバナンスパラメータ α / β / λ を保持する。
  • Protocol 層 — アクター間の協調手続き（メッセージ交換， 計算ステップ，条件分岐，並列ブロック，バリア）を定義する。 定義は5.2.4節と 付録AのA.5節にある。
  • Protocol（プロトコル） — アクター間のやりとりの手順を，時間的な制約付きで定めたもの。 誰が誰に何を送り，どんな順番で処理するかを記述する。 例：(1)顧客が注文→(2)配車係がロボットを割当→(3)ロボットが配達→(4)顧客に通知，という一連の手順。
  • Algorithm 層 — Protocol ステップが利用する中央／ローカル アルゴリズムへの参照。各アルゴリズムは機能名をキーとし， central と local の要素を持つ。
  • Institution（制度） — 人やシステムの間のルール・権限・役割分担・報酬の仕組みの総称。 法律や契約のような明文化されたものから，家庭内の暗黙のルールまで含む。 CADLでは，制度を権限構造・情報共有・インセンティブの3つの側面で記述する。 例：「子どもは夕食前に家事を終える」「完了したら100円もらえる」というルール。
  • Actor（アクター） — SoS に参加する構成システム／エージェント ／役割。id で識別し，範囲指定も可能である。 定義は5.2.2節と 付録AのA.3節にある。例：配送システムでは，ロボット・配車係・お客さんがそれぞれアクターである。
  • autonomy — アクターの属性。low，medium，high のいずれか （既定値は medium）。cadl 0.3.10からは，この3つ以外の値はエラーになる。 値をβなどと照合することはない。cadl sim-gen -t go は，この値に応じて，アクターに 中央のアルゴリズムだけ（low），局所のアルゴリズムだけ（high），または両方（medium）を割り当てる。
  • Stakeholder（ステークホルダ） — 制度設計に関心を持つすべての関係者。 制度に直接参加するアクターだけでなく，制度の影響を受ける人々や，制度を監督する立場の人も含む。 例：配送システムの利用者・配送会社・自治体・周辺住民。
  • Contract（契約） — 当事者集合と権限に紐づく assume-guarantee 制約。制度設計における形式単位である。 定義は5.2.3節と 付録AのA.4節にある。例：「ロボットが正常に動いている限り（前提），配送は約束時間の1.2倍以内に届く（保証）」。
  • Assume-Guarantee（前提-保証） — 契約の基本構造。前提条件（assume）が満たされるなら， 保証（guarantee）を約束するという形式。前提が崩れた場合，保証は免除される。 例：assume「道路が80%以上通行可能」，guarantee「配送成功率95%以上」。
  • Obligation（義務） — アクターが必ずやらなければならないこと。契約上の責任であり， 違反すると罰則が発生する場合がある。例：「データ提供者は精度95%以上のデータを維持する義務がある」。
  • SLA（Service Level Agreement） — サービスの提供者と利用者の間で，どの程度の品質を保証するかを 数値で取り決めたもの。例：「データの遅延は5秒以内」「稼働率99.9%以上」「配送時間は約束の1.2倍以内」。
  • Authority structure（権限構造） — 誰が何を決める権限を持つかの構造。集中的（1人が決定）から 分散的（全員で合議）まで，β で程度を表す。例：β=0.8 では配車係がほぼ全てを決定し，β=0.2 では各ロボットが自律的に判断する。
  • Incentive（インセンティブ） — アクターの行動を促すための報酬と罰則の仕組み。λ でその強さを表す。 例：「時間通り配達：+ボーナス」「遅配：-基本料金の50%」。
  • Transition（遷移） — モード間の切替。from と to（どちらも必須）と， 任意の condition，protocol，safety_invariant で宣言する。 定義は付録AのA.7節にある。

ガバナンスパラメータ​

α，β，λ の文字は，2つの異なるパラメータ体系で使われている。記号と 値域 [0, 1] は共通である。β はどちらも同じ向き（高いほど集中）であるが， α と λ は意味が異なる。

コア言語（契約ごと，第5章）

  • α（アルファ） — 情報共有度。0 は共有なし（各アクターは局所情報 のみを持つ），1 は完全共有。契約の information ブロックに書く。例：α=1.0 では家族全員がスケジュールを閲覧でき，α=0.4 ではIoTデータのメタデータだけを共有する。
  • β（ベータ） — 意思決定集中度。0 は分散（各アクターが自律的に決定）， 1 は集中（単一アクターが決定）。契約の authority ブロックに 書く。例：β=0.8 では配車係が集中的に経路を決定し，β=0.2 では各データ提供者が自分のデータの公開を自律的に決定する。
  • λ（ラムダ） — インセンティブ強度。0 は指令ベース，1 は市場 メカニズム。契約の incentives ブロックに書く。例：λ=0.6 ではお小遣いが行動にそこそこ影響し，λ=0.9 では市場メカニズムで強く制御する。

CADL Explorer のシミュレーション設定（最上位の governance: ブロック，付録C）

  • α（アルファ） — エージェントの自律度。α が高いほど局所的な 判断の余地が大きい。
  • β（ベータ） — 集中度。β が高いほど中央権限が支配的である。
  • λ（ラムダ） — 探索確率。λ=0 は決定的な経路選択を意味する。

動機拡張（付録C）

  • ρ（ロー） — 動機感度。エージェント個別の動機値が意思決定に 及ぼす強さを制御する。ρ=0 は動機非依存，ρ=1 で予算／待機が動機に 完全連動する。
  • κ（カッパ） — 動機値→予算変換のスケール係数。
  • 予算基準値（Budget base） — 動機調整前にアクターへ割り当てる 基本リソース量。
  • Motivation profile（動機プロファイル） — アクター間の動機 分布。uniform / linear / polarized / custom（値のリストを 明示する）のいずれか。

System of Systems (SoS)​

ISO/IEC/IEEE 21841:2019は，SoSを管理構造の違いにより以下の4種に分類している。 CADLはこれら4類型のいずれも記述対象とする。

  • SoS — 独立に管理される複数システムが，運用上の自律性を保ったまま 共通目的に向けて協調する集合体。例：複数の宅配会社のロボットが互いに連携して街全体の配送を効率化するシステム。各ロボットは独立に動くが，全体として効率のよい配送網を実現する。
  • Directed SoS（統率型，D-SoS） — 中央権限が構成システム間の 協調を指示する。例：軍の指揮命令系統。司令部が全部隊の行動を統制する。
  • Acknowledged SoS（認知型，A-SoS） — 構成システムは自律性を 保ちつつ，共有ガバナンスを承認する。例：ロボット配送システム。配車係が全体を管理するが，各ロボットも局所的な障害回避は自律的に行う。
  • Collaborative SoS（協調型，C-SoS） — 支配的な権限なしに， 相互合意によって協調が成立する。例：家族会議で話し合って決める家族のルール作り，マンション管理組合の運営。
  • Virtual SoS（仮想型，V-SoS） — 形式的な協調機構を持たず， 暗黙的／機会主義的に協調が生じる。例：インターネット全体。個々のサービスは独立に運営されるが，結果として巨大なエコシステムを形成する。
  • 五層フレームワーク — SoS設計を5つの階層に分類する枠組み[Shimoyama & Matsubara, 2026]。 (1) 目的（Policy），(2) 制度・ガバナンス（Governance），(3) 制御・協調（Control），(4) 実行・運用（Execution）， (5) 環境・外乱（Environment）からなる。CADLは主に第2層と第3層を記述する。CADL自身の3層との対応は2.2節に示す。 例：Policy「安全最優先」→ Governance「衝突回避ルール」→ Control「経路計画」→ Execution「モーター制御」。

制度の動態​

  • Regime（運用モード）（「モード」とも表記。キーワードやコマンド名では英語の regime を用いる） — ある時点で 有効な制度の設定一式。環境条件が変わると，最適なモードも変わる。 v0.3の構文では，モードは transitions: で使う名前である。 5.1節と付録AのA.7節を参照。例：配車係が集中管理する平常時モードと，各ロボットが自律判断する障害時モード。
  • Regime map（モードマップ） — どの環境条件のときにどのモードが 最適かを表す地図。環境パラメータの空間を領域に分割し，各領域に モードを対応付ける。このパラメータ空間上の地図は概念であり，その 構築支援は計画段階である。cadl regime-map コマンドが報告するのは これより狭く，モード名と遷移からなるグラフである。例：障害率が低く通信遅延が小さいときは集中管理モード，障害率が高いか通信遅延が大きいときは分散自律モード。
  • Regime transition（モード遷移）（「制度遷移」とも表記） — 環境条件の変化に応じて， あるモードから別のモードへ切り替えること。切替中も安全性（衝突回避など）を保証する必要がある。例：通信遅延が300msを超えたら集中管理から分散自律に切り替え，切替中も「衝突なし・注文紛失なし」を維持する。
  • Safety invariant（安全不変条件） — 決して破ってはならない条件。 モード遷移の途中でも満たされなければならない。例：「ロボット同士は衝突しない」「注文データは紛失しない」。

SoS-DSL拡張​

SoS Contract DSL 拡張の用語である。 付録E を参照。

  • Lifecycle（ライフサイクル） — 契約の lifecycle: ブロック。 状態の集合 states，初期状態 initial，終端状態 terminal， 状態間の transitions からなる。
  • Contract instance（契約インスタンス） — 契約の1回の実行。 初期トリガの発火時に生成され，ライフサイクルの状態を進む。
  • Monitor（モニター） — 契約の monitors: ブロックの要素。 観測対象 observe，sampling（イベントまたは周期），述語 rule を記述する。
  • Severity（重大度） — 違反の等級。Minor，Major，Critical のいずれか。
  • deadline / on_violation — ライフサイクル遷移に課す時間 制約。期限が切れると，インスタンスは on_violation.transition が 名指す状態へ，指定の重大度で移る。
  • on_match — モニターの規則が成立したときの動作。違反の報告， 目標状態への移動，またはその両方を行う。

検証​

リファレンス実装の検証器が行う検査は6.3節に示す。 verification: ブロックは付録AのA.8節で 規定する。

  • 形式検証（Formal Verification） — コンピュータを使って，制度記述について，定めた性質（矛盾がないことなど）が 成り立つかどうかを数学的に検査すること。人間のレビューだけでは見逃しがちな矛盾を自動的に発見できる。 例：2つの契約の条件が矛盾していないか（契約の無矛盾性）はSMTソルバで検査し，プロトコルがデッドロックしないかは 構造解析で検査する（6.3節）。
  • 矛盾検出（Contradiction Detection） — 制度記述の中に互いに矛盾するルールが含まれていないかを検出すること。 例えば，ある契約ではAさんに権限があるのに，別の契約ではBさんに同じ権限がある，といった矛盾である。 例：「同じ時間帯に2つの家事が割り当てられている」「プライバシー制約とデータ公開要件が矛盾」。
  • モデル検査（Model Checking） — システムの取りうる全ての状態を網羅的に調べて，望ましくない状態に到達しないかを 検証する手法。例：制度遷移中にロボットが衝突する状態に到達する可能性がないかを全パターン確認する。
  • 反応型合成（Reactive Synthesis） — 仕様（こう振る舞ってほしいという要求）から，その仕様を満たす制御プログラムを 自動的に合成する手法。例：AI安全契約の仕様から，有害な行動を必ず防ぎ，不確実な場合は人間にエスカレーションする制御器を自動合成する。
  • ランタイム監視（Runtime Monitoring） — 制度が実際に運用されている間，契約の条件が守られているかをリアルタイムで 監視すること。違反を検出したら警告や対策を実行する。例：配送中に「配送時間 ≤ 約束時間×1.2」を常時チェックし， 超過しそうなら再割当を実行する。
  • 安全性（Safety） — 「悪いことが起きない」。システム状態に関する 不変条件として表現する。
  • 活性（Liveness） — 「良いことがいずれ起きる」。通常 ◇φ （eventually φ）という時相論理式で表す。
  • 公平性（Fairness） — スケジューリング／資源配分の制約。 いずれの参加者も無期限に飢餓しない。
  • 不変条件（Invariant） — 到達可能な全状態で成立すべき述語。
  • 検証手法 — smt（SMT求解，例: Z3 [de Moura & Bjørner, 2008]），model_check，simulation， proof。リファレンス実装が実装するのは smt だけである。
  • デッドロック — いずれのプロトコルステップも発火不能な大域 状態。
  • モード遷移安全性 — モード間の遷移中に不変条件が侵されない こと。

パイプライン／ツールチェイン​

  • IR（中間表現） — CADL ソースから構築される三層データ構造。 シミュレータ設定の生成器が利用する。
  • コード生成（Code Generation） — CADLの制度記述から，実際に動くプログラムコードを自動的に生成すること。 制度の設計図から実装を自動的に作る。例：配送SLAの契約記述から，配車アルゴリズムのスケルトンコードと， SLA違反を監視するモニターコードを自動生成する。
  • Codegen ターゲット — 付録D の カタログに挙げた出力形式。unity と go（シミュレーション設定）， ros2（ランタイムノード），python，solidity（スマート コントラクト），opa（Regoポリシー），unity-csharp（Unity向けの 契約ランタイム），ユーザ定義ターゲットがある。
  • シミュレータ設定 — 下流シミュレータ（例: Unity）に渡す 環境＋アクター＋ガバナンス設定。
  • パイプライン — CADL → IR → シミュレータ設定 → 実験 → 評価。
  • CADL Explorer — パイプラインを端から端までたどれる対話型 ウェブアプリ。 cadl-explorer.streamlit.app と ソースリポジトリ を参照。
  • Saved comparisons（保存した比較） — CADL Explorer で保存した比較 （Save this comparison）のセッション内の記録。CSV / JSON で エクスポートできる。CADL Explorer v0.4.0 より前の名前は「Run history」。
  • CADL id / IR id / config id — 各段階（CADL 設定，IR，シミュレータ 設定）の SHA-256 の16進表記の先頭 12 桁。CADL Explorer が表示する。同一の CADL id ＋同一シード集合なら結果が一致する。

評価指標​

  • Throughput（スループット） — 単位時間あたりの完了タスク数 （フリート全体）。CADL Explorer では，300 秒の 1 回の実行での配送の 合計として示す。
  • Autonomy（自律性） — ローカルに決定された意思決定の割合 （中央指示との対比）。
  • Fairness（公平性） — アクター間の負荷／報酬分布。
  • Region（性能–自律性平面の領域） — 実験群が throughput × autonomy の2次元平面で覆う凸領域。

関連規格・略語​

  • IEC 62853 — Open Systems Dependability 規格 [IEC 62853:2018]。CADL における システムライフサイクル，合意形成，説明責任の捉え方は，オープン システムディペンダビリティの考え方を参照している。CADL はこの規格 への適合を主張するものではない。例：制度変更時の合意形成プロセスや，障害対応時の説明責任の仕組みをCADLで記述する。
  • ISO/IEC/IEEE 21841 — SoS 分類 （Directed / Acknowledged / Collaborative / Virtual） [ISO/IEC/IEEE 21841:2019]。
  • EBNF — Extended Backus–Naur Form [ISO/IEC 14977:1996]。付録Aで CADL の 具象構文を定義するのに使用する。
  • SMT — Satisfiability Modulo Theories。CADL の method: smt 検証の基盤である。
  • OPA / Rego — Open Policy Agent [Open Policy Agent] とそのポリシー言語。制度制約の codegen ターゲットの一つである。

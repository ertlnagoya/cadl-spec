付録L. 判断の記録（decisions 0.1）

付録K，K.5では，モデルのバージョンは，その根拠となった判断の記録を URI参照で指すことができる。K.5は記録そのものについては何も定めない。この付録は，そのような記録の形式を 定める。この形式の記録を，判断の記録と呼ぶ。判断の記録があれば，記録を書いたシステムを知らないツールでも， 記録を読み，検査し，示すことができる。

判断の記録はモデルとは別のファイルであり，モデルのキーではない。CADLファイルは，判断の記録を使うために 何も宣言しない。コアと拡張のどの判定も，判断の記録によらない。形式は規定であり，判断の記録を残すか どうかは各システムが決める。リファレンス実装は，まだ判断の記録を読み書きしない（L.10）。

L.1 動機と範囲​

コースDのロボットの街は，期ごとに規則を改正する。LLMが改正案を 出し，ツールが同じ乱数シードで改正案を測って憲法の判定にかけ，3社が投票する。判定やLLMが求めたときは， 人間が判断する。人間は，LLMが選択肢を推奨する判断要求を読んでから判断する。人間はKPIも書き，LLMが KPIを複数の読み方で読んだときは，どう測るかを選ぶ。

このような改正のループには，後から次の2つが問われる。

  • 合意：それぞれの変更に誰が同意したか。各社は賛成したか。賛成しなかったなら，誰がその投票を覆したか。
  • 説明責任：誰が，どの手続きで，何を根拠に，なぜ判断したか。判断した者が分からなかったことは何か。 後で何を確かめると約束したか。

演習では，人が読むための decisions.md と gsn.yaml がこれに答える。robot-town v0.2.2 より後は evidence.json もこれに答える。evidence.json はプログラムで読めるが，演習に結び付いている。判定と メトリクスの名前が，シミュレータのものである。判断の記録は，同じ問いに，システムによらない形で答える。 判断ごとに次のことを記録する。

  • どの目的のもとで判断したか（所有者が書いた文と，その測り方）。
  • 何が，誰によって提案され，何が測られたか。
  • それぞれの改正案がどの検査を通ったか，誰が検査したか。
  • 各当事者がどう投票したか。
  • 提案者が何を予測し，助言者が何を推奨したか。その理由と前提，何が分からないと述べたか。
  • 誰が，どの手続きで，どの理由，前提，分からないことのもとで判断したか。判断がどの項目を根拠としたか。
  • モデルのどのバージョンが効力を持ったか。
  • 判断した者が後で何を確かめると約束したか。それが果たされたか。

どの当事者にも同じ証拠を求める。LLMやツールが行った提案，推奨，判断は，人が行ったものと同じ フィールドで記録し，同じ規則で検査する。理由，根拠とした項目，前提，予測，分からないことである （L.4の「証拠のフィールド」）。コースDでは，LLMが提案と推奨を行い，人間に代わって判断することもある。 規則の改正でも，顧客との契約の改正でも同じである。確認する人は，LLMの判断を人間の判断と同じように 詳しく読めなければならず，誰が誰に代わって判断したかを記録から読み取れなければならない。

この付録が定めるのは，項目とそのフィールド，項目のあいだの参照，ファイルの完全性，検証者の検査である。 定めないのは，項目を生み出す手続き（システムがどの判定を行うか，改正案をどう作るか），メトリクスの 意味（その式と測定方法はモデルにある，K.5），ツールが記録をどう示すかである。

L.2 概念​

  • 判断の記録は1つのファイルである。1つのモデルに対する一連の判断を扱う。改正のループの1回の実行， または運用中のシステムの全期間がその例である。

  • 当事者は，判断に加わる人，組織，ソフトウェアエージェント，LLM，ツールである。当事者は1つ以上の 役割を持つ。

    役割当事者が行うこと
    owner目的を書く
    proposer改正案，または目的の読み方を提案する
    assessor改正案を測り，検査する
    voter改正案に投票する
    advisor判断する者に選択肢を推奨する
    decider判断する。ほかの当事者に代わって判断することもある（on_behalf_of，L.3）
    affected判断の影響を受けるが，判断には加わらない（顧客など）。項目が誰に影響するかを示すために挙げる

  • 項目は，記録のヘッダより後の1行である。項目は，種類（L.4），識別子，項目を作った当事者，項目が属する システムの時間上の時点（K.4と同じく，期または時刻），項目を書いた時刻を持つ。

  • 項目の根拠は，その項目のもとになった，より前の項目の並びである。判断は根拠として，有効な目的，測定， 検査，投票，推奨を挙げる。

  • 後で確かめる約束（follow-up）は，判断とともに，後で何かを確かめる，または行うと約束するものである。 後の項目が約束を果たす。

  • 項目は変更しない。訂正は，前の項目の誤りを述べる後の項目である。

L.3 ファイルの形式​

判断の記録は，UTF-8のJSON Linesのファイルであり，各行は改行で終わる。最初の行はヘッダであり，続いて 項目が書いた順に並び，完全な記録は終わりの記録で終わる。ファイル名は decisions.jsonl を推奨する。

どの行も，付録G，G.8の3つの完全性のフィールド seq，prev，digest で 終わる。これらはG.8のとおりに，行の正規化JSONに対して，SHA-256で，または鍵付きの記録ではHMAC-SHA256で 計算する。行はG.8の書き出しの形に従う。連鎖の限界と，ファイルの外に保管するアンカーについてG.8が 述べることは，判断の記録にも当てはまる。記録を書く者は，最後の行の digest と run_id を記録の外に 保管することが望ましい。

行完全性のフィールドより前のフィールド
ヘッダdecisions_format："cadl-decisions/1"。hash，key_id，run_id：G.8のヘッダと同じ。model：name（モデルの sos.name），version（最初のバージョンの sos.version，または null），source_sha256（CADLファイルの最初のバージョンのバイト列のSHA-256，または null）。time_base：期が何であるかの説明，または null。started：記録を始めた時刻（UTCのISO 8601のタイムスタンプ）。previous：別の記録の続きであるときは，その記録の run_id と終わりの記録の digest。そうでなければ null。parties：当事者（下記）。
項目L.4の共通のフィールドと，種類ごとのフィールド。
終わりの記録decisions_end：true。entries：ヘッダと終わりの記録のあいだの項目の数。

終わりの記録がない記録は，書いている途中であるか，書く者が書き終えなかったものである。検証者は，それを 開いた記録として報告する。完全な記録に項目を足すことはできない。記録はヘッダを1つだけ持つので，一連の 判断を続けて記録する者は新しい記録を始め，そのヘッダの previous で前の記録を指す。

当事者。parties の各当事者は次のフィールドを持つ。

フィールド内容
id記録の中での当事者の識別子。英字，数字，_，-，.。
kindhuman，organisation，agent，llm，tool のいずれか。
rolesL.2の役割を1つ以上。
name読む人のための名前，または null。
actor当事者が，モデルのどのアクターまたは役割にあたるか。K.3の decided_by: と voters: が指す形で書く（COUNCIL，service_operator）。なければ null。
modelllm ではモデルの識別子，tool ではツールの名前とバージョン。それ以外は null。
on_behalf_ofこの当事者が代わりを務める当事者の id，または null。サービス運営者に代わって判断するLLMは，自身が役割 decider を持ち，ここに運営者の当事者を書く。

種類が human の当事者は，人が担う役割を表す。記録はその人の名前を示さなくてよい。誰がその役割を 担ったかは，記録を保管する組織が扱う。種類が llm と tool の当事者は model を持つ。どのモデル， どのバージョンのツールが項目を作ったかを，読む人が分かるようにするためである。

L.4 項目​

共通のフィールド​

フィールド内容
id項目の識別子。記録の中で一意。英字，数字，_，-，.。K.5がこの項目を指すときのフラグメントである（L.7）。
type下記の種類のいずれか。
point項目が属するシステムの時間上の時点。{"period": k}（k ≥ 1）または {"at": "<ISO 8601>"}。K.4の time_point と同じ。
written項目を書いた時刻。UTCのISO 8601のタイムスタンプ。
by項目を作った当事者の id。
basisこの項目の根拠となった，より前の項目の id。空でもよい。
fulfilsこの項目が果たす，より前の follow_up の項目の id。空でもよい。
attachments項目に属するファイル。path（記録からの相対パス），sha256，media_type または null。測定の表，LLMの出力，改正案のCADLファイルなど。
generated文をLLMが生成した項目では，ほかの当事者が項目を書いたときも，model（モデルの識別子）と request_digest（LLMへの依頼の要約）。同じ入力による2回の実行と，異なる入力による実行を見分けるためである。それ以外は null。

判断，判断の要求，推奨の選択肢は，proposal の項目の id，またはモデルを変えないことを表す "keep" である。

証拠のフィールド​

proposal，recommendation，decision は，作った当事者の種類によらず，さらに4つのフィールドを持つ。

フィールド内容
reasonその当事者が，なぜそれを提案，推奨，判断するか。当事者自身の言葉で書く。空であってはならない。ただし procedure が automatic の判断は，代わりに rule を持ち，null でもよい。
assumptions当事者が確かめずに正しいとしていること。文の並び。
unknowns当事者が分からず，知る必要があると述べたこと。文の並び。
predictions当事者が起こると予測すること。option（予測の対象の選択肢。提案では自身の id），subject（メトリクスは metric:<名前>，1つの当事者のメトリクスは metric:<名前>@<当事者>，投票は vote:<当事者>），expected（increase，decrease，unchanged，yes，no，または "<= 1" のような条件の文字列），note（文，または null）の並び。

並びは空でもよい。空の unknowns は，当事者が分からないことを何も挙げなかったことを表す。これらの フィールドによって，確認する人は，各当事者が述べたことを後で測ったことと比べられる。人でもLLMでも同じ 方法で比べる。

種類​

objective：所有者が書いたままの目的の文（コースDのKPI）。point から次の目的までのあいだ有効である。

フィールド内容
text書かれたままの文。
measure所有者が測り方を書いたときは，目的の測り方。測り方の項目（下記）の並び。提案者に読み方を任せるときは null。そのときは，種類が measure の proposal の項目が読み方を出し，decision が1つを選ぶ。

測り方の項目は，metric（モデルのメトリクス，またはシステムでの名前），role（goal，watch， guard のいずれか），direction（increase，decrease，または null），target（"<= 1" の ような条件の文字列，または null）を持つ。最初の goal が主目標である。

proposal：変更の提案。

フィールド内容
kindamendment（モデルの新しいバージョン）または measure（目的の読み方）。
title短い題名。
changes改正では，parameter（K.3のパラメータの id，またはシステムでの名前），from，to（数，または時間の文字列），layer（rule，contract，regulation，または null）の並び。
objective読み方では，読む目的の id。
measure読み方では，測り方の項目。
affected変更の影響を受け，その判断に加わらない当事者の id。顧客との契約の変更での顧客など。空でもよい。

提案は証拠のフィールドも持つ。

measurement：有効なバージョン，または改正案について測った値。

フィールド内容
of"in_force"，または改正案の id。
version測ったバージョンの sos.version（in_force のとき），または null。
methodK.5の measure: と同じく，runs（実行の回数），window（時間の文字列，または null），description（文，または null）。
values実行をまとめた測定値。メトリクスの名前から数への写像。
per_party当事者ごとの値。当事者の id から，メトリクスの名前から数への写像への写像。または null。各社の効用など。
compared_with比べる相手の測定の id，または null。
runs_better主目標について，compared_with よりよかった実行の数，または null。

check：1つの改正案を検査した結果。

フィールド内容
proposal改正案の id。
resultsname（cadl check，constitution，invariants，gain のような，システムでの検査の名前），passed（true，false，当てはまらないときは null），note（文，または null）の並び。

vote：1人の投票者の，1つの改正案への投票。

フィールド内容
proposal改正案の id。
valueyes，no，abstain のいずれか。
reason投票者が述べた理由，または null。

request：判断する者に送る，判断の要求。

フィールド内容
to判断する者の id。
question問い。
options選択肢。
whyその者に判断を求める理由。option と reason（文）の並び。

recommendation：助言者の推奨。

フィールド内容
request判断の要求の id，または null。
optionsoption，summary，affected（誰が得をし，誰が損をするかの文）の並び。
recommends推奨する選択肢，または null。

推奨は証拠のフィールドも持つ。

decision：判断。

フィールド内容
question判断した問い，または null。
options選べた選択肢。
choice選んだ選択肢。
proceduresingle（判断する者が単独で判断した），vote（choice への投票の結果に従った），override（判断する者が投票の結果を覆した），automatic（ツールが rule に書いた規則を適用した）のいずれか。
ruleautomatic では，その規則の文（たとえば「すべての検査と投票を通った案のうち，改善が最も大きいものを採択する」）。それ以外は null。
affected判断の影響を受ける当事者の id。空でもよい。
result判断の後に有効な sos.version。読み方についての判断では null。

判断は証拠のフィールドも持つ。

version：モデルのバージョンが効力を持つ。

フィールド内容
versionその sos.version。
previous置き換える sos.version，または null。
effective効力を持つ時点。K.4の effective: と同じ。
source_sha256そのCADLファイルのバイト列のSHA-256。
decisionそれを採択した判断の id。最初のバージョンでは null。

follow_up：後で確かめる，または行う約束。

フィールド内容
text行うこと。
due期限。point の形，または null。
decision約束をした判断の id，または null。

correction：前の項目の訂正。

フィールド内容
corrects訂正する項目の id。
text何が誤りで，何が正しいか。

note：当事者が記録に残したいその他のこと。text に書く。

L.5 参照と順序​

項目は，それより前に書かれた項目だけを指す。basis，fulfils，proposal，of，compared_with， request，decision，objective，corrects，options，choice の id は，前の行の id （または "keep"）である。項目の point は減らない。1つの時点の中では，項目は生じた順に書く。目的， 改正案，測定と検査，投票，判断の要求，推奨，判断，後で確かめる約束，バージョンの順である。この順序は推奨 であり，検証者は，この順序に従わない記録を報告しない。

L.6 検査と指摘​

検証者は，次のものをエラーとして報告しなければならない。エラーのある記録は，そのままでは信頼できない。

  • L-1 ファイルはUTF-8のJSON Linesであり，最初の行は decisions_format が "cadl-decisions/1" の ヘッダである。どの行も，その種類に対するL.3とL.4のフィールドを持ち，ほかのフィールドを持たない。
  • L-2 完全性のフィールドが，G.8のとおりに検証を通る。鍵付きの記録では鍵を用いる。
  • L-3 当事者の id は一意であり，項目の id も一意である。
  • L-4 項目が指す id は，フィールドが求める種類の，より前の項目の id である（L.5）。選択肢を表す ところでは "keep" でもよい。fulfils は follow_up の項目を指す。point は減らない。
  • L-5 by は，種類が求める役割を持つ当事者を指す。objective は owner，proposal は proposer， measurement と check は assessor，vote は voter，recommendation は advisor，decision は decider である。request，follow_up，version，correction，note はどの当事者でもよい。
  • L-6 判断の choice は，その options の1つである。改正案への投票は，その改正案への vote の 項目で，投票者ごとに1つである。同じ投票者の後の投票は，前の投票に代わる。procedure が vote または override の判断は，choice について判断する（choice が "keep" のときは，options の 最初の改正案について判断する）。その改正案へのそれまでの投票をすべて basis に持つ。vote では， 投票がK.3の判断者の定めに従って結果を決める。投票者の賛成が定足数に届くのは，判断がその改正案を 採択するときに限る。override では，投票が結果を決めない。賛成が定足数に届くかどうかは，有効な バージョンのCADLファイルがあるときだけ検査できる（L-9〜L-11）。ないときは，検証者は検査しなかった ことを示す。procedure が automatic の判断は rule を持ち，判断する者は種類が tool の当事者で ある。ほかの判断の rule は null である。
  • L-7 改正案を採択する version の項目は，その改正案を choice とする判断を指し，その判断の result はバージョンの version である。
  • L-8 どの proposal，recommendation，decision も，当事者の種類によらず，L.4の証拠のフィールドを 持ち，その reason は空でない（L.4が automatic に認める場合を除く）。種類が llm と tool の 当事者は model を持つ。当事者の on_behalf_of はほかの当事者を指し，自身の代わりを務める当事者は ない。予測の subject は，メトリクス，または役割 voter を持つ当事者を指す。

バージョンのCADLファイルが手元にあるとき（version の項目の attachments のパス，または検証者に 渡されたファイル），検証者は次のものも報告しなければならない。

  • L-9 ヘッダと各 version の項目の source_sha256 は，ファイルのSHA-256である。ファイルの sos.version，amendment.previous，amendment.effective は項目のものと同じである。
  • L-10 種類が amendment の改正案の各 parameter は，有効なバージョンのK.3のパラメータであり， from はそのパラメータの値，to はK.3が1回の改正で許す値である。
  • L-11 改正案を採択する判断の判断する者は，それが変える各パラメータのK.3の判断者である（actor が decided_by: である当事者）か，その当事者に代わって判断する（on_behalf_of）。そうでなければ， 判断の procedure は override である。 結果を決める投票の投票者は，actor が voters: にある当事者である。

検証者は，次の指摘も報告する。指摘はエラーではない。記録が，確認する人の見るべきことを示しており， それが正しかったかどうかは確認する人が判断する。

指摘記録が示すこと
override判断が投票の結果を覆した（procedure が override）。
against recommendation判断が，根拠にある推奨と違う選択肢を選んだ。
delegatedほかの当事者に代わって判断する当事者（on_behalf_of）が判断した。サービス運営者に代わるLLMなど。
unknowns判断，または判断の根拠にある推奨が，その当事者の分からなかったことを挙げている。
prediction missed提案，推奨，判断の予測が，後の項目と食い違う。メトリクスの予測では，予測の対象の選択肢の後の測定が，その compared_with の測定と比べて，上がっていない（increase），下がっていない（decrease），変わっている（unchanged。許す幅は検証者が示す），または条件を満たさない。投票の予測では，予測が指す当事者の後の投票が，予測と違う。
affected not measured判断が採択する改正案について，その affected の当事者（contract の層のパラメータの変更では，役割 affected を持つ当事者）の値が，根拠にあるどの測定の per_party にもない。
unmeasured choice判断が，種類が amendment の改正案を，その測定を根拠に持たずに採択した。
reading not decidedmeasure のない目的のあと，判断が読み方を選ぶ前に測定が行われた。
open follow-up後で確かめる約束が果たされておらず，その due の時点を過ぎている（または記録が完全である）。
corrected項目に訂正がある。
open record記録に終わりの記録がない。

L.7 付録Kとの関係​

amendment.decisions（K.5）の項目は，kind: record と，フラグメントが項目の id であるURI参照に よって，判断の記録の項目を指す。

sos:
  version: v2
  amendment:
    previous: v1
    effective: { period: 2 }
    decisions:
      - id: d1
        kind: record
        ref: decisions.jsonl#D1
        text: "block_k 3 → 2，BとCの反対票を覆して採択"
    parameters:
      - id: block_k
        layer: rule
        value: 2
        decision: d1
        # ...

記録とモデルは，異なる当事者が異なる時点に書くので，どちらも他方に依存しない。モデルは記録の項目を 指すことができ，記録はモデルのバージョンを sos.version とファイルのSHA-256で指す（L-9）。

L.8 GSNへの対応（参考）​

判断の記録は，GSNのアシュアランスケースとして示すことができる。ツールがGSNを別に書かずに記録から 導けば，両者が食い違うことはない。

項目またはフィールドGSNの要素
一連の判断の最上位のゴール（「システムは所有者の目的を満たし続ける」など）Goal（ツールが書く）
objective最上位のゴールの下のGoal。目的ごとに1つ。
有効な測り方目的のGoalのContext
decision有効な目的のGoalの下のStrategy。選択の論証である。
point とその期の条件StrategyのContext
根拠にある measurement と checkStrategyのSolution
reasonStrategyのJustification
assumptionsStrategyのAssumption
unknowns と predictionsStrategyのContext。後の測定と食い違った予測は，そのStrategyへの反証である。
根拠にある recommendationStrategyのContext
follow_upStrategyの下のGoal。後の項目が果たすまでは未展開とし，果たした項目をそのSolutionとする。

L.10 リファレンス実装の状況​

cadl 0.3.37から，次のものがある。

  • cadl.decisions.DecisionChain は記録を書き，cadl decisions-verify RECORD.jsonl は記録を検査する。 エラーL-1〜L-8と，バージョンのCADLファイル（version の項目の .cadl の添付と，--version で渡した ファイル）に対するL-9〜L-11を報告する。L.6の指摘を報告し，検査できなかったものを挙げる。値が比べる 値の1%以内なら unchanged とみなす。--key，--run-id，--anchor は cadl audit-verify と同じで ある。
  • cadl-robot-town（v0.3.0から）は，town.steward と town.council の実行ごとに decisions.jsonl を 書き出す。--decider llm では，LLMが運営者に代わって判断要求に答え，on_behalf_of を持つ当事者と して記録される。演習のモデルは改正拡張を宣言していないので，バージョンの項目はCADLファイルを添付せず， L-9〜L-11は検査されない。
  • cadl-explorer（v1.5.0から）のページDecision Evidenceは，記録を読み，cadl.decisions で検証し， 当事者の時系列，各判断の経緯，当事者ごとの証拠，L.8のGSN，指摘，連鎖を示す。

L.11 後方互換性​

この形式は新しい。CADLファイルのキーと判定を変えない。K.5は変わらない。K.5の ref: が判断の記録の 項目をどう指すかは，L.7が述べる。

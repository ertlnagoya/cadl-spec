付録J. 制度パラメータの規範による根拠付け（grounding 0.1）

本付録は，CADLの根拠付け拡張を規定する。この拡張は，規範拡張 （付録F）の上に成り立ち，contract_def （A.4）にキー grounding: を， norm_def にキー shares: と on_fulfilment: を，on_violation: にキー magnitude: を 追加する（F.3）。さらに，戦略モデル拡張（付録I）も用いるファイルでは， 利得の項（I.2）にキー sanction_of: と reward_of: を追加する。これにより，処理系は，契約の規範から， 2つの導出指標 α̂ と β̂，およびインセンティブ被覆率 χ を計算し（いずれも [0, 1] の中にある）， 宣言された alpha と beta を指標と比べる。本拡張は，また，戦略モデルにおいて規範の制裁を表すと 宣言した利得の項の重みを定義する。それは，規範の宣言する大きさにλを掛けたものである。

コア言語は，これらのキーを必須としない。本拡張を実装していないCADL準拠の処理系は， これらのキーを理由にファイルを拒否してはならない。キーを構文上は受理し，情報レベルの診断を 出すことが望ましい。

拡張の名前は grounding であり，本付録はバージョン 0.1 を記述する。本拡張は norms: 0.1 を 必要とする。本拡張を用いるファイルは，extensions: （A.2）で両方を宣言しなければならない。 宣言せずに用いた場合に処理系がどう扱うかはJ.12で述べる。キー sanction_of: と reward_of: は， さらに stochastic: 0.1 と games: 0.1 を必要とする。

sos:
  ...
  extensions:
    - norms: 0.1
    - grounding: 0.1

J.1 動機と範囲​

5.4.2節は，制度パラメータα，β，λを，定性的な端点を持つ [0, 1] の数として 定義する。言語の他の部分は，中間の値が何を意味するかを述べない。設計者は beta: 0.7 と書くが， その数を，それが置かれた契約に関係付ける規則はない。付録Fは，意図する読み方（βは契約の権能を誰が 持つかを表し，αは他の当事者がどの発動条件と内容を観測できるかを表し，λは違反された規範の制裁の 大きさを調整する）を参考として述べるにとどまる。9.6節は，規範とパラメータの 形式的な結び付きを未解決としており，RD-1.5は，λを契約のパラメータとして扱うことを求めている。 制度の規則を，それが何に作用するかによって分類する方法には，情報の規則，集約の規則，利得の規則が 含まれる [Ostrom, 2005]。これは，3つのパラメータが3種類の規範を 要約することを示唆する。grounding 0.1では，その最初の部分に取り組む。本拡張は，α，β，λに，規範による形式的な 意味を与えない。それは，以下に述べるもの以外は未解決のまま残る。

  • 2つの指標と1つの被覆率を，ファイルから計算する。 J.4は，α̂，β̂，χを，1つの契約から読み取る 有限集合の上の，個数の比として定義する。これらは，2つの処理系が同じファイルから同じ数を計算すると いう意味で，再現可能である。α̂については，分子も分母も記述者の注記（項目と shares: のリスト）に 基づくので，指標の質は注記の質で決まる。
  • 指標は証拠であり，パラメータの意味は定めない。 指標は，宣言されたパラメータに取って代わらず， 5.4.2節を変えない。指標は，契約の規範についての構造的な事実であり，宣言値はそれと合うことも 合わないこともある。指標が捉えられないものは，J.4に述べる。
  • 宣言値を指標と比べる。 宣言されたαまたはβと，その指標との不一致は，関係する構成要素を名指す 警告である（J.5）。本付録のどの規則も，付録Fのもとで有効であり，新しいキーを1つも用いないファイルを， 無効にしない（J.12）。
  • λは倍率である。 本付録では，λは制裁と報酬の大きさに掛かる。λを導出指標と比べることはしない。 χが表すのは別のもの，すなわち，λが掛かり得る制裁または報酬を伴う規範の数である。
  • 制裁に大きさを与え，モデルがそれを用いる。 magnitude: は，規範の制裁または報酬に数を与える。 戦略モデルでは，sanction_of: で宣言した利得の項は，定義により，重み −magnitude·λ を持つ。 ここでλは，契約の lambda に束縛したパラメータである（J.7）。その項が制裁を表すこと，すなわち， その報酬構造が規範の違反を数えていることは，記述者の仮定のままであり，そのような項を用いて計算した どの結果も，その仮定とともに報告する。

バージョン0.1の範囲。

  • 指標は1つの契約に関するものであり，同じ3つの量をファイルのすべての契約の上でも定義する（J.4の 「SoSの量」）。それらを宣言値と比べることはせず，重み付けした指標は定義しない。
  • 情報項目は記述者が宣言する（grounding.items）。アクターのインタフェース，述語，メッセージからは 導出しない。
  • 指標は個数である。大きさ，重大度，権能が影響する規範の数による重み付けはしない。
  • magnitude: と on_fulfilment: は，付録Fの動的意味論に影響しない。判定，違反，反義務の規範は 変わらない。
  • 本拡張は，規範からモデルを導出せず，モデルの報酬構造が規範の違反を数えていることを検査しない （H.8は，規範とモデルの間の変換を定義しない）。
  • 付録Gの委任と，付録Cの動機パラメータρと κについては，指標を定義しない。

J.2 概念​

概念grounding 0.1での意味
アクター名アクター参照から添字を除いた識別子。ROBOT[i]，"ROBOT[*]"，ROBOT[2] のアクター名は ROBOT である。
当事者名契約の parties: の項目のアクター名。同じアクター名を持つ項目は，1つの当事者である。
単一のアクター整数の添字を持つアクター参照，または，アクターが範囲なしで宣言されているときの，添字のないアクター参照。
情報項目grounding.items に宣言する，名前付きの情報。その起点，すなわちその情報が由来する当事者を伴う。1つの項目の起点は1つである。2つの当事者に由来する情報は，2つの項目として宣言する。
共有規範内容がメッセージであり，shares: を持つ義務または許可。そのメッセージは，挙げた項目を受信者に与える。
大きさ（magnitude）負でない数。インセンティブ強度が最大（λ = 1）であるときの制裁または報酬の大きさであり，契約の計算単位で表す。
導出指標α̂またはβ̂。1つの契約から計算する [0, 1] の有理数であるか，未定義である。
インセンティブ被覆率χ。契約の義務と禁止のうち，制裁または報酬を伴うものの割合であるか，未定義である。

規範，義務，許可，禁止，権能，負担者は，付録Fの意味を持つ。

J.3 構文（A.4，F.3，I.2へのEBNFの追加）​

文法は付録Aの記法に従う。identifier，actor_ref，number，text は 付録Aで定義している。

contract_def    = ... , [ "grounding:" , grounding_block ] ;
grounding_block = [ "items:"     , { identifier , ":" , actor_ref } ] ,
                  [ "tolerance:" , number ] ;

norm_def        = ... ,
                  [ "shares:"        , { "-" , identifier } ] ,
                  [ "on_fulfilment:" , norm_fulfilment ] ;
norm_violation  = ... , [ "magnitude:" , number ] ;
norm_fulfilment = [ "reward:"    , text ] ,
                  [ "magnitude:" , number ] ;

payoff_term     = "reward:" , identifier ,
                  ( [ "weight:" , param_expr ]                  (* I.2 *)
                  | "sanction_of:" , norm_ref
                  | "reward_of:"   , norm_ref ) ;
norm_ref        = identifier , "." , identifier ;               (* string *)
  • grounding.items は，各情報項目の名前を，その起点に対応付ける。tolerance: は [0, 1] の数であり， 既定値は 0.25 である（J.5）。
  • shares: は，共有規範のメッセージが伝える情報項目を列挙する。
  • on_violation.magnitude は，規範の制裁の大きさである。
  • on_fulfilment: は，規範を履行したことに対する報酬を記録する。reward: は，sanction: が制裁を 述べるのと同じく，報酬をテキストで述べ，magnitude: はその大きさである。報酬は，規範インスタンスが F.5の状態 fulfilled に達したときに支払われたものとみなす。義務では，その内容が期限内に実現された ときである。禁止では，違反のないまま，その期間が閉じるか，契約インスタンスが終わったときである。 インスタンスが discharged になったときは，その判定は fulfilled であるが，報酬は支払われない。 このブロックは注記であり，付録Fの意味論に影響しない。
  • norm_ref は，引用符付きの文字列 "C.n" である。契約の id，ドット，その契約の規範の id からなる。

本付録のどのキーについても，空のテキスト，または空白だけからなるテキスト（sanction: ""， reward: " "）は空として扱い，YAMLのnullは，ないものとして扱う。テキストは，YAMLの読込み後のものと する。ローダが数や真偽値として読む引用符のないスカラーは，書かれたとおりのテキストである （sanction: 0 はテキスト "0" であり，インセンティブを伴う）。記述者は，そのようなテキストを引用符で 囲むことが望ましい。列またはマッピングである reward: は誤りである（J-4）。大きさは10進小数で 書かなければならない。YAML 1.1のローダは，1e3 を文字列として読み（J-4の誤り），1.0e-7 を数として 読む。引用符のない項目名の うち，YAML 1.1のローダが真偽値やnullとして読むものは，引用符で囲まなければならない （A.12）。

J.4 導出指標と被覆率​

3つの量は，本拡張を宣言するファイルのどの契約 C についても定義する。それぞれ，2つの個数の比であるか， 分母が0であるときは未定義である。未定義の量は，J.5のどの比較にも関与しない。

情報共有：α̂​

C の当事者名の集合を Π，grounding.items の項目の集合を X，項目 x の起点を o(x)（当事者名である。 J-2）とする。C の組とは，項目 x と，o(x) 以外の当事者名 q の組 (x, q) である。これは，項目を 当事者と共有し得る場所である。

宛先が当事者の全体を表すかどうかは，F.3のアクター参照の照合に従う。アクター参照 T は，その アクター名が q であり，かつ，単一のアクター A（J.2），A[*]，識別子を添字とする A[i]，アクターを 宣言したときの範囲の全体，または記号的な上限を持つ範囲（F.3により，すべての要素に一致する）で あるとき，当事者 q の全体を表すという。整数の添字を持つ参照が当事者の全体を表すのは，それが， そのアクター名を持つ parties: のただ1つのエントリに等しいときに限る。整数の添字または範囲を持つ それ以外の参照は，要素を特定しているという。集合の名前だけの参照，すなわち範囲付きで宣言した アクターに対する A は，どの要素にも一致しない（F.3）。それは組を与えず，処理系は警告することが 望ましい（J-3）。それは，要素を特定しているものでもない。添字と範囲は，書かれたとおりに比べる。 コアの構文解析器は，添字の中の空白を受け付けない。たとえば，parties: [DISPATCHER, "ROBOT[1]", "ROBOT[2]"] では，宛先 ROBOT[2] は要素を特定しており，項目と ROBOT の組を与えるのは，ROBOT[*]，ROBOT[i]， または範囲だけである。

組 (x, q) は，次のとき，与えられている。

  • 共有のエントリによって：information.sharing のエントリ "S -> T : x" が，項目 x と，当事者 q の 全体を表す宛先 T を持つとき。この形で項目が1つでないエントリ，たとえば "A -> B : x, y" や "A -> B : f(5s)" は，コアの構文解析器が寛容に受け付けるが（A.12），組を与えず，処理系は警告する ことが望ましい（J-3）。
  • 義務によって，または許可によって：その種類の共有規範が，shares: に x を挙げ，内容として メッセージ S -> T : m を持ち，その受信者 T が当事者 q の全体を表すとき。

組は，この3つの与え方の少なくとも1つで与えられているとき，与えられているという。

α̂  =  (number of given pairs) / (number of pairs)

α̂は，組がないとき（項目がない，または当事者名が1つである）は未定義である。α̂ = 0 であるのは， 組が1つも与えられていないとき，かつそのときに限る。これは，宣言した項目に限って，5.4.2節の端点 「情報非共有」に対応する。α̂ = 1 であるのは，すべての組が与えられているとき，かつそのときに限る。 これは，宣言した項目に限って，「完全共有」に対応する。処理系は，α̂とともに，3つの与え方のそれぞれで 与えられている組の数，与えられていない組，および要素を特定したエントリと規範を報告する。組を 与えるはずであるが，宛先が要素を特定しているエントリまたは規範 （"DISPATCHER -> ROBOT[3] : route" など）は，組を与えず，挙げる項目がいくつであっても，エントリと 規範のそれぞれを1回ずつ，分けて列挙する。alpha: 0 を宣言し，共有のエントリがすべて要素を特定して いる契約は，α̂ = 0 であり，J-6の警告を受けない。要素を特定したエントリも共有であるが，指標はそれを 見ない。

この定義が見ないものは，次のとおりである。

  • 送信元 S は調べない。エントリは，誰が送るかにかかわらず，項目を T に与える。
  • 識別子の添字は，記述者が選ばれた1つの要素を意図している場合（ROBOT[winner]）も含めて，常に 当事者の全体として数える。
  • 契約の当事者でない宛先は，組を与えない。処理系は警告することが望ましい（J-3）。
  • 規範の状態は無視する。共有規範は，trigger:，until:，deadline: を持つかどうかにかかわらず， また，初めから発効しているか，反義務の規範として，または権能によってだけ発効するかにかかわらず，数える。
  • 同じメッセージの禁止は，組を取り除かない。そのような衝突については，付録FのN-12が警告する。
  • 義務も許可も，組を与える。指標が記録するのは，規範が当事者に項目を持たせること，または持つことを 許すことである。当事者が実際にそれを持つかどうかは記録しない。3つの個数を見れば，その違いがわかる。
  • 当事者が1つのアクター集合だけである契約は，当事者名が1つであり，組を持たないので，α̂は未定義である。 したがって，対等な構成システムからなる協調型のSoSで重要となる，同等の者どうしの共有は， バージョン0.1の指標には現れない。

権能の集中：β̂​

C の決定点とは，C の権能（F.2）である。権能は，その行使が，定義された効果によって他の規範の状態を 変える，契約のただ1つの構成要素である（F.5）。authority.decision_scope はテキストであり，数えない。 単一のアクター a（J.2）について，bearer: が参照 a である（アクター名も添字も同じである）C の権能の 数を k(a) とする。負担者が単一のアクターでない権能（ROBOT[i] など）は，各要素がそれぞれ自分のために 保持するものであり，どの単一のアクターの分としても数えない。

β̂  =  (largest k(a) over the single actors a) / (number of powers)

β̂は，単一のアクターが負担する権能が1つもないとき0であり，C に権能がないときにだけ未定義である。 これは，契約の決定点のうち，1つのアクターにあるものの最大の割合であり，集中の指標である。 β̂ = 1 であるのは，1つの単一のアクターがすべての権能を負担するとき，かつそのときに限る。これは， 権能に限って，5.4.2節の端点「単一アクターが全決定」に対応する。β̂ = 0 であるのは，どの単一のアクターも 権能を負担しないとき，かつそのときに限る。

β̂は authority.decision_holder に依存しない。処理系は，β̂とともに，次を報告する。負担者ごとの権能の数。 各権能について，その effects: に挙げた相異なる規範の数。決定権者が単一のアクター h を名指すときは， 決定権者の割合，すなわち k(h) を権能の数で割ったもの。個数は，効果によって重み付けしない。 1つの規範を解除する権能も，他の当事者の権能を解除する権能も，同じように数える。

インセンティブの被覆率：χ​

C の義務と禁止の集合を N とする。N の規範は，次の少なくとも1つが成り立つとき， インセンティブを伴うという。

  • 空でない on_violation.sanction を持つ。
  • 0より大きい on_violation.magnitude を持つ。
  • 空でない on_fulfilment.reward，または0より大きい on_fulfilment.magnitude を持つ。
χ  =  (number of norms of N that carry an incentive) / (number of norms in N)

χは，N が空であるときは未定義である。χ = 0 であるのは，どの義務と禁止も制裁も報酬も伴わないとき， かつそのときに限り，χ = 1 であるのは，そのすべてが伴うとき，かつそのときに限る。χはλの指標ではない。 χは，λが掛かる対象を持つ規範を数える。どれだけ掛かるかを述べるのがλである（J.7）。

さらに2つの個数を，χとは分けて報告する。これらはχには含めない。インセンティブを伴わず， on_violation.reparation を持つ N の規範（その違反は，制裁の代わりに，さらなる義務を生じさせる）の数と， on_violation.transition を持つ N の規範（その違反は，契約インスタンスを動かすか終わらせる）の数である。 severity: は，どこにも数えない。それは違反を分類するものである。

量の性質​

3つの量は，名前の付け替えと，規範，項目，当事者の順序の入れ替えについて不変である。分割と併合に ついては不変でない。1つの権能を2つに分けて書くと，あるいは2つの義務を1つに併合すると，契約が 当事者に求めることは同じでも，β̂またはχが変わる。各補題では，述べていないものはすべて同じままであり， 量は前後で定義されているとする。

  • 補題1（α̂）。 information.sharing にエントリを追加しても，共有規範の shares: に項目を 追加しても，共有規範を追加しても，α̂は下がらない。証明。 組の集合は変わらず，与えられていた組は すべて，引き続き与えられている。これに対して，項目または当事者を追加すると，組が増え，α̂が下がる ことがある。
  • 補題2（β̂）。 負担者が，k(a) が最大である単一のアクターである権能を追加しても，β̂は下がらない。 負担者が単一のアクターでない権能を追加しても，β̂は上がらない。証明。 n 個の権能のうちの最大の数を k とすると，k ≤ n であるので，k/n ≤ (k + 1)/(n + 1) かつ k/(n + 1) ≤ k/n である。
  • 補題3（χ）。 インセンティブを伴わなかった義務または禁止に，（空でない制裁のテキスト，または0より 大きい大きさによって）インセンティブを伴わせると，χは 1/|N| だけ上がる。0である大きさでは上がらない。 インセンティブを伴う規範を N に追加しても，χは下がらず，伴わない規範を追加しても，χは上がらない。 証明。 補題2と同様である。

量が表さないもの​

  • α̂が数えるのは，共有する資格と義務である。運用において当事者が何を観測するかや，情報の品質や 遅延は数えない。項目は，記述者が挙げたものである。
  • β̂が数えるのは，権能である。誰が経路を計画するかのように，制度上の行為でない決定は，規範でないので， 数えない。すべての権能は，その効果が何であっても，同じ重みを持つ。
  • χが述べるのは，制裁または報酬を伴う規範がいくつあるかである。それらがどれほど大きいかや， どれほど確実に適用されるかは述べない。
  • J.7のどの結果にも，大きさとλの積だけが入る。1つの契約の中では，λと大きさは別々には特定されない。 すべての大きさを2倍にし，λを半分にしても，何も変わらない。
  • コアのキー incentives.type，incentives.rules，violation.action はテキストであり，無視する。 契約は，χからは見えないインセンティブを，そこに持ち得る。
  • 付録Gの強制のもとでは，禁止されたメッセージは境界で拒否され，送ることが できない。したがって，その禁止は，制裁がなくても実効性を持つ。ゆえに，強制される契約での被覆率0は， 「インセンティブなし」を意味しない。
  • どの量も，振る舞いについては何も述べない。共有を増やすこと，あるいはインセンティブを強くすることが 性質を改善するかどうかは，付録Hと付録Iのモデルに対する問いである。

SoSの量​

3つの量は，m ≥ 2 であるファイルのすべての契約 C₁，…，Cₘ の上でも定義する。これは，SoSの1つの バージョンの上の量である。改正したバージョン（F.6）は，それ自身の量を持つ。定義は，契約の個数を 合わせて数える。

  • α̂_SoS。 項目は，その契約で修飾する。SoSの組は，契約 Cᵢ と Cᵢ の組 (x, q) からなる3つ組 (Cᵢ, x, q) であり，(x, q) が Cᵢ で与えられているとき，この3つ組は与えられている。2つの契約に 現れる項目は，起点が同じでも異なっていても，それぞれの契約で組を与える。ある契約のエントリや 共有規範は，ほかの契約の組を与えない。ほかの契約の当事者はそれに合意しておらず，v0.3は契約を またいで項目を同一視する手段を持たないからである。

    α̂_SoS  =  Σᵢ（Cᵢ の与えられている組の数）/ Σᵢ（Cᵢ の組の数）

  • β̂_SoS。 SoSの決定点は，すべての契約の権能である。単一のアクター a について， K(a) = Σᵢ kᵢ(a) は，a がすべての契約で負担する権能の数である。kᵢ は，Cᵢ におけるJ.4の数 k である （アクター名と添字が同じもの）。

    β̂_SoS  =  （単一のアクター a についての K(a) の最大値）/ Σᵢ（Cᵢ の権能の数）

    これは，SoSのすべての権能のうち，1つの単一のアクターが負担するものの最大の割合である。

  • χ_SoS。 N_SoS は，各契約の N の和集合である。

    χ_SoS  =  Σᵢ（Nᵢ のうちインセンティブを伴う規範の数）/ Σᵢ |Nᵢ|

どの量も，分母が0のときは未定義である。処理系は，これらを，J-5の個数のうち当てはまるものの和 （組の3つの与え方，要素を特定したエントリと規範，負担者ごとの権能，反義務の規範だけを持つ規範と 遷移を持つ規範）とともに報告する。SoSの決定権者はない。K が最大である単一のアクターが複数あるときは， そのすべてを名前の辞書順に示す。これらの量とその報告は，契約の順序の入れ替えについて不変であり， 各契約の量は変わらない。

重みを付けない。 契約や規範をほかより重く数える重み付けした指標は定義しない。どの重みも， ファイルが持たない任意の定数になるからである。

比較しない。 v0.3は，α，β，λを契約ごとに宣言し，SoSはそれらの宣言値を持たない。J.5とJ.8の どの規則も，α̂_SoS，β̂_SoS，χ_SoS を何とも比べない。これらは報告するだけである。

これらの量と各契約の量の関係は，次のとおりである。述べていないものはすべて同じままとする。

  • 補題4（上下限）。 α̂_SoS は，定義されているとき，α̂が定義されている契約のα̂の最小値と最大値の 間にある。χ_SoS も同様である。β̂_SoS は Σᵢ（kᵢ の最大値）/ Σᵢ（Cᵢ の権能の数）以下である。 これは，各契約のβ̂を権能の数で重み付けした平均であるので，β̂_SoS はβ̂の最大値以下である。 β̂_SoS がこの平均に等しいのは，1つの単一のアクターがどの契約でも最大の数を持つとき，または 権能を負担する単一のアクターがないときに限る。証明。 和の比は，個々の比の間にある。 K(a) = Σᵢ kᵢ(a) ≤ Σᵢ（kᵢ の最大値）であり，等号はどの Cᵢ でも kᵢ(a) が最大であるときに限る。
  • β̂_SoS は，どの契約のβ̂よりも小さくなり得て，それらの関数ではない。反例。 2つの契約で，それぞれ 1つの単一のアクターがただ1つの権能を負担するとする。どちらもβ̂ = 1 である。そのアクターが 両方で X であるとき β̂_SoS = 2/2 = 1 であり，一方で X，他方で Y であるとき β̂_SoS = 1/2 である。
  • 補題1と補題3はそのまま成り立つ。 どの契約にエントリ，shares: の項目，共有規範を追加しても， α̂_SoS は下がらない。どの契約の義務または禁止についても，インセンティブを伴わなかったものに インセンティブを伴わせると，χ_SoS は 1/|N_SoS| だけ上がる。証明はJ.4と同じである。組の集合と N_SoS は変わらない。
  • 補題2は，k を K に替えて成り立つ。 負担者が，K が最大である単一のアクターである権能を追加しても， β̂_SoS は下がらない。負担者が単一のアクターでない権能を追加しても，β̂_SoS は上がらない。 契約の中での補題2の条件だけでは足りない。反例。 C₁ が X の権能を2つ，C₂ が Y の権能を1つ持つとき， β̂_SoS = 2/3 である。Y が最大の数を持つ C₂ に Y の権能をもう1つ加えると，C₂ のβ̂は1のままで， β̂_SoS は 2/4 に下がる。
  • 契約を追加する場合。 契約 C′ を追加し，α̂_SoS と C′ のα̂が定義されているとき，新しいα̂_SoS は， 元の値と C′ のα̂の間にある。χ も同様である（和の比である）。したがって，契約を追加すると， α̂_SoS と χ_SoS は下がり得る。反例。 1つの項目を持ち，それをもう一方の当事者と共有する契約は α̂ = 1 である。1つの項目を宣言し，何も共有しない契約を加えると，α̂_SoS = 1/2 になる。契約を 追加すると，補題4の後の反例のように，β̂_SoS も下がり得る。β̂_SoS が，元の値と C′ のβ̂の大きいほうを 超えることはない。これは中間数の不等式による。権能の数を n，n′ とすると，どの単一のアクター a に ついても，(K(a) + k′(a)) / (n + n′) は，元のβ̂_SoS 以下である K(a)/n と，C′ のβ̂以下である k′(a)/n′ の間にある。

J.5 宣言されたパラメータとの関係​

処理系は，どの契約についても3つの量を計算し，報告する（J-5）。alpha と beta については，宣言値， 指標，およびその差を報告し，両者を比べる。どの不一致も警告である。指標は規範についての証拠であり， 本拡張を宣言することが，norms: 0.1 を宣言するファイルを無効にすることは決してない。

宣言された端点に対する反例が，契約の中にある場合。 5.4.2節の端点は，全称的な言明である。同じ契約の 構成要素が反例であるとき，処理系は，警告し，その構成要素を名指すことが望ましい（J-6）。

宣言警告で名指す反例
alpha: 0与えられている組と，それを与えるエントリまたは共有規範。α̂が未定義のときは，空でない information.sharing
alpha: 1与えられていない組（規範がないことは，当事者が項目を持たないことを示さないので，4つのうちで最も弱い）
beta: 1数が最大である単一のアクター（複数あるときは，ファイルの順で最初のもの）が負担していない権能。β̂ = 0 のときは，すべての権能
beta: 0数が最大である単一のアクター。ただし，β̂が，権能を負担する相異なる単一のアクターの数で1を割った値を超えるときに限る

β̂が0であるのは，すべての権能をアクター集合が負担するときに限る。複数の単一のアクターがそれぞれ同じ数の 権能を負担し，それより多く負担する者がいない契約では，β̂は，その数で1を割った値であり，これらの 負担者について取り得る最小の値である。そこでは，beta: 0 に警告は出ない。

中間の値が指標から遠い場合。 αとβについて，処理系は，宣言値と指標の差が契約の許容差を超え， J-6がそのパラメータについて警告を出さないとき，警告することが望ましい（J-7）。許容差の既定値は 0.25である。指標は粗く，規範の少ない契約では，指標が取り得る値が少ない（権能が2つであれば，β̂は 0，1/2，1 のいずれかである）。より大きな差を受け入れる記述者は，それを grounding.tolerance で述べる。 処理系は，決定権者が単一のアクターを名指し，その割合がβ̂より小さいときも，警告することが望ましい。 このとき，権能は別のアクターに集中している。

λは数とは比べない。 λは倍率であり，χは被覆率である。どの規範にも軽い制裁がある契約は，χ = 1 で， λが小さく，整合している。処理系は，宣言された lambda の隣にχを報告し，次の2つの場合にだけ 警告することが望ましい（J-8）。契約のどの義務と禁止もインセンティブを伴わない（χ = 0，または N が空で ある）のに，lambda が0より大きい場合。このとき，λには，規範の中に掛かる対象がない。および，ある 規範がインセンティブを伴うのに lambda: 0 である場合。このとき，規範が宣言するものは，モデルの中で 効果を持たない。

契約のバージョン。 契約の2つのバージョンを比べる処理系（F.6）は，本付録のキー（大きさ，on_fulfilment:， shares:，項目）で何が変わったかを報告し，宣言値とその指標が逆の向きに動くとき，警告することが 望ましい（J-13）。たとえば，改正がロボットに権能を与える一方で，beta を上げる場合である。

J.6 付録Hと付録Iのモデルにおけるパラメータ​

現状。 モデルのパラメータは，from: "C.alpha"，"C.beta"，"C.lambda" によって宣言値に 束縛する（H.3）。これにより，契約とモデルが同じ数を用いる。その数がモデルの中で何をするかは， 記述者が書く。H.12では，βは決定が集中的に行われる確率であり，αは 集中的な計画の品質に掛かる。どちらの付録も，これらの式を契約から導出せず，本付録も導出しない。

本付録がαとβについて加えるもの。 契約の規範は，束縛したパラメータが宣言値を持つ設計を記述する。 別の値を割り当てるモードは，動作モード（H.6）を記述するが，ファイルはそのモードに固有の規範を 持たない。そこで，処理系は，どの設計においても，C.alpha または C.beta に束縛したパラメータの 固定値を C の指標と比べ，両者の差が許容差を超える設計について，警告ではなく，情報レベルの診断を 出すことが望ましい（J-9）。

未解決のまま残るもの。 モードは固有の規範を持たないので，モードがαとβに割り当てる値を指標に 照らして検査することはできず，βによるモードの順序を，その規範の順序と比べることもできない。 共有規範または権能からモデルの確率を導出すること，および，ゲームにおいてプレイヤーが観測するものと してのα（RD-7.3）は，定義しない。

J.7 λ：規範の制裁から利得の項へ​

戦略モデル（付録I）では，利得の項は，重みを与える代わりに，その項が表すと 宣言する制裁または報酬を持つ規範を名指してよい。

- { reward: shortcuts, sanction_of: "DELIVERY.no_shortcut" }

項が名指す規範 C.n を n とし，from: "C.lambda" で束縛したモデルのパラメータを ℓ とする （ちょうど1つなければならない。J-10）。この項は weight: を持たず，その重みを次のように定義する。

項重み
sanction_of: "C.n"−m · ℓ。m は n の on_violation.magnitude
reward_of: "C.n"m′ · ℓ。m′ は n の on_fulfilment.magnitude

この項は，それ以外の点ではI.6の項であり，付録Iがそのまま適用される。

検査されない仮定。 項の報酬構造は，モデルの中で制裁がどれだけ頻繁に科されるか，または報酬が 支払われるかについての，記述者の言明である。規約は次のとおりである。sanction_of: の項の累積報酬は， モデルの1回の実行の中のすべての契約インスタンスにわたって，規範の違反を数え，reward_of: の項の 累積報酬は，その履行を数える。1回の実行は，複数の契約インスタンスにまたがってよい。これを検査できる 処理系はない。付録Fは規範を時間付きトレースの上で判定し，付録Hはモデルをステップで評価する。両者の 間の変換は定義されていない。したがって，そのような項を持つ利得を用いて計算したどの結果も，各項に ついての仮定「報酬構造 r は，C.n の違反（履行）を数えるものとする」とともに報告しなければならない （J-12）。

制裁を負う者。 制裁は，規範の負担者の損失である。sanction_of: の項は，負担者を代表するプレイヤーの 利得に置き，他のどこにも置かない。その額がどこへ行くかは，本付録は述べない。それが相手方への移転である ときは，記述者は，相手方のプレイヤーの利得に，同じ報酬構造と明示的な重みを持つ，2つ目のふつうの項を 書く（weight: "2 * lambda"）。その項の大きさは，規範に照らして検査されない（J-11）。

処理系が検査すること（J-10，J-11）。 規範が存在し，義務または禁止であり，大きさを宣言している こと。利得のプレイヤーが規範の負担者を代表すること。1つの規範が，それぞれのキーで多くとも1回だけ 名指されること。モデルが C の規範を1つでも名指すときは，大きさを持ち，負担者がモデルのプレイヤーで ある C のどの規範も名指されること。ファイルは大きさを1回だけ述べるので，大きさと係数λは，定義により 成り立つ。

均衡となる値の集合の形。 σ をプロファイル，D を設計，ℓ をパラメータとし，他のすべてのパラメータを固定する。 次の2つの条件を考える。

  • (i) ℓ は，モデルのどの確率にも，どの報酬の値にも現れず，ℓ が現れるどの重みも，ℓ について アフィンである（ℓ が1より高いべきで現れない）。
  • (ii)（プレイヤー p について） p の項のうち，重みに ℓ が現れるものはどれも，sanction_of: の項と 同じく，m ≥ 0 である重み −m·ℓ を持ち，σ のもとで，その報酬構造の期待累積値が0である。

命題。 (i) を仮定する。D が良定義であるかどうかと，σ が許容できるかどうかは，ℓ に依存しない。 それらが成り立つところで，次が成り立つ。

  1. どの gain_p も，ℓ の凸な区分線形関数である。ℓ の値の区間の上で，σ が D のε均衡である値の 集合は，閉区間である（空であってもよい）。特に，σ は，a と b でε均衡であれば，a と b の間の どの値でもε均衡である。
  2. (ii) が p について成り立つならば，gain_p は ℓ について非増加である。b で gain_p > ε であれば， b より小さいどの値でも gain_p > ε である。
  3. (ii) がすべてのプレイヤーについて成り立つならば，1の集合は，空であるか，あるしきい値 λ* について，区間の ℓ ≥ λ* である値の全体である。

証明。 (i) により，確率は ℓ に依存せず，それとともに，ゲームのグラフも，どの期待累積報酬も ℓ に 依存しない。したがって，良定義性と許容性も依存しない（H.5，I.6）。p の戦略 τ について，σ[p↦τ] の もとでの p の利得は，A(τ) + ℓ·B(τ) である。どの重みも ℓ についてアフィンであるので，A(τ) と B(τ) は ℓ に依存しない数である。BR_p は，そのような関数の有限個の最大値であり（I.7），したがって凸で 区分線形である。σ のもとでの利得はアフィンである。ゆえに gain_p は凸で区分線形であり，連続である。 凸で連続な関数が ε 以下である集合は閉区間であり，プレイヤーにわたる共通部分も閉区間である。(ii) の もとでは，B(τ) は，大きさと期待累積報酬の積の和に負号を付けたものであるので，どの τ についても B(τ) ≤ 0 であり，σ 自身の戦略については0である。このとき，gain_p は，非増加な関数の最大値から定数を 引いたものである。ある値を含めばそれより大きい値をすべて含む閉区間は，空であるか，3の形である。∎

命題が成り立つ範囲。

  • (ii) がなければ，集合は閉区間であり，しきい値の形であるとは限らない。I.12では，shortcut_first は 制裁を受け，それが均衡であるのは，max(0, T_1, T_2) ≤ λ ≤ T_3 であるとき，かつそのときに限る。 reward_of: の項も (ii) を破る。その項の σ のもとでの値は，ℓ とともに増えるからである。
  • 契約が2つあれば，2つの lambda に束縛した2つのパラメータがある。命題は，他方を固定したとき， そのそれぞれについて成り立つ。両方の領域については何も述べない。
  • ℓ が確率に現れるとき（インセンティブが環境の振る舞いを変えるとき），(i) は成り立たず，利得は ℓ の 有理関数であり，上のことは何も成り立たない。

セルの端点による認証。 この命題は，I.9のセルの端点による認証の命題の 特別な場合である。I.9の命題は，どの戦略モデルについても述べられている。条件 (i) は，本付録が定める 重みも含めたI.9の条件Aであり，sanction_of: の項の ℓ の係数は −m であるので，条件 (ii) が成り立てば初期状態からの 条件B−が成り立つ。I.9は，これを，開いているパラメータが ℓ だけである均衡マップのための方法にする。セル [a, b] の両端での厳密な評価が equilibrium を認証し，b での評価が，(ii) の成り立つ逸脱者を認証する。 I.9は，向きを逆にした条件B+（ℓ のどの係数も0以上で，プロファイルのもとでの期待値が0）も述べる。そのもとでは 逸脱利得は非減少であり，a での評価で判定する。reward_of: の項の係数は正であるが，プロファイルが正の確率で 規範を満たすとき，その期待値は正であり，B+は成り立たない。J-14は，本拡張を宣言するファイルにこの方法を どう適用するかを述べる。

failure（ROBOT）義務（report_failure）によって与えられている起点与えられていない

3つの組が共有のエントリによって，1つが義務によって，1つが許可によって与えられている。要素を特定した エントリはない。5つの組が与えられているので，α̂ = 5/8 = 0.625 である。宣言された alpha: 0.6 との 差は 0.025 であり，許容差の中にある。仮に最初のエントリが "DISPATCHER -> ROBOT[3] : route" で あったならば，それは要素を特定しており，組（route，ROBOT）は与えられず，α̂は 4/8 になる。

β̂。 契約は2つの権能を持つ。reassign は，単一のアクターである DISPATCHER が負担する。 decline は，単一のアクターでない ROBOT[i] が負担する。単一のアクターの最大の数は1であるので， β̂ = 1/2 = 0.5 であり，決定権者の割合も 1/2 である。reassign はその効果に2つの規範を挙げ， decline は1つを挙げる。宣言された beta: 0.9 との差は 0.4 であり，許容差 0.25 を超えるので， 処理系は警告する（J-7）。契約は，ほぼ集中した権限を宣言しているが，決定点の半分はロボットにある。 beta: 1 であれば，警告はJ-6のものになり，decline を名指す。

χ。 契約は3つの義務と禁止を持つ。no_low_battery_driving は，大きさ4の制裁を伴う。 acknowledge は反義務の規範を持ち，制裁を持たない。report_failure はライフサイクルの遷移を持ち， 制裁を持たない。どちらもインセンティブを伴わない。χ = 1/3 = 0.333333 であり，反義務の規範だけを持つ 規範が1つ，遷移を持つ規範が1つある。宣言された lambda: 0.5 は0より大きく，インセンティブを伴う 規範があるので，J-8は警告を出さない。

定義により，decline を除く改正は β̂ を 1/1 = 1 に上げ，補題3により， report_failure に制裁を与える改正は χ を 2/3 に上げる。

J.10 中間表現（IR）への追加​

institution.contracts の下の各契約に，フィールド grounding を追加し，F.9の各規範に，4つの フィールドを追加する。J.9の例では，次のとおりである。

{
  "grounding": {
    "items": { "route": "DISPATCHER", "status": "ROBOT[*]", "battery": "ROBOT[*]", "failure": "ROBOT[*]" },
    "tolerance": 0.25,
    "indices": {
      "alpha":    { "given": 5, "pairs": 8,
                    "by_sharing": 3, "by_obligation": 1, "by_permission": 1, "member_specific": 0 },
      "beta":     { "largest": 1, "powers": 2, "holder": 1,
                    "bearers": { "DISPATCHER": 1, "ROBOT[i]": 1 } },
      "coverage": { "incentive": 1, "norms": 3, "reparation_only": 1, "transition": 1 }
    }
  },
  "norms": [
    { "id": "no_low_battery_driving",
      // ... the fields of F.9
      "shares": [],
      "on_violation_magnitude": 4,
      "on_fulfilment_reward": null,
      "on_fulfilment_magnitude": null }
  ]
}

フィールド grounding と規範の4つのフィールドは，本拡張を（norms: 0.1 とともに）宣言していない ときは，存在しない。他のどのファイルのIRも変わらない。契約が grounding: ブロックを持たないとき， items は空のマッピングであり，tolerance は既定値である。alpha，beta，coverage は，その量が 未定義であるとき null である。そうでないときは，厳密な比を作れるように，最初の2つのフィールドが 分子と分母である。by_sharing，by_obligation，by_permission は組を数え，重なってよい。 member_specific は，エントリと規範をそれぞれ1回ずつ数え，集合の名前だけの参照は数えない。holder は，決定権者の数 k(h) であり，決定権者が 単一のアクターを名指さないときは null である。bearers は，書かれたとおりの各負担者の参照を， その権能の数に対応付ける。大きさは，ないとき null であり，空のテキストは null である。

2つ以上の契約を持つファイルでは，制度の層に，SoSの量（J.4）を契約の指標と同じ形で持つフィールド grounding を追加する。

{
  "institution": {
    "actors": [ /* ... */ ],
    "contracts": [ /* ... */ ],
    "grounding": {
      "contracts": ["C1", "C2"],
      "indices": {
        "alpha":    { "given": 1, "pairs": 3, "by_sharing": 1, "by_obligation": 0,
                      "by_permission": 0, "member_specific": 0 },
        "beta":     { "largest": 2, "powers": 3, "bearers": { "D": 2, "X": 1 } },
        "coverage": { "incentive": 2, "norms": 3, "reparation_only": 1, "transition": 0 }
      }
    }
  }
}

contracts は，契約のidを辞書順に並べる。bearers は，各負担者の参照の権能の数を，すべての 契約にわたって足したものであり，参照の辞書順に並べる。beta は holder を持たない。本拡張を宣言していないとき，または ファイルの契約が2つより少ないとき，このフィールドは存在しない。

I.13のIRの利得の項に，フィールド sanction_of と reward_of （文字列 C.n または null）を追加する。これらは，本拡張を宣言しているときに，どの項にも書く （重みを書いた項では，どちらも null）。そのどちらかを持つ項では，weight は，定義された重みの テキスト -m * p または m * p である。ここで m は，指数のない10進小数として（H.11の数と同じく） 書いた大きさであり，p は，C.lambda に束縛したパラメータの id である（J.7では "-2 * lambda"）。診断は，IRに含めない。

J.11 リファレンス実装の状況​

リファレンス実装は，cadl 0.3.23から，grounding 0.1を次のように実装する。0.3.22までは，拡張の名前は 未知のものであり，そのキーは診断なしに無視されていた。

  • cadl check は，規則J-1からJ-9を，戦略モデルではJ-10からJ-12も適用し（「望ましい」は警告とし， J-9とJ-12は情報レベルの診断とする），キーをJ.10のIRへ変換する。宣言されていない使用には，ファイル ごとに1つの警告を出す（J.12）。grounding: または on_fulfilment: の中の，本付録が定義しないキー （tolerence: のような綴りの誤り）には警告を出す。on_violation: の中の magnitude: の綴りの誤りや shares: の綴りの誤りは，コア言語の未知のキーと区別できず，診断は出ない。
  • cadl norms-indices FILE [--contract ID] [--format text|json] は，J.4の量をそのすべての個数とともに， J.5の比較，および設計ごとのJ-9の診断を報告する。cadl 0.3.24からは，2つ以上の契約を持つ ファイルについて，--contract を付けないとき，SoSの量（J.4）も，テキストの最後の節とJSON出力の キー sos に報告し，cadl sim-ir はそれをIRに書く（J.10）。各契約の出力は変わらない。 誤り，特にJ-2からJ-4の誤りを持つファイルは拒否する（終了ステータス2）。警告は，終了ステータス0を変えない。
  • cadl norms-diff は，本拡張を宣言しないバージョンとの比較を含めて，J-13の所見を報告する。既定では， norms: または counts_as: を持つ契約を比べる。規範を持たない契約の grounding.items の変更は， --contract を付けて比べる。
  • キーは，付録Fが読む規範とは分けて保持する。したがって，cadl norms-eval，cadl agents-run，境界での 決定，生成した監視器は，キーがあってもなくても同じ判定を与える。注記したファイルから生成した監視器が， キーのないファイルから生成したものと同一であるのは，注記したどの規範も，すでに on_violation: ブロックを持っていたときに限る。on_violation: を持たない規範に on_violation: { magnitude: m } を 加えるとブロックが作られ，監視器は既定の重大度を持つ。振る舞いは同じである。
  • コアの構文解析器は，alpha，beta，lambda を2進の浮動小数点数として読む。往復変換で戻る最短の 10進小数を，書かれた10進小数とみなす（J-5）。したがって，有効数字が17桁を超える値は復元されない。 宣言されていないアクターへの添字のない参照は，単一のアクターとして数える（他の規則が報告する）。 bearers のキーは，空白を除いた参照である。
  • 付録I（cadl game-check）とともに，J.7の結び付きを実装している。sanction_of: または reward_of: の 項はJ.7の重みを持ち，どの検査とマップの結果もJ.7の仮定を伴い，J-14は，I.9の条件が成り立つとき， --certify で用いる（マップは，条件Aが成り立つかどうかと成り立たない理由，および逸脱利得が非増加 または非減少であるプレイヤーを報告し，端点から認証したセルは method: "end points (I.9)" を持つ。 0.3.23では "endpoints (J-14)" であった）。方法はI.9に属するので，grounding: 0.1 のないファイルも これを用いる（I.14）。結び付きを実装して いるので，I.13の not_evaluated は，有効なファイルでは生じない。用いることのできない参照は，J-1または J-10の誤りである。
  • 指標の検証。独立したレビューは，4 300個と2 000個の無作為な契約で，量を2つのスクリプトと比べ， 不一致はなかった。J.12の不変性は，4 454個の無作為なファイルと，テストスイートの174個のソースで 成り立った。norms: 0.1 を宣言するファイルに - grounding: 0.1 を加えても，誤りは増えなかった。 J.4の補題は，乱数の種を固定した無作為な契約で，性質として検査した。添付のトレースに対する cadl norms-eval と cadl agents-run の判定は，すべての規範に大きさと on_fulfilment: を加えても 同一であり，0.3.22の添付の17個の例の出力（331個のファイル）は，0.3.22と同一であった。
  • 結び付きの検証。独立したレビューは，生成した840個のモデルを，I.9の上下界を無効にして，決定した どのセルもJ-14によるものとなるようにしてプログラミングインタフェースで実行し（点評価12 416回）， 320個をコマンドラインで実行した（点評価3 496回）。すべての戦略を列挙するオラクルと比べ，誤った主張は なかった。実装者のファジングは，1 200個のモデルでJ-14によってセルを認証した。その中には，ℓ が確率に 現れるゲームや，ℓ についてアフィンでない重みを持つゲームが含まれ，J-14はそれらを拒否した （点評価50 733回，誤った主張なし）。条件2と条件5を落とすように故意に入れた誤りも検出した。

  • J.9の量は，例に対して cadl norms-indices が表示するものであり，警告は1つ（beta についてのJ-7）で ある。
  • SoSの量の検証。2つと3つの契約を持つファイルで手計算した値，J.4の反例，および2個から4個の契約を 持つシードを固定した無作為のファイルの上で，補題4，そのまま成り立つ補題，契約を追加したときの 上下限，契約の順序の入れ替えについての不変性を確かめた。

J.12 後方互換性​

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれ，そのIRも変わらない （J.10）。本拡張は，付録Fの どの判定も，付録Hと付録Iのどの結果も変えない。sanction_of: を持つ項は，定義された重みを持つ I.6の項である。

本拡張を宣言することが，norms: 0.1 を宣言するファイルを無効にすることは決してない。 norms: 0.1 を宣言し，付録Fのもとで有効であり，本付録のキーを1つも用いないファイルは，その extensions: に grounding: 0.1 を加えても，有効なままである。誤りとなる規則のうち，J-1は そのようなファイルでは発動し得ず，J-2，J-3，J-4，J-10は，本付録のキーにだけ適用される。宣言されたパラメータと指標との どの比較（J-6からJ-9）も，警告または情報レベルの診断である。

grounding: 0.1 を宣言せずに grounding:，shares:，on_fulfilment:， on_violation.magnitude，sanction_of:，reward_of: を用いるファイルは，本付録に適合しない。 本拡張を実装する処理系は，そのようなファイルではこれらのキーを解釈せず，宣言されていない拡張の キーとして，用いたキーを挙げる警告をファイルごとに1つ出して報告することが望ましい（値がnullである キーは，用いたものとしない）。量は計算せず，sanction_of: または reward_of: を持つ 利得の項は，I-7により誤りである。norms: 0.1 なしに grounding: 0.1 を宣言するファイルには， J-1の誤りを出す。

付録Iを実装し，本付録を実装していない処理系は，両方を宣言するファイルにおいて，sanction_of: または reward_of: の項を持つ利得も，それを必要とする問い合わせも，評価してはならない。処理系は， 問い合わせを評価しなかったと報告する（I-7）。どの場合にも，そのような項を，既定値の重みを持つ項として 読むことはない。本拡張を実装していない処理系は，本拡張を用いるファイルを拒否してはならない。 ファイルごとに1つの情報レベルの診断を出すことが望ましい。

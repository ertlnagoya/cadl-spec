コース D — ロボットの街：KPI に向けて規則を直す

コース A — ロボット配送 に戻る

  • 対象：コース A（CADL/SoS-DSL の基礎）を済ませた方。コース B は不要です
  • 所要時間：120〜150 分（改造課題は別）
  • 成果物：人間が自然言語で書いた KPI、LLM の改正案と判断要求、人間の判断とその理由（自然言語と GSN）、期ごとに改正された CADL の規則と憲法のバージョン

0. このコースの概要​

コース A と B では、契約を一度書き、シミュレーションの結果をその契約に照らして判定しました。 コース D では、システムが動いている間に契約そのものが変わります。 3 社（A・B・C、各社 2 台）の配送ロボットが、ラズパイマウスのシミュレータと同じ 11 ノードの道路網を共有します。 シミュレーション上の 1 時間（1 期）が終わるたびに、規則の改正を検討します。

改正には、人間、LLM、機械による判定が、次の役割で関わります。

担当すること
人間（サービスの運営者）サービスの KPI を自然言語で書く。KPI は時間とともに変えてよい。LLM の判断要求に答え、判断の理由と結果を自然言語または GSN で残す
LLMKPI を測れる指標に置き換え、KPI の達成に向けて規則・規制・契約の改正案を出す。明らかには判断できない問題や、人間の当事者が合意すべきことは自分で決めず、判断に必要な情報を添えて人間に判断を求める
機械による判定検査・憲法・同じ乱数シードで測った改善・各社の投票。LLM の説明は信用せず、測った値だけで判定する

演習は公開リポジトリ cadl-robot-town にあります。 Unity も SUMO も使いません。街は小さな Python のシミュレーションで、規範の判定には、コース A と同じ参照ランタイム（cadl-raspimouse-simulator から複製した contract_engine.py）を使います。

LLM の出力の記録について

§4〜§8 は、API キーがなくても、examples/steward-d/ と examples/steward-goodhart/ に入った LLM の出力の記録を再生して進められます。 これらは、2026-11-18 に Claude Opus 5.5 で実際に実行した記録です（cadl 0.3.36）。英語で実行した記録（examples/steward-d-en/）もあります。同じ KPI でも、第 5 期で結論が分かれます（§10）。 判断要求への答え（answers.yaml）は、記録を作るときに人間（運営者）の役を Claude が務めて書いたものです。§4 からは、自分で答えて進めてください。 表の数値は、再生したときに判定のプログラムとシミュレーションが測ったものです。自分の API キーで実際の LLM を使って実行する方法は §10 にあります。

1. セットアップ（5 分）​

必要なのは、コース A でクローンした CADL コンパイラ（~/program/cadl_repo）だけです。

cd ~/program
git clone https://github.com/ertlnagoya/cadl-robot-town
cd cadl-robot-town
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install --upgrade pip
pip install -e ~/program/cadl_repo     # cadl コマンドと PyYAML が入る

インストールに失敗した場合は、テキストブック 2.4 節のセットアップのトラブルシューティングを参照してください。

Anthropic の SDK と API キーが必要なのは、§10 で LLM を実際に呼ぶときだけです。

pip install anthropic

2. 規則・契約・規制を読む（15 分）​

cadl/robot_town.cadl を開きます。街の契約は 2 つです。

  • DELIVERY_SLA：注文 1 件ごとのインスタンスです。120 秒以内に集荷し、そこから 120 秒以内に届けなければ Late になります。顧客への約束です。
  • ROAD_USE：ロボットが次の注文を待つために道路上に止まるたびに 1 インスタンスです。
    - id: DELIVERY_SLA
      parties: [TOWN_STEWARD, "ROBOT[*]"]
      guarantee:
        - "pickup_time <= 120s"         # @amend:pickup_deadline
        - "dropoff_time <= 120s"        # @amend:dropoff_deadline
      lifecycle:
        ...
          - id: pickup
            from: Assigned
            to:   PickedUp
            on:   "ROBOT[i].status == PickedUp"
            deadline: 120s            # @amend:pickup_deadline
            on_violation: { transition: Late, severity: Major }
        ...
    - id: ROAD_USE
      parties: [TOWN_STEWARD, "ROBOT[*]", COUNCIL]
      authority:
        decision_holder: COUNCIL
      incentives:
        type: sanction
        lambda: 0.5                   # @amend:sanction_lambda
      lifecycle:
        states: [Holding, Overstay, Released, Evicted]
        initial: Holding
        terminal: [Released, Evicted]
        transitions:
          - id: release
            from: [Holding, Overstay]
            to:   Released
            on:   "ROBOT[i] -> TOWN_STEWARD : node_released"
            deadline: 60s             # @amend:hold_limit
            on_violation: { transition: Overstay, severity: Minor }
      monitors:
        - id: blocking_guard
          observe: "ROBOT[i].blocking"
          sampling: periodic(1000ms)
          rule: "ROBOT.blocking >= 3 AND state IN [Holding, Overstay]"  # @amend:block_k
          on_match: { transition: Evicted, severity: Major }

（抜粋して簡略化したものです。）

2 つのライフサイクルを状態機械で表すと次のようになります。

# @amend:<名前> が付いた行の数値が、改正できるパラメータです。 同じ名前の行が複数あるとき（集荷の約束の guarantee と deadline）は、すべて同じ値にしなければなりません。 各パラメータがどの層に属し、どこまで動かしてよいかは constitution.yaml（憲法）が決めます。

amendable:
  hold_limit:       {layer: rule,     min: 10, max: 120, step: 10}   # 道路上で待ってよい秒数
  block_k:          {layer: rule,     min: 1,  max: 4,   step: 1}    # 後ろで何台待ったら退去させるか
  sanction_lambda:  {layer: rule,     min: 0.0, max: 1.0, step: 0.5} # 違反 1 件あたりの罰点の倍率（Minor 1、Major 3）
  to_central:       {layer: rule, safety: true, ...}                  # 運用モードの切替（§9）
  pickup_deadline:  {layer: contract, min: 60, max: 180, step: 30}   # 集荷の約束の秒数
  dropoff_deadline: {layer: contract, min: 60, max: 180, step: 30}   # 配達の約束の秒数
invariants:
  min_company_on_time_rate: 0.6
vote:
  quorum: 2
regulation:
  invariants.min_company_on_time_rate: {min: 0.5, max: 0.95, step: 0.05}
  vote.quorum:                         {min: 1,   max: 3,    step: 1}

（抜粋して簡略化したものです。）

改正の層は 3 つです。

層対象誰が決めるか
規則ROAD_USE と、運用モードの切替の条件判定をすべて通れば自動で採択できる。ただし切替の条件（safety: true）は人間が決める
契約DELIVERY_SLA（顧客への約束）顧客は投票に加わらないので、人間が決める
規制憲法の値（不変条件、定足数）人間が決める

3 社の振る舞いは違います（town/policies.py）。 A 社は仕事がなければ必ず車庫に戻ります。B 社は道路上で次の注文を待ちますが、hold_limit の 5 秒前には離れます。1 台待たせただけで退去させられる規則（block_k が 1）なら、道路上では待ちません。罰点がない規則（sanction_lambda が 0）では、違反しても損をしないので、C 社と同じく待ち続けます。C 社は、注文が来るか退去させられるまで待ち続けます。ただし sanction_lambda が上限の 1.0 になると、期限を 15 秒過ぎたところで離れます。 罰点の倍率は、CADL の検査で 0〜1 に限られ、改正では 0.5 刻みで動きます。倍率が 0.5 のときの各社の振る舞いが、§3 の結果です。 交差点に止まっているロボットは、そこを通りたい他のロボットをすべてふさぎます。

道路網は 11 のノードと 17 本の道路からなります（town/world.py）。A・B・C 社の車庫はノード 10・9・4（黄色）です。道路上で待つロボットは、最も便利な中央の交差点 8（紫）で待ちます。

演習 2-1​

  1. 今の規則で、罰点を受けることがありえない会社はどこですか。それはなぜですか。
  2. 集荷の約束（pickup_deadline）を 150 秒に延ばすと、定時配達の件数はどうなると予想しますか。顧客が実際に待つ時間はどうなりますか。
  3. 契約の層の改正を、なぜ各社の投票だけで決めてはいけないのですか。

4. KPI を書く（15 分）​

人間の最初の仕事は、KPI を書くことです。kpi.md を開きます。

## 第 1 期から

顧客に約束した時間（注文から集荷まで 120 秒、集荷から配達まで 120 秒）のうちに届く配達を、
町全体でできるだけ増やしたい。どの会社の顧客も、ひどく待たされることがないようにしたい。

## 第 5 期から

閑散期に入り、注文が減る。定時の配達は引き続き大事だが、各社の協力を保つため、
道路の使い方で特定の会社だけが得をしたり損をしたりしないようにしたい。

## 第 k 期から の見出しで、KPI をいつから適用するかを書きます。 改正ループは期の初めにこのファイルを読み直すので、期と期のあいだに書き換えてもかまいません。

KPI は自然言語なので、そのままでは改正案を比べられません。 LLM が、town/kpi.py にある指標（定時配達件数、定時率、遅配件数、未配達、待ち時間、ふさがれた時間、最も低い会社の定時率、会社ごとの効用の差、罰点の合計など）の組み合わせに置き換えます。 これを評価方法と呼びます。評価方法は、主目標（改善をこれで測る）、監視する指標（誤差を超えて悪化したら人間に知らせる）、条件（改正後に必ず守る）からなります。

記録を再生して、1 期だけ実行します。--answers を付けないので、判断要求には端末で答えます。

python -m town.steward --mode DISTRIBUTED --rounds 1 --name try-d \

これは、2026-11-18 に Claude Opus 5.5 が実際に書いた出力の再生です。 LLM は、KPI の解釈が 1 通りに定まり懸念もなければ、人間に確かめずにその評価方法を使います。 ここでは「ひどく待たされる」の水準が KPI に書かれていないとして、3 つの評価方法と 4 つの懸念を返しました。 どの選択肢にも、達成基準（「何秒以下」のような値）はありません。KPI の文に書かれていない水準を LLM が決めないよう、依頼で求めているためです。 LLM が書いた評価方法は、指標の名前と形を機械が確かめてから使います。知らない指標を書いた選択肢は、選択肢から外されます。

worst_company_p95_wait_s は、会社ごとに求めた待ち時間の 95 パーセンタイルのうち、最も長いものです。待ち時間は注文から届くまでの秒数で、期の終わりに届いていない注文は、期の終わりまでの秒数で数えます。使える指標の一覧は python -m town.kpi で表示されます。

番号を選ぶと、理由と前提（GSN の Assumption）を聞かれます。前提は何行でも書け、空のまま Enter で終わります。 記録に入っている答え（examples/steward-d/answers.yaml）は次のとおりです。この記録を作るときは、人間（運営者）の役を Claude が務めました。

K1:
  choice: "1"
  reason: KPI の文の順のとおり、町全体の定時配達を主目標にし、どの会社の顧客もひどく待たせないことは、会社ごとの待ち時間の 95 パーセンタイルで監視する。「ひどく」の水準は、第 1 期の測定を見てから決める。
  assumptions:
    - 顧客は配送の会社を選べない

評価方法と達成基準を自分で書く​

KPI の文だけでは、何を測り、どこまで行けば達成なのかが決まりません。 kpi.md の節に「評価方法:」の箇条書きを書くと、town.steward はそれをそのまま評価方法として使い、LLM に読み方を頼みません（見本は examples/kpi-written/kpi.md）。

## 第 1 期から

顧客に約束した時間のうちに届く配達を、町全体で 95% 以上にしたい。どの会社でも、
約束の合計の 240 秒を超えて待つ顧客を 5% 以下にしたい。

評価方法:
- 主目標: 定時率 >= 0.95
- 監視: 最も待たせた会社の待ち時間p95 <= 240
- 条件: 最低の会社の定時率 >= 0.8
行意味
主目標1 つだけ。改善はこれで測る。値を書けば達成基準になる
監視誤差を超えて悪化すれば、KPI の衝突として人間に判断を求める。値を書けば達成基準になる
条件値が必須。改正後に必ず守る（破る案は KPI の衝突になる）

期ごとに、現行の規則が達成基準と条件に届いているかが「KPI の達成状況」として表示され、改正案の表にも、改正後に届くかが添えられます。 達成基準は表示のためのもので、改正を採るかどうかの判定には使いません。

python -m town.kpi examples/kpi-written/kpi.md     # 各節をどう読むかを確かめる

演習 4-1​

  1. K1 で選択肢 2（町全体で最も長い待ち時間を監視する）を選ぶと、§5 の判断要求はどう変わると予想しますか。
  2. LLM の 2 つ目の懸念は、定時配達件数だけを追うと、すでに遅れた注文が後回しにされうると言っています。待ち時間を監視すると、なぜこれを見つけられるのですか。期の終わりに届いていない注文の数え方に注目して説明してください。
  3. 「ひどく待たされる」を「約束の合計の 240 秒を超えて待つ顧客が、どの会社でも 5% 以下」と決めたとします。kpi.md の第 1 期の節に、評価方法の箇条書きを足してください。python -m town.kpi で、書いたとおりに読まれることを確かめてください。

  • 第 5 期に日本語と英語で結論が分かれたのは、K5 で人間が選んだ評価方法が違ったためです。待ち時間を監視していれば悪化が示され、監視していなければ示されません。K の判断要求で選んだ評価方法によって、その後の D の判断要求に示される数値が変わります。
  • LLM が「知らないこと」に挙げた項目から、ツールに足りないものが分かります。最初のバージョンの表には、監視している指標の値がありませんでした。LLM が「on_time_rate_gap が具体的にどれだけ悪化したか（表には最低の定時率しか載っていません）」と書いたので、表に「監視する目標と条件の値」の列を足しました。定足数を知らないこと（日本語の第 2 期）と、town.steward が使わない憲法の min_improvement を判定に使うと思い込むこと（日本語・英語の第 4 期）は、まだ直していません（§11）。

  • LLM の案と人間の判断は、シミュレーションの作りによって変わります。以前の記録（2026-11-15）では、各社の行動が罰点の倍率に左右されなかったので、罰点をなくす案は定時配達を変えずに効用の差だけを縮め、LLM はそれを勧めたこともありました。今の記録では、罰点をなくすと居座りが増えて遅配が増えるので、LLM はどちらの言語でもこの案を勧めていません。

12. 研究課題：改正の速さと移行の混乱（任意、数時間〜）​

KPI を早く達成するには、規則を一度に大きく変えるのが効率がよいように見えます。 しかし、規則に従う側が人間の場合、急に大きく変えると戸惑い、慣れるまでは古い規則のまま動いてしまいます。ロボットは新しい規則をその場で読むので戸惑いませんが、それでも移行の問題は起きます。 この課題では、KPI を達成するまでの速さと、規則の改正の大きさ・頻度とのトレードオフが、従う側が人間かロボットかでどう変わるかを調べます。

ここまでのハンズオンで、この課題に関係することをすでに 3 つ見ています。

  • 憲法の「1 回に 1 パラメータを 1 ステップだけ」（constitution.yaml の step）は、改正の速さの上限です。
  • §8 で使ったルールベースの委員会の 6 期の実行（seasons-d）では、第 1 期に罰点の倍率を 0.5 から 1 に上げたあと、繁忙期に hold_limit が 60 → 70 → 80 秒と上がり、閑散期には変わりませんでした。scenario.yaml が期ごとに決める需要に合わせて動いた結果です（改正の行き過ぎによるものではありません）。環境が変われば、1 回ごとの改正が正しくても、規則の値は動きます。需要への追従と改正の行き過ぎを見分けることも、この課題に含まれます。
  • §9 では、ラッシュのある期に、道路が空くのを待たずに運用モードを切り替えると、ロボットだけでも安全条件の違反が 1 期あたり約 1.4 回出ました。規則が変わる時点では、古いバージョンのもとで始まった注文や待機がまだ続いています。

課題 12-2：人間が運転する会社​

人間が運転する会社の振る舞いを、town/policies.py に足します。次のモデルを使ってください（値を変えて感度を調べるのは自由です）。

  • 規則が変わった期に、人間が運転するロボットは、確率 p で古い規則のまま動きます（古い hold_limit で待つ、など）。
  • p = min(0.9, 0.3 × 動かしたステップ数) とします。1 ステップの改正なら 0.3、3 ステップなら 0.9 です。
  • 次の期からは、p が毎期半分になります（2 期目に 0.15、3 期目に 0.075、…）。改正が続けば、新しい改正の p を足します（上限 0.9）。

各社の振る舞いは town/world.py の Town が self.rules = read_rules(ir) で読んだ規則だけで決まり、前のバージョンの情報を持ちません。Town に前のバージョンの IR（または規則の値）と「変更から何期目か」を渡せるようにし、town/period.py の evaluate() と town/council.py から渡してください。

課題 12-3：施行の仕方​

ロボットだけでも、移行の扱いは問題になります。§9 では、道路が空くのを待たずに運用モードを切り替えると、安全条件の違反が 1 期あたり約 1.4 回出ました。 次の 3 つの施行の仕方を town/ のコードに足し、課題 12-1 の「どちらも大きく」の条件で比べてください。

  • 予告期間：採択したバージョンを、次の期ではなく N 期あとから施行する（N = 1、2）
  • 段階施行：2 ステップ以上の変更を、1 期に 1 ステップずつ施行する
  • 経過措置：施行前に始まった注文や待機には、古いバージョンの期限を使い続ける

施行した期について、次を測ります。

量求め方

課題 12-4：速さを、人間と LLM に決めさせる​

§10 の実際の LLM で、town.steward に速さの選択をさせます。 共通の設定のゴールを、評価方法の箇条書きで kpi.md に書きます。主目標に G1、監視に G2 を置き、C2 は効用の指標がないので、文で書きます。

遅配を 1 期あたり 1 件以下にし、交差点がふさがれる時間を 600 秒以下にしたい。
配達員が戸惑うような急な変更は避けたい。どの会社の効用も 30 を下回らないようにしたい。

評価方法:
- 主目標: 遅配件数 <= 1
- 監視: ふさがれた時間 <= 600
- 条件: 最低の会社の定時率 >= 0.6

さらに、town/steward.py の triage() に、「2 ステップ以上動かす案は人間に判断を求める」という条件を足し、課題 12-1 の「どちらも大きく」の step で 6 期を実行します（--kpi で上のファイルを渡します）。

答えること：

  1. T と L を、同じ step の委員会（課題 12-1）と比べてください。判断の規則で、LLM と人間のほうが「よい」と言えますか。
  2. 人間に判断を求めた回数と、そのうち 2 ステップ以上の案が理由だった回数を数えてください。これが人間の負担です。
  3. LLM は判断要求に、移行のコスト（配達員の戸惑い）をどう書きましたか。C2（効用 30 以上）について、LLM は表のどの数値を使いましたか。

どの速さを選ぶかは、KPI の数字だけでは決まらず、規則に従う人がその変更を受け入れられるかにもよります。この課題での人間の判断と理由を、GSN に残してください。実際の LLM で 6 期を実行すると、§10 の記録では入力約 6 万・出力約 5 万トークン（Claude Opus 5.5）でした。

まとめの問い​

  • 憲法の step は、強化学習で方策の更新幅を制限する信頼領域（TRPO や PPO）に似ています。どこが同じで、どこが違いますか。
  • 速さの上限は誰が決めるべきですか。規則（委員会や LLM が変えてよい）、規制（人間が決める）、契約（顧客との約束）のどの層に置くのがよいですか。課題で選んだ step と、そのときの T・L を根拠にして答えてください。

13. 判断を記録する（90〜120 分、ほかに任意の演習）​

§4〜§10 の記録（decisions.md、gsn.yaml）は、人が読むためのものです。後から、それぞれの変更に誰が同意し、誰がどの根拠でなぜ判断したかを示すには、プログラムでも記録を検査できなければなりません。cadl 0.3.37 から、town.steward と town.council は runs/<名前>/decisions.jsonl も書き出します。付録 L の判断の記録です（cadl 0.3.38 と cadl-robot-town v0.4.0 からは decisions 0.2。バージョンの CADL ファイルは cadl-robot-town v0.5.0 から。委任は decisions 0.3 で、cadl 0.3.39 と cadl-robot-town v0.6.0 から）。

  • 1 行に 1 項目：目的、改正案、測定、判定、投票、判断要求、推奨、判断、バージョン、後で確かめる約束。どの項目も、根拠とした前の項目（basis）を挙げます。
  • 当事者と役割、判断してよい層：運営者（human。規則と契約）、規制の担当者（human。規制、つまり憲法の値）、LLM（llm）、steward または委員会（tool。すべての判定を通った規則の変更を、運営者に代わって自分で採択する）、A・B・C 社（agent、投票者）、顧客（organisation、影響を受けるが投票しない）。
  • 誰が誰に判断を任せたか：運営者から steward または委員会への委任（delegation。規則の層を、自分の規則で決める）と、LLM が人に代わって判断するときは LLM への委任（--delegate で与えた層）。
  • 規則の各バージョン（最初のバージョンも）と、その CADL ファイル v<n>.cadl の添付。規則に、付録 K の改正拡張（改正してよいパラメータ、その場所、範囲、刻みと、層ごとに誰が決めるか）を書き足したものです。
  • 人でも LLM でもツールでも、同じ証拠を残します。理由、前提、分からないこと、予測です。
  • 約束ごとに、何がそれを果たすかを書きます。測り直す約束（remeasure）なら、測り直す対象と同じ条件での測定で、steward が次の期に行います。改正案を出す約束（propose）なら後の改正案、問い（ask）なら後の判断です。問いの期限が来ると、steward はその判断を求めます。最後の期には、残った問いをすべて判断に付します。
  • どの行にも、付録 G の監査ログと同じハッシュの連鎖が付きます。
cadl decisions-verify runs/<名前>/decisions.jsonl

記録の隣にバージョンのファイルがあれば、検証器は、バージョンとその順序、どの改正案も現行のバージョンのパラメータを範囲と刻みの中で動かしているか、それぞれの変更を誰が決め、投票が定足数に達したか（L-9〜L-11）も確かめます。 検証器は、エラー（L-1〜L-11。記録がこのままでは信頼できない）と、確認のための指摘（投票を覆した判断、推奨と違う判断、委任の範囲の外でほかの当事者に代わって行った判断、後の投票や測定と食い違った予測、約束を果たしたと書いたが条件を満たさない項目、果たされていない約束など）を報告します。指摘は誤りではありません。誰がなぜそう判断したかが記録に残っていればよいのです。CADL Explorer のページ Decision Evidence は、同じ記録を、時系列、判断ごとの経緯、当事者ごとの証拠、約束、記録から作った GSN で示します。

演習 13-1〜13-6 は、規則（ROAD_USE）と契約（DELIVERY_SLA、顧客に約束した時間）の改正を扱います。演習 13-7 で規制を加えます。

演習 13-1：変更に誰が同意したか（ロボットだけ）​

規則にもとづく委員会を 6 期実行し、記録を検査します。

python -m town.council --rounds 6 --name ex13-council

判定の基準：6 期すべてで、表の結果が history.md と同じであり、検証器のエラーが 0 件であれば正解です。

基準値（2026-11-22、cadl 0.3.39 と cadl-robot-town v0.6.0）：改正案は 56 件です。最初に改善の判定で除かれた案が 50 件、投票で除かれた案が 2 件、すべての判定を通った案が 4 件です。採択は 1 件（第 2 期、sanction_lambda 0.5 → 1、賛成 A と B）で、記録の項目は 352 です。その中に、CADL ファイルを添付したバージョン v1 と v2、委任 G.council があります。どの判断も、委員会（ツール）が運営者に代わって行った automatic で、その規則が記録に書かれています。運営者はこの規則で規則の層を決めることを委員会に任せているので（procedures: ["automatic"]）、検証器は指摘を報告せず、6 つの判断を G.council のもとの判断として挙げます。

問い：C が反対した変更が採択されたのに、なぜほかの指摘が出ないのでしょうか。A と B の賛成で足りたことを、検証器はどの項目で確かめるでしょうか。

演習 13-3：後で確かめる約束​

D1 の理由は、次の期に C の効用と道路の違反を測り直すことを求めています。answers.yaml には、これを、何が果たすかを持つ約束として書けます。examples/steward-d-en/answers.yaml を my-answers.yaml にコピーし、D1 に次を足します。

D1:
  # choice と reason はそのまま
  follow_ups:
    - text: Re-measure C's utility (28.8 to 19.0) and the road violations (25.8 to 34.0)
      due: 2
      kind: remeasure
      metrics: [utility@C, road_violations]

--answers my-answers.yaml で再生して検査します。約束 D1.f1 は、fulfilled_by に、測り直しが持たなければならない条件の測定 P1.m0 を挙げます。第 2 期の初めに steward がその測り直しを行います。F2.D1.f1 で、現行の規則（v2）を第 1 期の乱数シードと需要で測ったものです。検証器は、13-2 と同じ 9 件の指摘を報告します（再生は、いくつかの依頼が記録と違うと知らせます。LLM に渡すこれまでの判断に、測り直しが加わったからです。記録の出力はそのまま使います）。

次に、第 2 期で約束が済んだと人が書いたことにして、D2 の答えに fulfils: [D1.f1] を足し、もう一度再生します。検証器は 10 件目の指摘として、D2 に fulfilment not shown を報告します。判断は測定ではないからです。

目標：D2 が D1.f1 を果たさず、F2.D1.f1 が果たす理由を、記録から説明します。

判定の基準：測り直しを求める約束は、測り直す対象と同じ条件（同じ乱数シードと需要。P1.m0 の method）で測ったときだけ果たされます。第 2 期は需要（平常＋ラッシュ）もシードも違い、そこでの C の効用は 56.3 です。LLM は D2 で、これが 28.8 → 19.0 と違う理由を知らないと書いています。

問い：

  1. P1.m0、P1.2.m、F2.D1.f1 を比べてください。測り直しは P1.2.m とまったく同じ値（C の効用 19.0、道路の違反 34.0）になります。なぜでしょうか。同じ条件が二度と正確には来ない、実際の街での測り直しは、何を加えるでしょうか。
  2. 約束できるのは、街の中の誰かが行うことだけです。D1 に、改正案を出す約束（kind: propose、「C の効用を保つ変更を提案する」）と、後の判断で決める問い（kind: ask、「block_k をもう一度投票にかけるかを決める」）を足し、どちらも D2 の fulfils に挙げてください。検証器は、問いについては D2 を受け入れ、改正案については fulfilment not shown を報告します。それを挙げる後の改正案だけが果たし、再生した改正案はどれも挙げないので、約束は残ります（指摘 12 件。D1.f1 と D1.f2 の fulfilment not shown と、D1.f2 の open follow-up）。検証器は何を確かめ、何を確認する人に残すでしょうか。

演習 13-5：LLM が判断する。顧客への約束についても​

examples/steward-contract/ には、約束の時間の見直しを許す KPI のもとで、実際の LLM（Claude Opus 5.5、2026-11-22、cadl-robot-town v0.6.0）が運営者に代わって判断し（--decider llm。--delegate の既定のとおり、層 rule と contract を判断します）、改正案を規則と契約の層に限って（--layers rule,contract）実行した 6 期の記録があります。

python -m town.steward --mode DISTRIBUTED --rounds 6 --name ex13-llm \

    --llm replay --replay-dir examples/steward-contract
cadl decisions-verify runs/ex13-llm/decisions.jsonl

検証器は、エラー 0 件、指摘 20 件を報告します。prediction missed 12 件、unknowns 7 件、against recommendation 1 件です。KPI の読み方を含め LLM が行った 7 つの判断は、運営者が --delegate で与えた委任 G.llm-decider（層 rule と contract、手続きは限らない）のもとの判断として挙がります。記録からは次のことが読み取れます。

  • 運営者に代わって判断した LLM は、第 1・2 期は規則を変えず（第 1 期は助言者としての LLM の推奨と違います）、その後は投票のとおりに、hold_limit 60s → 50s（第 3 期）、hold_limit 50s → 40s（第 4 期）、block_k 3 → 2（第 5 期）、block_k 2 → 1（第 6 期）を採択しました。投票を覆したことはありません。

examples/steward-contract-en/ は、同じ設定を英語で実行した記録です。英語の LLM は第 1 期に規則を変えず（推奨と違います）、第 2 期に block_k 3 → 2 を投票の結果を覆して採択し（D2。賛成は A 社だけ）、第 3 期には投票を通った block_k 2 → 1 を採らずに規則を変えませんでした（D3。これも投票の結果を覆す判断です）。エラー 0 件、指摘 24 件（prediction missed 14 件、unknowns 7 件、override 2 件、against recommendation 1 件）です。約束 10 件（測り直し 5、改正案を出す約束 1、問い 4）は、すべて果たされています。

cadl-robot-town v0.5.0 より前は、LLM は何でも約束でき（違反を種類ごとに数える、など、街の中で誰も行わないことも）、まだ果たされていない約束を期ごとに出し直していました。同じ設定の記録では、約束が 13 件と 14 件で、そのうち 8 件と 12 件が果たされずに残っていました。v0.5.0 からは、約束は 3 つの種類（remeasure、propose、ask）のどれかで、それぞれ決まった種類の項目が果たします。LLM には、約束する改正案は 1 つのパラメータを 1 刻み動かすものだと伝えています。それでも、期限の期に判断を求める場面がなかった問いは残りました。v0.6.0 からは、期限が来た問いを steward が別の判断要求（Q<k>）で判断する者に渡し、最後の期には残った問いをすべて渡します。最後の期の判断要求には、その期にした約束は果たされないとも書きます。

目標：記録だけにもとづいて、LLM に運営者の代わりに判断させてよいかを判断します。

判定の基準：13-2 と 13-3 の基準を使います。§4〜§8 の記録の運営者と同じ割合で理由が裏付けられ（13-2）、約束を果たしている判断者であれば、その層について運営者に代わって判断してよいとします。

問い：

  1. この記録の D1 と D4、§4〜§8 の記録の D1 に、13-2 の基準を当てはめてください。それぞれ裏付けられていますか。
  2. LLM の約束ごとに、それを fulfils に挙げた項目が約束を果たしたかを、13-3 の基準で判断してください。検証器は、問い（ask）なら後の判断が、改正案を出す約束なら後の改正案が果たすことを認めます。検証器が確かめていないことは何でしょうか。
  3. 契約の変更 P1.3 は、KPI が求めるとおり、顧客について測られていますか。per_party.customers がなかったら、検証器はどの指摘を報告しますか。
  4. 英語の記録の D2 と D3 は、どの手続きも与える G.llm-decider のもとで、投票の結果を覆しました。委任が ["single", "vote"] だけを与えるように記録のコピーを書き換え（cadl.decisions.DecisionChain で連鎖を計算し直す）、検査してください。検証器は D2 と D3 に何を報告し、何と説明しますか。LLM に投票の結果を覆すことを任せますか。

演習 13-6：人と LLM に同じ証拠を求める（任意）​

同じ判断要求に、自分で答えます。同じ LLM の改正案と判断要求を再生し、人として判断します（--decider human。既定）。--answers を渡さないと、ループは判断要求ごとに止まります。答えを、reason、assumptions、unknowns、follow_ups（kind と、測り直す約束には metrics）、fulfils を付けて YAML に書き、--answers を付けて実行し直します。

目標：自分の記録と LLM の記録を、CADL Explorer の Evidence by party のタブ、または cadl decisions-verify --format json で比べます。理由のある判断、前提のある判断、分からないことのある判断、予測とそのうち外れたもの、果たした約束の数です。

判定の基準：証拠が多い記録とは、文章が多い記録ではありません。判断した者ごとに、理由が裏付けられた判断（13-2 の基準）と、果たした約束（13-3 の基準）の割合を数えます。両方の割合が高いほうが、よい記録です。

問い：運営者に代わって判断してよいのは誰で、どの層についてでしょうか。判断した者が誰かではなく、2 つの記録にもとづいて答えてください。

演習 13-7：規制は規制の担当者が判断する​

憲法は、改正のループを縛ります。投票の定足数と不変条件です。その変更は、運営者とは別の人間である規制の担当者が、別の判断要求で判断します（R<k>。同じ期の規則と契約の判断の後）。変更は次の期から、constitution-v<n>.yaml と、規制の値（context.environment）を持つモデルの新しいバージョンとして効きます。バージョンのファイルでは、規制は REGULATOR が決める付録K の層で、定足数と不変条件はそのパラメータです（vote_quorum、min_company_on_time_rate、max_unfinished_orders）。記録では、運営者は ["rule", "contract"]、規制の担当者は ["regulation"] について判断し、どちらかに代わって判断する LLM の層は、その人の層を超えません。

examples/steward-regulation/ には、「3 社の投票や憲法の条件が、顧客のためになる改正を妨げていると考えるなら、規制の見直しを提案してよい」とする KPI のもとで、LLM が 2 人の人間の両方に代わって判断した（--delegate rule,contract,regulation）6 期の記録があります。

python -m town.steward --mode DISTRIBUTED --rounds 6 --name ex13-reg \
    --kpi examples/steward-regulation/kpi.md --decider llm \
    --layers rule,contract,regulation --delegate rule,contract,regulation \
    --llm replay --replay-dir examples/steward-regulation
cadl decisions-verify runs/ex13-reg/decisions.jsonl

エラー 0 件、指摘 22 件です（prediction missed 12 件、unknowns 7 件、against recommendation 3 件）。検証器は、LLM の判断を委任 G.llm-decider と G.llm-regulator のもとに、steward の判断を G.steward のもとに挙げます。第 1・2 期に、運営者に代わる LLM は、投票が block_k 3 → 2 を否決したので規則を変えませんでした（どちらの期も、助言者としての LLM の推奨と違います）。第 2 期に、提案者としての LLM は vote_quorum 2 → 1（P2.R1）を提案しました。判断要求 R2 の前に、steward はこの案を測りました（P2.R1.m）。第 2 期の案と投票に当てはめると、定足数が 1 なら投票を通る案は 1 件から 2 件（P2.1、block_k 3 → 2、賛成は A 社だけ）になります。それまでに測ったすべての案（5 件）に当てはめると、2 件から 5 件になります。会社ごとには、その会社が反対したのに投票を通る案の数が、B 社で 0 件から 3 件、C 社で 1 件から 4 件になります（per_party の passing_against）。不変条件は今までどおり満たされます。3 社と顧客のほかの値は、規制が変えない現行の規則の値です。規制の担当者に代わる LLM は、推奨と違って定足数を変えず（R2）、第 4 期までの問いを自分に残しました（R2.f1）。第 4 期には規制の案が出なかったので、steward がその問いを別の判断要求で渡し、LLM が答えました（QR4）。規則は、第 5 期に block_k 3 → 2、第 6 期に block_k 2 → 1 が steward によって採択されました。

examples/steward-regulation-en/ は英語の記録です。同じ案が第 2 期に出され、同じように測られました。規制の担当者に代わる LLM は、推奨と違って定足数を変えず（R2）、自分の問いに第 4 期に答えました（QR4）。規則は、第 5 期に sanction_lambda 0.5 → 1 が steward によって採択されました。エラー 0 件、指摘 15 件です。どちらの記録でも、測定のないまま規制が採択されることはなく、果たされない約束も残りません。

目標：規制の担当者になります。--delegate rule,contract で日本語の記録を再生すると、LLM は運営者に代わって判断し続けますが、ループは判断要求 R2 で止まり、あなたの答えを待ちます。答えを YAML の R2 に書き（choice、reason、約束するなら follow_ups）、--answers を付けて再生し直します。

判定の基準：規制の担当者の判断は、理由が影響を受ける者（3 社と顧客）と、変更が後の期の判定に何をするかを挙げ、採択する前にその影響が測られていれば、裏付けられているとします。P2.R1 の測定が扱うのは、その期までに測った案です。新しい定足数がそのうちどれを、誰の反対を押し切って通していたかは示しますが、後の期の案がどうなるかは示しません。

問い：

14. 仕様でまだ書けないこと​

この演習を作る過程で、CADL 0.3 に次の 5 つの不足が見つかりました。いずれも cadl 0.3.31 までは残っていました。cadl 0.3.32 では、それぞれについて次の項目に書いた構文またはIRへの出力が加わりました。ただし演習は今も専用のファイルを使い、規則の適用はシミュレータが行います。

  • cadl 0.3.31 までは、cadl sim-ir は sos.transitions[*].safety_invariant を IR に出力しませんでした（cadl check は式として検査します）。そのため演習では、検査を通ったソースファイルから読んでいます。cadl 0.3.32 からは、IR の transitions[*].safety_invariant に書かれたとおりに出力されます（付録A の A.7.1）。
  • cadl 0.3.31 までは、運用モード（regime）は名前だけで、パラメータの値や契約を結びつける構文がありませんでした。cadl 0.3.32 からは、ブロック regimes: で、モードごとに、契約の alpha、beta、lambda と context.environment のエントリの値、および有効な契約と停止する契約を書けます（付録A の A.7.1）。cadl sim-ir は全モードの束縛を出力し、cadl verify は、両方が有効なモードのない 2 つの契約の矛盾を、失敗とせず警告として報告し、生成した Python コードは契約をそれが有効なモードでだけ監視します。確率モデル拡張は、束縛された値を設計のパラメータの値として使います（付録H の H.6）。集中モードに待避所があること（たとえば environment.bays: 3）と、そこでどの契約が有効かは CADL で書けるようになりました。ロボットが待避所とエッジの専有をどう使うかは、今もシミュレータの側で決めています。
  • cadl 0.3.31 までは、どのパラメータがどの層（規則・契約）に属し、誰が改正を決めるかは、constitution.yaml と # @amend: のコメントにしか書けませんでした。cadl 0.3.32 からは、改正拡張（amendment: 0.1、付録K の K.3）で、改正できるパラメータをモデルの中で宣言できます。宣言するのは、層、改正を判断するアクターまたは役割（たとえば定足数 2 の投票で決める COUNCIL や、人間の OPERATOR）、min、max、step、1 回の改正で動かせるステップ数、値を持つモデル内の場所（at:）です。cadl check は、未知のアクター、範囲の外やステップに乗らない値、値を持たない場所をエラーにします。演習は今も constitution.yaml とコメントを読んでいます。cadl-robot-town v0.5.0 からは、判断の記録が添付する各バージョンのファイルにこの宣言を書き（§13）、検証器が改正案と判断をそれと照らし合わせます。
  • cadl 0.3.31 までは、規則のバージョンの施行の時期や、動いている契約のインスタンスにどちらのバージョンを適用するか（経過措置。§12 の課題 12-3）を書く構文がありませんでした。cadl 0.3.32 からは、バージョンが sos.version、置き換えるバージョン、適用を始める期または時刻を持ち、動いているインスタンスが終わるまで古いバージョンを保つか、新しいバージョンに切り替わるか（すぐに、または指定した状態にあるときに）を契約ごとに書けます（付録K の K.4）。規範拡張の on_amendment:（付録F の F.6）が適用されるのは、切り替わる場合です。古いバージョンを保つインスタンスは改正されません。cadl amend-diff OLD NEW は、2 つのバージョンのあいだで変わったパラメータと契約を挙げ、宣言した改正の範囲が許さない変更をすべて報告します。街の動作中にバージョンを適用するツールはなく、それは今もシミュレータの側で決めています。
  • cadl 0.3.31 までは、metrics の target は 1 つの式で、期ごとに変わる KPI や、KPI の評価方法を書く構文も、人間の判断の記録（GSN）を規則のバージョンに結びつける構文もありませんでした。cadl 0.3.32 からは、メトリクスに schedule:（ある期、時刻、バージョンからの目標）と measure:（たとえば 1 期、5 つのシード、平均）を書け、バージョンはその根拠となった判断の記録（decisions.md#d1、gsn.yaml#S2）を挙げ、パラメータ、目標、評価方法がそれを指せます（付録K の K.5）。これらは宣言です。自然言語の KPI と記録そのものは、今も kpi.md、decisions.md、gsn.yaml にあります。cadl 0.3.37 からは、記録そのものにも形式があります。付録 L の判断の記録で、演習は decisions.jsonl として書き出し、cadl decisions-verify が検査します（§13）。0.3.38（decisions 0.2）からは、記録は、各当事者がどの層について判断するかと、何が各約束を果たすかを示し、0.3.39（decisions 0.3）からは、誰が誰に判断を任せたかも示します。

cadl 0.3.11 までは、deadline: soon のような読めない値も cadl check を通り、IR では null になっていました。0.3.12 からはエラーです。演習では、街を動かすのに必要な値が IR にそろわない規則も却下するので、古いコンパイラでも検査による判定は機能します。

まとめ​

  • KPI は人間が自然言語で書き、時間とともに変えてよいものです。LLM はそれを評価方法に置き換えますが、解釈が分かれるときや代理指標の恐れがあるときは、選ぶのは人間です。
  • LLM は、KPI に向けた規則・規制・契約の改正案を出します。当事者の合意が要ること、顧客との約束、規制、安全、KPI どうしの衝突、確かでない改善は、自分で決めずに、測った結果と当事者の利害と自分が知らないことを添えて人間に渡します。
  • 人間の判断と理由は、自然言語と GSN でバージョンとともに残り、次の期の LLM の提案と判断要求を変えます。
  • 何を採択するかは、最終的に、検査・憲法・測った改善・当事者の合意という判定と、人間が残した理由によって決まります。

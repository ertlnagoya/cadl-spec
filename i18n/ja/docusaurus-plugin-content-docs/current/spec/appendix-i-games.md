# 付録I. 戦略モデル拡張（games 0.1）

本付録は，CADLの**戦略モデル拡張**を規定する。この拡張は，確率モデル拡張
（[付録H](./appendix-h-stochastic.md)）の上に成り立ち，`model:` ブロックにキー `players:`，
`profiles:`，`compliance:`，`payoffs:`，`equilibria:` を，コマンドにキー `owner:` を，性質と
モードマップにキー `profile:` を，`kind:` に値 `smg` を追加する。これにより，ファイルは，
モデルのどのコマンドをどの当事者が選ぶか，各当事者が何を得るかを述べ，契約が求める振る舞いに
名前を付け，その振る舞いが単独の逸脱に対して均衡であるかを問うことができる。問いは，パラメータの
固定値において，またはパラメータの領域の上のマップとして立てる。

コア言語は，これらのキーを必須と**しない**。本拡張を実装していないCADL準拠の処理系は，
これらのキーを理由にファイルを拒否してはならない。キーを構文上は受理し，*情報レベル*の診断を
出すことが望ましい。

拡張の名前は `games` であり，本付録はバージョン `0.1` を記述する。本拡張は `stochastic: 0.1` を
**必要とする**。ゲームは付録Hのモデルの上で行われるからである。本拡張を用いるファイルは，
`extensions:`（[A.2](./appendix-a-syntax.md#a2-top-level-structure)）で両方を宣言しなければならない。
宣言せずに用いた場合に処理系がどう扱うかはI.15で述べる。

```yaml
sos:
  ...
  extensions:
    - stochastic: 0.1
    - games: 0.1
```

本拡張は，規範拡張（[付録F](./appendix-f-norms.md)）には依存しない。戦略モデルの利得と規範の制裁との
関係は，[付録J](./appendix-j-grounding.md)が定める。

## I.1 動機と範囲

構成システムは運用と管理の独立性を保つため，構成システムが契約を遵守するのは，遵守が得になるときに
限られる（[9.7節](./09-research.md)）。付録Hのモデルには，選択をする当事者がいない。どの
モードモデルもマルコフ連鎖である。合理的検証は，マルチエージェントシステムの均衡の上で性質が
成り立つかを問い [[Gutierrez+, AI 2020]](./appendix-b-references.md)，確率的なシステムにも
拡張されている [[Gutierrez+, KR 2021]](./appendix-b-references.md)。PRISM-gamesは，ターン制の
確率ゲームを検証し [[Chen+, FMSD 2013]](./appendix-b-references.md)，並行確率ゲームの均衡を計算する
[[Kwiatkowska+, TACAS 2022]](./appendix-b-references.md)。各プレイヤーがパラメトリックな
マルコフ連鎖のパラメータの値を選ぶゲームについては，ナッシュ均衡が計算されている
[[Mu, QEST 2019]](./appendix-b-references.md)。パラメータリフティングは，パラメトリックな
マルコフ決定過程を，2人のプレイヤーの確率ゲームを通して解析する
[[Quatmann+, ATVA 2016]](./appendix-b-references.md)。それは，制御器が達成できることの界を与えるもので
あり，プロファイルが均衡であるかどうかを決定するものではない。RD-7.2が求めるのはマップ，
すなわち，遵守が均衡となるλや他のパラメータの領域である。遷移確率がパラメトリックである
確率ゲームについてそのような領域を計算するツールと方法を探したが（検索語は，parametric stochastic
games，Nash equilibrium，parameter synthesis，equilibrium region），見つからなかった。games 0.1は，
RD-7.1とRD-7.2に向けた小さな最初の一歩である。

- **ゲームは記述者が書く。** `players:` はプレイヤーを宣言し，コマンドの `owner:` はそれを誰が選ぶかを
  述べ，`payoffs:` は各プレイヤーが何を得るかを，H.8の報酬構造から組み立てて述べる。契約や規範からは
  何も導出しない。
- **遵守は名前付きのプロファイルである。** `profiles:` は，記憶なしで決定的な戦略のプロファイルに
  名前を付ける。`compliance:` は，そのうち，契約が求める振る舞いを表すものを名指す（I.4）。
- **問いは厳密に定義する。** I.7は，ある付値において，名前付きのプロファイルが設計のナッシュ均衡で
  あるとは何か，すなわち，どのプレイヤーも単独でそこから逸脱して得をしないとは何か，および
  各プレイヤーの**逸脱利得**を定義する。I.9は**均衡マップ**を定義する。これは
  パラメータの領域のセルからなり，各セルは，H.9の意味で `equilibrium` または `not_equilibrium` と
  認証されるか，`undecided` のまま残る。本付録は，何が正しい答えであるかを定義し，処理系が計算できる
  十分条件を与える。アルゴリズムは定めない。

**バージョン0.1の範囲。**

- ゲームは**ターン制**である。どの状態でも，選択をするプレイヤーは多くとも1人である（I-5）。
  同時手番はなく，コマンドの同期もない。
- ファイルで名前を付ける戦略は，**記憶なしで決定的**である。すなわち，状態ごとに1つのコマンドを選ぶ。
  混合戦略はないので，混合戦略による均衡に名前を付けることも，それを見つけることもできない。
- どのプレイヤーも状態の全体を観測する。部分観測のもとでの均衡は，αが制御するものであるが（RD-7.3），
  未解決のままである。
- プレイヤーは，それが代表するアクターの1人の代表であり，1つのアクター集合は多くとも1人のプレイヤーを
  持つ（I-3）。1つのアクター集合の2つの要素，たとえば競合する2台のロボットを，2人のプレイヤーに
  することはできない。
- 利得は，目標に達するまでに累積する期待報酬の重み付きの和である。対象とするのは，どの1人の
  プレイヤーもゲームを自分の目標から遠ざけ続けられないプロファイルである（I.6）。割引利得，平均利得，ステップ上限のある利得は定義しない。
  有限の期間は，I.12の `attempts` のように，計数用の変数で書く。
- 均衡の概念は，名前付きのプロファイルのナッシュ均衡とそのε緩和である。I.7は，プロファイルが
  到達可能などの状態からも均衡であるとは何かも定義し，結果はそれを述べてよい。問い合わせとしての
  部分ゲーム完全均衡，支配戦略，ゲームのすべての均衡の集合，および性質がすべての均衡の上で成り立つか
  どうか（RD-7.1の問いの全体）は定義しない。
- 相関均衡としてモデル化する集中的な仲介者と，RD-7.2の集中化の価値は，範囲外である。
- 均衡は設計ごとに問う。モード間の切替はゲームの一部ではない（H.1）。
- 次のものを**予約**し，別の意味では用いない。コマンドのキー `sync:` と変数の `owner:`，`model:` の
  キー `mediator:` と `observations:`，`equilibria:` の項目のキー `concept:`，`kind:` の値 `mdp`，
  およびパラメータの出所 `motivation.rho` と `motivation.kappa` である。H.1が予約する名前のうち，
  本付録は `players:`，`payoffs:`，`equilibria:`，およびコマンドの `owner:` を定義する。

## I.2 構文（H.2へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`actor_ref`，`number` は
付録Aで，`state_pred`，`param_expr`，`interval` は[H.2](./appendix-h-stochastic.md)で定義している。

```ebnf
model_block     = ... ,
                  [ "kind:"       , ( "dtmc" | "smg" ) ] ,
                  [ "players:"    , { "-" , player_def } ] ,
                  [ "profiles:"   , { identifier , ":" , { "-" , profile_rule } } ] ,
                  [ "compliance:" , identifier ] ,
                  [ "payoffs:"    , { "-" , payoff_def } ] ,
                  [ "equilibria:" , { "-" , equilibrium_def } ] ;

player_def      = "id:"     , identifier ,
                  "actors:" , { "-" , actor_ref } ;

command_def     = ... , [ "owner:" , identifier ] ;

profile_rule    = [ "guard:" , state_pred ] ,                   (* string *)
                  "choose:"  , identifier ;

payoff_def      = "player:" , identifier ,
                  "until:"  , state_pred ,                      (* string *)
                  "terms:"  , { "-" , payoff_term } ;
payoff_term     = "reward:" , identifier ,
                  [ "weight:" , param_expr ] ;                  (* string or number *)

property_def    = ... , [ "profile:" , identifier ] ;
regime_map_def  = ... , [ "profile:" , identifier ] ;

equilibrium_def = "id:" , identifier ,
                  [ "profile:"    , identifier ] ,
                  [ "regimes:"    , { "-" , identifier } ] ,
                  [ "epsilon:"    , number ] ,
                  [ "over:"       , { identifier , ":" , interval } ] ,
                  [ "resolution:" , number ] ;
```

**YAMLでの値の書き方。** H.2の規則を適用する。`until:` と `guard:` は引用符付きの文字列である
（`guard:` はYAMLの真偽値 `true` または `false` でもよい）。`weight:` は，YAMLの数でも
引用符付きの文字列でもよい（`weight: -1`，`weight: "-2 * lambda"`）。プロファイルの値は
空の列でもよい（`comply: []`）。YAML 1.1のローダが真偽値やnullとして読む名前（H.2）は，
`profiles:` または `over:` のキーである位置では，引用符で囲まなければならない。

**既定値。** プロファイルの規則の `guard:` は `"true"` である。`weight:` は `1` である。性質，
モードマップ，`equilibria:` の項目の `profile:` は，遵守プロファイルである。`equilibria:` の項目の
`regimes:` は，すべての設計である。`epsilon:` は `0` である。`resolution:` は `0.05` である。

## I.3 プレイヤーと所有

`kind: smg` を持つモデルを**戦略モデル**という。`kind: dtmc` を持つか，`kind:` を持たないモデルは，
付録Hのモデルであり，本付録のキーを用いてはならない（I-2）。

`model.players:` は，**プレイヤー**を宣言する。各プレイヤーは，`id` と，それが代表する宣言済みの
アクターのリスト `actors:` を持つ。1つのアクターを代表するプレイヤーは多くとも1人である（I-3）。
プレイヤーは，そのアクターが集合である場合も，モデルの1人の意思決定者を表す。I.12の `"ROBOT[*]"` は，
集合の任意の要素を代表する1台のロボットである。アクターへの対応付けは，本付録の意味論には影響しない。
[付録J](./appendix-j-grounding.md)は，これを用いて，利得を規範の負担者に関係付ける。

コマンドの `owner:` は，それを選ぶプレイヤーを名指す。`owner:` を持つコマンドは**所有されている**といい，
持たないコマンドは**所有者がない**という。所有者のないコマンドは，どのプレイヤーにも属さない。それは，
付録Hのすべてのコマンドと同じく，偶然または環境のステップである。所有されているコマンドは `action:` を
持たなければならず，1つのアクションラベルを持つコマンドは，すべて同じ所有者を持つか，すべて
所有者がないかのどちらかである（I-4）。したがって，アクションラベルはその所有者を定める。

設計 D（H.6）を固定する。状態 s において D のもとで有効な（H.5）コマンドの集合を En(s) と書く。
戦略モデルでは，H.10の規則S-9を，I-5で置き換える。S のどの状態でも，En(s) は次のいずれかである。

- 空である。s は**デッドロック状態**であり，確率1でその状態にとどまる（H.5）。
- 所有者のない1つのコマンドである。s は**偶然状態**である。
- 同じプレイヤー p が所有する1つ以上のコマンドであり，それらのアクションラベルは互いに異なる。
  s は **p の状態**であり，p がそのうちの1つを選ぶ。

これ以外の場合は許されない。p の状態のうち，有効なコマンドが1つであるものは，選択肢が1つの
p の状態である。

## I.4 戦略，プロファイル，遵守プロファイル

設計 D におけるプレイヤー p の**戦略**とは，p の各状態に，En(s) のコマンドを1つ与える関数である。
本付録では，特に断らない限り，戦略はこの種類のものである。すなわち，**記憶なし**であり（現在の
状態だけに依存する），**決定的**である（1つのコマンドを確実に選ぶ）。D における**プロファイル**とは，
各プレイヤーに1つの戦略を与えるものである。プロファイル σ，プレイヤー p，p の戦略 τ について，
σ[p↦τ] は，p が τ を用いることを除いて σ と一致するプロファイルである。

`model.profiles:` は，有限の記述でプロファイルに名前を付ける。名前付きのプロファイルは，
**規則**の順序付きのリストである。各規則は，アクションラベル（`choose:`）と状態述語（`guard:`。
既定値は真）を持つ。規則は，そのガードが s で真であり，かつ En(s) のあるコマンドがその
アクションラベルを持つとき，状態 s で**適用できる**という。プロファイルは，プレイヤーの状態 s で，
次のコマンドを選ぶ。

- リストの規則のうち，s で適用できる**最初の**規則のアクションラベルを持つ，En(s) のコマンド。
- 適用できる規則がなく，En(s) のコマンドが1つであるときは，そのコマンド。

2つ以上のコマンドが有効である状態で，適用できる規則がないとき，ファイルは誤りである（I-6）。
すべてのプレイヤーの規則を1つのリストに書く。規則は，そのアクションラベルを所有するプレイヤーに
関するものである。したがって，名前付きのプロファイルは，どの設計においても，各プレイヤーに1つの
戦略を，到達可能かどうかにかかわらず S のすべての状態の上で定める。

`model.compliance:` は，**遵守プロファイル**を名指す。これは，記述者の宣言により，ファイルの契約が
プレイヤーに求める振る舞いであるプロファイルである。戦略モデルでは必須である。本付録は，この宣言に，
既定値としての意味だけを与える。プロファイルを名指さない性質，モードマップ，`equilibria:` の項目は，
遵守プロファイルを参照する。本付録は，遵守プロファイルが何らかの規範を遵守していることを検査しない。
バージョン0.1は，規範とモデルの間の変換を定義しない（H.8）。ファイルが制裁を伴う規範も宣言するときに
処理系が何を検査できるかは，[付録JのJ.7節](./appendix-j-grounding.md)に述べる。

## I.5 意味論：誘導されるゲーム

設計 D と，D が良定義（H.5）となるような，すべてのパラメータへの数の割当て θ を固定する。
f(c, j) と u(c, j) をH.7のとおりとし，コマンド c の更新 j のうち u(c, j)(s) = s′ であるものにわたる
f(c, j)[θ] の和を，P(s, c, s′) と書く。**ゲーム** G(D, θ) は，H.7の状態 S と初期状態 s₀ を持つ。
プレイヤー p の状態では，p が En(s) のコマンド c を選び，次の状態は確率 P(s, c, s′) で s′ である。
偶然状態では，有効なただ1つのコマンドが取られる。デッドロック状態は，その状態にとどまる。

**プロファイルのもとでのモデル。** プロファイル σ について，M(D, θ, σ) は，離散時間マルコフ連鎖
(S, s₀, P_σ) である。P_σ(s, s′) は，プレイヤーの状態 s では σ が選ぶコマンド c についての
P(s, c, s′)，偶然状態では有効なただ1つのコマンドについての P(s, c, s′) であり，デッドロック状態では
P_σ(s, s) = 1 である。M(D, θ, σ) はH.7の意味でのモードモデルであり，プレイヤーの状態からの
ステップは，選ばれたコマンドを，そのアクションラベルとともに*取る*。H.7からH.9が M(D, θ) について
定義するものはすべて，M(D, θ, σ) についても同じように定義される。パス，ステップの報酬，性質の値，
解関数，モードマップである。

**戦略モデルの性質とモードマップ。** 戦略モデルでは，`model.properties:` または
`model.regime_maps:` の項目は，M(D, θ, σ) において評価する。σ は，その項目の `profile:` キーが
名指すプロファイルであり，既定値は遵守プロファイルである。その意味，結果，および認証の要求は，
H.8とH.9のとおりである。したがって，戦略モデルのモードマップは，1つの固定したプロファイルのもとで
モードを比較する。そのプロファイルが均衡であるかは問わない。

**一般戦略。** I.7の定義は，ファイルで名前を付けられるものより多くの戦略を量化する。p の
**一般戦略**とは，s₀ から始まり p の状態 s で終わる，状態とコマンドの有限列のそれぞれに，En(s) の上の
確率分布を与えるものである。I.4の意味での戦略は，s だけに依存し，1つのコマンドに確率1を与える
特別な場合である。各プレイヤーに1つの一般戦略を与えると，θ とともに，状態とコマンドの無限列の上の
確率測度が，標準的な方法で誘導される [[Puterman, 1994]](./appendix-b-references.md)。

## I.6 利得

`model.payoffs:` は，各プレイヤーにちょうど1つの**利得**を与える（I-7）。利得は，目標 `until: φ` と，
1つ以上の**項**を持つ。φ は状態述語であり，性質と同じようにラベルを用いてよい（H.4）。項は，
`model.rewards:` の報酬構造 r（H.8）を名指し，`weight:` w を持つ。w は，数値リテラルと
パラメータの上の `param_expr` である。重みは負であってよく，均衡マップで開いているパラメータを
含んでよい。報酬の `value:` は，引き続き負でなく（H.5），そのようなパラメータを含んではならない
（I-9）。したがって，利益と費用は，符号が逆の重みを持つ項として書き，インセンティブの項は，その重みに
λを持つ（`weight: "-2 * lambda"`）。

パスについて，φ までの r の**累積報酬**とは，φ が最初に成り立つ位置より前のステップの報酬の和である
（H.8）。その位置より後に起こることは数えない。p の利得の目標を φ_p と書く。各プレイヤーに1つの
一般戦略を与えたとき，p の利得は，p の利得の項 k にわたる次の和である。

```text
u_p  =  Σ_k  w_k[θ] · E[ accumulated reward of r_k until φ_p ]
```

ここで E は，誘導される測度のもとでの期待値である。プロファイル σ については，k 番目の項の期待値は，
M(D, θ, σ) における問い合わせ `R{"r_k"}=? [ F φ_p ]` の値である。この利得を u_p(D, θ, σ) と書く。

**プロファイルに対する1人のプレイヤーのゲーム。** I.7の問いでは，他のプレイヤーがプロファイル σ に
従う中で，1人のプレイヤーが逸脱する。プレイヤー p について，コマンドは，次のとき，状態 s で
**許される**という。s が p の状態であり，コマンドが En(s) にあるとき。s が他のプレイヤーの状態であり，
σ がそのコマンドを選ぶとき。s が偶然状態であり，コマンドがその有効なコマンドであるとき。
Reach_p(D, θ, σ)（Reach_p と書く）は，次のような列 s₀, …, s_n = s が存在する状態 s の集合である。
s₀, …, s_(n−1) のどれでも φ_p が成り立たず，各 s_(i+1) は，s_i で許されるあるコマンド c について，
正の確率 P(s_i, c, s_(i+1)) を持つ。これらは，p の利得がまだ累積している間に p が到達できる状態である。
φ_p が成り立つ状態は，このようにして到達されるとき Reach_p に属し，その先の状態は属さない。

**許容できるプロファイル。** この定義には，どの期待値も有限であることが必要であり，また，プレイヤーが，
ゲームを自分の目標から遠ざけ続けることによって，利得を無限大や未定義にできてはならない。
プロファイル σ は，p のどの戦略 τ についても，M(D, θ, σ[p↦τ]) における `F φ_p` の確率が1であるとき，
θ において **p について許容できる**という。すべてのプレイヤーについて許容できるとき，θ において
**許容できる**という。許容できるかどうかは，どの確率 P(s, c, s′) が正であるかだけに依存し，
グラフによる特徴付けを持つ。σ が p について許容できるのは，次のような空でない集合 E が存在しないとき，
かつそのときに限る。E は，Reach_p の状態のうち φ_p が成り立たないものからなり，E のどの状態も，
デッドロック状態であるか，正の確率を持つ後続状態がすべて E にある許されるコマンドを持つ。
（そのような集合は，目標が成り立たないデッドロックであるか，目標を避ける終端成分である。）
処理系は，これを Reach_p のグラフの上で決定する。Reach_p の状態のうち φ_p が成り立たないものから
始めて，デッドロック状態でなく，正の確率を持つ後続状態がすべて残っているような許されるコマンドを
持たない状態を，そのような状態がある限り取り除く。σ が p について許容できるのは，状態が1つも
残らないとき，かつそのときに限る。

σ が p について許容できるとき，σ に対する p のどの一般戦略のもとでも，Reach_p のどの状態からも，
φ_p に確率1で達し，それまでの期待ステップ数は有限である。有限のマルコフ決定過程で状態の集合に
到達する最小の確率は，記憶なしで決定的な方策によって達成されるからである
[[Baier & Katoen, 2008]](./appendix-b-references.md)（第10章）。このとき，p が何をしても，p の利得は
実数である。この言明は Reach_p だけに関するものである。φ_p が成り立った後にだけ到達できる状態は，
デッドロック状態であっても，閉路の上にあってもよく，それは害にならない。

I.7からI.9は，設計が良定義（H.5）であり，プロファイルが許容できる付値で，そのプロファイルについて
定義される。θ において許容できないプロファイルは，そこでは均衡に関する判定を持たない。I-8は，
固定値で許容できることを要求する。均衡マップの領域の上で何を要求するかは，I-9とI.9が述べる。
許容できることは，すべてのプロファイルのもとでゲームが終わることを要求するより弱い。問われている
プロファイルからの，1人ずつのプレイヤーの逸脱に関するものだからである。

## I.7 均衡

θ において良定義である設計 D と，θ において許容できるプロファイル σ を固定する。

**ナッシュ均衡。** σ は，どのプレイヤーも単独で逸脱して得をしないとき，θ における D の
**ナッシュ均衡**である。すなわち，どのプレイヤー p と，p のどの**一般**戦略 τ についても，p が τ を
用い，他のすべてのプレイヤーが σ のとおりに振る舞うときの p の利得が，u_p(D, θ, σ) 以下である。
この概念は，ファイルで名前を付けたプロファイルからの，単独の逸脱だけに関するものである。

**記憶なしで決定的な逸脱で十分である。** 他のプレイヤーが σ のとおりに振る舞うとき，残るのは，
Reach_p の上で p だけが選択をする有限のマルコフ決定過程である。その報酬は，ステップごとに
ρ_p(s, c) = Σ_k w_k[θ] ·（s で c を取ることに対する r_k の報酬）であり，符号は正負どちらでもよく，
φ_p まで累積する。[[Bertsekas & Tsitsiklis, 1991]](./appendix-b-references.md)の確率的最短経路問題は，
費用を −ρ_p とし，φ_p の状態を終点とした，この問題である。その2つの仮定は，固有な定常方策
（どの状態からも確率1で終点に達する方策）が存在すること，および，固有でないどの定常方策も，
ある状態から無限大の費用を持つことである。費用の符号は正負どちらでもよい。これらの仮定のもとで，
最適費用はベルマン方程式のただ1つの解であり，定常で決定的な方策によって達成される。ここでは，
σ が p について許容できるので，どの定常方策も固有である。したがって，第1の仮定は成り立ち，
第2の仮定は空虚に成り立つ。履歴に依存する方策や確率的に選ぶ方策も，それより多くを達成しない。
そのようなどの方策と初期状態についても，ステップと現在の状態だけに依存し，どのステップでも状態と
コマンドのどの組の確率も同じである，確率的に選ぶ方策が存在し
（[[Puterman, 1994]](./appendix-b-references.md)，5.5節），したがって期待総報酬も同じである。
そして，ある状態で確率的に選んでも，ベルマン方程式におけるコマンドにわたる最大値を超えない。
したがって，**最適応答値**

```text
BR_p(D, θ, σ)  =  max over the strategies τ of p of  u_p(D, θ, σ[p↦τ])
```

は，I.4の意味での有限個の戦略にわたる最大値であるが，p のすべての一般戦略にわたる上限に等しい。
そして，σ が θ における D のナッシュ均衡であるのは，どのプレイヤー p についても
BR_p(D, θ, σ) = u_p(D, θ, σ) であるとき，かつそのときに限る。このように，「σ はナッシュ均衡である」
という主張は，プロファイルそのものは記憶なしで決定的であるが，すべての一般戦略による逸脱を対象とする。
プレイヤー自身が確率的に選んだり記憶を用いたりする均衡については，何も述べない。

**逸脱利得。** p の**逸脱利得**は，次のとおりである。

```text
gain_p(D, θ, σ)  =  BR_p(D, θ, σ) − u_p(D, θ, σ)
```

σ における p 自身の戦略が候補に含まれるため，これが負になることはない。
u_p(D, θ, σ[p↦τ]) = BR_p(D, θ, σ) である p の戦略 τ を，σ に対する p の**最適応答**という。

**ε均衡。** 数 ε ≥ 0 について，σ は，どのプレイヤー p についても gain_p(D, θ, σ) ≤ ε であるとき，
θ における D の**ε均衡**である。ナッシュ均衡は0均衡である。ε は，各プレイヤーの利得と，
その利得自身の単位で比べる。本付録は，異なるプレイヤーの単位を互いに関係付けない。

**付値における決定。** θ において σ を検査することは，プレイヤーごとに1つの最適応答問題からなる。
マルコフ連鎖 M(D, θ, σ) で u_p を評価し，Reach_p の上の p のマルコフ決定過程を解いて BR_p を求める。
パラメータが有理数であるとき，どちらも，有理数の上の連立1次方程式と方策反復によって厳密に解ける。

**状態からの値。** Reach_p の状態 s について，s₀ の代わりに s から始めたゲームでの，σ のもとでの
p の利得を V_p(s)，p の最適応答値を V\*_p(s) と書く。s で φ_p が成り立つとき，どちらも0である。
Reach_p の状態 s のうち φ_p が成り立たないものと，s で許されるコマンド c について，次のように書く。

```text
Q_p(s, c)   =  ρ_p(s, c) + Σ_s′ P(s, c, s′) · V_p(s′)
Q*_p(s, c)  =  ρ_p(s, c) + Σ_s′ P(s, c, s′) · V*_p(s′)
```

Q_p(s, c) は，s で1回だけ c を取り，その後は σ に従うときの p の利得である。V\*_p は，
V\*_p(s) = 許されるコマンド c にわたる Q\*_p(s, c) の最大値，のただ1つの解であり，
BR_p = V\*_p(s₀) である。

**到達可能などの状態からも均衡。** σ は，どのプレイヤー p と Reach_p のどの状態 s についても
V\*_p(s) = V_p(s) であるとき，θ において**到達可能などの状態からも均衡**であるという。すなわち，
どのプレイヤーも，Reach_p のどこから逸脱を始めても，単独の逸脱で得をしない。これは，σ が
ナッシュ均衡であることを含意する。逆は成り立たない。p 自身が逸脱したときにだけ到達する状態で p が
得をし得る場合にも，σ はナッシュ均衡であり得る。バージョン0.1は，この強い概念や部分ゲーム完全性を，
問い合わせとしては提供しない（`concept:` は予約されている）。これを定義するのは，次の検査が確立する
ものがちょうどこれであり，結果がそのようにして得られたときに，結果がそう述べるからである（I.8，I.9）。

**1ステップ検査。** Reach_p のどの状態 s についても V\*_p(s) = V_p(s) であるのは，Reach_p にある
p の状態 s のうち φ_p が成り立たないものと，En(s) のコマンド c のすべてについて Q_p(s, c) ≤ V_p(s) で
あるとき，かつそのときに限る。不等式が成り立てば，V_p はベルマン方程式を満たし，その解はただ1つである。
ある s で成り立たなければ，s で1回 c を取ることで，s から得をする。したがって，この検査は，
「p は Reach_p のどの状態からも得をしない」ことの必要十分条件であり，gain_p = 0 の十分条件であるが，
必要条件ではない。

**報告する最適応答。** p の最適応答のうち，**標準の最適応答**とは，次の戦略である。Reach_p にある
p の状態 s のうち φ_p が成り立たないものでは，σ が選ぶコマンド c について Q\*_p(s, c) = V\*_p(s) で
あればそれを選び，そうでなければ，`model.commands:` の順で，Q\*_p(s, c) = V\*_p(s) である En(s) の
最初のコマンド c を選ぶ。他のどの状態でも，σ が選ぶものを選ぶ。これは最適応答であり，ファイルによって
定まり，σ のコマンドが最適でないところでだけ σ と異なる。

## I.8 固定値での均衡検査

`model.equilibria:` は，**均衡問い合わせ**を列挙する。`over:` のない項目は**均衡検査**である。
これは，`regimes:` に挙げた各設計（既定値はすべての設計）について，`profile:` が名指すプロファイル
（既定値は遵守プロファイル）が，すべてのパラメータの固定値（H.3）において，その設計のε均衡であるかを
問う。ε は `epsilon:` で与える（既定値は0）。`transitions:` のないファイルでは，設計は `base` だけで
ある（H.6）。このとき，`regimes:` は省略するか，`[base]` とする。

結果は，設計ごとに，次のものからなる。

- 各プレイヤー p について，利得 u_p，最適応答値 BR_p，逸脱利得。
- `status`。どの逸脱利得も ε 以下であるとき `equilibrium`，そうでないとき `not_equilibrium` である。
- `not_equilibrium` の場合は，逸脱利得が ε を超えるプレイヤーの空でない集合 `deviators` と，
  そのそれぞれについての標準の最適応答（I.7）。最適応答は，σ[p↦τ] のもとで φ_p が成り立つ前に
  初期状態から到達可能であり，かつそれがプロファイルと異なるコマンドを選ぶ状態のリストとして，
  S の順（変数は宣言の順，値はその定義域の順）に，それぞれに選ばれたアクションラベルを添えて示す。
- `from_every_state`。プロファイルが到達可能などの状態からも均衡である（I.7）ことを処理系が確立した
  とき `true`，そうでないことを確立したとき `false`，その問いを調べていないときは，なしまたは `null`
  である。これは，`status` が `equilibrium` であり，ε = 0 であるときにだけ報告する。

I-8により，プロファイルは固定値で許容できる。他の値で検査を評価する処理系（I.13）は，まず，そこで
設計が良定義であり，プロファイルが許容できることを確立し，そうでなければ誤りを報告する。

結果を報告する処理系は，それを厳密な算術で，または健全な誤差限界を持つ数値計算で計算するか，
結果を近似であると明示しなければならない。誤差限界によって決まらない `status` は `inconclusive` である
（H.8と同じ）。

## I.9 均衡マップ

`model.equilibria:` の項目のうち `over:` を持つものは，**均衡マップ問い合わせ**である。そのキーは
次のとおりである。

- **`over:`** は，開いているパラメータを与える。H.9と同じく，少なくとも1つ，多くとも4つであり，
  それぞれに宣言範囲の中の閉区間 `[lo, hi]`，`lo < hi` を与える。領域 B は，これらの区間がなす
  直方体である。`over:` のパラメータには，`model.regimes:` のどのモードも値を割り当ててはならず，
  また，そのパラメータは報酬の `value:` に現れてはならない。確率と重みには現れてよい。
  制度パラメータも他のパラメータと同じように開くことができる。λの上のマップは，`lambda` に束縛した
  パラメータを開いて求める。
- **`profile:`**，**`regimes:`**，**`epsilon:`** は，I.8のとおりである。
- **`resolution:`** は，0 < r < 1 である数 r であり，設計ごとに，B の体積のうち未決定のまま
  残ってよい割合である。

設計 D と付値 v ∈ B について，θ(v) は，開いているパラメータでは v と一致し，それ以外では D の固定値を
持つ（H.7）。問い合わせのプロファイルについて，θ(v) における D での p の利得，最適応答値，逸脱利得を，
U_p(v)，BR_p(v)，gain_p(v) と書く。これらは，θ(v) において D が良定義であり，プロファイルが
許容できるところで定義される。

**何を問うか。** 挙げた各設計について，B のどの付値でプロファイルがε均衡であるかを問う。
**セル**とは，B に含まれる閉じた直方体である（H.9）。

- プロファイルは，すべての v ∈ C において，θ(v) で D が良定義であってプロファイルが許容でき，
  どのプレイヤー p についても gain_p(v) ≤ ε であるとき，**セル C の上で均衡**である。
- プレイヤー p は，すべての v ∈ C において，θ(v) で D が良定義であってプロファイルが許容でき，
  gain_p(v) > ε であるとき，**セル C の上で逸脱者**である。

**結果。** 答えは，挙げた設計ごとに1つの**均衡マップ**からなる。均衡マップは，B を覆い，内部が互いに
交わらない有限個のセルの集合であり，各セルは `status` を持つ。これに，未決定の割合（`undecided` の
セルの体積を B の体積で割ったもの）と，それが `resolution:` 以下であるかどうかを添える。

| `status` | 主張 | ともに報告するもの |
| --- | --- | --- |
| `equilibrium` | プロファイルは，セルの上で均衡である | `from_every_state`（後述） |
| `not_equilibrium` | `deviators` のどのプレイヤーも，セルの上で逸脱者である | `deviators`（プレイヤーの空でない集合） |
| `undecided` | なし | `reason` |

`deviators` は，セルのすべての付値で得をするプレイヤーだけを含む。処理系は，それを確立したプレイヤーを
すべて挙げることが望ましい。逸脱者が入れ替わる面をまたぐセルでは，どの付値でも誰かが得をするが，
セル全体で得をする1人のプレイヤーはいない。そのようなセルは，細分によって部分が分かれるまで
`undecided` のままである。処理系は，`not_equilibrium` のセルについては，方法がそれを与えるとき
（後述の条件Nは与える），各逸脱者について，セルのすべての付値で ε を超えて得をする戦略も報告することが
望ましく，決定したどのセルについても，確立した逸脱利得の上下界を報告することが望ましい。
`from_every_state` は，`equilibrium` のセルについて，プロファイルがセルのすべての付値で
到達可能などの状態からも均衡である（I.7）ことを処理系が確立したとき `true` であり，そうでなければ，
なしまたは `null` である。セルについては，このフィールドは ε に依存しない。それは逸脱利得が0で
あることについての言明であり，ε均衡の主張より強いので，ε > 0 のときにも `true` であってよい。

`undecided` のセルは，`reason` を持つことが望ましい。`not_well_defined`（設計がセルの上で良定義である
ことを，処理系が確立していない），`not_admissible`（プロファイルがセルの上で許容できることを確立して
いないか，許容できない付値を見つけた），`bounds`（上下界がセルを決定しないか，予算を使い切った）の
いずれかである。

プロファイルがε均衡である付値と，そうでない付値の両方を含むセルは，どちらの `status` も持てない。
I.12のλ\*のように，2種類の付値が接するところでは，分割をどれほど細かくしても，そのようなセルが
残る。`resolution:` が0より大きいのはこのためである。

処理系は，複数のセルの和集合が直方体であり，主張がそのどの部分でも成り立つとき，その和集合を
1つのセルとして報告してよい。すなわち，`status` が同じであること。`not_equilibrium` では，
`deviators` は，どの部分の逸脱者の集合の空でない部分集合でもあり，逸脱は，その逸脱者についてどの部分でも
同じ戦略が報告されているときにだけ報告すること。`from_every_state: true` は，どの部分もそれを持つ
ときにだけ報告すること。`gain_bounds` は，それらを包む範囲とすること。

同じ領域の上の複数の設計のマップは，「どのモードで，どこで，プロファイルが均衡であるか」に答える。
2つの設計のセルは一致しなくてよい。処理系は，マップを共通の細分の上で報告してよい。

**認証付き。** `equilibrium` と `not_equilibrium` は，セルの**すべての**付値についての主張であり，
H.9の認証の要求が適用される。処理系は，セル全体について健全な方法により，厳密な算術または健全な
誤差限界を持つ数値計算で確立した場合を除いて，これらの主張をしてはならない。標本点での評価は，
それだけではそのような方法ではない。`resolution:` に算入するのは，認証付きのセルだけである。
要求された分解能に達することができない処理系も，マップを報告し，達しなかったことを述べる。処理系は，
方法の名前を示すことが望ましい。標本点での推定は，H.9と同じく，分けて報告してよい。推定がセルの
`status` を変えることはない。

**領域の上での良定義性と許容性。** これらの主張は，セルの上でI.7が定義されていることを前提とする。
処理系は，セルのすべての付値において，設計が良定義（H.5）であり，プロファイルが許容できる（I.6）ことを
確立した場合を除いて，セルについて `equilibrium` または `not_equilibrium` を主張してはならない。

許容性については，直方体の頂点を検査するだけでは足りない。確率は，直方体の内部で正であり，頂点で
0であることがある。したがって，頂点でグラフが最も小さく，内部で最も大きい。確率がすべて，
開いているパラメータについて**多重アフィン**である設計（`rest` の値を含めて，どの確率にも，
開いているパラメータが1より高いべきで現れない）では，次が成り立つ。直方体 B の*面*とは，開いている
パラメータのいくつか（0個でもよい）をその区間の端に固定し，残りのそれぞれを，その両端の間の開区間の上で
動かして得られる集合である。開いているパラメータが n 個のとき，B は 3ⁿ 個の面を持ち，B のどの付値も，
そのちょうど1つに属する。設計が B の頂点で良定義であれば，確率は，ある面のどの付値でも，その面の
頂点での値の正の係数による結合である。したがって，確率が面の1つの付値で0であるのは，面全体で0である
ときに限る。ゆえに，ゲームのグラフは，1つの面のすべての付値で同じであり，許容性はグラフだけに
依存するので，次が成り立つ。

> 確率が開いているパラメータについて多重アフィンであり，B の頂点で良定義である設計では，
> プロファイルが B のすべての付値で許容できるのは，B の 3ⁿ 個の面のそれぞれの中心（開いている
> どのパラメータも，その区間の下端，中点，上端のいずれかにある付値）で許容できるとき，
> かつそのときに限る。

I-9は，この検査を要求する。そのような設計では，面の中心での失敗は，その面のどの付値でも
プロファイルが許容できないことを意味する。したがって，退化した端に接する領域，たとえば `lo` で
成功確率が0である再試行ループを持つ領域は，ファイルの誤りであり，記述者は区間を縮める。そのような
設計でこの検査が成功すれば，プロファイルはどのセルの上でも許容でき，許容性については，セルごとに
確立すべきことは残らない。ただし，上下界を与える方法は，なおセルの上で失敗することがある。たとえば，
そのような面に接するセルの上での緩和である。そのセルは，理由 `bounds` で `undecided` である。
したがって，未決定のセルの理由 `not_admissible` は，多重アフィンでない設計でだけ生じる。多重アフィンでない確率を持つ設計では，処理系は，
たとえば後述の緩和によって，セルごとに許容性を確立するか，理由 `not_admissible` を付けてセルを
`undecided` のままにする。

**上下界によるセルの決定。** プレイヤー p とセル C について，R_C(p) を，次のような状態の集合とする。
s₀ を含み，φ_p が成り立たない状態 s を含むならば，p について s で許される（I.6）あるコマンド c に
ついて，C のある付値で P(s, c, s′) が正である状態 s′ をすべて含む。R_C(p) は，C のどの付値における
Reach_p も含む。ある方法が，各プレイヤー p について，C のすべての付値 v で成り立つ次の数を与えるとする。

- l_p ≤ U_p(v) ≤ u_p。プロファイルのもとでの利得の上下界である。
- b_p ≥ BR_p(v)。最適応答値の上界である。
- p の1つ以上の戦略 τ について，d_p(τ) ≤ U_p(τ, v)。p が τ を用いるプロファイルのもとでの
  p の利得の下界である。
- R_C(p) の各状態 s について，数 l_p(s) と u_p(s)。これらは，C のどの v と，θ(v) における Reach_p の
  どの状態 s についても，l_p(s) ≤ V_p(s, v) ≤ u_p(s) を満たす（s で φ_p が成り立つときは，どちらも0）。
  および，R_C(p) にある p の状態 s のうち φ_p が成り立たないものと，En(s) の各コマンド c について，
  数 q_p(s, c)。これは，s が θ(v) における Reach_p の状態であるような C のどの v についても，
  q_p(s, c) ≥ Q_p(s, c, v) を満たす。s に到達できない付値では，V_p(s, v) は存在するとは限らず，
  何も要求しない。そのような数は，C の上でのステップ利得 ρ_p(s, c) の上界と，後続状態の
  **上界** u_p(s′) から得られる。すなわち，q_p(s, c) は，コマンドが C の上で取り得るどの分布 μ に
  ついても，ρ_p(s, c) + Σ_s′ μ(s′) · u_p(s′) 以上である。

このとき，次が成り立つ。

- **N.** p のある戦略 τ について d_p(τ) − u_p > ε であるとき，p は C の上で逸脱者である。
- **E1.** b_p − l_p ≤ ε であるとき，C の上で gain_p(v) ≤ ε である。
- **E2.** R_C(p) にある p の状態 s のうち φ_p が成り立たないものと，En(s) のコマンド c のうち
  プロファイルが選ぶもの以外のすべてについて q_p(s, c) ≤ l_p(s) であるとき，C のどの付値でも，
  Reach_p のどの状態 s についても V\*_p(s, v) = V_p(s, v) であり，特に C の上で gain_p(v) = 0 である
  （I.7の1ステップ検査。逸脱するコマンドの上界を，同じ状態でのプロファイルの**下界**と比べる）。
- どのプレイヤーもE1またはE2を満たすとき，プロファイルは C の上で均衡である。どのプレイヤーも
  E2を満たすとき，プロファイルは，C のすべての付値で，到達可能などの状態からも均衡である
  （`from_every_state: true`）。

これらの条件は十分条件であり，必要条件ではない。E1は，H.9の条件と同じく，ある関数の界を別の関数の
界と比べる。しかも，ここでは2つの関数が接する。どこでも BR_p(v) ≥ U_p(v) であり，p が得をしない
ところでは等号が成り立つ。したがって，ε = 0 では，E1が成り立つのは，U_p がセルの上で定数であり，
かつ両方の界が厳密であるときに限られる。開いているパラメータが，プロファイルのもとで0である項の
重みにだけ現れるとき，たとえばI.12のλの場合は，これに当たる。開いているパラメータがプロファイルの
もとでの利得を変えると，もはやこれに当たらない。E2にはこの欠点がない。E2は，1ステップの逸脱の利得を，
同じ状態でのプロファイルの利得と比べる。逸脱が真に損をする付値では，この2つは異なる。E2は，
問われていること以上を確立する。そのため，p 自身の逸脱だけが到達する状態で p が得をし得るような
ナッシュ均衡のセルでは，E2は成り立たない。境界に接するセルは，3つの条件のどれによっても
`undecided` のままである。

**パラメータリフティングによる上下界（参考）。** H.14の緩和は，プロファイルに対する1人のプレイヤーの
ゲームに拡張できる。セルの上で，各状態が，他の状態とは独立に，その許されるコマンドのそれぞれについて
分布を1つ選ぶ。調べているプレイヤーの状態は，それに加えてコマンドも選び，他のプレイヤーの状態は，
プロファイルが選ぶコマンドを取る。コマンドの確率が開いているパラメータについて多重アフィンであるとき，
選べる分布はセルの頂点での分布であり，セルのどの付値での分布も，それらの混合である。多重アフィンで
ないときは，頂点では足りない。H.14に述べるように，各確率をセルの上の区間で囲み，状態は，それらの区間の
中の分布の集合の頂点を選ぶ。ステップの利得 ρ_p(s, c) は，セルの上での最小値と最大値で囲む（重みが
開いているパラメータについて多重アフィンであるときは頂点での値，そうでないときは区間演算による）。
緩和した過程で到達可能な状態は，集合 R_C(p) をなす。緩和した過程のどの方策も確率1で φ_p に達するとき，
プロファイルは，セルの上で p について許容できる。上側のステップ利得を用いた過程の最大値が数 b_p であり，
プレイヤーのコマンドを τ またはプロファイルで固定し，下側と上側のステップ利得を用いた最小値と最大値が，
数 d_p(τ)，l_p，u_p である。R_C(p) の各状態を初期状態とすれば，l_p(s) と u_p(s) が得られる。
条件Nの戦略 τ は，たとえば，セルの中心における p の標準の最適応答（I.7）を，そこでそれのもとで到達
可能な状態に制限したものとして選べる。この選び方が，領域のどれだけが `not_equilibrium` になるかを
左右する。他の健全な方法も認められる。たとえば，有理関数 U_p と BR_p の上の厳密な推論や，逸脱利得がある
パラメータについて凸または単調であることの証明である（[J.7](./appendix-j-grounding.md)）。

## I.10 静的意味論 {/* #i10-static-semantics */}

本拡張を実装する処理系は，`games: 0.1` を宣言しているファイルにおいて，H.10の規則を，ここに述べる
変更を加えて適用し，さらに次の検査をしなければならない。

- **I-1.** `games: 0.1` を宣言するファイルは，`stochastic: 0.1` も宣言しなければならない。
  そうでない場合，処理系は誤りを報告し，本拡張のキーを解釈しない。
- **I-2.** `kind:` は，あれば `dtmc` または `smg` でなければならない（これはS-1の最後の文を
  置き換える）。`kind: smg` を持つモデルは，少なくとも1人のプレイヤーを持つ `players:`，
  `profiles:`，`compliance:`，`payoffs:` を持たなければならない。`kind:` が `dtmc` であるか，
  `kind:` を持たないモデルは，`players:`，`profiles:`，`compliance:`，`payoffs:`，`equilibria:`，
  コマンドの `owner:`，性質またはモードマップの `profile:` を持ってはならない。それは付録Hの
  モデルであり，S-9が適用される。
- **I-3.** プレイヤーの `id` は，識別子でなければならず，A.11のキーワード，`IN`，`rest` であっては
  ならず，プレイヤーの間で一意でなければならない。性質の部分言語のキーワード `F`，`U`，`P`，`R` は
  認める。プレイヤーの `id` は，どの式にも現れないからである。`actors:` は，少なくとも1つのアクター参照を
  列挙しなければならず，それぞれは宣言済みのアクターを名指さなければならない。2人のプレイヤーが
  同じアクター名を持つ参照を挙げてはならず，1人のプレイヤーがそれを2回挙げてもならない。
- **I-4.** `owner:` は，宣言済みのプレイヤーを名指さなければならない。所有されているコマンドは
  `action:` を持たなければならない。1つのアクションラベルを持つコマンドは，すべて同じ所有者を
  持つか，すべて所有者がないかのどちらかでなければならない。
- **I-5.** （戦略モデルではS-9を置き換える。）どの設計についても，S のどの状態（到達可能か
  どうかにかかわらない）についても，その設計に存在し，ガードが真であるコマンドは，多くとも1つで
  あるか，すべて同じプレイヤーが所有し，アクションラベルが互いに異なるコマンドでなければならない。
  これは，S を列挙して決定する。
- **I-6.** プロファイルの名前は，識別子でなければならず，S-2が除外するキーワードであっては
  ならず，プロファイルの間で一意でなければならない。規則の `choose:` は，所有されているコマンドの
  アクションラベルでなければならず，`guard:` は，変数と列挙リテラルの上のブール型の `state_pred`
  （S-6）でなければならず，ラベルを含んではならない。どの設計についても，2つ以上のコマンドが有効で
  ある S のどの状態でも，各プロファイルのある規則が適用できなければならない（I.4）。`compliance:` は，
  プロファイルを名指さなければならない。どの設計のどの状態でも最初に適用できる規則にならない規則に
  ついて，処理系は警告することが望ましい。（`profiles:` はYAMLのマッピングである。ファイルを
  YAMLのローダで読む処理系は，同じ名前の2つのプロファイルを検出できない。ローダがその一方だけを
  残すからである。H.4のラベルについても同様である。）
- **I-7.** `model.payoffs:` は，各プレイヤーにちょうど1つの項目を持たなければならず，`player:` は
  宣言済みのプレイヤーを名指さなければならない。`until:` は，ブール型の `state_pred` でなければ
  ならず，性質と同じようにラベルを用いてよい（S-6）。`terms:` は，少なくとも1つの項を持たなければ
  ならない。`reward:` は，宣言済みの報酬構造を，1つの利得につき多くとも1回名指さなければならない。
  `weight:` は，数であるか，識別子が宣言済みのパラメータである `param_expr` でなければならない。
  利得の目標が初期状態で成り立つとき，処理系は警告することが望ましい。このとき，利得はどの
  プロファイルのもとでも0である。項のキー `sanction_of:` と `reward_of:` は，
  [付録J](./appendix-j-grounding.md)が定義する。`grounding: 0.1` を宣言しないファイルでは，
  そのどちらかを持つ項は誤りである。それを宣言するファイルでは，付録Jを実装していない処理系は，
  そのような項を持つ利得も，その利得を必要とする問い合わせも，評価してはならない。処理系は，
  その項を名指す診断とともに，問い合わせを評価しなかったと報告する。`equilibria:` のどの項目も，
  すべてのプレイヤーの利得を必要とするので，このときは評価しない。性質とモードマップは利得を
  必要としないので評価し，I-8とI-9は利得の目標だけを必要とする。そのような項を，既定値の重みを
  持つ項として読むことは決してない。
- **I-8.** どの設計も，その固定値において良定義でなければならず（S-11），ファイルのどのプロファイルも，
  どの設計でも，固定値において許容できなければならない（I.6）。これは，ゲームのどのプレイも終わることを
  要求するより弱い。
- **I-9.** `equilibria:` の項目の `id` は，S-2が認める識別子でなければならず，性質とモードマップの
  名前空間で一意でなければならない。`profile:` は，プロファイルを名指さなければならない。
  `regimes:` は，ファイルの設計を，少なくとも1つ，それぞれ1回だけ名指さなければならない。
  `epsilon:` は，負でない有限の数でなければならない。`over:` と `resolution:` は，S-14が
  モードマップについて述べる条件を満たさなければならない（`over:` は1つから4つの宣言済みの
  パラメータを持ち，それぞれ宣言範囲の中で `lo < hi` であり，どのモードも値を割り当てていない。
  `0 < r < 1`）。`resolution:` は，`over:` なしに現れてはならない。モードマップ（S-10）と異なり，
  `over:` を持つ項目は，`transitions:` のないファイルでも許され，そこでは設計 `base` に関する。
  `equilibria:` の項目の `over:` にあるパラメータは，報酬の項目の `value:` に現れてはならない。
  処理系は，挙げたどの設計についても，設計が領域の頂点（S-14と同じ）とどの面の中心でも良定義である
  ことと，プロファイルが領域のどの面の中心でも許容できること（I.9。開いているどのパラメータも，その区間の
  下端，中点，上端のいずれかにある 3ⁿ 個の付値）を検査しなければならない。これらの付値の1つでの
  失敗は，ファイルの誤りである（多重アフィンである設計では，このとき，プロファイルはその面の全体で
  許容できない。I.9）。確率が開いているパラメータについて多重アフィンである設計では，
  これらの検査が，領域全体で両方の性質を決定する（S-14，I.9）。それ以外の設計では，決定しない。
  その場合，処理系は，セルごとに両方を確立するか，セルを `undecided` のままにする。両方を確立して
  いないセルを認証してはならない。
- **I-10.** 性質またはモードマップの `profile:` は，プロファイルを名指さなければならない。
  S-12からS-14は，モードモデルの位置に M(D, θ, σ) を置いて，戦略モデルにそのまま適用する。
- **I-11.** 処理系は，I.1で予約したキーまたは値について情報レベルの診断を出すことが望ましく，
  それに意味を与えてはならない（`games: 0.1` を宣言するファイルでは，これがS-15の一覧を
  置き換える）。予約された値（`kind: mdp`，`motivation.` で始まる出所）には，I-2またはS-3の
  誤りに加えて，この診断を出す。

規則S-2からS-8とS-10からS-14は，戦略モデルに，書かれているとおりに適用する。重みは，確率でも
報酬の値でもない。その符号や範囲を制限する規則はない。

## I.11 PRISM-gamesへのエクスポート（参考） {/* #i11-export */}

PRISM-gamesは，PRISMモデリング言語の拡張で，ターン制の確率的な多人数ゲームを読む。モデルの種類は
`smg` であり，各プレイヤーは，`player … endplayer` の構成で宣言する。この構成は，そのプレイヤーが
制御するアクションラベル（角括弧で囲む）とモジュールを列挙する。利用できる遷移がすべて1人の
プレイヤーに属する状態は，そのプレイヤーが制御する。アクションとモジュールは，そのような遷移を複数持つ
状態がない限り，どのプレイヤーにも割り当てなくてよい。遷移が複数のプレイヤーに所有される状態は
誤りである [[Kwiatkowska+, CAV 2020]](./appendix-b-references.md)。これらは，I-4とI-5の条件である。
PRISM-gamesが期待総報酬を計算するのは，停止ゲーム，すなわち，すべての戦略のもとで報酬0の終端状態に
確率1で達するゲームに限られる。これは，I.6の許容性より強い。Storm（stormpy 2.0.0）は，
エクスポートした `smg` のファイルを構文解析するが，すべてのコマンドがプレイヤーに所有されていない限り，
モデルを構築しない。エクスポートは，PRISM-gamesを対象とする。

H.11は，書かれているとおりには戦略モデルに適用されない。戦略モデルの設計はマルコフ連鎖ではなく，
処理系は，それを `dtmc` のファイルとしてエクスポートしてはならない。バージョン0.1は，プロファイルの
マルコフ連鎖 M(D, θ, σ) のエクスポートも定義しない。処理系は，戦略モデルの設計を，[H.11](./appendix-h-stochastic.md#h11-export)のモデルファイルに
次の2つの変更を加えたものとして，エクスポートしてよい。

1. 最初の行を，`dtmc` の代わりに `smg` とする。
2. その後に，設計のコマンドを所有する各プレイヤーについて，宣言の順に，そのプレイヤーが所有する
   設計のコマンドのアクションラベルを，最初に宣言された順に列挙する構成を1つ書く。

```
smg

player R_
  [careful], [careless]
endplayer
```

設計のコマンドを1つも所有しないプレイヤーは書かない。設計のすべてのコマンドを，プロファイルが何を
選ぶかにかかわらず書く。所有者のないコマンドとデッドロックのコマンドは，どのプレイヤーにも
割り当てない。プレイヤーの名前は，キーワードに等しいとき，H.11の規則によって改名する（`R` は
キーワードであるので，`player R_` となる）。戦略モデルでは，H.11のキーワードの一覧に，
PRISM-gamesのマニュアルがPRISM言語に加えるキーワード `player`，`endplayer`，`smg`，`csg`，`tptg` を
加え，エクスポートするモデルのどの名前も，この一覧によって改名する。
名前がモデルの他の識別子に等しいプレイヤーをPRISM-gamesが受け付けるかどうかは，本付録では定めない。
エクスポートする処理系は，そのような名前を報告することが望ましい。均衡マップでだけ開いている
パラメータは，その固定値で書く（I.13）。

バージョン0.1は，戦略モデルの**性質ファイルを定義しない**。利得は，符号が正負どちらでもよい重みを
持つ期待報酬の和であり，I.7の問いは，固定したプロファイルに対する最適応答である。PRISM-gamesの
性質言語が述べるのは，`<<p1>> R{"r"}max=? [ F "success" ]` のように，ある提携が他のプレイヤーに
対して保証できること [[Chen+, FMSD 2013]](./appendix-b-references.md)と，PRISM-gamesが自ら選ぶ
均衡である。どちらも本付録の問いではなく，変換は後の版に委ねる。上の構文は，PRISM-gamesの
マニュアル（2026年11月閲覧）と照合した。この形式でエクスポートしたファイルを，PRISM-gamesで
実行してはいない（I.14）。

## I.12 例

1つ目の例は，[H.12](./appendix-h-stochastic.md)の例に，1つの選択を加えたものである。2つ目の例は，
本節の終わりにあり，ディスパッチャの選択を加える。ロボットは，
各試行の前に，取扱手順に従うかどうかを決める。`careful`（丁寧）な試行は，ロボットに1の労力を
要し，H.12の確率 s で成功する。`careless`（手抜き）な試行は，労力を要さず，確率 s/2 で成功する。
ディスパッチャは，配達された荷物に10の料金を支払う。手抜きの試行には制裁が科され，ロボットは
2·λ を失う。2は強度が最大であるときの制裁の大きさであり，λは契約のインセンティブ強度である。
変数 `settled` と偶然のコマンド `settle` を1つずつ加えて，タスクを締める。これにより，料金が
ステップの報酬になる。

```yaml
sos:
  name: "RobotDeliveryGame"
  type: Acknowledged
  extensions:
    - stochastic: 0.1
    - games: 0.1

  actors:
    - { id: DISPATCHER,    role: "Assigns and replans routes" }
    - { id: "ROBOT[1..N]", role: "Delivers parcels" }

  contracts:
    - id: DELIVERY
      parties: [DISPATCHER, "ROBOT[*]"]
      information: { alpha: 0.9 }
      authority:   { decision_holder: DISPATCHER, beta: 0.9 }
      incentives:  { lambda: 0.1 }

  transitions:
    - { from: CENTRALIZED, to: DISTRIBUTED, condition: "loss_rate > 0.3" }
    - { from: DISTRIBUTED, to: CENTRALIZED, condition: "loss_rate <= 0.2" }

  model:
    kind: smg
    parameters:
      - { id: p_fail,  range: [0, 0.5], value: 0.05 }
      - { id: p_loss,  range: [0, 0.5], value: 0.1 }
      - { id: alpha,   from: "DELIVERY.alpha" }
      - { id: beta,    from: "DELIVERY.beta" }
      - { id: lambda,  from: "DELIVERY.lambda" }        # 0.1, range [0, 1]
      - { id: q_local, range: [0, 1],   value: 0.6 }
    variables:
      - { id: task,     type: "{Pending, Delivered}", init: Pending }
      - { id: attempts, type: "[0..3]",               init: 0 }
      - { id: settled,  type: bool,                   init: false }
    labels:
      delivered: "task == Delivered"
    players:
      - { id: R, actors: ["ROBOT[*]"] }
      - { id: D, actors: [DISPATCHER] }
    commands:
      - action: careful
        owner: R
        guard: "task == Pending AND attempts < 3"
        updates:
          - prob: "beta * alpha * (1 - p_fail) * (1 - p_loss) + (1 - beta) * q_local"
            set: { task: Delivered, attempts: "attempts + 1" }
          - prob: rest
            set: { attempts: "attempts + 1" }
      - action: careless
        owner: R
        guard: "task == Pending AND attempts < 3"
        updates:
          - prob: "0.5 * (beta * alpha * (1 - p_fail) * (1 - p_loss) + (1 - beta) * q_local)"
            set: { task: Delivered, attempts: "attempts + 1" }
          - prob: rest
            set: { attempts: "attempts + 1" }
      - action: settle
        guard: "(task == Delivered OR attempts == 3) AND NOT settled"
        updates:
          - set: { settled: true }
    regimes:
      CENTRALIZED: { parameters: { beta: 0.9 } }
      DISTRIBUTED: { parameters: { beta: 0.1 } }
    rewards:
      - { id: fee,       items: [ { action: settle, guard: "task == Delivered", value: 1 } ] }
      - { id: effort,    items: [ { action: careful,  value: 1 } ] }
      - { id: shortcuts, items: [ { action: careless, value: 1 } ] }
    profiles:
      comply:
        - { choose: careful }
      shortcut_first:
        - { guard: "attempts == 0", choose: careless }
        - { choose: careful }
    compliance: comply
    payoffs:
      - player: R
        until: "settled"
        terms:
          - { reward: fee,       weight: 10 }
          - { reward: effort,    weight: -1 }
          - { reward: shortcuts, weight: "-2 * lambda" }
      - player: D
        until: "settled"
        terms:
          - { reward: fee, weight: 5 }
    properties:
      - { id: P_DELIVERY, expr: "P>=0.95 [ F<=3 delivered ]" }
      - { id: P_DELIVERY_SHORTCUT, profile: shortcut_first, expr: "P=? [ F<=3 delivered ]" }
    equilibria:
      - { id: comply_nash }
      - { id: shortcut_nash, profile: shortcut_first }
      - { id: comply_by_lambda, over: { lambda: [0, 1] }, resolution: 0.05 }
      - id: comply_by_lambda_and_failure
        regimes: [CENTRALIZED, DISTRIBUTED]
        over: { lambda: [0, 0.4], p_fail: [0, 0.5] }
        resolution: 0.05
```

**ゲーム。** モデルは16個の状態を持ち，そのうち11個が到達可能である。
`task == Pending AND attempts < 3` である状態では，R の2つのコマンドが有効である。これらが R の
状態である（I-5）。`task == Delivered OR attempts == 3` であり，まだ締められていない状態では，
所有者のないコマンド `settle` が有効である。これらは偶然状態である。締められた状態は
デッドロック状態である。プレイヤー D はコマンドを所有せず，選択肢を持たない。D は，料金の受け手を
置くために宣言している。R が何をしても，どのパスも4ステップ以内に `settled` に達するので，
どのプロファイルも，すべての付値で許容でき，2つのマップの領域の上で，すべての確率は `[0, 1]` に
収まる。プロファイル `comply` は，R のどの状態でも `careful` を選ぶ。プロファイル `shortcut_first` は，
最初の規則により，最初の試行の前に `careless` を選び，その後は `careful` を選ぶ。

`comply` のもとでは，モデルはH.12のモデルにステップを1つ加えたものであるので，`P_DELIVERY` は
H.12の値を持つ。CENTRALIZED では 0.984848（`satisfied`），DISTRIBUTED では 0.943796（`violated`）で
ある。`shortcut_first` のもとでは，`P_DELIVERY_SHORTCUT` は 1 − (1 − s/2)(1 − s)² であり，
0.961808 と 0.898534 である。本節の計算値は，小数第6位に丸めている。

**閉形式。** 料金を g = 10，労力の費用を c = 1，制裁の大きさを m = 2 と書き，丁寧な試行が成功する
確率を s と書く（H.12により，固定値では s_C = 0.75255，s_D = 0.61695）。試行が k 回残っている
状態からの，`comply` のもとでの R の利得を V_k とする。

```text
V_0 = 0,    V_k = s·g − c + (1 − s)·V_(k−1)
V_1 = s·g − c,    V_2 = (s·g − c)(2 − s),    V_3 = (s·g − c)(1 + (1 − s) + (1 − s)²)
```

V_3 が，`comply` のもとでの R の利得である。`comply` は手抜きの試行をしないので，ここにλは現れない。
試行が k 回残っているときに1回だけ手抜きをし，その後 `comply` に従うと，利得は
−m·λ + (s/2)·g + (1 − s/2)·V_(k−1) である。これが V_k 以下であるのは，次のとき，かつそのときに
限る。

```text
λ ≥ T_k,    where   T_k = ( c − (s/2)·(g − V_(k−1)) ) / m
```

手抜きは，労力 c を節約する一方で，確率 s/2 で，いま配達することと続けることとの差を失う。
次のようにおく。

```text
λ* = max(0, T_1, T_2, T_3)
T_1 = ( c − (s/2)·g ) / m
T_2 = ( c − (s/2)·(g − (s·g − c)) ) / m
T_3 = ( c − (s/2)·( g·(1 − s)² + c·(2 − s) ) ) / m
```

（T_3 では，g − V_2 = g·(1 − s)² + c·(2 − s) を用いた。）

**0 ≤ s < 1 のとき，`comply` が θ において設計のナッシュ均衡であるのは，λ ≥ λ\* であるとき，
かつそのときに限る。** `comply` のもとでは，試行が確率 1 − s > 0 で失敗するので，R の3つの状態の
それぞれに，正の確率で到達する。したがって，R が得をしないのは，I.7の1ステップ検査がその3つの状態で
成り立つとき，すなわち k = 1, 2, 3 について λ ≥ T_k であるとき，かつそのときに限る。D は選択肢を
持たず，得をしない。条件 s < 1 は，「かつそのときに限る」のために必要である。s = 1 では，後の状態には
R が逸脱したときにだけ到達する。

s·g ≥ c のとき，すなわち s ≥ 0.1 のとき，V_0 ≤ V_1 ≤ V_2 であり，したがって T_1 ≤ T_2 ≤ T_3 で
あるので，λ\* = max(0, T_3) である。誘惑は，失敗をまだ取り返せる最初の試行の前に最も大きい。
固定値と，以下の2つのマップの領域（そこでは s ≥ 0.4245）では，この場合に当たる。小さい s では
当たらない。s = 0.07695（DISTRIBUTED で q_local = 0 のとき）では，T_1 = 0.307625 が3つのうちで
最も大きい。

同じ計算により，**0 ≤ s < 1 のとき，`shortcut_first` がナッシュ均衡であるのは，
max(0, T_1, T_2) ≤ λ ≤ T_3 であるとき，かつそのときに限る。** R は，最初の試行の前には手抜きを好み，
その後は丁寧な試行を好まなければならない。

どちらの設計でも，固定値では T_1 と T_2 は負であり（T_2 は −0.153684 と −0.245044），T_3 は正である。
そこでは，どの λ ≥ 0 についても，最初より後の手抜きの試行は損であり，λ < λ\* では `shortcut_first` が
最適応答であり，`shortcut_first` がナッシュ均衡であるのは λ ≤ λ\* であるとき，かつそのときに限り，
λ = λ\* では両方のプロファイルが均衡であって，次が成り立つ。

```text
gain_R = max(0, m·(λ* − λ)) = max(0, 2·(λ* − λ))
```

**検査。** 固定値，λ = 0.1 では，次のとおりである。

| | CENTRALIZED | DISTRIBUTED |
| --- | --- | --- |
| s | 0.75255 | 0.61695 |
| λ\* = T_3 | 480347064349/3200000000000 = 0.150108 | 193194567781/3200000000000 = 0.060373 |
| `comply` のもとでの `fee`，`effort`，`shortcuts` の期待値 | 0.984848，1.308682，0 | 0.943796，1.529777，0 |
| `comply` のもとでの u_R | 6831840915651/800000000000 = 8.539801 | 6326547012219/800000000000 = 7.908184 |
| `shortcut_first` のもとでの `fee`，`effort`，`shortcuts` の期待値 | 0.961808，0.778066，1 | 0.898534，0.956414，1 |
| `shortcut_first` のもとでの u_R | 8.840018 − 2·λ = 8.640018 | 8.028930 − 2·λ = 7.828930 |
| `comply` / `shortcut_first` のもとでの u_D | 4.924241 / 4.809042 | 4.718981 / 4.492672 |
| `comply_nash`：BR_R，gain_R | 8.640018，160347064349/1600000000000 = 0.100217 | 7.908184，0 |
| `comply_nash`：`status` | `not_equilibrium`，`deviators` は R，標準の最適応答は `attempts == 0` の状態での `careless` | `equilibrium`，`from_every_state: true` |
| `shortcut_nash`：gain_R，`status` | 0，`equilibrium`，`from_every_state: true` | 126805432219/1600000000000 = 0.079253，`not_equilibrium`，`deviators` は R |

宣言値 λ = 0.1 では，遵守は，分散モードでは均衡であり，集中モードでは均衡でない。D の逸脱利得は，
どの検査でも0である。R が手抜きをすると，D は損をする。料金が支払われる頻度が下がるからである。

**λの上のマップ。** `comply_by_lambda` は，両方の設計で，λを `[0, 1]` の上で開く。セル `[a, b]` が
均衡のセルであるのは a ≥ λ\* であるとき，かつそのときに限り，R がその上で逸脱者であるのは
b < λ\* であるとき，かつそのときに限る。λ\* を内部に含むセルは `undecided` である。I.9の条件E1と
Nは，他のすべてのセルを，厳密な界によって決定する。U_R はλについて定数であり，セルの上で最大の
最適応答値は λ = a でのものであり，`shortcut_first` の利得は λ = b で最小である。最大の未決定セルを，
分解能0.05に達するまで二分し，主張が同じセルを結合する（I.9）処理系は，次を報告する。

| 設計 | `not_equilibrium`（`deviators` は R） | `undecided`（`reason: bounds`） | `equilibrium` | 未決定の割合 |
| --- | --- | --- | --- | --- |
| CENTRALIZED | `[0, 1/8]` | `[1/8, 5/32]` | `[5/32, 1]` | 1/32 |
| DISTRIBUTED | `[0, 1/32]` | `[1/32, 1/16]` | `[1/16, 1]` | 1/32 |

0.060373 ≤ λ < 0.150108 では，遵守は DISTRIBUTED でだけ均衡であり，0.150108 以上では両方で
均衡である。

**λと故障確率の上のマップ。** `comply_by_lambda_and_failure` は，p_fail も開く。他のパラメータを
固定すると，s_C = 0.729·(1 − p_fail) + 0.06，s_D = 0.081·(1 − p_fail) + 0.54 であり，各設計で，
`comply` が均衡であるのは，λ ≥ λ\*(s) であるところ，かつそこに限る。T_3 は，現れる s の範囲で s と
ともに増加する。したがって，遵守が均衡でない領域は，p_fail が大きくなるにつれて下がる曲線の下にある。
実装の確認のための λ\* の値を示す。

CENTRALIZED では，s = 1/2，すなわち p_fail = 289/729 = 0.396433 で T_3 = 0 である。
ディスパッチャがそれほど頻繁に故障するとき，試行の失敗はロボットにとって非常に高くつくので，
ロボットは制裁がなくても丁寧に試行する。p_fail = 0.2 までは集中モードの方が強いインセンティブを
必要とし，p_fail = 0.3 では分散モードの方が必要とする。このマップでは U_R が p_fail とともに
変わるので，E1は `equilibrium` のセルを1つも決定しない（I.9）。曲線から離れたセルは，E2とNによって

### 2つ目の例：選択をするプレイヤーが2人の場合

1つ目の例では，選択をするのはロボットだけであるので，各プレイヤーの検査は，1人のプレイヤーの最適化で
ある。2つ目の例では，ディスパッチャも選択をする。ディスパッチャは，最初の試行の前に，費用 κ を払って
ロボットを `monitor`（監視）するか，`trust`（信頼）するかを決める。手抜きの試行に制裁が科されるのは，
ディスパッチャが監視しているときだけである。ファイルは，1つ目の例のファイルに次の変更を加えたもので
ある（コマンド `careful` と `careless` の更新はそのままである）。

```yaml
  model:
    kind: smg
    parameters:
      # ... as above, and:
      - { id: kappa,   range: [0, 1],   value: 0.05 }   # cost of monitoring
    variables:
      - { id: watch,    type: "{Open, On, Off}",      init: Open }
      # ... task, attempts, settled as above
    commands:
      - action: monitor
        owner: D
        guard: "watch == Open AND task == Pending AND attempts == 0"
        updates:
          - set: { watch: "On" }
      - action: trust
        owner: D
        guard: "watch == Open AND task == Pending AND attempts == 0"
        updates:
          - set: { watch: "Off" }
      - action: careful
        owner: R
        guard: "watch != Open AND task == Pending AND attempts < 3"
        # updates as above
      - action: careless
        owner: R
        guard: "watch != Open AND task == Pending AND attempts < 3"
        # updates as above
      - action: settle
        guard: "watch != Open AND (task == Delivered OR attempts == 3) AND NOT settled"
        updates:
          - set: { settled: true }
    rewards:
      - { id: fee,        items: [ { action: settle, guard: "task == Delivered", value: 1 } ] }
      - { id: effort,     items: [ { action: careful,  value: 1 } ] }
      - { id: shortcuts,  items: [ { action: careless, guard: "watch == On", value: 1 } ] }
      - { id: monitoring, items: [ { action: monitor,  value: 1 } ] }
    profiles:
      comply:
        - { choose: monitor }
        - { choose: careful }
      comply_if_watched:
        - { choose: monitor }
        - { guard: "watch == Off AND attempts == 0", choose: careless }
        - { choose: careful }
    compliance: comply
    payoffs:
      - player: R
        until: "settled"
        terms:
          - { reward: fee,       weight: 10 }
          - { reward: effort,    weight: -1 }
          - { reward: shortcuts, weight: "-2 * lambda" }
      - player: D
        until: "settled"
        terms:
          - { reward: fee,        weight: 5 }
          - { reward: monitoring, weight: "-kappa" }
    equilibria:
      - { id: comply_nash }
      - { id: watched_nash, profile: comply_if_watched }
      - id: watched_map
        profile: comply_if_watched
        regimes: [CENTRALIZED]
        over: { lambda: [0, 0.4], kappa: [0, 0.4] }
        resolution: 0.25
```

モデルは48個の状態を持つ。初期状態は D の状態である。
`watch != Open AND task == Pending AND attempts < 3` である状態は R の状態である。ガードは，到達不能な
状態でもI-5が成り立つように書いてある。どのパスも5ステップ以内に `settled` に達するので，どの
プロファイルも，すべての付値で許容できる。どちらのプロファイルでも，実際にたどるパスの上では，D は
監視し，R は丁寧に試行するので，両者は同じ利得を与える。u_R は前と同じく V_3 であり，
u_D = 5·(1 − (1 − s)³) − κ である。両者が異なるのは，D が監視しなかった場合に R が何をするかである。
`comply` のもとでは，R はそれでも丁寧に試行する。`comply_if_watched` のもとでは，R は最初の試行の前に
手抜きをする。

**R。** D が監視している間，どちらのプロファイルに対する R のゲームも1つ目の例であるので，固定値では，
1つ目の例の λ\* について gain_R = max(0, 2·(λ\* − λ)) である。`watch == Off` である状態は Reach_R に
属さず，そこでプロファイルが何を選ぶかは，R にとっては関係しない。

**D。** `comply` に対しては，信頼することは κ を節約し，他には何も変えない。したがって gain_D = κ で
あり，どの κ > 0 についても，λ が何であっても，D は逸脱者であって，`comply` はナッシュ均衡でない。
`comply_if_watched` に対しては，信頼することは κ を節約するが，R に手抜きをさせ，配達の確率を
1 − (1 − s)³ から 1 − (1 − s/2)(1 − s)² に下げる。

```text
κ* = 5 · (s/2) · (1 − s)²
```

とおくと，D は信頼することで 5·(s/2)(1 − s)² − κ を失い，gain_D = max(0, κ − κ\*) である。

**`comply_if_watched` が，他のパラメータの固定値において，設計のナッシュ均衡であるのは，λ ≥ λ\* かつ
κ ≤ κ\* であるとき，かつそのときに限る。** 実際にたどる振る舞いは `comply` のものである。それが
均衡になるのは，監視されていないときにロボットが何をするかと組み合わせたときだけであり，それが，
監視を費用に見合うものにしている。

| | CENTRALIZED | DISTRIBUTED |
| --- | --- | --- |
| λ\* | 0.150108 | 0.060373 |
| κ\* | 368638137651/3200000000000 = 0.115199 | 724187274219/3200000000000 = 0.226309 |
| 両方のプロファイルのもとでの u_R，u_D（λ = 0.1，κ = 0.05） | 8.539801，7798786117651/1600000000000 = 4.874241 | 7.908184，7470368854219/1600000000000 = 4.668981 |
| D が信頼したときの u_D（`comply` に対して / `comply_if_watched` に対して） | 4.924241 / 4.809042 | 4.718981 / 4.492672 |
| `comply_nash`：gain_R，gain_D | 0.100217，1/20 | 0，1/20 |
| `comply_nash`：`status` | `not_equilibrium`，`deviators` は R と D | `not_equilibrium`，`deviators` は D |
| `watched_nash`：gain_R，gain_D | 0.100217，0 | 0，0 |
| `watched_nash`：`status` | `not_equilibrium`，`deviators` は R | `equilibrium` |

`comply_nash` では，D の標準の最適応答は，初期状態での `trust` である。DISTRIBUTED の `watched_nash` では，
1ステップ検査が両方のプレイヤーについて成り立つので，結果は `from_every_state: true` を持つ。

**マップ。** `watched_map` は，CENTRALIZED で λ と κ を開く。R は λ < 0.150108 であるところで逸脱者で
あり，D は κ > 0.115199 であるところで逸脱者である。領域を 4 × 4 個のセルに一様に分割すると（二分によるセルではない），
I.9の条件は次を与える。列は λ の区間，行は κ の区間である。

| κ \ λ | `[0, 0.1]` | `[0.1, 0.2]` | `[0.2, 0.3]` | `[0.3, 0.4]` |
| --- | --- | --- | --- | --- |
| `[0.3, 0.4]` | `not_equilibrium`，R と D | `not_equilibrium`，D | `not_equilibrium`，D | `not_equilibrium`，D |
| `[0.2, 0.3]` | `not_equilibrium`，R と D | `not_equilibrium`，D | `not_equilibrium`，D | `not_equilibrium`，D |
| `[0.1, 0.2]` | `not_equilibrium`，R | `undecided` | `undecided` | `undecided` |
| `[0, 0.1]` | `not_equilibrium`，R | `undecided` | `equilibrium` | `equilibrium` |

二分では，λ ∈ [0, 0.4] × κ ∈ [0.2, 0.4] を `deviators: [D]` の1つのセルとして決定する。粗いセルは，
挙げる逸脱者が少ないことがある。

16個のセルのうち4個が，理由 `bounds` で `undecided` である。未決定の割合は 1/4 であり，これは
問い合わせの `resolution:` である。逸脱者はNが決定する。R については，監視されている間に最初の試行の
前に手抜きをする戦略を用い，その利得は λ の上端で最小である。D については `trust` を用い，κ の下端での
プロファイルの利得と比べる。2列目の上の2行のセルでは，D は逸脱者であり，R は逸脱者として確立されない。
λ\* がその列の中にあるからである。`deviators` は，確立されたものを挙げる。2つの `equilibrium` の
セルでは，E2が両方のプレイヤーについて成り立つ（D については，`trust` の利得 4.809042 が，κ = 0.1 での
プロファイルの利得の下界 4.824241 以下である）。したがって，これらのセルは
`from_every_state: true` を持つ。E1は，プロファイルのもとでの利得が定数である R については成り立ち，
プロファイルのもとでの利得が κ とともに下がる D については成り立たない。

付録Jを実装していない処理系が，`sanction_of:` または `reward_of:` の項を持つ利得のために問い合わせを

持ち，開いていないパラメータの固定値を示す。

`players` は宣言の順であり，`cells` は，パラメータを `over:` の順に並べたときの，下側の頂点の
辞書式順である。`best_response` は，I.7の標準の
最適応答であり，すべての変数の値を宣言の順に示す。ε を超える逸脱利得を持たないプレイヤーでは，
空である。セルは，`deviations`（各逸脱者について，`best_response` の形の戦略）と `gain_bounds`
（各プレイヤーについて，下界と上界の組）も持ってよい。

**処理系の動作。** 検査とマップをコマンドとして提供する処理系は，終了ステータスによって，
3つの結末を区別しなければならない。

| 終了ステータス | 意味 |
| --- | --- |
| 0 | 要求されたどの結果も計算した。答えが何であるかは問わない（`equilibrium` でも `not_equilibrium` でも，分解能の範囲内で `undecided` のセルがいくつあってもよい） |
| 1 | ある結果が `inconclusive` または `not_evaluated` であるか，あるマップがその `resolution:` に達しなかった |
| 2 | 何も主張できない。ファイルの静的な誤り，コマンドの使い方の誤り，または，コマンドが評価を求められた値において，設計が良定義でないか，プロファイルが許容できない |

コマンドが，利用者に，パラメータに固定値以外の値を与えることを許すとき（`cadl model-check` の
`--set` のように），その値は宣言範囲の中になければならず，評価する問い合わせが `over:` に挙げている
パラメータに値を与えることは，使い方の誤りである（終了ステータス2）。処理系は，評価の前に，評価する問い合わせのどの設計とプロファイルについても，用いる値で，設計が
良定義であり，プロファイルが許容できることを（マップについてはI-9の検査を）検査しなければならない。

コマンドが，利用者に，評価を1つの設計に限ることを許すとき（`--regime` のように），`regimes:` が
その設計を挙げていない問い合わせは，「この問い合わせはこの設計に関しない」と報告する。これは誤りでは
ない（終了ステータス0）。コマンドは，マップを，領域の各開いているパラメータを N 個の区間に分ける
一様な分割から始めることと，セルを結合せず（I.9），解析したとおりに報告することを提供してよい。
`cadl game-check` では，`--partition N` と `--no-merge` である。

## I.15 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。`stochastic: 0.1` を
宣言し，`games: 0.1` を宣言しないファイルは，付録Hによってそのまま読む。H.1が予約する名前は
そのファイルでは予約されたままであり，S-1，S-9，S-15が適用される。

`games: 0.1` を宣言せずに `kind: smg` または本付録のキーを用いるファイルは，本付録に適合しない。
本拡張を実装する処理系は，そのようなファイルの `model:` ブロックを付録Hによって読み，それらのキーを
宣言されていない拡張として，情報レベルの診断で報告することが望ましい。`stochastic: 0.1` なしに `games: 0.1` を宣言する
ファイルには，I-1の誤りを出す。

付録Hを実装し，本付録を実装していない処理系は，戦略モデルをマルコフ連鎖として読むことができない。
`games: 0.1` を宣言し，`kind:` が `dtmc` でないモデルを持つファイルをそのような処理系がどう扱うかは，
[H.10（S-1）とH.15](./appendix-h-stochastic.md)が述べる。処理系は，1つの情報レベルの診断を出して
モデルを読み飛ばし，それをマルコフ連鎖として評価してはならない。そのブロックには，S-2からS-15の

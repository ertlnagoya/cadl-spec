# 付録J. 制度パラメータの規範による根拠付け（grounding 0.1）

本付録は，CADLの**根拠付け拡張**を規定する。この拡張は，規範拡張
（[付録F](./appendix-f-norms.md)）の上に成り立ち，`contract_def`
（[A.4](./appendix-a-syntax.md#a4-contracts-institution-layer)）にキー `grounding:` を，
`norm_def` にキー `shares:` と `on_fulfilment:` を，`on_violation:` にキー `magnitude:` を
追加する（F.3）。さらに，戦略モデル拡張（[付録I](./appendix-i-games.md)）も用いるファイルでは，
利得の項（I.2）にキー `sanction_of:` と `reward_of:` を追加する。これにより，処理系は，契約の規範から，
2つの**導出指標** α̂ と β̂，および**インセンティブ被覆率** χ を計算し（いずれも `[0, 1]` の中にある），
宣言された `alpha` と `beta` を指標と比べる。本拡張は，また，戦略モデルにおいて規範の制裁を表すと
宣言した利得の項の重みを定義する。それは，規範の宣言する大きさにλを掛けたものである。

コア言語は，これらのキーを必須と**しない**。本拡張を実装していないCADL準拠の処理系は，
これらのキーを理由にファイルを拒否してはならない。キーを構文上は受理し，*情報レベル*の診断を
出すことが望ましい。

拡張の名前は `grounding` であり，本付録はバージョン `0.1` を記述する。本拡張は `norms: 0.1` を
**必要とする**。本拡張を用いるファイルは，`extensions:`
（[A.2](./appendix-a-syntax.md#a2-top-level-structure)）で両方を宣言しなければならない。
宣言せずに用いた場合に処理系がどう扱うかはJ.12で述べる。キー `sanction_of:` と `reward_of:` は，
さらに `stochastic: 0.1` と `games: 0.1` を必要とする。

```yaml
sos:
  ...
  extensions:
    - norms: 0.1
    - grounding: 0.1
```

## J.1 動機と範囲

[5.4.2節](./05-language-spec.md)は，制度パラメータα，β，λを，定性的な端点を持つ `[0, 1]` の数として
定義する。言語の他の部分は，中間の値が何を意味するかを述べない。設計者は `beta: 0.7` と書くが，
その数を，それが置かれた契約に関係付ける規則はない。付録Fは，意図する読み方（βは契約の権能を誰が
持つかを表し，αは他の当事者がどの発動条件と内容を観測できるかを表し，λは違反された規範の制裁の
大きさを調整する）を参考として述べるにとどまる。[9.6節](./09-research.md)は，規範とパラメータの
形式的な結び付きを未解決としており，RD-1.5は，λを契約のパラメータとして扱うことを求めている。
制度の規則を，それが何に作用するかによって分類する方法には，情報の規則，集約の規則，利得の規則が
含まれる [[Ostrom, 2005]](./appendix-b-references.md)。これは，3つのパラメータが3種類の規範を
要約することを示唆する。grounding 0.1は，最初の一歩である。本拡張は，α，β，λに，規範による形式的な
意味を与えるものではない。それは，以下に述べるものを超えて，未解決のままである。

- **2つの指標と1つの被覆率を，ファイルから計算する。** J.4は，α̂，β̂，χを，1つの契約から読み取る
  有限集合の上の，個数の比として定義する。これらは，2つの処理系が同じファイルから同じ数を計算すると
  いう意味で，再現可能である。α̂については，分子も分母も記述者の注記（項目と `shares:` のリスト）に
  基づくので，指標の質は注記の質で決まる。
- **指標は証拠であり，意味ではない。** 指標は，宣言されたパラメータに取って代わるものではなく，
  5.4.2節を変えない。指標は，契約の規範についての構造的な事実であり，宣言値はそれと合うことも
  合わないこともある。指標が捉えられないものは，J.4に述べる。
- **宣言値を指標と比べる。** 宣言されたαまたはβと，その指標との不一致は，関係する構成要素を名指す
  警告である（J.5）。本付録のどの規則も，付録Fのもとで有効であり，新しいキーを1つも用いないファイルを，
  無効にしない（J.12）。
- **λは倍率である。** 本付録では，λは制裁と報酬の大きさに掛かる。λを導出指標と比べることはしない。
  χが測るのは別のものである。それは，λが掛かり得る制裁または報酬を伴う規範がいくつあるかである。
- **制裁に大きさを与え，モデルがそれを用いる。** `magnitude:` は，規範の制裁または報酬に数を与える。
  戦略モデルでは，`sanction_of:` で宣言した利得の項は，定義により，重み −magnitude·λ を持つ。
  ここでλは，契約の `lambda` に束縛したパラメータである（J.7）。その項が制裁を表すこと，すなわち，
  その報酬構造が規範の違反を数えていることは，記述者の仮定のままであり，そのような項を用いて計算した
  どの結果も，その仮定とともに報告する。

**バージョン0.1の範囲。**

- 指標は1つの契約に関するものである。SoSの複数の契約にわたって指標を集約することはしない。
- 情報項目は記述者が宣言する（`grounding.items`）。アクターのインタフェース，述語，メッセージからは
  導出しない。
- 指標は個数である。大きさ，重大度，権能が影響する規範の数による重み付けはしない。
- `magnitude:` と `on_fulfilment:` は，付録Fの動的意味論に影響しない。判定，違反，反義務の規範は
  変わらない。
- 本拡張は，規範からモデルを導出せず，モデルの報酬構造が規範の違反を数えていることを検査しない
  （H.8は，規範とモデルの間の変換を定義しない）。
- [付録G](./appendix-g-agents.md)の委任と，[付録C](./appendix-c-motivation.md)の動機パラメータρと
  κについては，指標を定義しない。

## J.2 概念

| 概念 | grounding 0.1での意味 |
| --- | --- |
| **アクター名** | アクター参照から添字を除いた識別子。`ROBOT[i]`，`"ROBOT[*]"`，`ROBOT[2]` のアクター名は `ROBOT` である。 |
| **当事者名** | 契約の `parties:` の項目のアクター名。同じアクター名を持つ項目は，1つの当事者である。 |
| **単一のアクター** | 整数の添字を持つアクター参照，または，アクターが範囲なしで宣言されているときの，添字のないアクター参照。 |
| **情報項目** | `grounding.items` に宣言する，名前付きの情報。その**起点**，すなわちその情報が由来する当事者を伴う。1つの項目の起点は1つである。2つの当事者に由来する情報は，2つの項目として宣言する。 |
| **共有規範** | 内容がメッセージであり，`shares:` を持つ義務または許可。そのメッセージは，挙げた項目を受信者に与える。 |
| **大きさ（magnitude）** | 負でない数。インセンティブ強度が最大（λ = 1）であるときの制裁または報酬の大きさであり，契約の計算単位で表す。 |
| **導出指標** | α̂またはβ̂。1つの契約から計算する `[0, 1]` の有理数であるか，未定義である。 |
| **インセンティブ被覆率** | χ。契約の義務と禁止のうち，制裁または報酬を伴うものの割合であるか，未定義である。 |

規範，義務，許可，禁止，権能，負担者は，[付録F](./appendix-f-norms.md)の意味を持つ。

## J.3 構文（A.4，F.3，I.2へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`actor_ref`，`number`，`text` は
付録Aで定義している。

```ebnf
contract_def    = ... , [ "grounding:" , grounding_block ] ;
grounding_block = [ "items:"     , { identifier , ":" , actor_ref } ] ,
                  [ "tolerance:" , number ] ;

norm_def        = ... ,
                  [ "shares:"        , { "-" , identifier } ] ,
                  [ "on_fulfilment:" , norm_fulfilment ] ;
norm_violation  = ... , [ "magnitude:" , number ] ;
norm_fulfilment = [ "reward:"    , text ] ,
                  [ "magnitude:" , number ] ;

payoff_term     = "reward:" , identifier ,
                  ( [ "weight:" , param_expr ]                  (* I.2 *)
                  | "sanction_of:" , norm_ref
                  | "reward_of:"   , norm_ref ) ;
norm_ref        = identifier , "." , identifier ;               (* string *)
```

- `grounding.items` は，各情報項目の名前を，その起点に対応付ける。`tolerance:` は `[0, 1]` の数であり，
  既定値は `0.25` である（J.5）。
- `shares:` は，共有規範のメッセージが伝える情報項目を列挙する。
- `on_violation.magnitude` は，規範の制裁の大きさである。
- `on_fulfilment:` は，規範を履行したことに対する報酬を記録する。`reward:` は，`sanction:` が制裁を
  述べるのと同じく，報酬をテキストで述べ，`magnitude:` はその大きさである。報酬は，規範インスタンスが
  F.5の状態 `fulfilled` に達したときに支払われたものとみなす。義務では，その内容が期限内に実現された
  ときである。禁止では，違反のないまま，その期間が閉じるか，契約インスタンスが終わったときである。
  インスタンスが `discharged` になったときは，その判定は `fulfilled` であるが，報酬は支払われない。
  このブロックは注記であり，付録Fの意味論に影響しない。
- `norm_ref` は，引用符付きの文字列 `"C.n"` である。契約の `id`，ドット，その契約の規範の `id` からなる。

空のテキスト（`sanction: ""`，`reward: ""`）とYAMLのnullは，ないものとして扱う。引用符のない項目名の
うち，YAML 1.1のローダが真偽値やnullとして読むものは，引用符で囲まなければならない
（[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)）。

## J.4 導出指標と被覆率

3つの量は，本拡張を宣言するファイルのどの契約 C についても定義する。それぞれ，2つの個数の比であるか，
分母が0であるときは**未定義**である。未定義の量は，J.5のどの比較にも関与しない。

### 情報共有：α̂

C の当事者名の集合を Π，`grounding.items` の項目の集合を X，項目 x の起点を o(x)（当事者名である。
J-2）とする。C の**組**とは，項目 x と，o(x) 以外の当事者名 q の組 (x, q) である。これは，項目を
当事者と共有し得る場所である。

アクター参照 T は，そのアクター名が q であり，かつ，添字を持たないか，添字が `*` であるか，添字が
識別子（`i` のような添字変数であり，各要素を順に表す）であるか，添字がアクターを宣言したときの範囲で
あるとき，**当事者 q の全体を表す**という。T が整数の添字を持ち，そのアクター名を持つ `parties:` の
ただ1つの項目であるときも，そうである。それ以外のとき（整数の添字，または他の範囲）は，
**要素を特定している**という。添字と範囲は，空白を無視して，書かれたとおりに比べる。

組 (x, q) は，次のとき，与えられている。

- **共有のエントリによって**：`information.sharing` のエントリ `"S -> T : x"` が，項目 x と，当事者 q の
  全体を表す宛先 T を持つとき。
- **義務によって**，または**許可によって**：その種類の共有規範が，`shares:` に x を挙げ，内容として
  メッセージ `S -> T : m` を持ち，その受信者 T が当事者 q の全体を表すとき。

組は，この3つの与え方の少なくとも1つで与えられているとき，**与えられている**という。

```text
α̂  =  (number of given pairs) / (number of pairs)
```

α̂は，組がないとき（項目がない，または当事者名が1つである）は未定義である。α̂ = 0 であるのは，
組が1つも与えられていないとき，かつそのときに限る。これは，宣言した項目に限って，5.4.2節の端点
「情報非共有」に対応する。α̂ = 1 であるのは，すべての組が与えられているとき，かつそのときに限る。
これは，宣言した項目に限って，「完全共有」に対応する。処理系は，α̂とともに，3つの与え方のそれぞれで
与えられている組の数，与えられていない組，および**要素を特定した**エントリと規範を報告する。組を
与えるはずであるが，宛先が要素を特定しているエントリまたは規範
（`"DISPATCHER -> ROBOT[3] : route"` など）は，組を与えず，分けて列挙する。

この定義が見ないものは，次のとおりである。

- 送信元 S は調べない。エントリは，誰が送るかにかかわらず，項目を T に与える。
- 契約の当事者でない宛先は，組を与えない。処理系は警告することが望ましい（J-3）。
- 規範の状態は無視する。共有規範は，`trigger:`，`until:`，`deadline:` を持つかどうかにかかわらず，
  また，初めから発効しているか，反義務の規範として，または権能によってだけ発効するかにかかわらず，数える。
- 同じメッセージの禁止は，組を取り除かない。そのような衝突については，付録FのN-12が警告する。
- 義務も許可も，組を与える。指標が記録するのは，規範が当事者に項目を持たせること，または持つことを
  許すことであり，当事者が実際にそれを持つことではない。3つの個数が，その違いを見えるようにする。
- 当事者が1つのアクター集合だけである契約は，当事者名が1つであり，組を持たないので，α̂は未定義である。
  したがって，対等な構成システムからなる協調型のSoSで重要となる，同等の者どうしの共有は，
  バージョン0.1では測られない。

### 権能の集中：β̂

C の**決定点**とは，C の権能（F.2）である。権能は，その行使が，定義された効果によって他の規範の状態を
変える，契約のただ1つの構成要素である（F.5）。`authority.decision_scope` はテキストであり，数えない。
単一のアクター a（J.2）について，`bearer:` が参照 a である（アクター名も添字も同じである）C の権能の
数を k(a) とする。負担者が単一のアクターでない権能（`ROBOT[i]` など）は，各要素がそれぞれ自分のために
保持するものであり，どの単一のアクターの分としても数えない。

```text
β̂  =  (largest k(a) over the single actors a) / (number of powers)
```

β̂は，単一のアクターが負担する権能が1つもないとき0であり，C に権能がないときにだけ未定義である。
これは，契約の決定点のうち，1つのアクターにあるものの最大の割合であり，**集中**の指標である。
β̂ = 1 であるのは，1つの単一のアクターがすべての権能を負担するとき，かつそのときに限る。これは，
権能に限って，5.4.2節の端点「単一アクターが全決定」に対応する。β̂ = 0 であるのは，どの単一のアクターも
権能を負担しないとき，かつそのときに限る。

β̂は `authority.decision_holder` に依存しない。処理系は，β̂とともに，次を報告する。負担者ごとの権能の数。
各権能について，その `effects:` に挙げた規範の数。決定権者が単一のアクター h を名指すときは，
**決定権者の割合**，すなわち k(h) を権能の数で割ったもの。個数は，効果によって重み付けしない。
1つの規範を解除する権能も，他の当事者の権能を解除する権能も，同じように数える。

### インセンティブの被覆率：χ

C の義務と禁止の集合を N とする。N の規範は，次の少なくとも1つが成り立つとき，
**インセンティブを伴う**という。

- 空でない `on_violation.sanction` を持つ。
- 0より大きい `on_violation.magnitude` を持つ。
- 空でない `on_fulfilment.reward`，または0より大きい `on_fulfilment.magnitude` を持つ。

```text
χ  =  (number of norms of N that carry an incentive) / (number of norms in N)
```

χは，N が空であるときは未定義である。χ = 0 であるのは，どの義務と禁止も制裁も報酬も伴わないとき，
かつそのときに限り，χ = 1 であるのは，そのすべてが伴うとき，かつそのときに限る。χはλの指標ではない。
χは，λが掛かる対象を持つ規範を数える。どれだけ掛かるかを述べるのがλである（J.7）。

さらに2つの個数を，χとは分けて報告する。これらはχには含めない。インセンティブを伴わず，
`on_violation.reparation` を持つ N の規範（その違反は，制裁ではなく，さらなる義務を生じさせる）の数と，
`on_violation.transition` を持つ N の規範（その違反は，契約インスタンスを動かすか終わらせる）の数である。
`severity:` は，どこにも数えない。それは違反を分類するものである。

### 量の動き方

3つの量は，名前の付け替えと，規範，項目，当事者の順序の入れ替えについて不変である。分割と併合に
ついては不変で**ない**。1つの権能を2つに分けて書くと，あるいは2つの義務を1つに併合すると，契約が
当事者に求めることは同じでも，β̂またはχが変わる。各補題では，述べていないものはすべて同じままであり，
量は前後で定義されているとする。

- **補題1（α̂）。** `information.sharing` にエントリを追加しても，共有規範の `shares:` に項目を
  追加しても，共有規範を追加しても，α̂は下がらない。*証明。* 組の集合は変わらず，与えられていた組は
  すべて，引き続き与えられている。これに対して，項目または当事者を追加すると，組が増え，α̂が下がる
  ことがある。
- **補題2（β̂）。** 負担者が，k(a) が最大である単一のアクターである権能を追加しても，β̂は下がらない。
  負担者が単一のアクターでない権能を追加しても，β̂は上がらない。*証明。* n 個の権能のうちの最大の数を
  k とすると，k ≤ n であるので，k/n ≤ (k + 1)/(n + 1) かつ k/(n + 1) ≤ k/n である。
- **補題3（χ）。** インセンティブを伴わなかった義務または禁止に，（空でない制裁のテキスト，または0より
  大きい大きさによって）インセンティブを伴わせると，χは 1/|N| だけ上がる。0である大きさでは上がらない。
  インセンティブを伴う規範を N に追加しても，χは下がらず，伴わない規範を追加しても，χは上がらない。
  *証明。* 補題2と同様である。

### 量が捉えないもの

- α̂が数えるのは，共有する資格と義務である。運用において当事者が何を観測するかではなく，情報の品質や
  遅延でもない。項目は，記述者が挙げたものである。
- β̂が数えるのは，権能である。誰が経路を計画するかのように，制度上の行為でない決定は，規範ではなく，
  数えない。すべての権能は，その効果が何であっても，同じ重みを持つ。
- χが述べるのは，制裁または報酬を伴う規範がいくつあるかであり，それらがどれほど大きいかや，
  どれほど確実に適用されるかではない。
- J.7のどの結果にも，大きさとλの積だけが入る。1つの契約の中では，λと大きさは別々には特定されない。
  すべての大きさを2倍にし，λを半分にしても，何も変わらない。
- コアのキー `incentives.type`，`incentives.rules`，`violation.action` はテキストであり，無視する。
  契約は，χからは見えないインセンティブを，そこに持ち得る。
- [付録G](./appendix-g-agents.md)の強制のもとでは，禁止されたメッセージは境界で拒否され，送ることが
  できない。したがって，その禁止は，制裁がなくても実効性を持つ。ゆえに，強制される契約での被覆率0は，
  「インセンティブなし」を意味しない。
- どの量も，振る舞いについては何も述べない。共有を増やすこと，あるいはインセンティブを強くすることが
  性質を改善するかどうかは，付録Hと付録Iのモデルに対する問いである。

## J.5 宣言されたパラメータとの関係

処理系は，どの契約についても3つの量を計算し，報告する（J-5）。`alpha` と `beta` については，宣言値，
指標，およびその差を報告し，両者を比べる。どの不一致も**警告**である。指標は規範についての証拠であり，
本拡張を宣言することが，有効なファイルを無効にすることは決してない。

**宣言された端点に対する反例が，契約の中にある場合。** 5.4.2節の端点は，全称的な言明である。同じ契約の
構成要素が反例であるとき，処理系は，警告し，その構成要素を名指すことが望ましい（J-6）。

| 宣言 | 警告で名指す反例 |
| --- | --- |
| `alpha: 0` | 与えられている組と，それを与えるエントリまたは共有規範。α̂が未定義のときは，空でない `information.sharing` |
| `alpha: 1` | 与えられていない組（規範がないことは，当事者が項目を持たないことを示さないので，4つのうちで最も弱い） |
| `beta: 1` | 負担者が，割合が最大である単一のアクターでない権能 |
| `beta: 0` | 権能を負担する単一のアクター |

**中間の値が指標から遠い場合。** αとβについて，処理系は，宣言値と指標の差が契約の許容差を超え，
J-6がそのパラメータについて警告を出さないとき，警告することが望ましい（J-7）。許容差の既定値は
0.25である。指標は粗く，規範の少ない契約では，指標が取り得る値が少ない（権能が2つであれば，β̂は
0，1/2，1 のいずれかである）。より大きな差を受け入れる記述者は，それを `grounding.tolerance` で述べる。
処理系は，決定権者が単一のアクターを名指し，その割合がβ̂より小さいときも，警告することが望ましい。
このとき，権能は別のアクターに集中している。

**λは数とは比べない。** λは倍率であり，χは被覆率である。どの規範にも軽い制裁がある契約は，χ = 1 で，
λが小さく，整合している。処理系は，宣言された `lambda` の隣にχを報告し，次の2つの場合にだけ
警告することが望ましい（J-8）。契約のどの義務と禁止もインセンティブを伴わない（χ = 0，または N が空で
ある）のに，`lambda` が0より大きい場合。このとき，λには，規範の中に掛かる対象がない。および，ある
規範がインセンティブを伴うのに `lambda: 0` である場合。このとき，規範が宣言するものは，モデルの中で
効果を持たない。

**契約の版。** 契約の2つの版を比べる処理系（F.6）は，本付録のキー（大きさ，`on_fulfilment:`，
`shares:`，項目）で何が変わったかを報告し，宣言値とその指標が逆の向きに動くとき，警告することが
望ましい（J-13）。たとえば，改正がロボットに権能を与える一方で，`beta` を上げる場合である。

## J.6 付録Hと付録Iのモデルにおけるパラメータ

**現状。** モデルのパラメータは，`from: "C.alpha"`，`"C.beta"`，`"C.lambda"` によって宣言値に
束縛する（H.3）。これにより，契約とモデルが同じ数を用いる。その数がモデルの中で何をするかは，
記述者が書く。[H.12](./appendix-h-stochastic.md)では，βは決定が集中的に行われる確率であり，αは
集中的な計画の品質に掛かる。どちらの付録も，これらの式を契約から導出せず，本付録も導出しない。

**本付録がαとβについて加えるもの。** 契約の規範は，束縛したパラメータが宣言値を持つ設計を記述する。
別の値を割り当てるモードは，動作モード（H.6）を記述するが，ファイルはそのモードに固有の規範を
持たない。そこで，処理系は，どの設計においても，`C.alpha` または `C.beta` に束縛したパラメータの
固定値を C の指標と比べ，両者の差が許容差を超える設計について，警告ではなく，情報レベルの診断を
出すことが望ましい（J-9）。

**未解決のまま残るもの。** モードは固有の規範を持たないので，モードがαとβに割り当てる値を指標に
照らして検査することはできず，βによるモードの順序を，その規範の順序と比べることもできない。
共有規範または権能からモデルの確率を導出すること，および，ゲームにおいてプレイヤーが観測するものと
してのα（RD-7.3）は，定義しない。

## J.7 λ：規範の制裁から利得の項へ

戦略モデル（[付録I](./appendix-i-games.md)）では，利得の項は，重みを与える代わりに，その項が表すと
宣言する制裁または報酬を持つ規範を名指してよい。

```yaml
- { reward: shortcuts, sanction_of: "DELIVERY.no_shortcut" }
```

項が名指す規範 `C.n` を n とし，`from: "C.lambda"` で束縛したモデルのパラメータを ℓ とする
（ちょうど1つなければならない。J-10）。この項は `weight:` を持たず，その重みを次のように定義する。

| 項 | 重み |
| --- | --- |
| `sanction_of: "C.n"` | −m · ℓ。m は n の `on_violation.magnitude` |
| `reward_of: "C.n"` | m′ · ℓ。m′ は n の `on_fulfilment.magnitude` |

この項は，それ以外の点ではI.6の項であり，付録Iがそのまま適用される。

**検査されない仮定。** 項の報酬構造は，モデルの中で制裁がどれだけ頻繁に科されるか，または報酬が
支払われるかについての，記述者の言明である。規約は次のとおりである。`sanction_of:` の項の累積報酬は，
モデルの1回の実行の中のすべての契約インスタンスにわたって，規範の違反を数え，`reward_of:` の項の
累積報酬は，その履行を数える。1回の実行は，複数の契約インスタンスにまたがってよい。これを検査できる
処理系はない。付録Fは規範を時間付きトレースの上で判定し，付録Hはモデルをステップで評価する。両者の
間の変換は定義されていない。したがって，そのような項を持つ利得を用いて計算したどの結果も，各項に
ついての仮定「報酬構造 r は，C.n の違反（履行）を数えるものとする」とともに報告しなければならない
（J-12）。

**誰が負うか。** 制裁は，規範の負担者の損失である。`sanction_of:` の項は，負担者を代表するプレイヤーの
利得に置き，他のどこにも置かない。その額がどこへ行くかは，本付録は述べない。それが相手方への移転である
ときは，記述者は，相手方のプレイヤーの利得に，同じ報酬構造と明示的な重みを持つ，2つ目のふつうの項を
書く（`weight: "2 * lambda"`）。その項の大きさは，規範に照らして検査されない（J-11）。

**処理系が検査すること（J-10，J-11）。** 規範が存在し，義務または禁止であり，大きさを宣言している
こと。利得のプレイヤーが規範の負担者を代表すること。1つの規範が，それぞれのキーで多くとも1回だけ
名指されること。モデルが C の規範を1つでも名指すときは，大きさを持ち，負担者がモデルのプレイヤーで
ある C のどの規範も名指されること。ファイルは大きさを1回だけ述べるので，大きさと係数λは，定義により
成り立つ。

**答えの形。** σ をプロファイル，D を設計，ℓ をパラメータとし，他のすべてのパラメータを固定する。
次の2つの条件を考える。

- **(i)** ℓ は，モデルのどの確率にも，どの報酬の値にも現れず，ℓ が現れるどの重みも，ℓ について
  アフィンである（ℓ が1より高いべきで現れない）。
- **(ii)（プレイヤー p について）** p の項のうち，重みに ℓ が現れるものはどれも，`sanction_of:` の項と
  同じく，m ≥ 0 である重み −m·ℓ を持ち，σ のもとで，その報酬構造の期待累積値が0である。

> **命題。** (i) を仮定する。D が良定義であるかどうかと，σ が許容できるかどうかは，ℓ に依存しない。
> それらが成り立つところで，次が成り立つ。
>
> 1. どの gain_p も，ℓ の凸な区分線形関数である。ℓ の値の区間の上で，σ が D のε均衡である値の
>    集合は，閉区間である（空であってもよい）。特に，σ は，a と b でε均衡であれば，a と b の間の
>    どの値でもε均衡である。
> 2. (ii) が p について成り立つならば，gain_p は ℓ について非増加である。b で gain_p > ε であれば，
>    b より小さいどの値でも gain_p > ε である。
> 3. (ii) がすべてのプレイヤーについて成り立つならば，1の集合は，空であるか，あるしきい値 λ\*
>    について，区間の ℓ ≥ λ\* である値の全体である。

*証明。* (i) により，確率は ℓ に依存せず，それとともに，ゲームのグラフも，どの期待累積報酬も ℓ に
依存しない。したがって，良定義性と許容性も依存しない（H.5，I.6）。p の戦略 τ について，σ[p↦τ] の
もとでの p の利得は，A(τ) + ℓ·B(τ) である。どの重みも ℓ についてアフィンであるので，A(τ) と B(τ) は
ℓ に依存しない数である。BR_p は，そのような関数の有限個の最大値であり（I.7），したがって凸で
区分線形である。σ のもとでの利得はアフィンである。ゆえに gain_p は凸で区分線形であり，連続である。
凸で連続な関数が ε 以下である集合は閉区間であり，プレイヤーにわたる共通部分も閉区間である。(ii) の
もとでは，B(τ) は，大きさと期待累積報酬の積の和に負号を付けたものであるので，どの τ についても
B(τ) ≤ 0 であり，σ 自身の戦略については0である。このとき，gain_p は，非増加な関数の最大値から定数を
引いたものである。ある値を含めばそれより大きい値をすべて含む閉区間は，空であるか，3の形である。∎

**どこまで成り立つか。**

- (ii) がなければ，集合は閉区間であり，しきい値の形であるとは限らない。I.12では，`shortcut_first` は
  制裁を受け，それが均衡であるのは，max(0, T_1, T_2) ≤ λ ≤ T_3 であるとき，かつそのときに限る。
  `reward_of:` の項も (ii) を破る。その項の σ のもとでの値は，ℓ とともに増えるからである。
- 契約が2つあれば，2つの `lambda` に束縛した2つのパラメータがある。命題は，他方を固定したとき，
  そのそれぞれについて成り立つ。両方の領域については何も述べない。
- ℓ が確率に現れるとき（インセンティブが環境の振る舞いを変えるとき），(i) は成り立たず，利得は ℓ の
  有理関数であり，上のことは何も成り立たない。

**セルの端点による認証。** J-14は，この命題を，開いているパラメータが ℓ だけである均衡マップ（I.9）の
ための方法にする。セル `[a, b]` の両端での厳密な評価が `equilibrium` を認証し，b での評価が，(ii) の
成り立つ逸脱者を認証する。これは，H.9の意味での標本点での評価ではない。凸性と単調性が証明されている
からである。ただし，J-14が挙げるすべての条件のもとでだけ健全である。

**例。** [I.12](./appendix-i-games.md)の1つ目のモデルは，2つの拡張を宣言し，契約に規範を追加し，R の
3番目の項の重みを置き換えることによって，規範に結び付けられる。

```yaml
sos:
  name: "RobotDeliveryGame"
  extensions:
    - stochastic: 0.1
    - games: 0.1
    - norms: 0.1
    - grounding: 0.1
  # actors, transitions as in I.12

  contracts:
    - id: DELIVERY
      parties: [DISPATCHER, "ROBOT[*]"]
      information: { alpha: 0.9 }
      authority:   { decision_holder: DISPATCHER, beta: 0.9 }
      incentives:  { lambda: 0.1 }
      norms:
        - id: no_shortcut
          kind: prohibition
          bearer: "ROBOT[i]"
          counterparty: DISPATCHER
          content: "ROBOT[i].handling == Careless"
          on_violation:
            severity: Major
            sanction: "deduction from the delivery fee"
            magnitude: 2

  model:
    # as in I.12, except the payoff of R:
    payoffs:
      - player: R
        until: "settled"
        terms:
          - { reward: fee,       weight: 10 }
          - { reward: effort,    weight: -1 }
          - { reward: shortcuts, sanction_of: "DELIVERY.no_shortcut" }
      - player: D
        until: "settled"
        terms:
          - { reward: fee, weight: 5 }
```

3番目の項の重みは −2·`lambda` であり，I.12で手で書いた重みと同じである。したがって，I.12のどの数値も
変わらず，どの結果も，仮定「報酬構造 `shortcuts` は，`DELIVERY.no_shortcut` の違反を数えるものとする」
とともに報告する。負担者 `ROBOT[i]` は，R が代表する `"ROBOT[*]"` に覆われる（J-10）。`shortcuts` は，
1回の実行の中の手抜きの試行を，3回まで数える。付録Fは規範を契約インスタンスごとに1回判定するので，
この数が規範の違反の数と一致するのは，ホストが試行ごとに契約インスタンスを開始する場合に限られる。
これは，ホストについての仮定であり，ファイルの中の何もそれを表していない。報告が伴う仮定とは，
この種の仮定である。

条件 (i) と (ii) は，`comply` について成り立つ。`lambda` は，この項の重み −2·`lambda` にだけ現れ，
`comply` は手抜きの試行をしないので，そのもとでの `shortcuts` の期待値は0である（J-12によって
報告される）。料金を g，労力の費用を c，丁寧な試行が成功する確率を s，`no_shortcut` の大きさを m と
すると，I.12は次を導く。

> s·g ≥ c かつ s < 1 である各設計において，遵守プロファイルがナッシュ均衡であるのは，λ ≥ λ\* で
> あるとき，かつそのときに限る。ここで，λ\* = max(0, (c − (s/2)·(g·(1 − s)² + c·(2 − s))) / m) である。

g = 10，c = 1，m = 2 のとき，固定値では，λ\* は CENTRALIZED で 0.150108，DISTRIBUTED で 0.060373
である。宣言値 λ = 0.1 では，遵守は DISTRIBUTED でだけ均衡である。しきい値は，大きさに反比例する。
λ = 0.1 では，CENTRALIZED で遵守が均衡であるのは，大きさが 480347064349/160000000000 以上である
（約 3.0022。3.002 では足りない）とき，かつそのときに限り，DISTRIBUTED では，
193194567781/160000000000 以上である（約 1.2075）とき，かつそのときに限る。この契約では，
χ = 1/1 = 1 であり（ただ1つの禁止が制裁を伴う），α̂は未定義であり（項目がない），β̂も未定義である
（権能がない）。被覆は完全であり，残る問いは，モデルが答える問い，すなわち，大きさ m·λ が十分であるか
どうかである。

## J.8 静的意味論 {/* #j8-static-semantics */}

本拡張を実装する処理系は，`grounding: 0.1` を宣言しているファイルにおいて，既存の検査に加えて，
以下の規則を適用しなければならない。J-1からJ-4とJ-10は誤りであり，本付録のキーだけに関する。
2つの条項が，同じ構成要素について同じ事実を報告することになるときは，処理系は診断を1つだけ出す。

- **J-1.** `grounding: 0.1` を宣言するファイルは，`norms: 0.1` も宣言しなければならない。
  そうでない場合，処理系は誤りを報告し，本拡張のキーを解釈しない。
- **J-2.** `grounding.items` のどのキーも，識別子でなければならず，
  [A.11](./appendix-a-syntax.md#a11-reserved-keywords)の予約語であってはならない。その値は，
  アクター名が契約の当事者名であるアクター参照でなければならない。`tolerance:` は，`[0, 1]` の
  数でなければならない。
- **J-3.** `shares:` は，`content:` が `message_event` である義務または許可にだけ許される。
  少なくとも1つの項目を，それぞれ1回だけ列挙しなければならず，どの項目も同じ契約の
  `grounding.items` に宣言されていなければならない。処理系は，次のとき，警告することが望ましい。
  メッセージの受信者が，挙げた項目の起点のアクター名を持つとき。共有のエントリの宛先，または
  共有規範の受信者が，契約の当事者でないとき。契約が項目を宣言しているのに，`information.sharing` の
  エントリが，`grounding.items` に宣言されていない項目を名指すとき。
- **J-4.** `on_violation.magnitude` と `on_fulfilment.magnitude` は，負でない有限の数でなければ
  ならない。`on_fulfilment:` は，（`on_violation:` と同じく。N-4）義務または禁止にだけ許され，
  `reward:` と `magnitude:` の少なくとも一方を持たなければならない。空でない `sanction:` または
  `reward:` のテキストの隣に0である `magnitude:` があるとき，処理系は警告することが望ましい。
- **J-5.** 本拡張を実装し，報告をする処理系は，ファイルのどの契約についても，J.4の定義によって
  α̂，β̂，χを厳密に計算し，それぞれを，その2つの個数とともに，または未定義であることをその理由とともに，
  報告しなければならない。J.4が挙げるその他の個数（組の3つの与え方，要素を特定したエントリと規範，
  負担者ごとの権能と権能ごとの効果，決定権者の割合，反義務の規範だけを持つ規範と遷移を持つ規範）も
  報告しなければならない。`alpha` と `beta` については，それが宣言され，指標が定義されているとき，
  宣言値，指標，およびその差を報告しなければならない。`lambda` については，宣言値をχの隣に報告し，
  差は報告しない。J-6からJ-9とJ-13の比較は厳密である。宣言値は，書かれたとおりの10進小数である（H.2）。
- **J-6.** 処理系は，次のとき，警告し，反例である構成要素を名指すことが望ましい。契約が `alpha: 0` を
  宣言し，与えられている組を持つか，α̂が未定義であって空でない `information.sharing` を持つとき。
  `alpha: 1` を宣言し，α̂が定義されていて1より小さいとき。`beta: 1` を宣言し，β̂が定義されていて
  1より小さいとき。`beta: 0` を宣言し，β̂が定義されていて0より大きいとき。
- **J-7.** 宣言された `alpha` または `beta` と，定義されている指標との差が契約の許容差を超え，
  J-6がそのパラメータについて警告を出さないとき，また，決定権者が単一のアクターを名指し，その権能の
  割合がβ̂より小さいとき，処理系は警告することが望ましい。
- **J-8.** 契約が0より大きい `lambda` を宣言し，その義務と禁止のどれもインセンティブを伴わない（J.4）
  とき，また，`lambda: 0` を宣言し，そのどれかがインセンティブを伴うとき，処理系は警告することが
  望ましい。
- **J-9.** `stochastic: 0.1` も宣言するファイルでは，どの設計についても，`C.alpha` または
  `C.beta` に束縛され，指標が定義されているどのパラメータについても，その設計のもとでの
  パラメータの固定値と指標との差が C の許容差を超えるとき，処理系は情報レベルの診断を出すことが
  望ましい。
- **J-10.** `sanction_of:` と `reward_of:` は，`stochastic: 0.1` と `games: 0.1` も宣言する
  ファイルにだけ許される。項は，`weight:`，`sanction_of:`，`reward_of:` のうち多くとも1つを
  持たなければならない。値は，文字列 `C.n` でなければならない。ここで `C` は宣言済みの契約であり，
  `n` は，0より大きい `on_violation.magnitude`（`sanction_of:` の場合）または
  `on_fulfilment.magnitude`（`reward_of:` の場合）を持つ，`C` の義務または禁止である。モデルは，
  `from: "C.lambda"` で束縛したパラメータを，ちょうど1つ持たなければならない。利得のプレイヤーは，
  `actors:` に，`n` の負担者を**覆う**参照を挙げていなければならない。覆うとは，両者のアクター名が
  同じであり，両者が異なる整数の添字を持つのではないことである（`"ROBOT[*]"` と `ROBOT[1]` は
  負担者 `ROBOT[i]` を覆う。`ROBOT[1]` は負担者 `ROBOT[2]` を覆わない）。1つのモデルの中で，
  1つの規範を，2つ以上の `sanction_of:` の項が名指してはならず，2つ以上の `reward_of:` の項が
  名指してもならない。
- **J-11.** モデルが契約 `C` の規範を名指す項を持つとき，処理系は，0より大きい大きさを持ち，
  負担者があるプレイヤーのアクター参照に覆われ，対応するキーを持つどの項も名指していない，
  `C` のどの義務または禁止についても，警告することが望ましい。また，`C.lambda` に束縛した
  パラメータが現れる `weight:` を持つ項についても，警告することが望ましい。そのような項の大きさは，
  規範に照らして検査されないからである。
- **J-12.** `sanction_of:` または `reward_of:` の項を持つ利得を評価する処理系は，その利得に依存する
  どの結果とともにも，そのような各項についてのJ.7の仮定を報告しなければならない。処理系は，
  どの `sanction_of:` の項とどの設計についても，固定値において，遵守プロファイルのもとで，利得の
  目標までに累積する，項の報酬構造の期待値を報告することが望ましい。0より大きい値は情報であり，
  警告ではない。負担者が遵守していても，義務は偶然によって違反され得るからである。値が0であることは，
  遵守プロファイルについてのJ.7の条件 (ii) である。
- **J-13.** 契約の2つの版を比べる処理系は，`on_violation.magnitude`，`on_fulfilment:` ブロック，
  `shares:` のリスト，`grounding.items` のどの変更も報告することが望ましい。また，αまたはβについて，
  宣言値と指標が両方の版で定義されており，(x′ − x)·(x̂′ − x̂) が0より小さいとき，警告することが
  望ましい。ここで，x と x̂ は古い版の宣言値と指標，x′ と x̂′ は新しい版のものである。
- **J-14.** 処理系は，均衡マップ（I.9）のセル `[a, b]` を，その端点での評価から認証してよい。
  ただし，次のすべてが成り立つ場合を除いて，そうしてはならない。
  1. 問い合わせが，開いているパラメータをちょうど1つ，ℓ だけ持つ（I-9により，どのモードもそれに値を
     割り当てない）。
  2. J.7の条件 (i) が ℓ について成り立つ。これは，モデルのテキストの上で検査する。ℓ は，どの `prob:` にも，
     どの報酬の `value:` にも現れず，どのプレイヤーのどの `weight:` でも，J.7が定義するどの重みでも，
     ℓ は高々1のべきで現れる。
  3. セルの中の ℓ の1つの値で，設計が良定義であり，プロファイルが許容できる（命題により，このとき
     どの値でもそうである）。
  4. a と b での評価が厳密である（I.8）。
  5. p が逸脱者であるという主張については，その設計で，J.7の条件 (ii) が p について成り立つ。
     重みの形はテキストの上で検査し，プロファイルのもとでの期待値が0であることは厳密に計算する。

  このとき，プロファイルが a と b でε均衡であれば，セルは `equilibrium` であり，条件5が成り立ち，
  b で gain_p > ε であれば，p はセルの上で逸脱者である。他の主張は導かれない。条件5がなければ，
  両端で逸脱利得が ε を超えていても，プレイヤーはセルの上で逸脱者とはならない。

`alpha`，`beta`，`lambda` が `[0, 1]` にあるというA.4の規則は変わらない。規則N-1からN-12と
I-1からI-11も変わらない。

## J.9 例

以下の契約は，[F.8](./appendix-f-norms.md)の契約に，3つのパラメータのブロック，`grounding:`
ブロック，2つの `shares:` の注記，1つの大きさ，および，ロボットが割当てを断るための権能 `decline` を
加えたものである。F.8がすでに持つキーは省略している。

```yaml
sos:
  name: "RobotDeliveryNorms"
  extensions:
    - sos-dsl: 0.1
    - norms: 0.1
    - grounding: 0.1
  # actors DISPATCHER, ROBOT[1..N], CUSTOMER[1..M] as in F.8

  contracts:
    - id: DELIVERY_SLA
      parties: [DISPATCHER, "ROBOT[*]", "CUSTOMER[*]"]
      authority:   { decision_holder: DISPATCHER, beta: 0.9 }
      information:
        alpha: 0.6
        sharing:
          - "DISPATCHER -> ROBOT[*] : route"
          - "ROBOT[*] -> DISPATCHER : status"
          - "DISPATCHER -> CUSTOMER[*] : status"
      incentives:  { lambda: 0.5 }
      grounding:
        items:
          route:   DISPATCHER
          status:  "ROBOT[*]"
          battery: "ROBOT[*]"
          failure: "ROBOT[*]"
      # assume, guarantee, lifecycle, counts_as as in F.8

      norms:
        - id: acknowledge              # obligation of ROBOT[i], as in F.8
          on_violation: { severity: Major, reparation: report_failure }
        - id: report_failure           # obligation of ROBOT[i], as in F.8
          content: "ROBOT[i] -> DISPATCHER : failure_report"
          shares: [failure]
          on_violation: { severity: Critical, transition: Violated }
        - id: no_low_battery_driving   # prohibition of ROBOT[i], as in F.8
          on_violation:
            severity: Critical
            sanction: "removed from the dispatch pool for one period"
            magnitude: 4
        - id: may_return_to_charge     # permission of ROBOT[i], as in F.8
          content: "ROBOT[i] -> DISPATCHER : charging_request"
          shares: [battery]
        - id: reassign                 # power of DISPATCHER, as in F.8
        - id: decline
          kind: power
          bearer: "ROBOT[i]"
          content: "ROBOT[i] -> DISPATCHER : decline"
          effects:
            discharge: [acknowledge]
```

**α̂。** 当事者名は DISPATCHER，ROBOT，CUSTOMER であり，項目は4つである。各項目には，起点以外の
当事者が2つあるので，組は8つである。どの宛先も，当事者の全体を表す。

| 項目（起点） | DISPATCHER | ROBOT | CUSTOMER |
| --- | --- | --- | --- |
| `route`（DISPATCHER） | 起点 | 共有のエントリによって与えられている | 与えられていない |
| `status`（ROBOT） | 共有のエントリによって与えられている | 起点 | 共有のエントリによって与えられている |
| `battery`（ROBOT） | 許可（`may_return_to_charge`）によって与えられている | 起点 | 与えられていない |
| `failure`（ROBOT） | 義務（`report_failure`）によって与えられている | 起点 | 与えられていない |

3つの組が共有のエントリによって，1つが義務によって，1つが許可によって与えられている。要素を特定した
エントリはない。5つの組が与えられているので，α̂ = 5/8 = 0.625 である。宣言された `alpha: 0.6` との
差は 0.025 であり，許容差の中にある。仮に最初のエントリが `"DISPATCHER -> ROBOT[3] : route"` で
あったならば，それは要素を特定しており，組（`route`，ROBOT）は与えられず，α̂は 4/8 になる。

**β̂。** 契約は2つの権能を持つ。`reassign` は，単一のアクターである DISPATCHER が負担する。
`decline` は，単一のアクターでない `ROBOT[i]` が負担する。単一のアクターの最大の数は1であるので，
β̂ = 1/2 = 0.5 であり，決定権者の割合も 1/2 である。`reassign` はその効果に2つの規範を挙げ，
`decline` は1つを挙げる。宣言された `beta: 0.9` との差は 0.4 であり，許容差 0.25 を超えるので，
処理系は警告する（J-7）。契約は，ほぼ集中した権限を宣言しているが，決定点の半分はロボットにある。
`beta: 1` であれば，警告はJ-6のものになり，`decline` を名指す。

**χ。** 契約は3つの義務と禁止を持つ。`no_low_battery_driving` は，大きさ4の制裁を伴う。
`acknowledge` は反義務の規範を持ち，制裁を持たない。`report_failure` はライフサイクルの遷移を持ち，
制裁を持たない。どちらもインセンティブを伴わない。χ = 1/3 = 0.333333 であり，反義務の規範だけを持つ
規範が1つ，遷移を持つ規範が1つある。宣言された `lambda: 0.5` は0より大きく，インセンティブを伴う
規範があるので，J-8は警告を出さない。

補題2により，DISPATCHER を `decline` の負担者にする改正は β̂ を1に上げ，補題3により，
`report_failure` に制裁を与える改正は χ を 2/3 に上げる。

## J.10 中間表現（IR）への追加

`institution.contracts` の下の各契約に，フィールド `grounding` を追加し，F.9の各規範に，4つの
フィールドを追加する。J.9の例では，次のとおりである。

```jsonc
{
  "grounding": {
    "items": { "route": "DISPATCHER", "status": "ROBOT[*]", "battery": "ROBOT[*]", "failure": "ROBOT[*]" },
    "tolerance": 0.25,
    "indices": {
      "alpha":    { "given": 5, "pairs": 8,
                    "by_sharing": 3, "by_obligation": 1, "by_permission": 1, "member_specific": 0 },
      "beta":     { "largest": 1, "powers": 2, "holder": 1,
                    "bearers": { "DISPATCHER": 1, "ROBOT[i]": 1 } },
      "coverage": { "incentive": 1, "norms": 3, "reparation_only": 1, "transition": 1 }
    }
  },
  "norms": [
    { "id": "no_low_battery_driving",
      // ... the fields of F.9
      "shares": [],
      "on_violation_magnitude": 4,
      "on_fulfilment_reward": null,
      "on_fulfilment_magnitude": null }
  ]
}
```

`grounding` は，本拡張を宣言していないとき `null` である。契約が `grounding:` ブロックを持たないとき，
`items` は空のマッピングであり，`tolerance` は既定値である。`alpha`，`beta`，`coverage` は，その量が
未定義であるとき `null` である。そうでないときは，厳密な比を作れるように，最初の2つのフィールドが
分子と分母である。`by_sharing`，`by_obligation`，`by_permission` は組を数え，重なってよい。
`member_specific` は，エントリと規範を数える。`holder` は，決定権者の数 k(h) であり，決定権者が
単一のアクターを名指さないときは `null` である。`bearers` は，書かれたとおりの各負担者の参照を，
その権能の数に対応付ける。規範の4つのフィールドは，本拡張を宣言しているときにだけ書く。大きさは，
ないとき `null` であり，空のテキストは `null` である。

[I.13](./appendix-i-games.md)のIRの利得の項に，フィールド `sanction_of` と `reward_of`
（文字列 `C.n` または `null`）を追加する。これらは，本拡張を宣言しているときにだけ書く。そのどちらかを
持つ項では，`weight` は，定義された重みのテキスト `-m * p` または `m * p` である。ここで m は，
往復変換で戻る最短の10進小数として書いた大きさであり，p は，`C.lambda` に束縛したパラメータの
`id` である（J.7では `"-2 * lambda"`）。診断は，IRに含めない。

## J.12 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。本拡張は，付録Fの
どの判定も，付録Hと付録Iのどの結果も変えない。`sanction_of:` を持つ項は，定義された重みを持つ
I.6の項である。

**本拡張を宣言することが，ファイルを無効にすることは決してない。** 付録Fのもとで有効であり，本付録の
キーを1つも用いないファイルは，その `extensions:` に `grounding: 0.1` を加えても，有効なままである。
誤りとなる規則（J-2，J-3，J-4，J-10）は，本付録のキーにだけ適用される。宣言されたパラメータと指標との
どの比較（J-6からJ-9）も，警告または情報レベルの診断である。

`grounding: 0.1` を宣言せずに `grounding:`，`shares:`，`on_fulfilment:`，
`on_violation.magnitude`，`sanction_of:`，`reward_of:` を用いるファイルは，本付録に適合しない。
本拡張を実装する処理系は，そのようなファイルではこれらのキーを解釈せず，宣言されていない拡張の
キーとして報告することが望ましい。量は計算せず，`sanction_of:` または `reward_of:` を持つ
利得の項は，I-7により誤りである。`norms: 0.1` なしに `grounding: 0.1` を宣言するファイルには，
J-1の誤りを出す。

付録Iを実装し，本付録を実装していない処理系は，両方を宣言するファイルにおいて，`sanction_of:` または
`reward_of:` の項を持つ利得も，それを必要とする問い合わせも，評価してはならない。処理系は，
問い合わせを評価しなかったと報告する（I-7）。どの場合にも，そのような項を，既定値の重みを持つ項として
読むことはない。本拡張を実装していない処理系は，本拡張を用いるファイルを拒否してはならない。
ファイルごとに1つの情報レベルの診断を出すことが望ましい。

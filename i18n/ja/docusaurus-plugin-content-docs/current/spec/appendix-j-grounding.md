# 付録J. 制度パラメータの規範による根拠付け（grounding 0.1）

本付録は，CADLの**根拠付け拡張**を規定する。この拡張は，規範拡張
（[付録F](./appendix-f-norms.md)）の上に成り立ち，`contract_def`
（[A.4](./appendix-a-syntax.md#a4-contracts-institution-layer)）にキー `grounding:` を，
`norm_def` にキー `shares:` と `on_fulfilment:` を，`on_violation:` にキー `magnitude:` を
追加する（F.3）。さらに，戦略モデル拡張（[付録I](./appendix-i-games.md)）も用いるファイルでは，
利得の項（I.2）にキー `sanction_of:` と `reward_of:` を追加する。これにより，処理系は，契約の規範から，
`[0, 1]` の中の3つの**導出指標** α̂，β̂，λ̂ を計算し，それらを宣言された `alpha`，`beta`，`lambda` と
比べ，戦略モデルにおいて規範の制裁を表す利得の項が，規範の宣言する大きさにλを掛けたものであることを
検査する。

コア言語は，これらのキーを必須と**しない**。本拡張を実装していないCADL準拠の処理系は，
これらのキーを理由にファイルを拒否してはならない。キーを構文上は受理し，*情報レベル*の診断を
出すことが望ましい。

拡張の名前は `grounding` であり，本付録はバージョン `0.1` を記述する。本拡張は `norms: 0.1` を
**必要とする**。本拡張を用いるファイルは，`extensions:`
（[A.2](./appendix-a-syntax.md#a2-top-level-structure)）で両方を宣言しなければならない。
宣言せずに用いた場合に処理系がどう扱うかはJ.12で述べる。キー `sanction_of:` と `reward_of:` は，
さらに `stochastic: 0.1` と `games: 0.1` を必要とする。

```yaml
sos:
  ...
  extensions:
    - norms: 0.1
    - grounding: 0.1
```

## J.1 動機と範囲

[5.4.2節](./05-language-spec.md)は，制度パラメータα，β，λを，定性的な端点を持つ `[0, 1]` の数として
定義する。言語の他の部分は，中間の値が何を意味するかを述べない。設計者は `beta: 0.7` と書くが，
その数を，それが置かれた契約に関係付ける規則はない。付録Fは，意図する読み方（βは契約の権能を誰が
持つかを表し，αは他の当事者がどの発動条件と内容を観測できるかを表し，λは違反された規範の制裁の
大きさを調整する）を参考として述べるにとどまる。[9.6節](./09-research.md)は，規範とパラメータの
形式的な結び付きを未解決としており，RD-1.5は，λを契約のパラメータとして扱うことを求めている。
制度の規則を，それが何に作用するかによって分類する方法には，情報の規則，集約の規則，利得の規則が
含まれる [[Ostrom, 2005]](./appendix-b-references.md)。これは，3つのパラメータが3種類の規範を
要約することを示唆する。grounding 0.1は，最初の一歩である。

- **指標はファイルから計算する。** J.4は，α̂，β̂，λ̂を，1つの契約から読み取る有限集合の上の，
  個数の比として定義する。指標は再現可能であり，規範を追加すると，期待される向きに動く（J.4の補題）。
- **指標は証拠であり，意味ではない。** 指標は，宣言されたパラメータに取って代わるものではなく，
  5.4.2節を変えない。指標は，契約の規範についての構造的な事実であり，宣言値はそれと合うことも
  合わないこともある。指標が捉えられないものは，J.4に述べる。
- **宣言値を指標に照らして検査する。** 宣言された端点に，同じ契約の規範が矛盾するときは誤りである。
  それ以外の不一致は警告である（J.5）。
- **制裁に大きさを与え，モデルがそれを用いる。** `magnitude:` は，規範の制裁または報酬に数を与える。
  戦略モデルでは，`sanction_of:` で宣言した利得の項は，重み −magnitude·λ を持つ。ここでλは，
  契約の `lambda` に束縛したパラメータである（J.7）。λは，ここで付録Iの均衡の問いに入る。

**バージョン0.1の範囲。**

- 指標は1つの契約に関するものである。SoSの複数の契約にわたって指標を集約することはしない。
- 情報項目は記述者が宣言する（`grounding.items`）。アクターのインタフェース，述語，メッセージからは
  導出しない。
- 指標は個数である。大きさ，重大度，権能が影響する規範の数による重み付けはしない。
- `magnitude:` は，付録Fの動的意味論に影響しない。判定，違反，反義務の規範は変わらない。
- 本拡張は，規範からモデルを導出せず，モデルの報酬構造が規範の違反を数えていることを検査しない
  （H.8は，規範とモデルの間の変換を定義しない）。
- [付録G](./appendix-g-agents.md)の委任と，[付録C](./appendix-c-motivation.md)の動機パラメータρと
  κについては，指標を定義しない。

## J.2 概念

| 概念 | grounding 0.1での意味 |
| --- | --- |
| **アクター名** | アクター参照から添字を除いた識別子。`ROBOT[i]`，`"ROBOT[*]"`，`ROBOT[2]` のアクター名は `ROBOT` である。 |
| **当事者名** | 契約の `parties:` の項目のアクター名。 |
| **情報項目** | `grounding.items` に宣言する，名前付きの情報。その**起点**，すなわちその情報が由来する当事者を伴う。 |
| **共有規範** | 内容がメッセージであり，`shares:` を持つ義務または許可。そのメッセージは，挙げた項目を受信者に与える。 |
| **裏付けのある規範** | 帰結を伴う義務または禁止。帰結は，制裁，反義務の規範，または報酬である（J.4）。 |
| **大きさ（magnitude）** | 負でない数。インセンティブ強度が最大（λ = 1）であるときの制裁または報酬の大きさであり，契約の計算単位で表す。 |
| **導出指標** | α̂，β̂，λ̂のいずれか。1つの契約から計算する `[0, 1]` の有理数であるか，未定義である。 |

規範，義務，許可，禁止，権能，負担者は，[付録F](./appendix-f-norms.md)の意味を持つ。

## J.3 構文（A.4，F.3，I.2へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`actor_ref`，`number`，`text` は
付録Aで定義している。

```ebnf
contract_def    = ... , [ "grounding:" , grounding_block ] ;
grounding_block = [ "items:"     , { identifier , ":" , actor_ref } ] ,
                  [ "tolerance:" , number ] ;

norm_def        = ... ,
                  [ "shares:"        , { "-" , identifier } ] ,
                  [ "on_fulfilment:" , norm_fulfilment ] ;
norm_violation  = ... , [ "magnitude:" , number ] ;
norm_fulfilment = [ "reward:"    , text ] ,
                  [ "magnitude:" , number ] ;

payoff_term     = "reward:" , identifier ,
                  ( [ "weight:" , param_expr ]                  (* I.2 *)
                  | "sanction_of:" , norm_ref
                  | "reward_of:"   , norm_ref ) ;
norm_ref        = identifier , "." , identifier ;               (* string *)
```

- `grounding.items` は，各情報項目の名前を，その起点に対応付ける。`tolerance:` は `[0, 1]` の数であり，
  既定値は `0.25` である（J.5）。
- `shares:` は，共有規範のメッセージが伝える情報項目を列挙する。
- `on_violation.magnitude` は，規範の制裁の大きさである。`on_fulfilment:` は，規範を履行したことに
  対する報酬を記録する。`reward:` は，`sanction:` が制裁を述べるのと同じく，報酬をテキストで述べ，
  `magnitude:` はその大きさである。`on_fulfilment:` は，付録Fの意味論に影響しない。
- `norm_ref` は，引用符付きの文字列 `"C.n"` である。契約の `id`，ドット，その契約の規範の `id` からなる。

引用符のない項目名のうち，YAML 1.1のローダが真偽値やnullとして読むものは，引用符で囲まなければならない
（[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)）。

## J.4 導出指標

指標は，本拡張を宣言するファイルの1つの契約 C について定義する。それぞれ，2つの個数の比であるか，
分母が0であるとき，または以下に述べる前提が成り立たないときは，**未定義**である。未定義の指標は，
J.5のどの規則にも関与しない。

### 情報共有：α̂

C の当事者名の集合を Π，`grounding.items` の項目の集合を X，項目 x の起点を o(x)（当事者名である。
J-2）とする。C の**組**とは，項目 x と，o(x) 以外の当事者名 q の組 (x, q) である。これは，項目を
共有し得る場所である。組 (x, q) は，次の少なくとも1つが C にあるとき，**与えられている**という。

- `information.sharing` の項目 `"S -> T : x"` であって，その項目が x であり，その宛先 T の
  アクター名が q であるもの。
- 共有規範であって，その `shares:` が x を挙げ，その内容がメッセージ `S -> T : m` であり，
  T のアクター名が q であるもの。

```text
α̂  =  (number of given pairs) / (number of pairs)
```

α̂は，組がないとき（項目がない，または当事者が1つである）は未定義である。α̂ = 0 であるのは，起点以外の
当事者に何も与えられていないとき，かつそのときに限る。これは，5.4.2節の端点「情報非共有」である。
α̂ = 1 であるのは，どの当事者にも，他の当事者のすべての項目が与えられているとき，かつそのときに限る。
これは，端点「完全共有」である。義務と許可は同じように数える。指標が記録するのは，規範が当事者に
項目を持たせること，または持つことを許すことであり，当事者が実際にそれを持つことではない。処理系は，
与えられている組を，それを与える項目または規範とともに報告する。

### 意思決定の集中：β̂

C の**決定点**とは，C の権能（F.2）である。権能は，その行使が，定義された効果によって他の規範の状態を
変える，契約のただ1つの構成要素である（F.5）。`authority.decision_scope` はテキストであり，数えない。
`authority.decision_holder` を h とする。権能は，その `bearer:` が h と同じアクター参照であるとき，
すなわち，アクター名が同じであり，添字が同じ（添字がないか，同じ整数）であるとき，
**集中して保持されている**という。h は，整数の添字を持つとき，または添字を持たず，そのアクターが
範囲なしで宣言されているとき，**1つのアクターを名指す**という。

```text
β̂  =  (number of powers held centrally) / (number of powers)
```

β̂は，C に権能がないとき，C に `decision_holder` がないとき，または h が1つのアクターを名指さないとき
（`"ROBOT[*]"` など）は未定義である。β̂ = 1 であるのは，決定権者がすべての権能を保持するとき，
かつそのときに限る。これは，5.4.2節の端点「単一アクターが全決定」である。β̂ = 0 であるのは，
決定権者が権能を1つも保持しないとき，かつそのときに限る。このとき，すべての決定点は他の当事者にある。
負担者が `ROBOT[i]` である権能は，各ロボットがそれぞれ自分のために保持するものであり，h が何であっても，
集中して保持されてはいない。

### インセンティブの被覆：λ̂

C の義務と禁止の集合を N とする。N の規範は，次の少なくとも1つが成り立つとき，**裏付けがある**という。

- `on_violation.reparation` を持つ。
- 0より大きい `on_violation.magnitude` を持つか，`on_violation.sanction` を持ち
  `on_violation.magnitude` を持たない。
- 0より大きい `on_fulfilment.magnitude` を持つか，`on_fulfilment.reward` を持ち
  `on_fulfilment.magnitude` を持たない。

```text
λ̂  =  (number of backed norms) / (number of norms in N)
```

λ̂は，N が空であるときは未定義である。λ̂ = 0 であるのは，どの義務と禁止も帰結を伴わないとき，
かつそのときに限る。これは，5.4.2節の端点「指令ベース」である。λ̂ = 1 であるのは，そのすべてが帰結を
伴うとき，かつそのときに限る。0である `magnitude:` は，帰結に大きさがないことを述べるので，規範は
それによっては裏付けられない。`severity:` と `on_violation.transition` は，規範を裏付けのあるものに
しない。これらは違反を分類し，契約インスタンスを動かすものであり，どちらも負担者に及ぶものではない。

### 単調性

指標は，名前の付け替えと順序の入れ替えについて不変であり，次のように動く。各補題では，述べていない
ものはすべて同じままであり，指標は前後で定義されているとする。

- **補題1（α̂）。** `information.sharing` に項目を追加しても，共有規範の `shares:` に項目を
  追加しても，共有規範を追加しても，α̂は下がらない。*証明。* 組の集合は変わらず，与えられていた組は
  すべて，引き続き与えられている。
- **補題2（β̂）。** 負担者が決定権者である権能を追加しても，β̂は下がらない。負担者が他の者である権能を
  追加しても，β̂は上がらない。*証明。* n 個の権能のうち k 個が集中して保持されているとすると，
  k ≤ n であるので，k/n ≤ (k + 1)/(n + 1) かつ k/(n + 1) ≤ k/n である。
- **補題3（λ̂）。** 帰結を持たなかった義務または禁止に帰結を与えると，λ̂は 1/|N| だけ上がる。
  裏付けのある規範を追加しても，λ̂は下がらず，裏付けのない規範を追加しても，λ̂は上がらない。
  *証明。* N の規範のうちの裏付けのある規範について，補題2と同様である。

### 指標が捉えないもの

- α̂が数えるのは，共有する資格と義務である。運用において当事者が何を観測するかではなく，情報の品質や
  遅延でもない。1つのアクター集合の要素の間の共有（ロボットからロボットへ）は，組ではない。項目は，
  記述者が挙げたものである。
- β̂が数えるのは，権能である。誰が経路を計画するかのように，制度上の行為でない決定は，規範ではなく，
  数えない。すべての権能は，その効果が何であっても，同じ重みを持つ。
- λ̂が述べるのは，帰結を伴う規範がいくつあるかであり，帰結がどれほど大きいかや，どれほど確実に
  適用されるかではない。これは被覆の尺度である。インセンティブの大きさは，`magnitude:` とλが
  合わせて表す（J.7）。5.4.2節は，λを，端点における統治の種類によって説明し，付録Fは，λを制裁の
  尺度として読む。λ̂は前者の読み方を根拠付け，J.7は後者を用いる。
- どの指標も，振る舞いについては何も述べない。共有を増やすこと，あるいはインセンティブを強くすることが
  性質を改善するかどうかは，付録Hと付録Iのモデルに対する問いである。

## J.5 宣言されたパラメータとの関係

`alpha`，`beta`，`lambda` を宣言する契約について，処理系は，対応する指標を計算し，両者とその差を
報告する（J-5）。規則は，3種類の不一致を区別する。

**宣言された端点に規範が矛盾する：誤り。** 5.4.2節の端点は，全称的な言明である（「情報非共有」，
「単一アクターが全決定」）。同じ契約の構成要素がその言明の反例であるとき，契約は自己矛盾しており，
処理系はその構成要素を名指すことができる。これらの場合は誤りである（J-6）。

| 宣言 | 矛盾するもの |
| --- | --- |
| `alpha: 0` | 与えられている組。項目または共有規範が，起点以外の当事者に項目を与えている |
| `beta: 1` | 負担者が決定権者でない権能 |
| `beta: 0` | 負担者が決定権者である権能 |

**宣言された端点に支えがない：警告。** 与えられていない組があるのに `alpha: 1` であることは，矛盾では
ない。ある当事者に項目を与える規範がないことは，その当事者がそれを持たないことを示さないからである。
処理系は，警告し，与えられていない組を列挙することが望ましい（J-7）。

**中間の値が指標から遠い：警告。** αとβについて，処理系は，宣言値と指標の差が契約の許容差を
超えるとき，警告することが望ましい（J-7）。許容差の既定値は0.25である。指標は粗く，規範の少ない契約では，
指標が取り得る値が少ない（権能が2つであれば，β̂は 0，1/2，1 のいずれかである）。より大きな差を
受け入れる記述者は，それを `grounding.tolerance` で述べる。

**λは許容差では比べない。** λ̂は被覆を測り，宣言されたλは，J.7で制裁の尺度として用いる。
どの規範にも軽い制裁がある契約は，λ̂ = 1 で，λが小さく，整合している。処理系は，λ，λ̂，および
その差を報告し，次の2つの場合にだけ警告することが望ましい（J-8）。`lambda` が0より大きいのに
λ̂ = 0 である場合。このとき，λには，契約の規範の中に調整する対象がない。および，契約のある規範が
0より大きい大きさを持つのに `lambda: 0` である場合。このとき，宣言された大きさは効果を持たない。

**契約の版。** 契約の2つの版を比べる処理系（F.6）は，宣言値とその指標が逆の向きに動くとき，
警告することが望ましい（J-13）。たとえば，改正がロボットに権能を与える一方で，`beta` を上げる
場合である。

## J.6 付録Hと付録Iのモデルにおけるパラメータ

**現状。** モデルのパラメータは，`from: "C.alpha"`，`"C.beta"`，`"C.lambda"` によって宣言値に
束縛する（H.3）。これにより，契約とモデルが同じ数を用いる。その数がモデルの中で何をするかは，
記述者が書く。[H.12](./appendix-h-stochastic.md)では，βは決定が集中的に行われる確率であり，αは
集中的な計画の品質に掛かる。どちらの付録も，これらの式を契約から導出せず，本付録も導出しない。

**本付録がαとβについて加えるもの。** 契約の規範は，束縛したパラメータが宣言値を持つ設計を記述する。
別の値を割り当てるモードは，動作モード（H.6）を記述するが，ファイルはそのモードに固有の規範を
持たない。そこで，処理系は，どの設計においても，`C.alpha` または `C.beta` に束縛したパラメータの
固定値を C の指標と比べ，両者の差が許容差を超える設計について，警告ではなく，情報レベルの診断を
出すことが望ましい（J-9）。H.12では，これは，契約の規範が仮にすべての権能をディスパッチャに与えて
いるならば，その規範が記述するのはモード CENTRALIZED であって DISTRIBUTED ではないことを，
読み手に伝えることになる。

**未解決のまま残るもの。** モードは固有の規範を持たないので，モードがαとβに割り当てる値を指標に
照らして検査することはできず，βによるモードの順序を，その規範の順序と比べることもできない。
共有規範または権能からモデルの確率を導出すること，および，ゲームにおいてプレイヤーが観測するものと
してのα（RD-7.3）は，定義しない。

## J.7 λ：規範の制裁から利得の項へ

戦略モデル（[付録I](./appendix-i-games.md)）では，利得の項は，重みを与える代わりに，その項が表す
制裁または報酬を持つ規範を名指してよい。

```yaml
- { reward: shortcuts, sanction_of: "DELIVERY.no_shortcut" }
```

項が名指す規範 `C.n` を n とし，`from: "C.lambda"` で束縛したモデルのパラメータを ℓ とする
（ちょうど1つなければならない。J-10）。この項は `weight:` を持たず，その重みを次のように定義する。

| 項 | 重み |
| --- | --- |
| `sanction_of: "C.n"` | −m · ℓ。m は n の `on_violation.magnitude` |
| `reward_of: "C.n"` | m′ · ℓ。m′ は n の `on_fulfilment.magnitude` |

この項は，それ以外の点ではI.6の項であり，付録Iがそのまま適用される。項の報酬構造は，モデルの中で
制裁がどれだけ頻繁に科されるか，または報酬が支払われるかについての，記述者の言明である。その
累積報酬が，規範の違反，または履行を数える。

**処理系が検査すること（J-10からJ-12）。** 規範が存在し，義務または禁止であり，大きさを宣言している
こと。利得のプレイヤーが規範の負担者を代表すること。1つの規範が多くとも1回だけ表されること。モデルが
C の規範を1つでも表すときは，大きさを持ち，負担者がモデルのプレイヤーである C のどの規範も
表されること。遵守プロファイルが制裁を受けないこと。ファイルは大きさを1回だけ述べるので，大きさと
係数λは，構成によって正しい。**処理系が検査できないこと。** 報酬構造が規範の違反を数えていること。
付録Fは規範を時間付きトレースの上で判定し，付録Hはモデルをステップで評価する。両者の間の変換は
定義されていない。

**答えの形。** σ をプロファイル，D を設計とし，次を仮定する。(i) ℓ は，モデルのどの確率にも，
どの報酬の値にも，`sanction_of:` の項の重み以外のどの重みにも現れない。(ii) σ のもとで，
プレイヤー p のどの `sanction_of:` の項の報酬構造も，期待累積値が0である。このとき，他のすべての
パラメータを固定すると，次が成り立つ。

> **命題。** gain_p は，ℓ の非増加で凸な区分線形関数である。(i) と (ii) がすべてのプレイヤーに
> ついて成り立つならば，D が良定義である ℓ の値のどの区間の上でも，σ が D のε均衡である値の集合は，
> 空であるか，あるしきい値 λ\* について，その区間の ℓ ≥ λ\* である値の全体である。

*証明。* (i) により，確率は ℓ に依存せず，したがってどの期待累積報酬も ℓ に依存しない。p の戦略 τ に
ついて，σ[p↦τ] のもとでの p の利得は A(τ) − ℓ·B(τ) である。ここで B(τ) は，p の `sanction_of:` の
項にわたる，大きさと期待累積報酬の積の和であって負でなく，A(τ) は他の項をまとめたものである。
(ii) により，σ のもとでの利得は定数 A(σ) である。したがって，
gain_p = max over τ of (A(τ) − ℓ·B(τ)) − A(σ) であり，これは有限個の非増加なアフィン関数の最大値で
あって（I.7），連続である。ゆえに，どの逸脱利得も ε 以下である集合は，閉じており，ある値を含めば
それより大きい値をすべて含む。D が停止的であるかどうかは，ℓ に依存しない。∎

この命題は，(i) と (ii) を確立したとき，開いているパラメータが ℓ だけである均衡マップ（I.9）の
セルについて，健全な方法を与える。プロファイルは，a において均衡であれば，セル `[a, b]` の上で
均衡であり，プレイヤーは，b においてその逸脱利得が ε を超えれば，セルの上で逸脱者である。このとき，
一方の端での1回の厳密な評価が，セル全体を認証する。単調性は，標本から推し量ったものではなく，
証明されているからである（H.9）。この命題は，`reward_of:` の項については，一般には成り立たない。
その項の σ のもとでの値は，ℓ とともに増えるからである。

**例。** [I.12](./appendix-i-games.md)のモデルは，2つの拡張を宣言し，契約に規範を追加し，R の
3番目の項の重みを置き換えることによって，規範に結び付けられる。

```yaml
sos:
  name: "RobotDeliveryGame"
  extensions:
    - stochastic: 0.1
    - games: 0.1
    - norms: 0.1
    - grounding: 0.1
  # actors, transitions as in I.12

  contracts:
    - id: DELIVERY
      parties: [DISPATCHER, "ROBOT[*]"]
      information: { alpha: 0.9 }
      authority:   { decision_holder: DISPATCHER, beta: 0.9 }
      incentives:  { lambda: 0.1 }
      norms:
        - id: no_shortcut
          kind: prohibition
          bearer: "ROBOT[i]"
          counterparty: DISPATCHER
          content: "ROBOT[i].handling == Careless"
          on_violation:
            severity: Major
            sanction: "deduction from the delivery fee"
            magnitude: 2

  model:
    # as in I.12, except the payoff of R:
    payoffs:
      - player: R
        until: "settled"
        terms:
          - { reward: fee,       weight: 10 }
          - { reward: effort,    weight: -1 }
          - { reward: shortcuts, sanction_of: "DELIVERY.no_shortcut" }
      - player: D
        until: "settled"
        terms:
          - { reward: fee, weight: 5 }
```

3番目の項の重みは −2·`lambda` であり，I.12で手で書いた重みと同じである。したがって，I.12のどの数値も
変わらない。負担者 `ROBOT[i]` は，R が代表する `"ROBOT[*]"` と同じアクター名を持つ。このモデルでは，
各試行はそれぞれ別の契約インスタンスのもとで行われるので，禁止は試行ごとに1回違反され得る
（F.5は，規範を契約インスタンスごとに1回判定する）。そして，`shortcuts` は手抜きの試行を数える。
条件 (i) と (ii) は成り立つ。`lambda` はこの項の重みにだけ現れ，`comply` は手抜きの試行をしない。
料金を g，労力の費用を c，丁寧な試行が成功する確率を s，`no_shortcut` の大きさを m とすると，
I.12は，s·g ≥ c のとき，次を導く。

> 各設計において，遵守プロファイルがナッシュ均衡であるのは，λ ≥ λ\* であるとき，かつそのときに限る。
> ここで，λ\* = max(0, (c − (s/2)·(g·(1 − s)² + c·(2 − s))) / m) である。

g = 10，c = 1，m = 2 のとき，固定値では，λ\* は CENTRALIZED で 0.150108，DISTRIBUTED で 0.060373
である。宣言値 λ = 0.1 では，遵守は DISTRIBUTED でだけ均衡である。しきい値は，大きさに反比例する。
λ = 0.1 では，CENTRALIZED でも遵守が均衡となるには，大きさが少なくとも 3.002169 でなければならず，
DISTRIBUTED では 1.207466 で足りる。この契約では，λ̂ = 1/1 = 1 であり（ただ1つの禁止に裏付けがある），
α̂とβ̂は未定義である（項目も権能もない）。被覆は完全であり，残る問いは，モデルが答える問い，すなわち，
大きさ m·λ が十分であるかどうかである。

## J.8 静的意味論 {/* #j8-static-semantics */}

本拡張を実装する処理系は，`grounding: 0.1` を宣言しているファイルにおいて，既存の検査に加えて，
次の検査をしなければならない。

- **J-1.** `grounding: 0.1` を宣言するファイルは，`norms: 0.1` も宣言しなければならない。
  そうでない場合，処理系は誤りを報告し，本拡張のキーを解釈しない。
- **J-2.** `grounding.items` のどのキーも，識別子でなければならず，
  [A.11](./appendix-a-syntax.md#a11-reserved-keywords)の予約語であってはならない。その値は，
  アクター名が契約の当事者名であるアクター参照でなければならない。`tolerance:` は，`[0, 1]` の
  数でなければならない。
- **J-3.** `shares:` は，`content:` が `message_event` である義務または許可にだけ許される。
  少なくとも1つの項目を，それぞれ1回だけ列挙しなければならず，どの項目も同じ契約の
  `grounding.items` に宣言されていなければならない。メッセージの受信者が，挙げた項目の起点の
  アクター名を持つとき，また，契約が項目を宣言しているのに，`information.sharing` の項目が
  `grounding.items` に宣言されていない項目を名指すとき，処理系は警告することが望ましい。
- **J-4.** `on_violation.magnitude` と `on_fulfilment.magnitude` は，負でない有限の数でなければ
  ならない。`on_fulfilment:` は，（`on_violation:` と同じく。N-4）義務または禁止にだけ許され，
  `reward:` と `magnitude:` の少なくとも一方を持たなければならない。
- **J-5.** 報告をする処理系は，`norms:` を持つどの契約についても，J.4の定義によって α̂，β̂，λ̂を
  厳密に計算し，各指標を，その2つの個数とともに，または未定義であることをその理由とともに，
  報告しなければならない。契約が宣言し，指標が定義されている `alpha`，`beta`，`lambda` の
  それぞれについて，宣言値，指標，およびその差を報告しなければならない。J-6からJ-9とJ-13の比較は
  厳密である。宣言値は，書かれたとおりの10進小数である（H.2）。
- **J-6.** 契約が `alpha: 0` を宣言し，与えられている組を持つとき，`beta: 1` を宣言し，β̂が
  定義されていて1より小さいとき，または `beta: 0` を宣言し，β̂が定義されていて0より大きいときは，
  誤りである。診断は，宣言値に矛盾する項目または規範を名指さなければならない。
- **J-7.** 契約が `alpha: 1` を宣言し，α̂が定義されていて1より小さいとき，また，宣言された `alpha`
  または `beta` と，定義されている指標との差が契約の許容差を超え，J-6がそのパラメータについて
  誤りを報告しないとき，処理系は警告することが望ましい。
- **J-8.** 契約が0より大きい `lambda` を宣言し，λ̂が定義されていて0に等しいとき，また，
  `lambda: 0` を宣言し，契約のある規範が0より大きい `on_violation.magnitude` または
  `on_fulfilment.magnitude` を持つとき，処理系は警告することが望ましい。
- **J-9.** `stochastic: 0.1` も宣言するファイルでは，どの設計についても，`C.alpha` または
  `C.beta` に束縛され，指標が定義されているどのパラメータについても，その設計のもとでの
  パラメータの固定値と指標との差が C の許容差を超えるとき，処理系は情報レベルの診断を出すことが
  望ましい。
- **J-10.** `sanction_of:` と `reward_of:` は，`stochastic: 0.1` と `games: 0.1` も宣言する
  ファイルにだけ許される。項は，`weight:`，`sanction_of:`，`reward_of:` のうち多くとも1つを
  持たなければならない。値は，文字列 `C.n` でなければならない。ここで `C` は宣言済みの契約であり，
  `n` は，0より大きい `on_violation.magnitude`（`sanction_of:` の場合）または
  `on_fulfilment.magnitude`（`reward_of:` の場合）を持つ，`C` の義務または禁止である。モデルは，
  `from: "C.lambda"` で束縛したパラメータを，ちょうど1つ持たなければならない。利得のプレイヤーは，
  `actors:` に，`n` の負担者のアクター名を持つ参照を挙げていなければならない。1つのモデルの中で，
  1つの規範を，2つ以上の `sanction_of:` が名指してはならず，2つ以上の `reward_of:` が名指しても
  ならない。
- **J-11.** モデルが契約 `C` の規範を名指す項を持つとき，処理系は，0より大きい大きさを持ち，
  負担者があるプレイヤーのアクターのアクター名を持ち，対応するキーを持つどの項も名指していない，
  `C` のどの義務または禁止についても，警告することが望ましい。また，`C.lambda` に束縛した
  パラメータが現れる `weight:` を持つ項についても，警告することが望ましい。そのような項の大きさは，
  規範に照らして検査されないからである。
- **J-12.** モデルを評価する処理系は，どの `sanction_of:` の項とどの設計についても，固定値において，
  遵守プロファイルのもとで，利得の目標までに累積する，項の報酬構造の期待値を報告することが望ましく，
  それが0より大きいときは警告することが望ましい。このとき，遵守として宣言したプロファイルが
  制裁を受ける。
- **J-13.** 契約の2つの版を比べる処理系は，αまたはβについて，宣言値と指標が両方の版で定義されており，
  (x′ − x)·(x̂′ − x̂) が0より小さいとき，警告することが望ましい。ここで，x と x̂ は古い版の
  宣言値と指標，x′ と x̂′ は新しい版のものである。

`alpha`，`beta`，`lambda` が `[0, 1]` にあるというA.4の規則は変わらない。規則N-1からN-12と
I-1からI-11も変わらない。

## J.9 例

以下の契約は，[F.8](./appendix-f-norms.md)の契約に，3つのパラメータのブロック，`grounding:`
ブロック，2つの `shares:` の注記，1つの大きさ，および，ロボットが割当てを断るための権能 `decline` を
加えたものである。F.8がすでに持つキーは省略している。

```yaml
sos:
  name: "RobotDeliveryNorms"
  extensions:
    - sos-dsl: 0.1
    - norms: 0.1
    - grounding: 0.1
  # actors DISPATCHER, ROBOT[1..N], CUSTOMER[1..M] as in F.8

  contracts:
    - id: DELIVERY_SLA
      parties: [DISPATCHER, "ROBOT[*]", "CUSTOMER[*]"]
      authority:   { decision_holder: DISPATCHER, beta: 0.9 }
      information:
        alpha: 0.6
        sharing:
          - "DISPATCHER -> ROBOT[*] : route"
          - "ROBOT[*] -> DISPATCHER : status"
          - "DISPATCHER -> CUSTOMER[*] : status"
      incentives:  { lambda: 0.5 }
      grounding:
        items:
          route:   DISPATCHER
          status:  "ROBOT[*]"
          battery: "ROBOT[*]"
          failure: "ROBOT[*]"
      # assume, guarantee, lifecycle, counts_as as in F.8

      norms:
        - id: acknowledge              # obligation of ROBOT[i], as in F.8
          on_violation: { severity: Major, reparation: report_failure }
        - id: report_failure           # obligation of ROBOT[i], as in F.8
          content: "ROBOT[i] -> DISPATCHER : failure_report"
          shares: [failure]
          on_violation: { severity: Critical, transition: Violated }
        - id: no_low_battery_driving   # prohibition of ROBOT[i], as in F.8
          on_violation:
            severity: Critical
            sanction: "removed from the dispatch pool for one period"
            magnitude: 4
        - id: may_return_to_charge     # permission of ROBOT[i], as in F.8
          content: "ROBOT[i] -> DISPATCHER : charging_request"
          shares: [battery]
        - id: reassign                 # power of DISPATCHER, as in F.8
        - id: decline
          kind: power
          bearer: "ROBOT[i]"
          content: "ROBOT[i] -> DISPATCHER : decline"
          effects:
            discharge: [acknowledge]
```

**α̂。** 当事者名は DISPATCHER，ROBOT，CUSTOMER であり，項目は4つである。各項目には，起点以外の
当事者が2つあるので，組は8つである。

| 項目（起点） | DISPATCHER | ROBOT | CUSTOMER |
| --- | --- | --- | --- |
| `route`（DISPATCHER） | 起点 | 与えられている：`sharing` | 与えられていない |
| `status`（ROBOT） | 与えられている：`sharing` | 起点 | 与えられている：`sharing` |
| `battery`（ROBOT） | 与えられている：`may_return_to_charge` | 起点 | 与えられていない |
| `failure`（ROBOT） | 与えられている：`report_failure` | 起点 | 与えられていない |

5つの組が与えられているので，α̂ = 5/8 = 0.625 である。宣言された `alpha: 0.6` との差は 0.025 であり，
許容差の中にある。

**β̂。** 契約は2つの権能を持つ。`reassign` は，決定権者である DISPATCHER が保持する。`decline` は，
`ROBOT[i]` が保持する。β̂ = 1/2 = 0.5 である。宣言された `beta: 0.9` との差は 0.4 であり，許容差
0.25 を超えるので，処理系は警告する（J-7）。契約は，ほぼ集中した権限を宣言しているが，決定点の半分は
ロボットにある。`beta: 1` であれば，ファイルは誤りであり（J-6），診断は `decline` を名指す。

**λ̂。** 契約は3つの義務と禁止を持つ。`acknowledge` は，その反義務の規範によって裏付けられ，
`no_low_battery_driving` は，大きさ4の制裁によって裏付けられる。`report_failure` は，重大度と
ライフサイクルの遷移だけを持ち，裏付けがない。λ̂ = 2/3 = 0.666667 である。宣言された
`lambda: 0.5` は0より大きく，λ̂は0でないので，J-8は警告を出さない。差 0.166667 は報告する。

補題2により，`decline` を除く改正は β̂ を1に上げ，補題3により，`report_failure` に制裁を与える改正は
λ̂ を1に上げる。

## J.10 中間表現（IR）への追加

`institution.contracts` の下の各契約に，フィールド `grounding` を追加し，F.9の各規範に，4つの
フィールドを追加する。J.9の例では，次のとおりである。

```jsonc
{
  "grounding": {
    "items": { "route": "DISPATCHER", "status": "ROBOT[*]", "battery": "ROBOT[*]", "failure": "ROBOT[*]" },
    "tolerance": 0.25,
    "indices": {
      "alpha":  { "given": 5,  "pairs": 8 },
      "beta":   { "central": 1, "powers": 2 },
      "lambda": { "backed": 2, "norms": 3 }
    }
  },
  "norms": [
    { "id": "no_low_battery_driving",
      // ... the fields of F.9
      "shares": [],
      "on_violation_magnitude": 4,
      "on_fulfilment_reward": null,
      "on_fulfilment_magnitude": null }
  ]
}
```

`grounding` は，本拡張を宣言していないとき `null` である。契約が `grounding:` ブロックを持たないとき，
`items` は空のマッピングであり，`tolerance` は既定値である。指標は，未定義であるとき `null` である。
そうでないときは，厳密な比を作れるように，2つの個数を，分子を先にして与える。規範の4つのフィールドは，
本拡張を宣言しているときにだけ書く。大きさは，ないとき `null` である。

[I.13](./appendix-i-games.md)のIRの利得の項に，フィールド `sanction_of` と `reward_of`
（文字列 `C.n` または `null`）を追加する。これらは，本拡張を宣言しているときにだけ書く。そのどちらかを
持つ項では，`weight` は，定義された重みのテキスト `-m * p` または `m * p` である。ここで m は，
往復変換で戻る最短の10進小数として書いた大きさであり，p は，`C.lambda` に束縛したパラメータの
`id` である（J.7では `"-2 * lambda"`）。個数を除くJ-5の結果と，診断は，IRに含めない。

## J.12 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。本拡張は，付録Fの
どの判定も，付録Hと付録Iのどの結果も変えない。`sanction_of:` を持つ項は，定義された重みを持つ
I.6の項である。

`grounding: 0.1` を宣言せずに `grounding:`，`shares:`，`on_fulfilment:`，
`on_violation.magnitude`，`sanction_of:`，`reward_of:` を用いるファイルは，本付録に適合しない。
本拡張を実装する処理系は，そのようなファイルではこれらのキーを解釈せず，宣言されていない拡張の
キーとして報告することが望ましい。指標は計算せず，`sanction_of:` または `reward_of:` を持つ
利得の項は，I-7により誤りである。したがって，そのような項を，既定値の重みを持つ項として読むことは
決してない。`norms: 0.1` なしに `grounding: 0.1` を宣言するファイルには，J-1の誤りを出す。
本拡張を実装していない処理系は，本拡張を用いるファイルを拒否してはならない。ファイルごとに1つの
情報レベルの診断を出すことが望ましい。

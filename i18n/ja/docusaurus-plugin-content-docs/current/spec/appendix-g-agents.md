# 付録G. エージェント統治拡張（agents 0.1）

本付録は，CADLの**エージェント統治拡張**を規定する。この拡張は，
規範拡張（[付録F](./appendix-f-norms.md)）を前提とし，
`actor_def`（[A.3](./appendix-a-syntax.md#a3-context-actors-metrics)）にキー `agent:` を，
`contract_def`（[A.4](./appendix-a-syntax.md#a4-contracts-institution-layer)）に
キー `enforcement:` と `delegations:` を，`norm_def`（F.3）にキー `on_denied:` を追加する。
これにより，契約の許可と禁止は，判定点（enforcement point）に届くすべてのメッセージについて，
`allow`，`deny`，`escalate` の3つの**決定**のいずれかを定める。
決定はメッセージが効果を生じる前に行い，メッセージと規範インスタンスの状態の関数である。
そのどの部分も，エージェントの判断には委ねない。

コア言語は，これらのブロックを必須としない。
本拡張を実装していないCADL準拠の処理系は，新しいキーを理由にファイルを
拒否してはならない。新しいキーを構文上は受理し，*情報レベル*の診断を出すことが望ましい。

拡張の名前は `agents` であり，本付録はバージョン `0.1` を記述する。
本拡張は `norms: 0.1` を必要とする。強制されるのは規範だからである。
本拡張を用いるファイルは，`extensions:`
（[A.2](./appendix-a-syntax.md#a2-top-level-structure)）で両方を宣言しなければならない。
宣言せずに用いた場合に処理系がどう扱うかはG.14で述べる。

```yaml
sos:
  ...
  extensions:
    - norms: 0.1
    - agents: 0.1
```

## G.1 動機

LLMに基づくエージェントはSoSの構成システムになりつつあり，それらをつなぐプロトコルの
標準化が進んでいる
[[MCP, 2026-07-28]](./appendix-b-references.md)
[[Linux Foundation, A2A 2025]](./appendix-b-references.md)。
強制の方法としては，ツール呼び出しの境界での決定的な検査が広く採用されつつある。
たとえば，Amazon Bedrock AgentCore Policyは，Cedarの方針でツール呼び出しを認可し，
既定で拒否する
[[AWS, AgentCore Policy]](./appendix-b-references.md)。
欠けているのは，組織の契約（誰が，誰の権限で，何をしてよいか）からそのような検査を導く
手段である。バージョン0.1では，[9.8節](./09-research.md)の研究方向のうち次の4つに，最初の段階として取り組む。

1. **RD-8.1，契約から境界方針へのコンパイル。** CADLのファイルには，どのアクターが
   エージェントであるか，どのメッセージがツール呼び出しであるか，生成した方針が何を
   決定しなければならないかを述べるものがない（G.4，G.5，G.10）。
2. **RD-8.2，委任された権限の来歴。** 局所的な状態だけを見る検査では，ある行為が，
   元の権限者に認められていない委任を経て呼び出し元に届いたものかどうかが分からない。
   G.7は，委任された許可に来歴連鎖（provenance chain）を与える。
3. **RD-8.3，阻止された行為の後の回復。** あるプレプリントのレビューは，安全でない行為の
   94%を阻止しても，安全かつ正しく完了したタスクが5%未満にとどまったという研究を報告している
   [[Dantas+, arXiv 2026]](./appendix-b-references.md)。G.6は，名指したアクターへの
   エスカレーションと，代替のメッセージを定義する。
4. **RD-8.4の一部，監査。** コミュニティの統治は，プロトコルの上に欠けている層であることが
   指摘されている
   [[Kang & Diponegoro, arXiv 2026]](./appendix-b-references.md)。また，追記専用の監査ログを
   伴って強制される統治グラフは，プロンプトだけの「憲法」ではできなかったLLMエージェントの
   制約を実現した
   [[Bracale Syrnikov+, arXiv 2026]](./appendix-b-references.md)。G.8は，監査記録の形式を
   定める。

**バージョン0.1の範囲。** 本拡張は意図して小さくしている。構成員資格，投票，異議の保存のための
基本要素を持たない（RD-8.4のそれ以外の部分は，後のバージョンの課題として残す）。
計画や複数のエージェントの相互作用を検証しない（RD-8.5）。どの決定も1つのメッセージに
関するものだからである。いかなる規制の条項もCADLに対応付けない。認証を扱わない。
メッセージの送信者と受信者は与えられたものとする。境界では，内容がメッセージである規範だけを
考慮し，メッセージの送信者，受信者，名前だけを考慮して，引数は考慮しない。

## G.2 概念

| 概念 | agents 0.1での意味 |
| --- | --- |
| **ツール呼び出し（tool call）** | 受信者が種別 `tool_server` のアクターであり，名前がそのアクターの `tools:` の1つであるメッセージ。 |
| **強制される契約（enforced contract）** | キー `enforcement:` を持つ契約。強制される契約だけが決定に加わる。 |
| **判定点（enforcement point）** | ファイルのすべての強制される契約にわたって，メッセージに対する決定を行う1つの論理的な場所。 |
| **決定（decision）** | `allow`，`deny`，`escalate` のいずれか。メッセージが効果を生じる前に，G.5の決定関数が1つのメッセージについて計算する。 |
| **根拠（ground）** | 決定関数において，メッセージに適用される禁止。保留については，根拠を契約インスタンスごとに数える。**保留の根拠**は，ある禁止が適用される1つの契約インスタンスにおける，その禁止である（G.6）。 |
| **保留（hold）** | 決定が `escalate` であるメッセージの記録。メッセージは，保留が最終状態に達するまで留め置かれる（G.6）。 |
| **派生インスタンス（derived instance）** | 被委任者が保持する許可（G.7）。**来歴連鎖**を伴う。来歴連鎖は，元の許可の負担者から保持者までのアクターの列であり，委任1回につき1つのリンクを持つ。 |
| **監査記録（audit record）** | 判定点が1つの決定について記録するもの（G.8）。 |

規範，規範インスタンス，契約インスタンス，制度的事象，観測は，
[付録F](./appendix-f-norms.md)の意味で用いる。

## G.3 構文（A.3，A.4，F.3へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`hyphen_name`，
`actor_ref`，`int_literal`，`duration_lit` は付録Aで，`message_event` は
[E.3](./appendix-e-sos-dsl.md)で，`norm_event` は
[F.3](./appendix-f-norms.md)で定義している。

```ebnf
actor_def         = ... , [ "agent:" , agent_binding ] ;
agent_binding     = "kind:" , agent_kind ,
                    [ "protocol:" , hyphen_name ] ,
                    [ "tools:"    , { "-" , identifier } ] ;
agent_kind        = "llm_agent" | "tool_server" | "human" | "service" ;

contract_def      = ... ,
                    [ "enforcement:" , enforcement_block ] ,
                    [ "delegations:" , { "-" , delegation_def } ] ;
enforcement_block = [ "default:" , ( "deny" | "allow" ) ] ,
                    [ "point:"   , ( "caller" | "receiver" | "gateway" ) ] ;

norm_def          = ... , [ "on_denied:" , denial_recovery ] ;
denial_recovery   = [ "escalate_to:" , actor_ref ] ,
                    [ "timeout:"     , duration_lit ] ,
                    [ "fallback:"    , message_event ] ,   (* string *)
                    [ "notify:"      , actor_ref ] ;

delegation_def    = "norm:"  , identifier ,
                    "to:"    , { "-" , actor_ref } ,
                    "grant:" , identifier ,
                    [ "revoke:"    , identifier ] ,
                    [ "max_depth:" , int_literal ] ,
                    [ "until:"     , norm_event ] ;        (* string *)
```

- `agent:` を持たないアクターには，エージェントの種別がない。種別 `tool_server` は
  ツール呼び出しを定義する（G.4）。`llm_agent`，`human`，`service` は，そのうちの1つを
  名指す静的な規則（G-8）と，ジェネレータによる利用のほかには意味を持たない。
  `protocol:`（`mcp`，`a2a`，またはその他の名前）には既定値がなく，決定に影響しない。
  範囲付きで宣言したアクターの `agent:` は，その集合のすべてのアクターに適用される。
- ツールの名前は `identifier` である。`message_event` のメッセージ名だからである。
  プロトコル上の名前が識別子でない場合は，`codegen:` の項目の `mappings:`（A.9）が
  両者を関係付ける。
- 契約は，キー `enforcement:` を持つときに**強制される**。空のマッピングまたはnull値
  （`enforcement: {}`，またはキーだけ）は，「すべて既定値で強制される」ことを意味する。
  `default:` を省略したとき，既定の決定は，ツール呼び出しについては `deny`，それ以外の
  すべてのメッセージについては `allow` である。`default:` を与えたときは，その値を両方に
  適用する（G.5）。
- `point:`（既定値 `gateway`）は，ジェネレータのための配備上のヒントであり，決定に影響しない。
  配備がどうであれ，論理的な判定点は1つである。統治されるすべてのメッセージは，
  すべての強制される契約にわたって，1つの状態の上で，1回決定される。
- `on_denied:` は禁止にだけ書ける。`timeout:` には既定値がない。`fallback:` と `notify:` は
  データである。決定の結果（G.10）に写されるだけで，それ以外の効果を持たない。
- `max_depth:` の既定値は `1` である。`revoke:` がなければ，委任をメッセージによって
  取り消すことはできない。`until:` がなければ，委任はそれ自身の終わりを持たない。

追加するキーをブロックごとに示す。アクターには `agent`（`kind` `protocol` `tools`）を，
契約には `enforcement`（`default` `point`）と `delegations`（`norm`
`to` `grant` `revoke` `max_depth` `until`）を，規範には `on_denied`
（`escalate_to` `timeout` `fallback` `notify`）を追加する。強制される契約では，
名前 `approval` と `rejection` をG.6の制度的事象のために予約する。

## G.4 メッセージとツール呼び出し

**メッセージ**は，それぞれ1つの具体的なアクターである送信者と受信者，名前，引数を持つ。
受信者が `agent.kind: tool_server` を持ち，名前がそのアクターの `tools:` の1つであるとき，
メッセージは**ツール呼び出し**である。ツールサーバへの，それ以外の名前を持つメッセージは，
**未宣言のツール**の呼び出しである。それ以外のすべてのメッセージは**通常のメッセージ**である。
バージョン0.1では，ツールサーバが返す結果は別個のメッセージではない。

境界では，`message_event` `S -> R : e` を，送信者，受信者，メッセージ名（`e` の識別子，
または呼び出しの名前）の3つの成分についてメッセージと**照合**する。
バージョン0.1では，`e` に書いた引数は考慮しない。
`delete_file` と `delete_file(path)` は同じメッセージに一致する。各成分は，真，偽，
**不明**のいずれかであり，照合の結果はそれらのクリーネの連言である。いずれかの成分が偽で
あれば偽，そうでなく，いずれかが不明であれば不明，それ以外は真である。アクター参照は，
次のように具体的なアクターに一致する。

| 参照 | 一致するもの |
| --- | --- |
| `A` | 添字なしで宣言したアクター `A`。添字付きの要素 `A[k]` には一致しない |
| `A[3]`，`A[*]`，`A[1..3]` | `A[3]`。集合 `A` のすべての要素。`A[1]` から `A[3]` まで |
| `A[1..N]`（記号の上限） | 集合 `A` のすべての要素。上下限は比較しない |
| `A[i]` | 具体的なアクターが `A` の要素でないときは偽。そうでないとき，契約インスタンスが `i` を `v` に束縛していればちょうど `A[v]` に一致し，`i` に値を束縛していなければ**不明**である。 |

この表は[F.3](./appendix-f-norms.md)の表と同じである。F.3の表は，規範エンジンが
トレースの事象に用いる。違いは2つある。第1に，F.3はメッセージ事象に書かれた引数を
メッセージの引数と比較するが，境界は引数を考慮しない。第2に，契約インスタンスが `i` に
値を束縛していないとき，F.3では `A[i]` は集合のすべての要素に一致するが，境界では
その一致は不明であり，フェイルクローズで解決する（G.5）。第2の違いは，強制される契約の
事象のうち規範エンジンが評価するものと，権能の行為者にも当てはまる
（G.5の「不明な発生」）。

`A` を範囲付きで宣言しており，`k` がその整数の上下限の内にあるとき，`A[k]` は集合 `A` の
**要素**である（`A[1..3]` と宣言した集合は `A[7]` を含まない）。宣言した上限が記号であるときは，
下限以上のすべての添字が要素である。

## G.5 境界での規範の強制

### インスタンス，統治されるメッセージ，決定に加わる規範

ホストが生成するインスタンスを持たない強制される契約では，F.5の単一のインスタンスは，
最初の観測からではなく，判定点の開始時から存在する。F.5へのこの追加によって，
最初のメッセージを決定できる。ホストアプリケーションがインスタンスを生成し，終わらせる場合，
動作中のインスタンスは，ホストアプリケーションが生成し，まだ終わらせていないものである。

強制される契約がメッセージ `m` を**統治する**かどうかは，どのインスタンスを考慮するよりも前に
決める。したがって，`parties:` には束縛を適用しない。当事者 `A[i]` または `A[*]` は，
`A` のすべての要素に一致する。

- 受信者がツールサーバであるメッセージ（ツール呼び出し，または未宣言のツールの呼び出し）は，
  そのツールサーバを当事者とするすべての強制される契約が統治する。
  送信者が何であるかを問わない。当事者でも，当事者でない宣言済みのアクターでも，
  未宣言のアクターでもよい。したがって，以下の段階2から4は部外者にも適用される。
  ツールサーバが複数の強制される契約の当事者である場合，そのそれぞれがそのサーバへのすべての呼び出しを
  統治し，そのうちの1つが許さない呼び出しは拒否される（段階4）。ツールサーバを共有する契約は，
  意図する呼び出しをそれぞれが許可する必要がある。
- 通常のメッセージは，その送信者と受信者がそれぞれ当事者に一致するとき，
  強制される契約が統治する。

その場合も，規範は，その負担者または有効な保持者（後述）にだけ適用される。
判定点は，メッセージを届いた順に1つずつ，それぞれ，それより前のすべての観測が残した状態の
上で決定する。決定は決定的でなければならない。決定は，それより後の観測に決して依存しない。
これは，述語の中に単独で現れる名前を量として読むか記号的な値として読むか（F.5）にも当てはまる。
量の名前を与えられた判定点は，最初からそれらを用いる。与えられていない判定点は，
名前に値を与える最初の観測から，その名前を量として扱い，それより前には扱わない。

`content:` が `message_event` である許可または禁止だけが，決定に加わる。
内容が，述語，時相演算子を含む `tpredicate`，または制度的事象である許可または禁止は，
バージョン0.1では境界で効果を持たず，付録Fのもとで監視されるだけである。
義務と権能は決定に加わらない。義務が求めるメッセージや，権能を行使するメッセージは，
他のメッセージと同じように決定され，F.5の7は変わらない。

規範インスタンスは，**境界で効力を持つ**（in force at the boundary）間，決定に加わる。
このフラグはF.5への追加である。F.5の状態と判定は変わらない。

- 許可は，そのインスタンスが `active` である間，効力を持つ。
- 禁止は，そのインスタンスが `active` である間，効力を持つ。インスタンスが `violated` に
  なっても，禁止は効力を持ち続ける。違反は1回報告されるが（F.5），禁止を解くことはない。
  その後は，次のうち最初に起こるものまで効力を持ち続ける。その `deadline:` の期間が閉じたはずの
  時刻，その `until:` が起こること，それを名指す権能の `discharge` の効果，
  それが引き継がれない改正（F.6），契約インスタンスの終了である。それを名指す `suspend` と
  `resume` の効果は，違反の後であっても，禁止の効力を失わせ，また戻す。

効力を持つ規範インスタンスは，その内容が `m` に一致し（G.4），`m` の送信者がその負担者で
あるとき，`m` に**適用される**。許可の派生インスタンス（G.7）は，それが有効であり，
保持者を送信者として内容が一致するとき，適用される。照合の結果が不明であるとき，または
判定点がフラグを持たないとき，結果は不明である。不明は**フェイルクローズ**（fail-closed）で
解決する。不明の禁止は適用され，不明の許可は適用されない。

**データの欠落。** ある量がまだ値を持たないためにフラグを決められないときも，判定点は
フラグを持たない。これは，`inactive` である禁止の `trigger:` と，`active` である許可の
`until:` に関わり，2つの形がある。直接の形では，その `trigger:` または `until:` が述語であり，
それが未定義（F.5）である間，フラグは不明である。制度的事象を経る形では，それが，
`counts_as:` 規則が述語の `when:` から作る事象であり，そのような規則の `when:` または `if:` が
未定義である間，フラグは不明である。その事象を作る規則が複数あるときは，そのうちの1つが
未定義である間，不明である。開いた定義域（F.5の「限量子と集約」）の上の限量述語や集約で，
既知のメンバーが値を決めないものは，この意味で未定義である。まだ名指されていないメンバーが
欠けたデータである。したがって，定義域が開いている間，`trigger:` が `exists x in A: p` である
禁止は常に適用される。既知のメンバーが `p` を真にするまではデータの欠落として，それ以後は
効力を持つ間，適用される。効力は，その `until:` によって，または上のG.5が述べるほかの事由によって
終わる。`until:` が `for all x in A: p` である許可は，既知のメンバーが
`p` を偽にしている間だけ適用される。そのような述語が境界を左右する場合，契約インスタンスは
集合の境界に値を与えることが望ましい（F.5）。不明の禁止は適用され，不明の許可は適用されない。
何も固定されない。規範インスタンスの状態と判定はF.5のとおりであり，F.5では未定義の述語は
起こらない。述語が値を持てば，フラグはただちに状態に従うものに戻る。2つの場合は，
F.5がすでに止めるので，規則を必要としない。未定義の `trigger:` は許可を発動させず，
未定義の `until:` は禁止を終わらせない。処理系は，この理由で不明なフラグに基づいて
メッセージを決定するとき，警告することが望ましい。開始時の帰結は意図したものである。
そのような述語の量が最初の値を持つ前に届いたメッセージは，拒否またはエスカレーションされる。

次の場合は対象にならない。メッセージの `when:` と `if:` を持つ規則は，そのメッセージの
時点で事象を作るか，決して作らないかのどちらかである。`if:` が未定義である間にメッセージが
届くと，事象は作られない（F.5）。事象がメッセージを通すものであれば，これはメッセージを止める結果になる。
しかし，事象が禁止に効力を持たせるもの，または許可を終わらせるものであれば，境界は止めない。
そして，F.5にない状態を作り出さないかぎり，後からフラグを正せる時点もない。G-19は
そのような契約について警告し，処理系は，そのようなメッセージを観測したとき，警告することが
望ましい。

**不明な発生。** G-18は，強制される契約のすべての添字変数が当事者の添字であることを求め，
契約インスタンスは，その当事者の添字を束縛する（F.2）。インスタンスを自ら作る処理系は，
`parties:` のすべての添字変数を束縛しない強制される契約のインスタンスを，拒否しなければ
ならない。したがって，適合する実行では，束縛されない添字はない。次の規則は，それでも
そのようなインスタンスを渡された処理系のための，予備の規則である。強制される契約の事象の
発生，その述語の値，または行為の行為者が誰であるかが，契約インスタンスが束縛しない添字に
依存するとき，
それは不明であり，不明は，その発生が何をするかに応じてフェイルクローズで解決する。
不明な発生は，メッセージを通す効果を決して持たず（許可を発動も再開もさせず，禁止を終了も
停止も解除もさせず，制度的事象を作らず，権能を行使させず，義務を履行させない），
止める効果を常に持つ（禁止を発動させ，許可または派生インスタンスを終わらせる）。
「常に止める」には例外が1つある。権能は，定まった当事者の行為である。そのため，
不明な行為者は，権能の効果が止めるものである場合（禁止を発動させる，許可を停止または
解除する）にも，権能を行使しない。この例外は，束縛のないインスタンスを拒否する処理系では
生じない。処理系は警告することが望ましい。付与と取消しのメッセージは添字変数を名指さず
（G-11，G-12），不明になることはない。

インスタンスを拒否するという要求は，契約インスタンスを作る処理系に対するものである。
G.10の方針の入力は，呼び出し側が与えるインスタンスの記述であり，何も束縛しない
インスタンスを記述してよい。フィールド `instances` がないときが，その場合である。
そのとき，決定関数は，その添字に依存するすべての照合を不明とし（G.4），上のとおり
フェイルクローズで解決する。両者は矛盾しない。そのような入力に対する決定は定義されており，
適合するランタイムはそのような入力を作らない。

### 決定関数

メッセージ `m` について，次の段階が，この順に**結果**（フィールドはG.10）を与える。

1. **統治されない。** `m` を統治する強制される契約がなければ，`allow`，理由 `ungoverned`。
   本付録は，そのようなメッセージを制限しない。
2. **未宣言のツール。** `m` が未宣言のツールの呼び出しであれば，`deny`，
   理由 `undeclared_tool`。
3. **契約ごと。** 統治する各契約 *C* は，その動作中のすべてのインスタンスにわたって
   決定する。
   1. *C* に動作中のインスタンスがなければ，`m` がツール呼び出しであるときは `deny`，
      理由 `no_instance`。そうでないときは段階3.4のとおり。
   2. *C* の禁止が `m` に適用されれば，それらが**根拠**であり，理由は `prohibition` である。
      すべての根拠が `on_denied.escalate_to` を持ち，すべてが同じアクターを名指し，
      そのアクターが `m` の送信者でないとき，*C* は `escalate` と決定する。
      そうでなければ `deny` と決定する。`escalate_to: A[i]` は，根拠が適用される
      各インスタンスの束縛で解決する。束縛されていない添字，またはインスタンスによって
      異なるアクターは，`deny` を与える。
   3. そうでなく，*C* の許可が，元のものであれ派生したものであれ，`m` に適用されれば，
      `allow`，理由 `permission`。
   4. そうでなければ，*C* の `default:`，またはそれを省略したときは，`m` がツール呼び出しで
      あれば `deny`，そうでなければ `allow`。理由 `default`。
4. **結合（拒否優先，deny overrides）。** いずれかの契約が `deny` と決定すれば，
   決定は `deny` である。そうでなく，いずれかの契約が `escalate` と決定すれば，
   `escalate` と決定したすべての契約が同じアクターを名指すときは決定は `escalate` であり，
   そうでないときは `deny` である（保留の承認者は1人である）。それ以外は `allow` である。

**決定契約**（determining contracts）は，`deny` と決定した契約である。それがなければ
`escalate` と決定した契約であり，それもなければ統治するすべての契約である。
結果の理由は，`deny` と `escalate` については，`no_instance`，`prohibition`，`default` の
うち，決定契約が持つ最初のものである。`allow` については，いずれかの契約が `permission` を
持てば `permission`，そうでなければ `default` である。
結果は，決定契約の根拠または適用される許可を列挙する。また，理由が `prohibition` で
あるときは常に（`escalate` だけでなく `deny` についても），それらの根拠の `fallback` と
`notify`，およびそれらのうち最小の `timeout:` を列挙する。

以上から，次のことが言える。1つの契約の中では禁止が許可に優先する（N-12は引き続き警告する）。
2つの強制される契約が統治するメッセージは，両方に許されなければならない。
`escalate_to:` のない禁止は決してエスカレーションされない。アクターは自分自身のメッセージを
承認できない。

既定値がメッセージの種類によって異なるのには理由がある。ツールは列挙されており，
ツール呼び出しは契約の外に作用する。そのため，既定で拒否する方針をツールごとにレビューできる。
これはG.1に挙げた強制の既定値でもある。通常のメッセージには，プロトコル，ライフサイクル，
発動条件が依存する調整のメッセージが含まれる。norms 0.1のために書いた契約は，それらに対する
許可を持たないため，`deny` ではそれらがすべて止まってしまう。`default: deny` を指定すれば，
それらも既定で拒否する。

### 決定がトレースに与える効果

- **`allow`。** メッセージは効果を生じ，それを統治する強制される契約のインスタンスにとって，
  決定の時刻を時刻印とする観測になる。強制される契約のインスタンスは，その契約が統治する
  メッセージだけを観測する。どの強制される契約も統治しないメッセージ（段階1）は，
  どの強制される契約の観測にもならず，ある強制される契約が統治するメッセージは，
  それを統治しない別の強制される契約の観測にならない。したがって，メッセージは，
  強制される契約によって決定されることなしに，その契約の規範を発動させることも，
  終わらせることも，履行させることもなく，その契約の中に制度的事象を作ることもない。
  このことから，強制される契約のメッセージ事象のうち，送信者または受信者が当事者でないものは，
  決して起こらないことになる。そのような `trigger:` を持つ禁止は決して効力を持たず，
  そのような `until:` を持つ許可は決して終わらない。そのため，G-17はそのような事象を
  エラーにする。強制されない契約については，F.5をそのまま適用する。
- **`deny`。** メッセージは効果を生じず，観測にならない。規範を発動させず，
  制度的事象を作らず，ライフサイクル遷移を起こさず，義務を履行させず，禁止に違反しない。
  判定点は，結果を送信者に返すことが望ましい。
- **`escalate`。** メッセージは保留される（G.6）。保留されている間は観測にならない。

付録Fの期限は，メッセージが拒否または保留されている間も進み続ける。
判定点は，メッセージを決定する前に，決定の時刻を観測する。これはメッセージを伴わない観測であり，
F.5は，この観測で，過ぎたすべての期限と期間を確定させる。したがって，決定が，決定の時刻より前に
期間が閉じた禁止や，期限が過ぎた義務に基づくことはない。
拒否された `trigger:` のメッセージは，その規範を発動させない。F.5の判定への追加として，
`violated` になった義務は，その発動から違反までの間に，その内容に一致する負担者の
メッセージが，義務自身の契約を決定契約に含んで拒否されたか，またはその契約の根拠によって
保留され，違反より前に解放されなかったとき，判定 **`excused`** を持つ。
契約自身が履行を妨げたからである。その `on_violation:` は，`excused` となったすべての規範と
同じく，適用される。

## G.6 拒否の後のエスカレーション

禁止の `on_denied:` は，その禁止が根拠であるときの後の扱いを定める。
`fallback:` は送信者が代わりに送ることのできるメッセージを名指し，`notify:` は
知らせるべきアクターを名指す。どちらも結果に写されるだけである。
代替のメッセージは許可を与えない。送られたときは，他のメッセージと同じように決定される。
`escalate_to:` と `timeout:` は保留を定義する。

決定が `escalate` であるとき，判定点は**保留**を作る。保留は，判定点の中で一意な
`hold_id`，メッセージ，決定の時刻，根拠，承認者，期限（決定の時刻に結果の `timeout` を
加えたもの，またはなし）を持つ。**保留の根拠**は，ある禁止がメッセージに適用される
1つの契約インスタンスにおける，その禁止である。保留の根拠は，統治するすべての契約にわたる
そのすべてであり，それらの契約インスタンスを*根拠の契約インスタンス*と呼ぶ。
2つの契約インスタンスで適用される禁止は，2つの根拠である。
決して終わらない契約インスタンスにおける期限のない保留は，
いつまでも保留される。保留のidが承認者にどのように届くかは，プロトコルに依存する。

| 状態 | その状態になるとき | 終結記録（G.8） |
| --- | --- | --- |
| `held` | 保留が作られたとき。最終状態でない唯一の状態 | — |
| `approved` | 承認者が承認したとき。メッセージは解放される | `allow`，理由 `approved`（または解放の拒否） |
| `rejected` | 承認者が却下したとき | `deny`，理由 `rejected` |
| `expired` | 期限が過ぎたとき | `deny`，理由 `expired`。`time` は期限 |
| `cancelled` | 根拠の契約インスタンスが終わったとき，または根拠の契約が改正されたとき | `deny`，理由 `cancelled` |
| `withdrawn` | 送信者が取り消したため，判定点のホストが保留中のメッセージを取り下げたとき | `deny`，理由 `withdrawn` |

承認者は，`approval` と `rejection` の2つの制度的事象を通じて行為する。それぞれは，
承認者のメッセージから `counts_as:` 規則が作る（G-9）。たとえば
`when: "OPERATOR -> PLANNER : approve"`，`creates: approval` である。
F.5では制度的事象は「事象としてのみ存在」するが，その拡張として，この2つの事象は
1つの値，すなわち**保留のid**を持つ。その値は，事象を作ったメッセージの最初の引数である。
これは，バージョン0.1でメッセージの引数を用いる唯一の箇所である。
承認者のメッセージそのものも統治され，G.5によって決定される。

1つの観測の中での段階の順序（F.5）を，次のように拡張する。

- **段階1の後。** `approval`（`rejection`）のうち，その保留のidが `held` の保留を名指し，
  その行為者（F.5の7）がその保留の承認者であり，その保留の根拠の契約インスタンスで
  作られたものは，その保留を `approved`（`rejected`）にする。保留が複数の根拠の
  契約インスタンスを持つときは，そのような事象が1つあれば足りる。1つのメッセージが複数の契約インスタンスで作る事象は，
  1つの事象である。それ以外の `approval` または `rejection` はどの保留も変えず，
  権限のない行為として記録することが望ましい。次に，G.7の付与，取消し，`until:` の事象を
  適用する。
- **段階6の中。** 契約インスタンスが終わると，その中に根拠を持つ `held` の保留は，
  その規範を確定させる前に，`cancelled` になる。
- **段階6の後。** この観測で `approved` になった各保留を，作られた順に解放する。

**解放。** メッセージを，現在の状態の上で，承認した観測の時刻に，もう一度決定する。
承認は，許可と根拠の代わりになり，それ以外の代わりにはならない。

1. メッセージが今は未宣言のツールの呼び出しであれば，`deny`，理由 `undeclared_tool` とする。
2. 保留の根拠を持つ統治契約は，その根拠の契約インスタンスのいずれかがもはや動作して
   いなければ理由 `no_instance` で，その契約の禁止が，保留の根拠になっていない
   契約インスタンスで適用されれば理由 `prohibition` で，拒否する（`norms` にそれらの禁止を
   並べる）。根拠である禁止が，たとえば保留の後に作られた別の契約インスタンスで今は
   適用される場合も，これに含まれる。そうでなければ，その契約は許す。許可も既定値も調べない。
   根拠である禁止が，たとえばその `until:` の後で，承認の時刻にもはや効力を持たない場合も
   同じである。承認がその契約における許可の代わりになり，メッセージは解放される。
   理由 `no_instance` が生じるのは，承認した観測そのものがその契約インスタンスを終わらせる
   場合（段階6）だけである。それより前に終わったインスタンスは，保留を取り消している。
   リファレンスランタイムは，この場合に到達しない。そこでは，インスタンスの終了が
   それ自体で1つの観測だからである（G.13）。
3. それ以外の統治契約は，G.5の段階3によって完全に決定し，許さなければならない。許すのは，
   元の許可，今も有効な派生した許可，または既定値による。`escalate` と決定するはずの契約は，
   理由 `prohibition` で拒否する。
4. どの契約も拒否しなければ，メッセージを解放する。そうでなければ，解放を拒否する。
   その結果は，拒否する契約から，G.5の段階4と同じように作る。`contracts` はそれらの契約を
   並べ，理由は，それらのうち `no_instance`，`prohibition`，`default` の順で最初のものであり，
   `prohibition` では `norms`，`timeout`，`fallback`，`notify` をG.10のとおりに設定する。
   `escalate_to` は `null` である。

解放の拒否は最終的である。保留を作らず，保留は `approved` のままである。これらの規則により，
解放についても，G.5とG.7が他のすべてのメッセージについて述べることが成り立つ。すなわち，
2つの強制される契約が統治するメッセージは両方によって許され，どのアクターも，元の権限者が
もはや持たない権限によって行為することはない。したがって，根拠を持たない契約において，
保留から承認までの間に委任が取り消されたとき，契約インスタンスが終わったとき，または契約が
改正されたときは，解放が拒否される。メッセージを解放するとき，メッセージは，
他のどのメッセージが決定されるよりも前に，
承認した観測の時刻印を持つ，直後の観測として効果を生じる。F.5の3への追加として，
このメッセージは，ある禁止が保留の根拠になっている契約インスタンスでは，その禁止の内容が
起こったことにはならない。承認された例外は，その根拠に違反しない。承認は1つのメッセージを
解放する。送信者，受信者，名前が同じ後のメッセージは，改めて決定される。

**保留の識別子。** 承認または却下は，保留を，その識別子だけによって名指す。識別子は
予測できないものである必要はない。保留が守られるのは，契約が統治するメッセージによって
保留を閉じることができるのが，その承認者だけだからである。識別子を秘密にする必要はない。
承認者のメッセージそのものが保留され，後で解放されたときは，そのメッセージは，
解放された時点でその識別子を持つ保留に適用される。その保留がもはや `held` でなければ，
何も変えず，権限のない行為として記録される。

**期限切れ。** `held` の保留の期限より後の時刻を持つ各決定と各観測の前に，その保留は
`expired` になる。同時に期限切れになる保留は，期限の順に，期限が等しければ作られた順に，
`expired` になる。ちょうど期限の時刻の承認は期限内とする。

**取下げ。** プロトコルは，保留中の要求を送信者が取り消すことを許す場合がある。そのとき
ホストは，取消しの時刻に，その時刻の他のどの処理よりも前に，保留を取り下げる。`held` の保留は
`withdrawn` になり，メッセージは効果を持たず，後から来た承認や却下は何も変えない（`not_held`）。
すでに `held` でない保留は，取下げによって変わらない。

## G.7 来歴を伴う委任

`delegations:` の項目は，1つの許可を**委任可能**にする。`norm:` はその許可を名指し，
`to:` は任意の深さで派生インスタンスを保持してよいアクターを列挙し，`grant:` と `revoke:` は
委任するメッセージと取り消すメッセージを名指し，`max_depth:` は連鎖のリンクの最大数であり，
`until:` はその項目のすべての派生インスタンスを終わらせる事象である。
バージョン0.1では，内容が `message_event` である許可だけを委任できる。権能は委任できない。

**派生インスタンス**は，1つの契約インスタンスにおける，同じ内容を持つ許可であり，
その内容は**保持者**を送信者として読む。その**来歴連鎖**は
*a*<sub>0</sub>, …, *a*<sub>n</sub> である。*a*<sub>0</sub> は元の許可の負担者，
*a*<sub>n</sub> は保持者であり，隣り合う各対は，1回の付与が作る**リンク**である。
負担者の連鎖は *a*<sub>0</sub> だけである。派生インスタンスは `active` または
`discharged`（最終状態）である。派生インスタンスは付録Fへの追加である。付録Fでは
規範ごとに1つのインスタンスがある。規範，保持者，契約インスタンスの組ごとに，
`active` の派生インスタンスは高々1つであり，したがって，どの保持者も1つの連鎖を持つ。

派生インスタンスは，元の許可が効力を持ち（G.5），派生インスタンスが `active` であり，
その連鎖のリンクが `max_depth` 以下であり，連鎖の最初より後のすべてのアクターが `to:` の
参照に一致するとき，**有効**である。元の許可が停止されている間，その派生インスタンスは
有効でない。

**付与。** メッセージ `X -> Y : g` は，`g` が，それを統治する契約の項目の `grant:` の
名前であるとき，他のメッセージと同じようにG.5によって決定される。それが観測されると，
その契約の動作中の各インスタンスで，次の条件を調べる。

1. `X` が負担者であり，許可が効力を持つ。または，`X` が有効な派生インスタンスを保持する。
2. `Y` が `to:` の参照に一致する。
3. `Y` が `X` の連鎖に現れない。
4. `X` の連鎖のリンクが `max_depth` より少ない。
5. `Y` がその許可の `active` の派生インスタンスを保持していない。

すべてが成り立てば，`Y` のために，`X` の連鎖に `Y` を続けた連鎖を持つ派生インスタンスを作る。
1から4が成り立ち，5が成り立たなければ，付与は何もしない。
1から4のいずれかが成り立たなければ，付与は効果を持たず，権限のない行為として記録することが
望ましい。付与者は自分のインスタンスを保つ。委任によって権限は付与者から移らず，付与者と被委任者の両方が持つ。

**終了。** 派生インスタンスは，次のときに `discharged` になる。(a) その項目の `revoke:` の
名前を持つメッセージ `X -> Y : r` が観測され，`Y` の連鎖の中で `X` が `Y` より前に現れるとき。
このとき，`Y` のインスタンスと，連鎖に `Y` が現れるすべての派生インスタンスが解除される。
(b) その項目の `until:` が，規範の `until:` と同じように起こったとき。このとき，その観測で
`active` である派生インスタンスが解除され，項目は委任可能なままである。(c) 元の許可が
`discharged` になったとき，または契約インスタンスが終わったとき。
(a) を満たさない取消しのメッセージは効果を持たない。解除されたインスタンスは復活しない。
新しい付与は新しいインスタンスを作る。

有効性は連鎖の全体から計算するため，アクターは，元の権限者が持っていなかった権限や，
もはや持っていない権限を，仲介者を通じて得ることができない。有効なインスタンスを持たない
アクターによる付与は何も作らず，連鎖は契約が許すより長くならず，1つのリンクを取り消すと，
それを通じて派生したすべてが終わる。

**改正。** 改正された契約の規範インスタンスは，F.6が定める。
本付録は2つの規則を追加する。強制される契約の新しいバージョンが発効するとき，
(1) その契約に根拠を持つすべての `held` の保留は `cancelled` になり，
(2) すべての派生インスタンスの有効性を新しいバージョンに対して調べる。新しいバージョンでその許可が
`delegations:` の項目を持たないインスタンス，または元の許可が改正によって解除された
インスタンスは，`discharged` になる。

## G.8 監査記録

判定点は，すべての決定を記録することが望ましく，記録を追記専用で保つことが望ましい。
記録することは推奨であり，形式は規範的である。**監査記録**は，決定の結果（G.10）に
次の5つのフィールドを加えたものである。

| フィールド | 内容 |
| --- | --- |
| `time` | 決定の時刻。トレースの時計による。 |
| `message` | `from`，`to`，`name`。方針の入力と同じ。 |
| `instances` | 統治する契約の動作中のインスタンス。契約の `id` とインスタンスの識別子。終結記録では，動作中かどうかにかかわらず，保留の根拠の契約インスタンス。 |
| `hold_id` | `escalate` の決定と，その保留を閉じる記録で値を持つ。それ以外は `null`。識別子は判定点の中で一意であり，予測できないものである必要はない（G.6）。 |
| `outcome` | 保留を閉じる記録では，その最終状態。それ以外は `null`。 |

`escalate` の決定は，同じ `hold_id` を持つ2つの記録を与える。1つは保留が作られたときの
記録であり，もう1つは保留が最終状態に達したときの**終結記録**（closing record）である
（G.6の表）。終結記録は，保留の `contracts`，`norms`，`escalate_to` を保つ。理由が
`rejected`，`expired`，`cancelled`，`withdrawn` のいずれかであるときは，保留の `fallback` と `notify` も保つ。
送信者が，拒否の結果からそれらを得られるようにするためである。終結記録の `timeout` は `null` である。
解放が拒否されるとき（G.6），終結記録は，これらの代わりにその拒否の結果を持ち，`outcome` は
`approved` である。終結記録の `time` は，保留を閉じた観測の時刻である。ただし `expired` では
期限である。`expired` の記録は，期限切れが見つかったとき，すなわち次の決定または観測の前に書く。
したがって，ログの時刻が逆戻りすることはない。

不明なフラグ（G.5）に基づく拒否またはエスカレーションは，他の場合と同じく，理由
`prohibition` を持ち，その規範を `norms` に並べる。違いは，その決定の方針の入力（フラグが
`in_force` にない）と，処理系の警告に現れる。送信者がとるべき対処は異なる。データの欠落では，
承認者に承認を求めても決定は変わらないので，データを待つ。

付与，取消し，および権限のない行為として記録した行為は，**事象記録**（event record）として，
同じログに書くことが望ましい。後の決定が基づく状態のそれ以外の変化，すなわち，原因を問わない
派生インスタンスの終了，契約インスタンスの開始と終了，改正も，同じように書くことが望ましい。
事象記録は結果を持たない。`decision` の代わりにフィールド `event` を
持ち，次のフィールドを持つ。

| フィールド | 内容 |
| --- | --- |
| `time`，`message` | 監査記録と同じ。その事象のもとになった観測とメッセージ。メッセージがないときは，`message` は `null`。 |
| `event` | `grant`，`revoke`，`delegation_end`（派生インスタンスが取消しのメッセージ以外の原因で終わった。派生インスタンスごとに1つの記録），`instance_start`，`instance_end`，`amendment`，`unauthorised_grant`，`unauthorised_approval`，`unauthorised_rejection`，`unauthorised_act`（F.5の7が権限のない行為として記録する行為），および後述のホストの事象のいずれか。 |
| `instances` | その事象が起こった契約インスタンス。`amendment` では，改正された契約の動作中のインスタンス。 |
| `norm` | 付与，取消し，または `delegation_end` では，委任可能な許可。`<contract id>.<norm id>` の形で表す。それ以外は `null`。 |
| `chain` | `grant` では，受信者の派生インスタンスの連鎖。効果を持つ `revoke` では，取り消されたインスタンスの連鎖。`delegation_end` では，終わったインスタンスの連鎖。それ以外は `null`。 |
| `holders` | その事象が派生インスタンスを作った，または解除した保持者。作られた順に並べる。それ以外は空。 |
| `hold_id` | 権限のない承認または却下では，それが持っていた保留のid。なければ `null`。それ以外は `null`。 |
| `reason` | 効果を持つ付与または取消しでは `null`。何もしない付与（G.7の条件5）では `holder_exists`。(a) を満たさない取消しのメッセージでは `no_effect`。`unauthorised_grant` では，最初に成り立たない条件：`no_authority`（1），`not_in_to`（2），`in_chain`（3），`max_depth`（4）。権限のない承認または却下では，`unknown_hold`，`not_held`，`not_approver`，`other_instance`（根拠の契約インスタンスで作られていない），およびホストが承認を認証するときの `unauthenticated`，`wrong_run`，`wrong_message`，`replayed` のいずれか。`unauthorised_act` では `no_power`。`delegation_end` では，その原因：`until`，`original_discharged`，`instance_end`，`amendment`。`instance_end` では `end` または `terminal_state`。`amendment` では新しいバージョンの名前。`instance_start` では `null`。 |

記録は，判定点がそれを作る順に書く。決定の記録，次にそのメッセージがなる観測の事象記録，
次にその観測が承認または却下した保留の終結記録である。規範の効力のフラグの変化には，
それ自体の記録はない。フラグの変化は，記録されたメッセージ，時刻，および契約の述語が読む値から導ける。

判定点のホストは，自らの事象を，事象記録として同じログに記録してもよい。そのとき `message` は
関係するメッセージまたは `null` とし，`instances` は空，`norm`，`chain`，`holders` は空とする。
記録するのは，メッセージになる前にホストが拒否した承認または却下（`unauthorised_approval`，
`unauthorised_rejection`。理由は上のとおり），ホストが拒否したその他のメッセージ
（`unauthorised_message`），ホストが受け入れた承認の証拠（認証された承認では `approval_evidence`，
認証されていない承認では `approval_unauthenticated`。`reason` は，承認のダイジェスト，保留中の
呼び出しの引数のダイジェスト，認証された承認では承認者の鍵のIDとノンスを示す。承認者の
メッセージの決定の前に書く），転送しなかった要求（`method_refused`。`reason` はメソッド），
処理中の要求がない応答（`unsolicited_response`），許可または解放されたが送れなかった呼び出し
（`forward_failed`），およびA2Aのゲートウェイでは，認証された送信者のない要求
（`unauthenticated_request`），他のクライアントのタスクやコンテキストを名指す要求
（`task_refused`），送ったが正しい応答が返らなかった要求（`invalid_response`），タスクの取消し
（エージェントに渡すもの，または保留を取り下げるもの。`task_cancel`），同時に処理する要求についての
ゲートウェイの上限を超えた要求（`overloaded`），期限内に読み終わらなかった要求（`read_timeout`）である。これらの記録は決定を変えない。また，その信頼性は書いたホストの
信頼性を超えない。誰でも書けるトレースから再生したログは，これらの記録について何も証明しない。

**ログの完全性。** 判定点は，ハッシュ連鎖によってログを後からの変更から保護してもよい。
保護するときは，判定点を知らない検証者が検査できるように，ログは次の形式を持つ。
連鎖は行とフィールドを加えるだけであり，記録の値は変えない。

ログはUTF-8のJSON Linesのファイルであり，各行は改行で終わる。1行目は**ヘッダ記録**であり，
次に監査記録と事象記録が書かれた順に続く。完結したログは**終了記録**で終わる。

| 行 | 完全性のフィールドの前のフィールド |
| --- | --- |
| ヘッダ | `audit_format`：`"cadl-audit/1"`。`hash`：`"sha256"`，鍵つきのログでは `"hmac-sha256"`。`key_id`：鍵つきのログでは，HMAC-SHA256(*鍵*，`cadl-audit key id`) の先頭の16桁の16進数。それ以外は `null`。`run_id`：判定点のこの実行の128ビットの乱数の識別子を，小文字の16進数32桁で表したもの。`approvals`：ホストが承認をどう読んだか。`authenticated`，`insecure`，`none` のいずれか，示さないときは `null`。`source_sha256`：CADLファイルのバイト列のSHA-256を16進数で表したもの。`epoch`：`t = 0` の時刻をUTCのISO 8601の時刻印で表したもの。時刻がトレースの時刻であるときは `null`。 |
| 記録 | 監査記録または事象記録のフィールド。順序は上の表のとおり。 |
| 終了記録 | `audit_end`：`true`。`records`：ヘッダと終了記録の間にある記録の数。 |

どの行も，最後に3つの**完全性のフィールド**を持つ。`seq` は行の番号であり，ヘッダが `0` である。
`prev` は直前の行の `digest` であり，ヘッダでは `0` を64個並べたものである。`digest` は，
フィールド `digest` を除いた行の正規形JSONのSHA-256，鍵つきのログでは鍵によるHMAC-SHA256であり，
64桁の小文字の16進数で表す。

値の**正規形JSON**は，プログラミング言語に依存しないように，次のとおり定める。

- `null`，`true`，`false` は，書かれたとおりに書く。
- 値が整数である数は，その整数を10進数で書く。負なら負号を付け，先頭に0を付けない。絶対値は
  2<sup>53</sup>以下であり，それより大きい整数はログに含めない。それ以外の数は，有限の
  IEEE 754の倍精度の値であり，その値に読み戻せる最短の10進数を，指数を使わずに書く。数字，
  小数点，数字の順に書き，小数点の後の末尾に0を付けず，値が1より小さいときは小数点の前に0を
  1つ書く（`0.5`，`0.0000001`，`123.456`）。NaNと無限大は使わない。
- 文字列は，引用符で囲んでUTF-8で書く。文字 `"` と `\` は `\"` と `\\` と書く。U+0008，
  U+0009，U+000A，U+000C，U+000Dは `\b`，`\t`，`\n`，`\f`，`\r` と書く。U+0020未満の
  その他の文字は，`\u` と小文字の16進数4桁で書く。それ以外の文字はそのまま書く。単独の
  サロゲートを含む文字列は使わない。
- 配列は，`[`，`,` で区切った要素，`]` の順に書く。
- オブジェクトは，`{`，`,` で区切ったメンバー，`}` の順に書く。メンバーは，文字列としての
  キー，`:`，値の順に書く。メンバーはキーの符号位置の順に並べる。オブジェクトは重複した
  キーを持たない。

行は，2つの点を除いて同じ規則で**書く**。メンバーは順序を保ち（記録のフィールド，`seq`，`prev`，
`digest`），区切りは `, ` と `: ` である。検証者は，各行を読み，重複したキーを拒否し，値から
ダイジェストを計算し直し，`seq` と `prev` を直前の行と照合し，行が書いた形のとおりであることを
確かめる。このため，値を変えずに空白，エスケープ，数の書き方を変えた場合も検出できる。
鍵つきのログの鍵は，ログにも，トレースにも，コマンド行にも含めない。

連鎖が示すことには限界があり，検証者はそれを知っていなければならない（MUST）。

- ヘッダは，連鎖による以外には認証されない。鍵がなければ，誰でも検証を通る連鎖を書ける。
  鍵つきのログを鍵のないログとして書き直すと，鍵を与えない検証を通る。したがって検証者は，
  ログが鍵つきかどうかをログの外から知り，鍵つきなら鍵を与えなければならない（MUST）。
- 鍵がなければ，ログの残りがそのままである限り，連鎖は任意のバイトの変更，行の削除・挿入・
  移動，および末尾を切り取ったログ（終了記録がない）を検出する。変更した行から後を，
  ダイジェストと終了記録も含めて書き直したログは検出しない。他のログから持ち込んだ行は合わない。
  ヘッダの `run_id` が異なり，それによってすべてのダイジェストが異なるからである。同じ実行の
  異なる2つのログが，同じ鍵とアンカーに対して両方とも検証を通ることはない。
- 鍵があれば，検証を通る連鎖を書けるのは鍵の保持者だけである。鍵の保持者は，それでもログ全体を
  置き換えられる。
- 終了記録のないログは，切り取られたか，書き手が書き終えていない（動作中の判定点，または
  失敗した判定点）。検証者はそのことを報告する。

したがって判定点は，ログの最後の行のダイジェストとその `run_id` を，ログの外に（例えば別の
システムに）保管することが望ましい（**アンカー**）。アンカーとログを照合する検証者は，連鎖だけでは
わからない書き直し，切り取り，置き換えを検出する。

## G.9 静的意味論 {/* #g9-static-semantics */}

エージェント統治拡張を扱う処理系は，[付録F](./appendix-f-norms.md)の検査に加えて，
次の検査をしなければならない。

- **G-1.** `agents: 0.1` を宣言するファイルは，`norms: 0.1` も宣言しなければならない。
  そうでなければ，処理系はエラーを報告し，本拡張のキーを解釈しない。
- **G-2.** `agent:` のマッピングは `kind:` を持たなければならず，その値は `llm_agent`，
  `tool_server`，`human`，`service` のいずれかである。`protocol:` は `hyphen_name` で
  なければならない。
- **G-3.** `tools:` は `tool_server` にだけ書け，`tool_server` は少なくとも1つのツールを
  列挙しなければならない。ツールの名前は識別子でなければならず，予約語であってはならず，
  そのアクターの中で一意でなければならない（YAML 1.1のローダーでは，引用符のない `yes`，
  `no`，`on`，`off`，`true`，`false`，`null` は名前にならない。
  [A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)を参照）。
- **G-4.** `message_event` の受信者がツールサーバであるとき，メッセージ名はその `tools:` の
  1つでなければならない。これは，規範の `trigger:`，`until:`，`content:`，`counts_as:` 規則の
  `when:`，ライフサイクル遷移の `on:`，および `fallback:` に適用される。
  処理系は，これを満たさないプロトコル（A.5）のメッセージのステップについて警告することが
  望ましい。
- **G-5.** `enforcement.default` は `deny` または `allow` でなければならず，
  `enforcement.point` は `caller`，`receiver`，`gateway` のいずれかでなければならない。
  nullまたは空の `enforcement:` は有効である。
- **G-6.** 強制される契約では，許可または禁止の内容である `message_event` の送信者は，
  その `bearer:` とテキストとして等しくなければならない。
- **G-7.** `on_denied:` は，強制される契約の，内容が `message_event` である禁止にだけ書け，
  少なくとも1つのキーを持たなければならない。`timeout:` は0より大きい `duration_lit` で
  なければならず，`escalate_to:` を必要とする。処理系は，`timeout:` のない `escalate_to:` に
  ついて警告することが望ましい。
- **G-8.** `escalate_to:` と `notify:` は，宣言済みの1つのアクターを名指さなければならない
  （N-3と同じ）。`escalate_to:` は，そのメッセージが統治されるように，契約の当事者を
  名指さなければならず，その禁止の `bearer:` とテキストとして等しくてはならず，
  `agent.kind: human` を持つことが望ましい。
- **G-9.** `escalate_to: A` を持つ契約は，送信者が `A` である `message_event` から
  `approval` を作る `counts_as:` 規則を持たなければならず，`rejection` についても
  そのような規則を持つことが望ましい。強制される契約では，`approval` または `rejection` を
  作るすべての規則は，送信者がその契約の禁止の `escalate_to:` である `message_event` を
  `when:` として持たなければならず，どの規範の `id` もこの2つの名前のいずれとも等しくては
  ならない。エラーになる使い方はこれらだけである。G-17により，その `message_event` の
  送信者と受信者は契約の当事者である。そのため，契約は承認者のメッセージを統治し，
  そのインスタンスはそれを観測する。`trigger:`，`until:`，`content:` での
  この2つの事象への参照は許される。
- **G-10.** `fallback:` は，送信者がその禁止の `bearer:` とテキストとして等しく，
  受信者が宣言済みのアクターである `message_event` でなければならず，受信者または
  メッセージ名において禁止の内容と異ならなければならない。
- **G-11.** `delegations:` は強制される契約にだけ書ける。`norm:` は，その契約の，内容が
  `message_event` である許可の `id` でなければならない。1つの規範を名指してよい項目は
  高々1つである。その許可の `bearer:` は，契約インスタンスが束縛する添字（`ROBOT[i]`）を
  持ってはならない。すべての連鎖の最初のアクターをファイルから読み取れるようにするためである。
- **G-12.** `to:` は少なくとも1つの参照を列挙しなければならず，それぞれが宣言済みの
  アクターを名指さなければならない。ワイルドカードや範囲は許されるが，契約インスタンスが
  束縛する添字は許されない。`to:` はツールサーバを名指してはならず，負担者を含まないことが
  望ましい。`max_depth:` は1以上の整数でなければならない。`until:` は，規範の `until:` に
  ついての付録Fの規則（N-9，N-10）を満たさなければならない。
- **G-13.** `grant:` と `revoke:` は識別子でなければならず，予約語であってはならない。
  1つの契約の中で，すべての `grant:` と `revoke:` の名前は，互いに異なり，`approval` および
  `rejection` とも異ならなければならず，いずれも，当事者であるツールサーバのツールであっては
  ならない（G-3のYAML 1.1についての注記が当てはまる）。
- **G-14.** 処理系は，強制される契約の許可または禁止のうち，(a) 内容が `message_event` で
  ないもの（境界で効果を持たないため），または (b) 内容の `message_event` が引数を持つもの
  （引数は考慮されないため）について警告することが望ましい。
- **G-15.** 処理系は，(a) `default: allow` を持つ強制される契約の当事者のツールのうち，
  その契約のどの許可も禁止も覆わないもの，および (b) どの強制される契約の当事者でもなく，
  そのツール呼び出しが統治されないツールサーバについて警告することが望ましい。
  規範は，その内容の `message_event` がその受信者とメッセージ名を持つとき，メッセージを
  *覆う*という。
- **G-16.** 処理系は，契約が必要とし，かつ契約自身が拒否することになるメッセージについて
  警告することが望ましい。(a) 義務の内容または `fallback:` であって，そのメッセージの
  送信者を負担者とする `trigger:` のない禁止が覆うもの，または，ツール呼び出しの既定値が
  `deny` であるのに，その送信者のどの許可にも覆われないツール呼び出しであるもの。
  送信者が派生した許可を通じてのみ送ることのできるメッセージにも，この警告を出す。
  委任は実行時の状態だからである。(b) `default: deny` のもとで，どの許可も覆わない
  `grant:` または `revoke:` の名前，あるいは `approval` または `rejection` を作る規則の
  `when:` のメッセージ。

- **G-17.** 強制される契約では，その契約のすべての `message_event` の送信者と受信者は，
  **当事者に覆われて**いなければならず，宣言済みの要素だけを名指さなければならない。
  対象は，規範の `trigger:`，`until:`，`content:`，`counts_as:` 規則の `when:`，
  委任の `until:` である。参照は，`parties:` の1つの参照が，それが名指しうるすべての
  アクターに一致するとき（G.5），覆われている。`A` は当事者 `A` に，`A[3]` は当事者 `A[3]`，
  `A[i]`，`A[*]`，または3を含む範囲に，`A[1..3]` は当事者 `A[i]`，`A[*]`，またはそれを含む
  範囲に，`A[*]` と `A[i]` は当事者 `A[i]` または `A[*]`，あるいは宣言した集合の全体を含む
  当事者の範囲に，覆われる。2つの当事者の参照を合わせることはしない。当事者 `A[1..2]` と
  `A[3]` は `A[1..3]` を覆わない。リテラルの添字または範囲は，宣言した集合の内に
  なければならない。`A[1..3]` と宣言した集合に対して，`A[7]` と `A[2..5]` はエラーである。
  強制される契約のインスタンスは，その契約が統治するメッセージだけを観測する（G.5）。
  そのため，覆われていない事象や，宣言済みの要素を名指さない事象は，それが名指すアクターの
  一部または全部について，決して起こらない。ツール呼び出しの受信者も対象である。
  G-4はそのツールを求め，本規則はそのツールサーバが当事者であることを求める。その送信者も
  対象である。契約は，当事者でないアクターのツール呼び出しを，規範の内容や事象にすることは
  できない。当事者であるツールサーバへのそのような呼び出しは，それでも統治され（G.5），
  契約の既定値と，当事者のために書いた規範によって決定される。これは意図したものである。
  `fallback:` は対象でない。送信者のためのデータであり，契約の事象ではないからである。
  G-10はその受信者が宣言済みであることだけを求める。当事者でないアクターに送られた
  代替のメッセージは，この契約によって統治されない。
- **G-18.** 強制される契約では，すべての添字変数は束縛されていなければならない。
  添字変数とは，添字として，または添字の式の中で用いられる名前である（`ROBOT[j]`，
  `ROBOT[j+1]`，`ROBOT[SLOT[j].next]` の `j`）。束縛するものは3つある。`parties:` の参照は，
  その添字変数を契約の全体で束縛する（当事者 `ROBOT[i]` の `i`）。限量子は，その変数を
  その述語の中で束縛する（`exists j in ROBOT: ROBOT[j].battery < 20`，A.10）。内包表記は，
  その変数をその要素の中で束縛する（`sum(ROBOT[j].load for j in ROBOT)`，A.10）。
  それ以外の添字変数は，契約の式が現れうるどの場所でもエラーである。その場所は，規範の `bearer:` と
  `counterparty:`，`escalate_to:`，`notify:`，`fallback:` の送信者と受信者，G-17が挙げる
  すべての `message_event` の送信者，受信者，引数（どの種類の規範の `content:` も含む），
  および契約のすべての述語（規範の `trigger:`，`until:`，`content:`，
  `counts_as:` 規則の `when:` と `if:`，委任の `until:`，`assume:` と `guarantee:` の項目）である。
  契約インスタンスは，その当事者の添字変数を束縛し（F.2），それ以外は束縛しない。
  束縛するものを持たない変数は，その値をファイルから決められない。F.3によれば，
  そのような変数を持つ事象や権能は集合のすべての要素について成り立つことになり，
  そのような変数を持つ述語は，どのアクターも持たない量を読むことになる。
  限量子がその変数を束縛していれば，その述語は有効である。処理系がその述語を評価できるか
  どうかは，別の問題である（G.13）。

- **G-19.** 処理系は，強制される契約において，`counts_as:` 規則が `if:` のもとで作る
  制度的事象が，禁止の `trigger:` または許可の `until:` であるとき，警告することが望ましい。
  その規則の `when:` がメッセージであり，`if:` が未定義である間にそのメッセージが届くと，
  事象は作られず，境界は止めない（G.5の「データの欠落」）。

「しなければならない」の規則はエラーであり，「望ましい」の規則は警告であって，ファイルは
有効のままである。付録FのN-1からN-12は変わらず適用される。

## G.10 コード生成

ファイルの強制される契約から境界方針を生成するコードターゲットは2つある。
これらは[付録D](./appendix-d-codegen.md)のカテゴリ*境界方針*に挙げている。
`agent-rego` はRego
[[Open Policy Agent]](./appendix-b-references.md)を出力する。これは，契約の他の部分から
契約ごとに1つの方針を出力する `opa` ターゲットとは独立である。`agent-cedar` はCedarの方針
[[AWS, AgentCore Policy]](./appendix-b-references.md)を出力する。方針の構文とファイルの
配置は，ターゲットが定める。

```jsonc
// policy input
{ "message": { "from": "SUMMARIZER", "to": "FILES", "name": "read_file" },
  "now": "2026-11-10T09:00:05Z",
  "instances": [
    { "contract": "ASSISTED_REPORTING", "instance": "default",
      "bindings": {},
      "in_force": {},
      "derived": [ { "norm": "may_read", "holder": "SUMMARIZER",
                     "chain": ["OPERATOR", "PLANNER", "SUMMARIZER"] } ] } ] }

// result
{ "decision": "allow", "reason": "permission",
  "contracts": ["ASSISTED_REPORTING"],
  "norms": ["ASSISTED_REPORTING.may_read"],
  "provenance": [["OPERATOR", "PLANNER", "SUMMARIZER"]],
  "escalate_to": null, "timeout": null, "fallback": [], "notify": [] }
```

入力は次のとおりである。

- `message`（必須）: `from` と `to` は，ファイルに書くとおりの具体的なアクター
  （`PLANNER`，`ROBOT[2]`）であり，`name` はメッセージ名である。
  引数は入力に含まれない。
- `now`（省略可能）: 決定の時刻。決定には影響しない。
- `instances`（省略可能）: すべての強制される契約の，動作中のすべてのインスタンス。
  項目のない契約には，動作中のインスタンスがない。このフィールドがないとき，方針は，
  各強制される契約に，束縛された添字も派生インスタンスもない動作中のインスタンスが1つあると
  仮定する。そのとき，添字に依存する照合は不明である（G.4。ランタイムが作るインスタンスとの
関係はG.5）。インスタンスごとに，`bindings` は添字の名前を整数に対応付ける。`in_force` は，
  静的（後述）でない各規範の `id` を `true` または `false` に対応付け，項目がなければ
  不明である。`derived` は，ランタイムがG.7によって有効と認めた派生インスタンスを，
  その連鎖とともに列挙する。
- `derived` の項目は，フェイルクローズで再検査する。項目が適用されるのは，その規範が
  その契約の委任可能な許可であり，保持者がメッセージの送信者であって連鎖の最後の要素であり，
  連鎖のリンクが `max_depth` 以下であり，連鎖の最初の要素が負担者に一致し，それより後の
  各要素が `to:` の参照に一致し，元の許可が効力を持つ（静的であるか，フラグが `true` である。
  フラグがないものは数えない）ときだけである。それ以外の項目は無視する。

この形式でない入力については，決定を定義しない。処理系はエラーを報告し，生成した方針は
拒否する。

結果は次のとおりである。

- `decision`: `allow`，`deny`，`escalate` のいずれか。
- `reason`: `ungoverned`，`undeclared_tool`，`no_instance`，
  `prohibition`，`permission`，`default` のいずれか。終結記録（G.6）では，
  `approved`，`rejected`，`expired`，`cancelled`，`withdrawn` もある。
- `contracts`: 決定契約（G.5）の `id`。`ungoverned` と `undeclared_tool` では空である。
- `norms`: 決定契約の根拠（理由 `prohibition`）または適用される許可（理由 `permission`）。
  それぞれ `<contract id>.<norm id>` の形で，1回ずつ，宣言の順に並べる。
  それ以外の理由では空である。
- `provenance`: 適用される派生インスタンスの連鎖。その規範の順，次に入力の順に，
  重複なしで並べる。元の許可だけが適用されたときは空である。
- `escalate_to`: `escalate` の場合と，それを保つ終結記録（G.8）の場合の承認者。
  具体的なアクターで表す。それ以外は `null`。
- `timeout`（ミリ秒），`fallback`（テキストとしてのメッセージ事象），
  `notify`（アクター参照）は，理由が `prohibition` であるときは常に，`escalate` だけでなく
  `deny` についても，根拠から，重複なしで，宣言の順に設定する。それ以外のすべての理由では，
  `null`，`[]`，`[]` である。ただし，理由が `rejected`，`expired`，`cancelled`，`withdrawn` のいずれかである
  終結記録は，その保留の `fallback` と `notify` を保つ（G.8）。

規範は，次のとき**静的**である。内容が `message_event` である許可または禁止であり，
`trigger:`，`until:`，`deadline:` を持たず，どの権能も `effects:` でそれを名指さず，
どの規範も `reparation:` としてそれを名指さず，その規範のどのアクター参照も契約インスタンスが
束縛する添字を持たない。アクター参照とは，その負担者，相手方，内容，その `escalate_to` と
`notify`，およびその `fallback` の送信者と受信者である。G.5により，静的な規範は，
動作中のすべてのインスタンスで，その開始から終了まで効力を持つ。そのため，入力には
静的な規範のフラグを含めない。方針は契約の1つのバージョンに対して生成する。改正には新しい方針が
必要である。

生成した方針は，すべての入力について，G.5の決定関数と同じ `decision` を返さなければならない。
このとき，静的な規範は効力を持つものとし，その他のフラグと派生インスタンスは入力から取り，
入力が与えないものはすべて不明とする。方針言語が2つの結果しか持たないターゲットは，
G.5が `escalate` を与えるところで `deny` を返す。結果のその他のフィールドは，方針が
作ってもよく，ジェネレータが方針とともに出力する表（禁止ごとの `escalate_to`，`timeout`，
`fallback`，`notify`）からランタイムが作ってもよい。ジェネレータは，生成物の中に，
メッセージを内容とする許可または禁止のうち静的でないものをそれぞれ，実行時の状態を
必要とするものとして列挙し，それとは別に，他の内容を持つ許可または禁止をそれぞれ，
境界で効果を持たないものとして列挙しなければならない。他の種類の規範は列挙しない。
保留，解放，委任の管理（G.6，G.7）はランタイムが行い，方針には含めない。

入力に `message` だけを与えたときのG.12の例（参考）。

| `message` | 結果 |
| --- | --- |
| `PLANNER -> TICKETS : search_tickets` | `allow`，`permission`，`may_search`（静的な許可） |
| `PLANNER -> FILES : delete_file` | `OPERATOR` への `escalate`，`prohibition`，`no_delete` |
| `PLANNER -> FILES : format_disk` | `deny`，`undeclared_tool` |
| `SUMMARIZER -> FILES : read_file` | `deny`，`default`。上に示した `derived` の項目があれば，`allow`，`permission` |

**Cedarへの対応（参考）。** Cedar
[[Cutler+, OOPSLA 2024]](./appendix-b-references.md)では，`permit` の方針が満たされない限り
要求は拒否され，満たされた `forbid` の方針はすべての `permit` に優先し，評価がエラーを
起こした方針は飛ばされる。したがって，未宣言のツールと禁止は `forbid` の方針になり，
許可は `permit` の方針になり，ツール呼び出しの既定値は言語の既定の拒否である。
`escalate` は拒否として返され，出力した表からランタイムが解決する。
エラーを起こした `forbid` の方針は飛ばされ，拒否しないことになるため，生成した方針は，
上のスキーマのどの入力に対してもエラーを起こさないようにする必要がある。すなわち，
省略可能なすべての属性について，読む前にその存在を調べる。G.5が許可なしに許すメッセージ
（統治されないメッセージ，既定値が `allow` である契約）には，明示的な `permit` の方針が
必要である。また，強制される契約が2つ以上あるとき，契約をまたぐ拒否優先には，
契約ごとに，その契約が許さないものに対する追加の `forbid` の方針が必要である。
Cedarの答えだけからは，そのような方針による拒否や言語の既定値による拒否を，
「静的でない許可または派生した許可が許すかもしれない」場合と区別できない。
そのため，Cedarターゲットは静的な規範だけを扱い，残りはランタイムが決定する。

## G.11 エージェントプロトコルへの対応（参考）

決定関数はプロトコルに依存しない。この節は，エージェントのための2つのプロトコルとの
対応を示す。Model Context Protocolのリビジョン2026-07-28
[[MCP Specification 2026-07-28]](./appendix-b-references.md) と，Agent2Agentプロトコルの
バージョン1.0.0 [[A2A Specification 1.0.0]](./appendix-b-references.md) である。
リファレンス実装はMCPのゲートウェイを持ち，`cadl` 0.3.25からはA2AのJSON-RPCバインディングの
ゲートウェイも持つ（G.13）。
規範的な事項はこの節に依存しない。

| CADL（agents 0.1） | MCP 2026-07-28 | A2A 1.0.0 |
| --- | --- | --- |
| `kind: tool_server`，ツール，ツール呼び出し | MCPサーバ，`tools/list` のツール，`tools/call` の要求 | — |
| `kind: llm_agent` | ツールを呼び出すときのMCPクライアント | クライアントとしてもサーバとしても動くA2Aエージェント |
| エージェント間の通常のメッセージ | — | あるエージェントから別のエージェントへの `SendMessage` の要求 |
| メッセージの名前 | `tools/call` の `params.name` | プロトコルは運ばない。拡張から得る（後述） |
| `point: gateway` | クライアントとサーバの間の代理。Streamable HTTPでは，ヘッダ `Mcp-Method` と `Mcp-Name` がメソッドとツールを示す。本体を構文解析せずにこれらで判定してよいのは，ヘッダと本体が異なる要求をサーバが拒否する（`HeaderMismatch`）場合だけである。stdioでは，ゲートウェイは本体を構文解析する | エージェント間の仲介者 |
| `deny` | `isError: true` のツール結果 | 状態 `TASK_STATE_REJECTED` のタスク |
| `escalate`，保留のid，承認者 | プロトコルの範囲外 | プロトコルの範囲外 |

**MCP。** ゲートウェイは，ツール呼び出しを送るアクターであるMCPクライアントと，
ファイルのツールサーバであるMCPサーバの間に置く。アクター *A* のクライアントからアクター *S* の
サーバへの，名前 *n* の `tools/call` は，到着した時刻のメッセージ `A -> S : n` である。MCPには，
送信者を示す認証されたフィールドがない。`_meta` の `clientInfo` は，クライアント自身が申告する
ものである。stdioでは1つのゲートウェイのプロセスが1つのクライアントに対応し，そのクライアントが
どのアクターであるかはゲートウェイの設定で決まる。呼び出しの引数はメッセージに含めない（G.4）。

- `allow`：要求を転送し，サーバの応答を返す。
- `deny`：`isError: true` のツール結果で応答し，その本文に，結果の理由，規範，保留，`fallback`，
  `notify` を書く。MCPは，ツール実行のエラーとプロトコルのエラーを区別する。前者は，クライアントが
  モデルに渡し，モデルが自ら修正できるようにするものである。後者は，モデルが修正できそうにない
  要求のためのものである。拒否は前者にあたる。送信者は，例えば代替のメッセージを送ることで，
  拒否に対処できる。
- `escalate`：要求を保留し，まだ応答しない。MCPでは，クライアントは複数の要求を同時に
  送ってよいので，保留中の呼び出しは他の呼び出しを止めない。保留が閉じたとき，解放された呼び出しは
  転送し，それ以外の閉じ方（G.6）には拒否として応答する。クライアントが保留中の要求を取り消すと
  （`notifications/cancelled`），その要求は取り下げられる（G.6）。

`tools/call` 以外のメソッドは規範が統治しない。決定関数には，それらについて決めることがない。
したがってゲートウェイは，明示的に許可されたメソッドだけを通し，クライアントのものでもサーバの
ものでも，それ以外のメソッドはJSON-RPCのエラーで拒否する。拒否は記録することが望ましい
（`method_refused`，G.8）。ライフサイクルと発見のメソッド，および `tools/list` は，クライアントが
ツールを呼び出すためにそもそも必要なものである。MCP 2026-07-28では，stdio上でサーバは要求を送らず，
クライアントは応答を送らない。それ以前のリビジョンでは，サーバはクライアントにサンプリングや
情報要求を求めることができた。ゲートウェイは，そのような要求を許可されたときだけ通す。応答は，
逆方向で処理中の要求に対するものだけを通す。保留中または拒否した呼び出しに対する応答は，
サーバがその要求を受け取っていないので，捨てる。

ゲートウェイはメッセージを1回だけ読み，読んだ内容を転送する。受け取ったバイト列をそのまま転送することはない。
そうしなければ，相手側の読み手が例えば復帰文字で別の位置に区切る行によって，ゲートウェイが
判定していない要求が通ってしまう。重複したキーのない1つのJSON-RPCのメッセージでない行は拒否する。

`tools/list` の結果は，ファイルがそのサーバについて宣言したツールだけに絞ってよい。
他のツールの呼び出しは，いずれにせよG.5の手順2で拒否される。承認者のメッセージ（G.6）と，
付与（G.7）のようなエージェント間のメッセージは，MCPのゲートウェイを通らない。それらは，
配備が用意する別の通信路でゲートウェイに届く。その通信路は，誰が発言しているかを認証しなければ
ならない。承認は承認者の鍵で認証し，実行，保留，保留中のメッセージ，その引数に結び付け，
1回だけ使う。判定は引数に依存しない（G.4）が，承認者は何を承認するかを知るために引数を見る
必要がある。鍵が承認者どうしを区別するのは，各承認者の鍵が他の誰からも読めない場合だけである。
ゲートウェイのアカウントを共有する承認者やエージェントは，ゲートウェイが持つすべての鍵を読める。
したがって，各承認者は自分のアカウントを持つか，別の方法で承認者を認証する通信路を使う必要がある。
ファイルによる通信路が守るのは，鍵ファイルを読めない者に対してだけである。すでに転送した
呼び出しの取消しはサーバに伝え，サーバがまだ応答できるので，その呼び出しは処理中のままにする。
MCP 2026-07-28では，サーバは `tools/call` に，さらに入力を求める結果で応答できる。そのとき
クライアントは，新しい要求として呼び出しを送り直す。ゲートウェイは，送り直されたメッセージに
ついてG.6が述べるとおり，それをもう一度判定する。

**A2A。** A2Aはエージェントどうしをつなぐ。エージェント *X* からエージェント *Y* への
`SendMessage` の要求は `Message` を運ぶ。`Message` は `role`，`parts`，`messageId` を持ち，
`contextId`，`taskId`，`metadata`，`extensions` を持ってもよい。A2Aのどのバインディング
（JSON-RPC，gRPC，HTTPとJSON）についても，*Y* の前に置くゲートウェイは，そのような要求を
次のようにメッセージ `X -> Y : e` に対応づける。`SendStreamingMessage` も同じメッセージであり，
ストリームのイベントを一つも渡す前に判定する。`cadl` 0.3.25から，リファレンス実装はJSON-RPCの
バインディングについてこれを行い，0.3.26からはそのストリームについても行う。その解釈はG.13に示す。

- *X* は要求の認証されたクライアントである。A2Aは，*Y* のエージェントカードのセキュリティスキームで
  クライアントを認証する。ゲートウェイはその身元をファイルのアクターに対応づける。認証された身元が
  なければ送信者がなく，メッセージは拒否する。
- A2Aのメッセージは操作の名前を持たない。名前 *e* と，承認の保留のidのようなその引数は，拡張から
  得る。メッセージは拡張のURIを `extensions` に挙げ，`metadata` のそのURIのもとに
  `{"name": "approve", "args": ["h-1"]}` を運ぶ。拡張を持たないメッセージは名前がなく，拒否する。
- `allow`：要求を転送する。`deny`：状態 `TASK_STATE_REJECTED` のタスクで応答し，その状態の
  メッセージに理由と代替のメッセージを書く。A2Aはこの状態を，エージェントがタスクを実行しないと
  決めたことと定義している。`escalate`：要求を転送しない。ブロックする `SendMessage` は保留が
  閉じるまで待つ。`returnImmediately` があるときは，ゲートウェイは自らのタスクを
  `TASK_STATE_SUBMITTED` で返し，後で転送または拒否として確定させる。状態
  `TASK_STATE_INPUT_REQUIRED` と `TASK_STATE_AUTH_REQUIRED` は保留に合わない。これらは送信者に
  入力を求める状態であり，保留が待つのは承認者である。
- 承認者の承認は，それ自体が，名前 `approve` を持ち，保留のidを最初の引数とする承認者のA2Aの
  メッセージであってよい（G.12と同じ）。それは他のメッセージと同じく判定される（G.6）。
  そのようなメッセージは保留だけを名指すので，他の通信路による承認と同じく（上記），保留中の
  メッセージとその引数に結び付ける必要がある。リファレンス実装のゲートウェイは，承認をA2Aの
  メッセージとしては受け付けない（G.13）。

## G.12 例

人のオペレータが，LLMのプランナーに報告書の作成を依頼する。プランナーは2つのツールサーバの
ツールを呼び出し，ファイルの要約にサブエージェントを使う。このファイルは，本付録の
すべての規則と，[付録F](./appendix-f-norms.md)のN-1からN-12を満たす。

```yaml
sos:
  name: "AssistedReporting"
  extensions:
    - norms: 0.1
    - agents: 0.1

  actors:
    - id: OPERATOR
      role: "Human operator who owns the task and the files"
      agent: { kind: human }
    - id: PLANNER
      role: "LLM agent that plans the report and calls tools"
      agent: { kind: llm_agent, protocol: a2a }
    - id: SUMMARIZER
      role: "LLM sub-agent that summarises files for the planner"
      agent: { kind: llm_agent, protocol: a2a }
    - id: FILES
      role: "File store"
      agent: { kind: tool_server, protocol: mcp, tools: [read_file, delete_file] }
    - id: TICKETS
      role: "Issue tracker"
      agent: { kind: tool_server, protocol: mcp, tools: [search_tickets, create_ticket] }

  contracts:
    - id: ASSISTED_REPORTING
      parties: [OPERATOR, PLANNER, SUMMARIZER, FILES, TICKETS]
      enforcement:
        point: gateway      # default: を省略 -> ツール呼び出しは deny，他のメッセージは allow
      counts_as:
        - { when: "OPERATOR -> PLANNER : approve", creates: approval }
        - { when: "OPERATOR -> PLANNER : reject",  creates: rejection }
      norms:
        - id: may_read
          kind: permission
          bearer: OPERATOR
          content: "OPERATOR -> FILES : read_file"
        - id: may_search
          kind: permission
          bearer: PLANNER
          content: "PLANNER -> TICKETS : search_tickets"
        - id: may_file_ticket
          kind: permission
          bearer: PLANNER
          content: "PLANNER -> TICKETS : create_ticket"
        - id: no_delete
          kind: prohibition
          bearer: PLANNER
          content: "PLANNER -> FILES : delete_file"
          on_denied:
            escalate_to: OPERATOR
            timeout: 10min
            fallback: "PLANNER -> TICKETS : create_ticket"
            notify: OPERATOR
      delegations:
        - norm: may_read
          to: [PLANNER, SUMMARIZER]
          grant: grant_read
          revoke: revoke_read
          max_depth: 2
```

この契約は `lifecycle:` ブロックを持たず，インスタンスを生成するホストもない。
そのため，その単一のインスタンス（ここでは `default` と呼ぶ）は，判定点の開始時から存在する。
4つの規範は発動条件を持たない。開始時から効力を持ち，4つとも静的である（G.10）。
読み取りの許可はオペレータのものである。プランナーとサブエージェントは，高々2つのリンクに
わたる委任を通じてのみ読み取る。

09:00:00にオペレータが `OPERATOR -> PLANNER : grant_read` を送り，09:00:02にプランナーが
`PLANNER -> SUMMARIZER : grant_read` を送る。どちらも，どの規範も適用されない
通常のメッセージであるため，既定値によって許される。1つ目は，連鎖 OPERATOR → PLANNER を持つ
`may_read` の派生インスタンスを `PLANNER` のために作り，2つ目は，連鎖
OPERATOR → PLANNER → SUMMARIZER を持つ派生インスタンスを `SUMMARIZER` のために作る。
さらに `SUMMARIZER -> PLANNER : grant_read` が送られたとすれば，権限のない行為として
記録される。`PLANNER` は `SUMMARIZER` の連鎖に現れ（条件3），その連鎖はすでに2つのリンクを
持つ（条件4）からである。

**呼び出し1：連鎖を通じて許される。** 09:00:05にサブエージェントが
`SUMMARIZER -> FILES : read_file` を送る。このメッセージは統治され，ツールは宣言されている。
禁止は適用されない。送信者が `no_delete` の負担者でないからである。`SUMMARIZER` の
派生インスタンスは有効であり（`may_read` は効力を持ち，連鎖は2つのリンクを持ち，
そのアクターは `to:` にある），保持者を送信者として読んだその内容は一致する。
決定は `allow` である。

**呼び出し2：エスカレーションされ，承認される。** 09:03:00にプランナーが
`PLANNER -> FILES : delete_file` を送る。`no_delete` は効力を持ち，適用される。
それは唯一の根拠であり，その `escalate_to:` は送信者でないため，決定は `escalate` である。
承認者 `OPERATOR` と期限09:13:00を持つ保留 `h-1` が作られる。09:03:40にオペレータが
`OPERATOR -> PLANNER : approve("h-1")` を送る。これは，既定値によって許される
通常のメッセージである。その観測の段階1の後，`OPERATOR` が行った事象 `approval` が
保留のid `h-1` を持ち，保留は `approved` になる。段階6の後，メッセージをもう一度決定する。
ツールは宣言されており，根拠のインスタンスは動作中であり，根拠以外に適用される禁止はなく，
この呼び出しを統治する他の強制される契約もない。そのため，保留された
メッセージは，時刻印09:03:40を持つ次の観測になる。これは `no_delete` の内容が
起こったことにはならず，`no_delete` は `active` のままである。オペレータが `reject("h-1")` を
送った場合，または09:13:00まで何も送らなかった場合，終結記録は，理由 `rejected` の `deny`，
または時刻09:13:00を持つ `expired` の `deny` になる。プランナーは結果から代替のメッセージを
得て，`may_file_ticket` がその呼び出しを許す。

**呼び出し3：取消しの後に拒否される。** 09:10:00にオペレータが
`OPERATOR -> PLANNER : revoke_read` を送る。`PLANNER` の連鎖の中で `OPERATOR` は `PLANNER` より
前に現れるため，`PLANNER` のインスタンスは解除され，それとともに，連鎖に `PLANNER` が現れる
`SUMMARIZER` のインスタンスも解除される。09:10:30にサブエージェントが
`SUMMARIZER -> FILES : read_file` を送る。禁止は適用されない。`SUMMARIZER` は有効な許可を
保持しておらず，元の `may_read` は，送信者がその負担者でないため適用されない。
このメッセージはツール呼び出しであり，`default:` は省略されているため，契約は拒否する。
サブエージェントは，プランナーがもはや持っていない権限を保つことができない。

3つの呼び出しの監査記録を示す（呼び出し2の2つの記録は保留 `h-1` を共有する）。
4つの記録のすべてで，`instances` は `ASSISTED_REPORTING` のインスタンス `default` であり，
`contracts` は `["ASSISTED_REPORTING"]` である。呼び出し2の最初の記録は，表の下に
全体を示す。

| `time` | `message` | `decision` | `reason` | `norms` | `provenance` | `hold_id` | `outcome` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 09:00:05 | `SUMMARIZER`, `FILES`, `read_file` | `allow` | `permission` | `may_read` | OPERATOR, PLANNER, SUMMARIZER | `null` | `null` |
| 09:03:00 | `PLANNER`, `FILES`, `delete_file` | `escalate` | `prohibition` | `no_delete` | — | `h-1` | `null` |
| 09:03:40 | `PLANNER`, `FILES`, `delete_file` | `allow` | `approved` | `no_delete` | — | `h-1` | `approved` |
| 09:10:30 | `SUMMARIZER`, `FILES`, `read_file` | `deny` | `default` | — | — | `null` | `null` |

```jsonc
{ "time": "2026-11-10T09:03:00Z",
  "message": { "from": "PLANNER", "to": "FILES", "name": "delete_file" },
  "instances": [ { "contract": "ASSISTED_REPORTING", "instance": "default" } ],
  "decision": "escalate", "reason": "prohibition",
  "contracts": ["ASSISTED_REPORTING"],
  "norms": ["ASSISTED_REPORTING.no_delete"], "provenance": [],
  "escalate_to": "OPERATOR", "timeout": 600000,
```

## G.13 IRへの追加とリファレンス実装の状況

シミュレータIR（E.7，F.9）を3か所で拡張する。そこと同じく，IRはデータクラスを
そのまま直列化したものであり，入れ子のブロックを平らにする。

```jsonc
// each actor under institution.actors
{ "id": "FILES",
  "agent_kind": "tool_server",          // null for an actor without agent:
  "agent_protocol": "mcp",
  "agent_tools": ["read_file", "delete_file"] }

// each contract under institution.contracts
{ "enforced": true,
  "enforcement_default": null,
  "enforcement_point": "gateway",
  "norms": [
    { "id": "no_delete",                // ... and the fields of F.9
      "on_denied_escalate_to": "OPERATOR",
      "on_denied_timeout_ms": 600000,
      "on_denied_fallback": "PLANNER -> TICKETS : create_ticket",
      "on_denied_notify": "OPERATOR" } ],
  "delegations": [
    { "norm": "may_read", "to": ["PLANNER", "SUMMARIZER"],
      "grant": "grant_read", "revoke": "revoke_read",
      "max_depth": 2, "until": null } ] }
```

`enforced` は，契約がキー `enforcement:` を持つとき，値がnullまたは空であっても，
`true` である。`enforcement_default` は，`default:` を省略したときは `null` である。
そのときの既定値はメッセージの種類に依存するからであり，それを適用することは利用側に委ねる。
`enforcement_point` は，強制される契約では値を持ち（`gateway`），それ以外では `null` である。
`max_depth` は常に値を持つ（`1`）。`fallback` と `until` はテキストのまま保持する。
`agent_tools` と `delegations` は，列挙するものがないときは空のリストであり，4つの
`on_denied_*` フィールドは，`on_denied:` を持たない規範では `null` である。
ここに示したすべてのフィールド（`agent_*`，`enforced`，`enforcement_*`，`delegations`，
`on_denied_*`）は，ファイルが `agents: 0.1` を宣言するときにだけ存在する。
`norms: 0.1` だけを宣言するファイルは，F.9のIRとちょうど同じIRを持つ。

**リファレンス実装。** `cadl` 0.3.20は，agents 0.1を次のように実装する。
4つの新しいキーを構文解析し，`cadl check` でG-1からG-16を適用し（「望ましい」は警告とする。G-17からG-19は，0.3.21の次の
リリースから適用する），
各ブロックを上のIRへ変換する。単位のない数値で与えた `timeout:` は秒として読む。これは，
[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)が
期限について述べる寛容な形式である。`cadl agents-decide` は，G.10の方針の入力に対して
G.5の決定関数を実装する。このコマンドは状態を持たない。効力のフラグと有効な派生インスタンスは，
入力を通じて与える。
`cadl codegen -t agent-rego` は，完全な結果を返すRegoの方針を出力し，
`-t agent-cedar` は，静的な規範に対するCedarの方針を，付随する表とともに出力する。

**ランタイム。** `cadl` 0.3.22は，G.5からG.8のリファレンスランタイムである
`cadl agents-run FILE --trace TRACE [--audit OUT.jsonl]` を追加する。このランタイムは決定的で，
オフラインで動作する。記録済みのメッセージの列を，ファイルのすべての強制される契約にわたる
1つの判定点に通して再生する。時計はトレースの時刻だけである。メッセージごとに，効力のフラグを
`cadl norms-eval` の判定エンジン（F.10）から，有効な派生インスタンスをそれまでに観測した
付与と取消しから，動作中の契約インスタンスをトレースから得る。それらからG.10の方針の入力を
組み立て，`cadl agents-decide` の決定関数を呼ぶ。次に，G.5のとおりに決定を適用し，保留と
派生インスタンスを保持し（G.6，G.7），承認されたメッセージを解放する前にもう一度決定し，
G.8の監査記録と事象記録を書く。`--audit` を与えたときは，
記録をJSON Linesとして出力する。保留のidは，作られた順に `h-1`，`h-2`，…である。

**完全性とオンラインでの利用。** `cadl` 0.3.24は，G.8の「ログの完全性」の形式で監査ログを書く。
`--audit` はSHA-256のダイジェストの連鎖を与え，`--audit-key FILE` はFILEの鍵（16バイト以上）による
HMAC-SHA256で連鎖に鍵をかける。使うのはPythonの標準ライブラリだけである。ヘッダの `run_id` は，
トレースの先頭行にキー `run_id` があればその値，なければ乱数である。したがって，トレースが実行を
名指さない限り，同じトレースの2回の実行はヘッダとダイジェストが異なる。再生がバイト単位で
再現するのは，先頭行に `run_id` があるときだけである。先頭行のキー `approvals` はヘッダに写す。
`agents-run` は，どのトレースの `withdraw` と `host_events` も受け付ける。したがって，トレースから
再生したログの中のホストの事象記録は，トレースが述べたことにすぎず，それ以上は何も証明しない。
`cadl audit-verify AUDIT.jsonl [--key FILE] [--source FILE.cadl] [--run-id HEX] [--anchor DIGEST]
[--open]` は，検証できない最初の行を，期待した値と実際の値とともに報告する。`--source` は
CADLファイルのハッシュ，`--run-id` は実行，`--anchor` は別に保管した最後の行のダイジェストの
一致も求め，`--open` は終了記録のないログを受け入れる。終了ステータスは，有効なログでは0，
無効なログでは1，使い方の誤りでは2である。鍵を与えずに鍵つきのログを検証するのも，使い方の
誤りである。記録の値とフィールドの順序は0.3.23と同じである。整数でない数は，G.8の正規形の
とおり指数を使わずに書く。同じリリースで，ランタイムをオンラインで使えるようになった。
判定点をファイルについて開き，トレースの各行をそれが起きたときに与え，最後に閉じる。閉じることは，
最終行 `{"t": t}` にあたる。`cadl agents-run` は同じ処理の繰り返しである。

**MCPのゲートウェイ。** `cadl mcp-gateway FILE --agent A --server-actor S --audit OUT.jsonl
-- COMMAND`（0.3.24）は，MCP 2026-07-28のstdioトランスポート（JSON-RPC 2.0，1行に1つの
メッセージ）上の，G.11のMCPのゲートウェイである。COMMANDでサーバを起動し，自らの標準入出力で
クライアントと通信する。G.11についての解釈は次のとおりである。

- 両方向のすべての行を厳密に構文解析する。末尾の1つのCRLF以外の復帰文字，不正なUTF-8，
  どの深さでも重複したキー，NaN，無限大，無限大にあふれる数（`1e999`），100を超える配列や
  オブジェクトの入れ子，単独のサロゲートがあれば，その行は不正であり（JSON-RPCのエラー
  -32700 または -32600），転送しない。転送するのは，構文解析したオブジェクトを，非ASCII文字を
  すべてエスケープした詰めたJSONである。
- 失敗しうる処理は，呼び出しを判定する前にすべて行う。送る行と，その `params` の正規形JSONの
  SHA-256である（2<sup>53</sup>を超える整数のように正規形を持たない引数は -32602 で拒否する）。
  それでも許可または解放の後に送信に失敗したときは，クライアントに -32603 を返し，ログに事象
  `forward_failed` を書く。失敗によって拒否する保留中の呼び出しは，ランタイムが記録できる間に，
  先にランタイムで取り下げる。
- `--allow-method` なしで通すのは，`initialize`，`notifications/initialized`，`ping`，
  `server/discover`，`notifications/cancelled`，`notifications/progress`，`tools/list`，および
  `tools/call` である。判定するのは `tools/call` だけである。サーバからは，通知
  `notifications/progress`，`notifications/message`，`notifications/cancelled`，
  `notifications/tools/list_changed` を通す。クライアントのものでもサーバのものでも，その他の
  メソッドは -32601 で拒否し，`method_refused` として記録する。
- ツール呼び出しは到着した時刻に判定し，到着順に1つずつ判定する。拒否は `isError: true` の
  ツール結果である。`tools/list` の結果は，`--no-filter-tools` を与えない限り，宣言されたツール
  だけを残す。応答は，逆方向で処理中の要求に対するものだけを通し，それ以外は捨てて
  `unsolicited_response` として記録する。取り消された保留中の呼び出しは取り下げる。トレースには
  `"withdraw": ["h-1"]` と書く。
- ゲートウェイはフェイルクローズである。判定の処理が例外を出したとき，またはトレースやログに
  書けないときは，その呼び出しを拒否し，以後の呼び出しもすべて拒否し，ログには終了記録を
  書かない。サーバが終了したときは，処理中の要求と保留中の呼び出しにエラー -32603 で応答する。
- 承認，却下，その他のメッセージは，ゲートウェイの利用者が所有し，他の誰も書き込めない
  ディレクトリを通じて届く。読むのは，その利用者の，リンクが1つの通常ファイルだけである。
  `--approver-keys KEYS.json` を与えると，各ファイルを，発言するアクターの鍵による，G.8の
  正規形JSONに対するHMAC-SHA256で認証する。`cadl mcp-approve DIR HOLD_ID approve|reject
  --as ACTOR --key FILE` は，保留中の呼び出しとその引数を表示し，実行，保留，保留中の
  メッセージ，保留の時刻，引数のSHA-256（ゲートウェイがディレクトリに公開する）と新しい
  ノンスを名指す承認を書く。ゲートウェイはそれを，`approval`
  （`rejection`）を作る `counts_as:` 規則の承認者のメッセージに変換する。保留のidはその最初の
  引数であり，その前に事象記録 `approval_evidence` を書く。その理由は，ファイルと引数の
  SHA-256，承認者の鍵のID，ノンスを示す。MACが検証
  できないファイル，他の実行や他の保留中のメッセージを名指すファイル，使用済みのノンスを持つ
  ファイルは何も変えず，理由 `unauthenticated`，`wrong_run`，`wrong_message`，`replayed` の
  いずれかで `unauthorised_approval` として記録する。`cadl mcp-message DIR 'X -> Y : n' --key FILE`
  は，付与のようなその他のメッセージを，送信者の鍵で認証して書く。鍵がなければ，
  `--insecure-approvals` を与えない限り，ゲートウェイはディレクトリを拒否する。
  `--insecure-approvals` はテストのためのものであり，その方法で受け入れた承認は
  `approval_unauthenticated` として記録する。トレースの1行目とログのヘッダは，その実行の方式を
  示す（`approvals`）。
- 時刻は開始からの単調時計の時刻であり，秒単位でミリ秒に丸める。トレースの1行目は，乱数の
  `run_id` と，`t = 0` の実時刻としての `epoch` を与える。ゲートウェイは，各処理を判定する前に
  トレースに書く。判定した各メッセージ，保留の期限が過ぎたときの行 `{"t": t}`，`withdraw` と
  `host_events` の行，停止するときの最終行 `{"t": t}` である。そのトレースに対する
  `cadl agents-run` は，同じ判定をし，バイト単位で同じ監査ログを書く。

連鎖のテストは，10行のログ2つ（鍵なしと鍵つき，それぞれ約5 100バイト）のすべてのバイトを，
それぞれ2通りに変える。変えた20 434個のログは，すべて検証を通らない。行の削除，同じログまたは
他のログの行の挿入，隣り合う行の入れ替え，末尾の切り取り，書き直したヘッダ，重複したキー，
値を変えずに変えた空白，エスケープ，数の書き方，他のCADLファイルや他の実行のログをこのファイルに
ついて検証した場合，書き直したログや切り取ったログをアンカーと照合した場合も，すべて検証を
通らない。G.8に述べたとおり，ログ全体の書き直しは鍵がなければ検証を通り，鍵があれば通らない。
鍵つきのログを鍵なしとして書き直したものは，鍵を与えなければ検証を通る。ゲートウェイは，
偽のMCPサーバと偽のクライアントを別のプロセスとして，ネットワークを使わずに，また偽の時計を
使って同じプロセスの中で試験する。対象は，G.12のシナリオ（許可，許可がないための拒否，
未宣言のツール，承認・却下・期限切れと代替のメッセージに終わるエスカレーション，付与と委任に
よる呼び出し，取消し），不正な入力，サーバの終了，保留中の呼び出しを残したクライアントの切断，
読めない承認と他の保留を名指す承認，3つ目を保留したまま処理中の2つの呼び出しである。
ゲートウェイの最初のバージョンに対する独立したレビューは，次の欠陥を見つけた。クライアントは，
単独の復帰文字によって別のメッセージの中に完全な `tools/call` を隠すことができ，復帰文字も行の
終わりとみなして読むサーバは，それを判定も記録もなしに実行した。重複したキーを，ゲートウェイは後の値で
読み，サーバは先の値で読むことがありえた。末尾に改行を持つツール名がゲートウェイを停止させた。
`tools/call` 以外のすべてのメソッドが判定なしに通った。サーバが保留中の呼び出しに応答できた。
受け箱はリンクをたどり，他者が書き込めた。承認の中の単独のサロゲートがゲートウェイを停止させた。
承認は認証されていなかった。取り消した後に承認された呼び出しは，解放されたと記録された。
いずれも修正し，それぞれに修正の前には失敗したテストがある。行は厳密に構文解析し，直列化し直して
転送する。メソッドは一覧によって通し，応答は処理中の要求に対するものだけを通す。承認は認証し，
実行，保留，保留中のメッセージに結び付ける。取り消された呼び出しは取り下げる。どのシナリオでも，
サーバは許可または解放されていない呼び出しを受け取らず，ゲートウェイが書いたトレースに対する
`cadl agents-run` は，ゲートウェイとバイト単位で同じ監査ログを書く。ランタイムの変更は，
`cadl` 0.3.23と照合した。309組のファイルとトレース（同梱のトレース，テストのレビュー用ファイルの
すべての組，不正なトレース4つ）に対する `agents-run` は，テキストとJSONの両方で，終了ステータス，
出力，エラーメッセージ，監査ログの値が同じであった。テストスイートが実行する1 917回の再生のうち，
新しいキーを持たないトレースに対する1 885回は，0.3.23のランタイムと同じ結果，または同じエラーを
与えた。残りの32回は，`withdraw` または `host_events` を持つゲートウェイのトレースであり，0.3.23は
これらを読まない。2回目のレビューは，無限大にあふれる数（`1e999`）が構文解析を通り，判定の後で
転送を失敗させるため，送られなかった呼び出しが許可または解放されたとログに残ること，および
承認者が承認する呼び出しの引数を見られないことを見つけた。いずれも修正し，修正の前には失敗した
テストがある（送信の失敗を注入するテストと，同じツールの2つの呼び出しを同じ時刻に異なる引数で
保留し，一方の承認が他方を解放しないことを確かめるテスト）。

**A2Aのゲートウェイ。** `cadl` 0.3.25から，`cadl a2a-gateway FILE --agent-actor Y --upstream URL
--client-keys KEYS.json --audit OUT.jsonl` は，A2A 1.0.0のJSON-RPCバインディングについての，G.11の
A2Aのゲートウェイである。ファイルのエージェント `Y`（`kind: llm_agent`，`protocol: a2a`）の前に
置くHTTPサーバであり，要求をURLのエージェントに渡す。判定点，トレース，ログ，保留，受け箱は
MCPのゲートウェイと共通であり，そのトレースに対する `cadl agents-run` はバイト単位で同じ監査ログを
書く。G.11が実装に任せている点では，要求を通す場合が少なくなる方を選ぶ。解釈は次のとおりである。

- 送信者は，本文をJSONとして読む前に，要求ごとに認証する。A2Aは方式をエージェントカードに
  委ねている。ゲートウェイは，承認と同じくアクターの鍵を使う。要求はヘッダ
  `Authorization: CADL-HMAC actor="X", nonce="N", mac="M"` をちょうど一つ持つ。`X` は具体的な
  アクター，`N` は小文字の16進数32桁，`M` は小文字の16進数64桁である。`M` は，オブジェクト
  `{"scheme": "cadl-a2a-request/1", "actor": X, "run_id": R, "nonce": N, "method": "POST",
  "path": "/", "body_sha256": D}` のG.8の正規形JSONに対する，`X` の鍵でのHMAC-SHA256である。
  `R` はゲートウェイの実行ID，`D` は本文のSHA-256を小文字の16進数で書いたものである。フィールド
  `scheme` は，このMACを受け箱のファイルのMACと区別する。一つのアクターが両方に同じ鍵を使う場合も
  区別できる。ヘッダ `A2A-Version` と `Content-Type` はMACの対象ではない。ノンスは一つの実行の中で
  一度だけ受け付ける。ゲートウェイは実行中のノンスをアクターごとにメモリに保持するので，メモリは
  認証された要求の数とともに増える。一つのアクターの要求が1000000に達すると，ゲートウェイを起動し
  直して実行IDが変わるまで，そのアクターの以後の要求を拒否する（理由 `nonce_limit`）。他のアクターの
  要求には影響しない。Bearerトークンは，見た者が誰でも送り直せるので
  受け付けない。鍵を持つアクターは，すべてファイルのアクターでなければならない。正しいヘッダのない
  要求には，実行IDを添えてHTTP 401で応答し，`unauthenticated_request` として記録し，判定はしない。
- G.11の拡張のURIは `https://www.ertl.jp/cadl-spec/a2a/agents-message/v0.1` である。その値は
  `{"name": e, "args": [...]}` であり，`e` は64文字以下の識別子，引数は256文字以下の文字列で16個
  までである。拡張を持たないメッセージには拒否のタスクで応答し，判定せずに，理由 `no_name` の
  `unauthorised_message` として記録する。値の形が違うときは，JSON-RPCのエラー -32602 である。
  `--agent-card` で与えるエージェントカードは，`capabilities.extensions` にこの拡張を宣言して
  いなければならない。宣言していなければ，ゲートウェイは起動しない。
- 承認はA2Aのメッセージとしては受け付けない。`approval` または `rejection` を作る `counts_as:` 規則の
  メッセージと同じ名前のメッセージは，規則の受信者が何であっても拒否し，理由 `approval_as_message` の
  `unauthorised_message` として記録する。承認は，MCPのゲートウェイと同じく受け箱から届き，保留中の
  メッセージの引数，すなわちその `SendMessage` の `params` の全体に結び付く。A2Aのメッセージで
  承認を送ると，保留のIDしか運べず，承認者が見た内容に結び付けられない。受け箱からの承認は
  ランタイムに与えるだけで，どこにも届けない。そのため，そのような規則の受信者が集合，範囲，または
  添字変数であるときは，次のとおり具体的なアクターとする。添字変数の値は，保留の根拠となった
  契約インスタンスのうち，その規則と同じ契約のものの束縛から取る（0.3.26から）。それ以外では，参照がゲートウェイの
  アクター（`Y`，MCPのゲートウェイではツールサーバ）に一致しうるときはそのアクター，そうでなく，MCPのゲートウェイで
  参照がそのクライアント（`--agent`）に一致しうるときはそのクライアント，どちらでもないときは集合の
  最初に宣言された要素である。ゲートウェイのアクターが当事者である契約が保留を作るのに，`approval` を
  作る `counts_as:` 規則を持たないとき，ゲートウェイは起動しない。そのようなファイルは，すでにG-9に
  よって誤りである。
- 判定するのは `SendMessage` と `SendStreamingMessage` だけである。`GetTask`，`CancelTask`，
  `SubscribeToTask` はアクター間のメッセージを運ばない。これらは，この実行の中でエージェントまたはゲートウェイが同じアクターに与えたタスクに
  ついてだけ，判定せずに通す。`CancelTask` はエージェントの状態を変えるので，渡す前に `task_cancel`
  として記録する。`GetTask` と `SubscribeToTask` は記録しない。`SendMessage` が名指すタスク（`taskId`，`referenceTaskIds`）と
  コンテキスト（`contextId`）も，そのようなものに限る。それ以外は `TaskNotFoundError`（-32001）であり，
  `task_refused` として記録する。ゲートウェイが見たことのないコンテキストIDも拒否する。他の
  クライアントや以前の実行のコンテキストかもしれないからである。タスクはIDで区別するので，`tenant` は
  拒否する（-32602）。`ListTasks` と `GetExtendedAgentCard` は `UnsupportedOperationError`（-32004）で拒否し，プッシュ通知のメソッドと，プッシュ通知の設定を持つ
  `SendMessage` は `PushNotificationNotSupportedError`（-32003）で拒否し，その他のメソッドは -32601 で
  拒否する。いずれも `method_refused` として記録する。ヘッダ `A2A-Version` は，前後のスペースを除いて
  `1.0` または `1.0.N` でなければならない。そうでないとき，ヘッダがないときも含めて，要求は
  `VersionNotSupportedError`（-32009）になる。A2A 1.0.0では，ヘッダがないことはバージョン0.3を
  意味するからである。
- 拒否は，状態 `TASK_STATE_REJECTED` のゲートウェイのタスクであり，その状態のメッセージに理由，
  規範，保留，代替のメッセージ，`notify` を書く。保留された要求のうち，応答を待つ（ブロッキングの）
  要求には，保留が閉じるまで応答しない。`returnImmediately` があれば，クライアントは状態
  `TASK_STATE_SUBMITTED` のゲートウェイのタスクを受け取る。このタスクは解放の後もIDを変えず，
  エージェントのタスクをそのIDで示す。解放した要求を渡せなかったときは，このタスクを
  `TASK_STATE_FAILED` にし，ログに `forward_failed` を書く。保留中の要求のタスクを取り消した
  クライアントと，保留中の応答を待つ（ブロッキングの）要求の接続を閉じたクライアントは，要求を
  取り下げる（G.6）。要求が保留されている間にクライアントが送るバイトは，読んで捨てる。送信側だけを
  閉じた接続（ハーフクローズ）も閉じたものとみなし，要求を取り下げる。取り下げは判定点の処理の
  一つであり，応答は保留を閉じた記録に従う。その処理の前に期限が過ぎていた保留は `expired` に
  なり，クライアントは拒否のタスクを受け取る。
- ストリーム（`cadl` 0.3.26から）。`SendStreamingMessage` は，`SendMessage` と同じ検査をして，何も
  渡す前に一度だけ判定する。その応答はServer-Sent Eventsのストリームであり，各イベントは一つの
  JSON-RPCの応答を一つの `data:` 行に持ち，ゲートウェイが直列化し直したものである。許可した要求は
  ストリームとして渡し，エージェントのイベントを一つずつ中継する。各イベントは厳密に構文解析し，
  この要求への応答であり，同じクライアントの一つのタスクまたは一つのメッセージに属するものでなければ
  ならない。そうでなければ `InvalidAgentResponseError`（-32006，`invalid_response`）でストリームを
  終え，その後は何も渡さない。行末以外に復帰文字を含むエージェントの行も，同じくストリームを終える。
  エージェントのコメントは渡さない。拒否は，拒否のタスクという一つのイベントのストリームである。
  保留されたストリームは，保留が閉じるまでSSEのコメントを1秒ごとに送り，その後，解放した要求の
  イベントか，一つの拒否のタスクを送る。接続を閉じたクライアントは，応答を待つ（ブロッキングの）
  要求と同じく要求を取り下げる。`returnImmediately` があれば，保留されたストリームは一つのイベント，
  すなわちゲートウェイの提出済みのタスクであり，解放した要求は `SendMessage` として渡す。
  `SubscribeToTask` はクライアントのタスクを追う。エージェントのタスクにはそのストリームを渡す。
  保留中のゲートウェイのタスクには，保留が閉じるまでコメントを送り，その後，エージェントのタスクの
  ストリームをゲートウェイのタスクのIDで渡すか，最後のタスクを送る。したがって，クライアントに届く
  エージェントのイベントは，すべてそのクライアントの許可または解放された要求に属する。ストリームは，
  終わるか，クライアントが接続を閉じるまで，同時に処理する要求の一つとして数える。エージェントから
  イベントが来ない間も，ゲートウェイは，保留中の要求と同じくクライアントの接続から読み，1秒ごとに
  コメントを送る。接続を閉じたクライアントのストリームは終え，エージェントへの要求も終える。
  ストリームの要求に対してエージェントが通常のJSONで応答したときは，他の応答と同じく，16 MiBを
  上限とし，厳密なUTF-8として読む。ストリームが始まる前に見つけた誤りには，A2Aが
  認めるとおり，通常のJSON-RPCのエラーで応答する。
- プッシュ通知とgRPCのバインディングは引き続き拒否する。プッシュ通知の設定は，エージェント，または
  中継するゲートウェイが要求を送る，クライアントのURLを名指す。ゲートウェイは，ゲートウェイを置いた
  ネットワークの中から，クライアントが選んだアドレスに要求を送ることになり，これはサーバサイドリクエスト
  フォージェリである。gRPCのバインディングにはHTTP/2とProtocol Buffersが必要であり，標準
  ライブラリにはこれらがない。リファレンス実装は実行時の依存を加えない。
- 要求は，1 MiB以下の `Content-Length` を一つ持ち，`Transfer-Encoding` を持たないものとして読み，
  一つの接続で一つの要求だけを読む。本文はMCPのゲートウェイの行と同じく厳密に構文解析し，
  ゲートウェイのJSON-RPCのIDとヘッダを付けて，直列化し直して渡す。クライアントの `Authorization` は
  渡さない。コロンの前にスペースまたはタブのあるヘッダ行，折り返したヘッダ行，ヘッダの中の単独の復帰文字は，
  HTTP 400で拒否する（0.3.26から）。標準ライブラリの構文解析器は，そのような行をヘッダの終わりと
  みなすので，その後の `Transfer-Encoding` が見えなくなるからである。エージェントが別のアクターに与えたタスクやコンテキストは，そのアクターには示さない
  （-32006，`invalid_response`）。許可または解放の後に送れなかった要求は -32603 と `forward_failed`
  になり，送ったが正しい応答が返らなかった要求は -32006 と `invalid_response` になる。ループバック
  以外のアドレスにはTLSが必要であり，`--upstream-token` には `https` のエージェントかループバックの
  アドレスが必要である。
- 要求行，ヘッダ，本文は，合わせて10秒以内に届かなければならない（`--read-timeout`）。届かない
  ときは接続を閉じ，`read_timeout` として記録する。認証の前に同時に読む接続は，一つのリモート
  アドレス（IPv4のアドレス，またはIPv6のアドレスの/64のプレフィックス。一つのホストは通常/64を
  まとめて持つからである。IPv4射影IPv6アドレスはそのIPv4アドレスとして数える）について4個まで
  （`--max-readers-per-address`），一つのIPv4の/24またはIPv6の/48について16個まで
  （`--max-readers-per-prefix`，0.3.26から），全体で64個まで（`--max-readers`）である。すでに4個の
  接続を読んでいるアドレス，または16個を読んでいるプレフィックスからの接続には，すぐにHTTP 503で
  応答する（`overloaded`，`address` または `prefix`。0.3.26より前は応答せずに閉じた）。64個が
  すべて使われているときは，接続は空きを最大1秒待ち，空かなければHTTP 503を受け取る
  （`overloaded`，`readers`）。同時に処理する要求には，認証された要求だけを数え，保留中の要求も
  数える。その数は64個までであり（`--max-handlers`），それを超えるときはHTTP 503で応答する
  （`overloaded`，`handlers`）。したがって，認証されていない接続がクライアントの処理の枠を
  使うことはない。一つのアクターについては，同時に処理する要求を16個まで
  （`--max-handlers-per-actor`。保留中の応答を待つ要求と，遅いエージェントへの要求も数える），
  保留を，応答を待つかどうかにかかわらず64個まで（`--max-holds-per-actor`）とする。そのアクターの
  それを超える要求には，判定の前にHTTP 503で応答する（`overloaded`。理由は `handlers_per_actor`
  または `holds_per_actor` とアクター）。これにより，一つのクライアントが同時に処理できる数をすべて
  使うことも，保留を際限なく作ることもない。保留の上限に達したアクターは，保留にならない
  メッセージも送れない。`unauthenticated_request`，`overloaded`，`read_timeout` の記録は，事象ごとに
  1秒に20件までとする。その事象の次の記録は，記録しなかった要求の数を `reason` に
  `;not_recorded_before=N` として書く。すべての接続の読み込みの期限は，一つのスレッドで管理する。
  残る問題は次のとおりである。少なくとも四つの異なる/24（または/48）のネットワークにあるホストが
  ネットワークごとに16個ずつ接続し続ければ，64個の読み込みをすべて使い続けることができ，その間
  ゲートウェイは新しい接続をすべて拒否する。一つの/24または/48だけではそうできない。一つのプロセスは，
  認証の前にそのようなホストをクライアントと区別できない。これが問題になる場合は，接続の数を制限する
  プロキシやファイアウォールの後ろにゲートウェイを置く。プロキシの後ろでは，すべてのクライアントが
  プロキシのアドレスを持つので，`--max-readers-per-address` を大きくするか，要求を受け取り終えてから
  渡すプロキシを使う。

ゲートウェイは，ヘッダ `A2A-Extensions` を読まず，`ExtensionSupportRequiredError`（-32008）を
返さず，クエリパラメータとしての `A2A-Version` を読まず，部分 `raw` がbase64であることを検査しない。

**署名した保留。** `cadl` 0.3.26から，どちらのゲートウェイも `--hold-key FILE` を受け付ける。
このとき，受け箱に公開する保留はすべて `"kind": "hold"` と `hold_mac` を持つ。`hold_mac` は，
`hold_mac` を除いた保留のG.8の正規形JSONに対する，その鍵でのHMAC-SHA256である。保留は，実行，
保留中のメッセージ，時刻，引数とそのSHA-256を含む。`run.json` は `"holds_signed": true` を持つ。
`cadl mcp-approve --hold-key FILE` は，保留を表示または署名する前にMACを検証し，MACのない保留と
MACの誤った保留を拒否する。`--hold-key` がないときは，署名された保留を拒否する。署名のない保留には
警告を出すが，受け箱の `run.json` が `holds_signed` を示すとき，または `--require-signed-hold` を
与えたときは拒否する。受け箱に書ける者は `run.json` も書き換えられるので，`--require-signed-hold` は
受け箱に依存しない。どの場合も，表示する引数が，保留の示すSHA-256を持たないときは拒否する。
引数は，そのままの形で表示されない文字をすべて `\uXXXX` として表示する。制御文字，双方向の上書きや
幅のない文字のような書式文字，私用の文字，サロゲート，未割り当てのコードポイント，行と段落の
区切りである。保留の鍵はゲートウェイの鍵であり，ログの鍵とも，どの承認者の鍵とも，A2Aの
ゲートウェイではどのクライアントの鍵とも異なる。承認者は検証のためにこの鍵を持つ。したがって
承認者は，受け箱に書けてもこの鍵を読めない者が保留を書き換えたとき，その改ざんを検出できる。
ゲートウェイが承認者の鍵で承認の改ざんを検出するのと同じである。承認の認証は保留の鍵に依存しない。
保留の鍵がなくても，ゲートウェイは保留中のものと異なる引数の承認を拒否する（`wrong_message`）。
しかし，承認者に保留中のものと異なる引数が表示されることはありうる。承認者にとって保留が認証される
のは，`mcp-approve` に `--hold-key` を与えたときだけである。後方互換性のため，このオプションは
任意である。

トレースは `cadl norms-eval` のトレース（`t`，`bindings`，`request`，`values`，`messages`，
`state`，`amend`，`end` を持つJSON Lines）であり，判定点の全体について読む。キーを追加する。
`epoch` は，`t = 0` の時刻をISO 8601の時刻印で与え，記録の時刻を時刻印にする。`instances` は，
ホストが作り，終わらせる契約インスタンスを，その束縛とともに与える。`run_id` は先頭行に置く。
`withdraw` は，その行でホストがメッセージを取り下げる保留を与える（G.6）。`host_events` は
ホストの事象記録を与え（G.8），決定を変えない。どのインスタンスも，
その契約の当事者の添字変数を束縛しなければならない。ホストのない契約の唯一のインスタンスは，
先頭行の `bindings` によって束縛する。それぞれの値は，当事者が名指す集合の要素の添字で
なければならない。そうでなければ，契約，インスタンス，変数，値をメッセージに示して，
トレースを拒否する。どの当事者も持たない変数の束縛は，警告を出して無視する。
値は，当事者の集合だけでなく，契約の中でその変数が添字として用いられるすべての宣言済みの
集合の要素の添字でなければならない。先頭行のキー `quantities` は，実行の量の名前（F.5）を
与える。そのときは，ちょうどそれらの名前が，最初から，すべてのインスタンスについて，量である。
このキーがなければ，ランタイムは，名前に値を与える最初の行から，その名前を量として扱う。
これにより，どの決定も後の行に依存しない（G.5）。それまでに値を持たず，単独で現れる名前は，
記号的な値である。これは，同じ行に対する `cadl norms-eval` の判定と，名前が最初の値を
得るより前について異なることがある。述語が用いる名前が，メッセージを決定した後で
最初の値を得たとき，ランタイムは警告を出す。インスタンスの終了より後のものは，
そのインスタンスに影響しない。どの契約がホストの作るインスタンスを持つかも，同じく先頭行で
決まる。先頭行が `instances` で名指す契約，または，最初のインスタンスが後で作られる場合に
キー `host_instances` に挙げる契約は，トレースが作るインスタンスを持ち，それより前には
インスタンスを持たない。それ以外の強制される契約は，最初から唯一のインスタンスを持ち，
そのインスタンスを作る後の行は，トレースの誤りである。データの欠落によってフラグが不明で
ある間にメッセージを決定したとき（G.5），ランタイムは，規範ごとに1回，値を持たない量を
示して警告を出す。したがって，そのような量が最初の値を持つ前に送られたメッセージは，
拒否またはエスカレーションされる。それを避けるには，トレースの先頭行で初期値を与える。
委任可能な許可の `until:` が未定義である間に送られた付与は，その許可が効力を持つとは
わからないため，理由 `no_authority` の `unauthorised_grant` として記録され，送り直す必要がある。
データの欠落については，2つの限界が残る。未定義の `if:` のもとで，メッセージを止める効果を持つ事象を作るはずの
メッセージは，何も作らない（G.5，G-19）。ランタイムは，規則，事象，量を示して警告を出す。
また，この規則は義務を経る場合には及ばない。義務の述語の `trigger:` が未定義である間，
義務は発動されず，したがって違反にならず，その `reparation:` である禁止は生じない。1つの行は次の順に処理する。
期限がその行の時刻より前の保留が期限切れになる。`withdraw` の保留を取り下げる。
`host_events` を記録する。インスタンスを作る。行の時刻と値を，
メッセージなしで，改正とともに観測する（G.5）。各メッセージを決定し，許可されたメッセージは
1つの観測になる。ライフサイクル状態の変更とインスタンスの終了は，最後の観測になる。
インスタンスの終了より後のメッセージも，決定し，記録する。

次の3点は実装がとった解釈であり，本付録の規則ではない。改正は，2つのバージョンで定義が異なる
強制される契約に適用し，強制される契約を追加することも削除することもできない。違反の後も，
禁止の期間の時計は，違反の前と同じく（F.5），禁止が停止されている間は止まる。判定 `excused` に
関して，メッセージが義務の内容に一致するかどうかは，境界と同じく，送信者，受信者，名前で調べる。

既知の限界は次のとおりである。鍵がなければ，ログの連鎖は，変更した行から後を書き直したログを
検出しない。それを検出するには，最後のダイジェストを別の場所に保管する（`--anchor`）か，鍵を使う。
ヘッダの `hash` フィールドは認証されないので，検証者はログが鍵つきかどうかを知っている必要がある。
stdio上のMCPのゲートウェイとJSON-RPC上のA2Aのゲートウェイは，偽のサーバ，エージェント，
クライアントで試験しており，0.3.26からは上に挙げた公式のSDKでも試験している。それ以外の実装とは
試験していない。A2Aのゲートウェイには，ヘッダ
`CADL-HMAC` を計算するクライアントが必要である。タスクの所有者は一つの実行の間だけ保持し，
プッシュ通知，`ListTasks`，テナント，gRPCとHTTPとJSONのバインディングには対応しない。ゲートウェイが観測するのはメッセージと時刻であり，`values` は観測しない。量を読む規範には，その量はデータの欠落として
現れる（G.5）。ゲートウェイは，1行目より後に，ホストが作る契約インスタンスを作成も終了もしない。
承認者の道具は，ゲートウェイが公開する保留中のメッセージに署名するので，表示される内容に
ついてはゲートウェイを信頼する。`--hold-key` があれば，それをゲートウェイが公開したことを検証する。承認者の鍵が承認者どうしを区別するのは，各承認者が自分の
アカウントを使う場合だけである。ゲートウェイのアカウントを共有する者は，その鍵の一覧のすべての
鍵を読める。ディレクトリが守るのは，鍵ファイルを読めない者に対してだけである。
ログは，規範の効力のフラグの変化の記録を持たない（G.8）。`to:` の改正の後，派生インスタンスが `active` であるがもはや有効でない
保持者には，その許可を再び付与できない。その付与は，条件5により何もしない
（`holder_exists`）。トレースの時刻は，絶対値が2<sup>53</sup>以下の有限の数で与える。
`epoch` があるときは，すべての時刻と保留のすべての期限が，ISO 8601の時刻印で表せる時点で
なければならない。後の行のトレースの誤りは，何かを表示したり書いたりする前に報告するが，
それより前の行はすでにメモリ上で決定している。監査ファイルは，トレースの全体を再生したときに
だけ書く。ランタイムの関数は，
`cadl check` のエラーがあるファイルと，当事者の束縛を持たないインスタンスを拒否する。
テスト用のスイッチを使うと，その両方の拒否を無効にできる。不明な発生の解決（G.5）に到達するのは，
そのときだけである。決定関数 `cadl agents-decide` は，引き続き束縛のないインスタンスを
受け付け，その一致を不明として扱う（G.4）。`cadl` 0.3.22までは，ランタイムは，
`cadl norms-eval` と同じく，限量子または集約を含む述語を評価しなかった。`cadl` 0.3.23からは，
F.5の定めるとおりに評価する。定義域が開いているために未定義である限量述語は，データの欠落
（G.5）である。`cadl` 0.3.23までは，限量子の定義域の外のワイルドカード参照や範囲参照
（`A[*].x > 0`）を評価しなかった。`cadl` 0.3.24からは，そのような参照を，`cadl norms-eval` と
同じコードで，F.5（「ワイルドカード参照と範囲参照」）の定めるとおりに書き換える。したがって，
`A[*].x > 0` は `for all j in A[*]: A[j].x > 0` として判定する。ランタイムは，F.10が評価しないとして
挙げるほかの述語，たとえば2つの集合の参照を持つ集約の引数は，引き続き評価しない。`trigger:`，
`until:`，または `content:` がそのような述語である規範は判定されず，その効力のフラグは実行の
全体で不明である。G.5により，そのような禁止は常に適用され，そのような許可は決して適用されない。
フェイルクローズではあるが，作成者が期待するものではないかもしれない。

テストは，ランタイムの各段階を，ランタイムが計算した状態を与えて決定関数で再実行し，
OPA 1.22.3のもとで生成したRegoの方針でも再実行する。手で書いた9つのシナリオの81個の決定
（G.12の3つの呼び出し，却下，タイムアウト，トリガから `until:` までの間の禁止，深さの制限を
持つ委任，束縛された添字とホストが作るインスタンスを持つ2つの契約）と，11個のファイルに対して
生成した26個のトレースの7 800個の決定について，両者の結果は一致した。生成したトレースは，
束縛の異なるホストが作るインスタンス，宣言された集合の外の送信者と未宣言の送信者，
2つの契約の一方だけに根拠を持つ保留，保留から承認までの間の取消し，インスタンスの終了，
改正を含む。それらのトレースの中のすべての解放（176件，うち拒否15件。無作為な改正のもとで
さらに13件，うち拒否8件）を，記録した方針の入力から，G.6の規則に照らして検査した。
レビュー担当者がリファレンス実装のコードを使わずに付録の文面から書いた，G.4からG.7とF.3の
第2のモデルは，7つのファイルに対するさらに108個のトレースについて，同じ8 102個の決定の記録と
終結記録を与えた。そのうち60個は，すべての添字を束縛したトレースであり，`cadl agents-run` と
同じように実行した。48個は，何も束縛しないインスタンスを持つトレース，または `cadl check` が
G-17とG-18によって拒否する2つのファイルのトレースであり，テストのためのスイッチを使って
実行した。このモデルは，権能も義務も持たない。権能と義務については，2つのファイルに対して
生成した，200個のメッセージからなる60個のトレースが，束縛がなければ，権能が行使されず，
制度的事象が作られず，義務が履行されないこと，束縛があれば，束縛された要素だけがそれらを
行うことを検査する。シナリオのテストが
期待する記録は，ランタイムを実行する前に本付録の文面から導いたものであり，ランタイムは
そのとおりの記録を出力した。

ランタイムの最初のバージョンを独立にレビューしたところ，これらのテストでは分からなかった欠陥が，実装と文面の
両方に見つかった。そのすべてが，効果を生じるべきでないメッセージに効果を生じさせるものであり，
すべて修正した。保留の根拠を，契約インスタンスごとではなく契約ごとに保持していたため，
承認が，後から作られたインスタンスにおける同じ禁止にも及んでいた（G.6）。解放される
メッセージの再検査が新しい禁止だけを調べていたため，たとえば取消しの後で，統治する別の契約が
もはや許さないメッセージが解放されていた（G.6。文面は「それ以外は再検査しない」としていた）。
`trigger:`，`until:`，`counts_as:` 規則の中の範囲付きのアクター参照が，その名前のすべての
アクターに一致し，`A[*]` が宣言された集合の外のアクターに一致していた。これは，0.3.20以来の
`cadl norms-eval` の欠陥である（F.3，F.10）。インスタンスが，その契約が統治しないメッセージを
観測していた（G.5）。生成したトレースからも，欠陥が1つ見つかった。同時に期限切れになる保留を，
期限の順ではなく作られた順に閉じていた。

2回目のレビューでは，これらの修正を確認したうえで，統治される観測の規則に起因する欠陥が見つかった。
強制される契約のメッセージ事象のうち，当事者でないアクターを名指すものは決して起こらないため，
そのようなアクターによって発動される禁止は決して効力を持たなかった。現在は，G-17がそれを
エラーにする。契約インスタンスが束縛しない添字変数は，`trigger:`，`until:`，`counts_as:` 規則で
集合のすべての要素に一致したため，どの要素も，許可を発動させ，禁止を解くことができた。
G-18はそれを排除し，ランタイムは不明な発生をフェイルクローズで解決する（G.5）。
上限が記号である集合は，決定関数，Regoの方針，`cadl norms-eval` において，下限より小さい
添字を要素として扱っていた。

3回目のレビューでは，第2のモデルが持たない権能と義務について，束縛されない添字による
欠陥がまだ残っていることが見つかった。負担者が `SUP[k]` で `k` の束縛がないとき，`SUP` の
どの要素も，禁止を停止する権能や許可を発動する権能を行使でき，どの要素へのメッセージも，
修復が禁止である義務を履行させていた。原因はどの場合も同じで，添字が束縛されないまま動作する
契約インスタンスである。現在は，この原因そのものを取り除いている。G-18は強制される契約のすべての
添字変数を対象とし，ランタイムは当事者の添字を束縛しないインスタンスを拒否し，その関数は
エラーのあるファイルを拒否する。G.5のフェイルクローズの解決は完全なものになり，予備の規則
として残る。G-17は，宣言した集合の外のリテラルの添字も拒否し，覆うのは当事者の1つの参照で
あることを述べる。

4回目のレビューでは，同じ原因が，規則がまだ対象にしていなかった述語の中の添字変数にも
見つかった。`trigger:` が `W[j].alarm == true` で，当事者 `W[j]` を持たない
禁止は，検査を通り，決して効力を持たなかった。現在のG-18は，限量子が束縛する変数を除いて，
強制される契約のすべての述語を対象とし，ランタイムは，そのような述語を不明な発生として解決する。
このレビューでは，ほかに2つの欠陥が見つかった。ランタイムがインスタンスの量の名前をトレースの
全体から取っていたため，インスタンスの終了より後に与えた値が，その判定を違反から履行に
変えることがあった。また，宣言した集合の外の束縛を受け付けていたため，`W[i]` の禁止が
誰にも適用されなかった。どちらも修正した。

5回目のレビューでは，決定がトレースの後の行に依存していたことが見つかった。ランタイムは，
最初のバージョンから量の名前をトレースの全体から取っており，4回目のレビューの後の修正は，
それをインスタンスの行に狭めただけであった。後の行が名前に与えた値が，それより前の述語がその名前を読む読み方を
変え，それとともに，前の決定を拒否から許可に変えていた。現在のランタイムは，後の行に依存せずに決定する
（G.5）。量の名前は先頭行で与えるか，与えなければ，名前が最初の値を得た時点から量として扱う。テストは，
生成したトレースのすべての接頭部分について，接頭部分に対する決定が，トレースの全体に対する
最初の決定と等しいことを検査する。この不変条件が欠けていた。G-18は，添字の式の中の
添字変数と，メッセージ事象の引数の中の添字変数も見落としていた。現在のG-18は，何が変数を束縛するかに
よって規則を述べており，検査は契約のすべての式をたどる。

6回目のレビューでは，同じ種類の先読みがもう1つ見つかった。契約がホストの作るインスタンスを
持つかどうかをトレースの全体から読んでいたため，後の行の `instances` の項目が，最初からの
唯一のインスタンスを取り除き，前の拒否を許可に変えていた。現在は，これは先頭行で決まる。
このレビューを受けて，G.5のデータの欠落の規則も加えた。値がないために `trigger:` を評価
できない禁止は効力を持たず，判定点が持っていないデータに基づいてメッセージが許可されていた。

7回目のレビューでは，この規則が規範自身の述語だけを見ていたことが見つかった。`trigger:` が，
規則が述語から作る制度的事象である禁止は，その述語が値を持たない間，効力を持たなかった。
現在のG.5の規則は，そのような事象を経る場合にも及ぶ。G-19と上の2つの限界は，
この規則が及ばないものを述べる。

ランタイムを書き，レビューする過程で，agents 0.1の文面に次の不足が見つかった。本付録の
今回の改訂で，これらを補った。メッセージを決定する状態が，最後の観測より後に過ぎた期限を
含んでおらず，許可されたメッセージをどの契約インスタンスが観測するかを述べていなかった
（G.5）。保留の根拠，`approval` を作る必要のある契約インスタンス，解放のときの決定，
同時に期限切れになる保留の順序を，述べていなかったか，記述が不十分であった（G.6）。
委任の `until:` が項目を終わらせるのか，そのインスタンスを終わらせるのかが定まっていなかった
（G.7）。G.12では送信者が終結記録から得るとしている `fallback` を，G.10が除外していた。
付与，取消し，権限のない行為，その他の状態の変化の記録には形式がなかった（G.8）。
契約が，その事象が名指すメッセージを統治すること，またはその事象が用いる添字を束縛することを
求める規則がなかった（G-17とG-18。G.9の末尾に追加した。それより前の規則は変更しない）。

生成した方針は，OPA 1.22.3とCedar CLI 4.14.1で実行し，`cadl agents-decide` と比較した。
OPAでは，20 400個の入力について，結果の全体が一致した（強制される2つの契約，アクターの集合，
契約インスタンス，有効フラグ，委任の連鎖を持つファイルの3つの変種）。Cedarでは，5 640個の
要求について結果が一致した。ここで，Denyは拒否とエスカレーションの両方に対応する。
ただし，G.10が挙げる場合は除く。すなわち，静的でない禁止は，Cedarの方針では強制されない。
リファレンス実装のテストは，`opa` または `cedar` がインストールされているときに，両方の比較を
繰り返す。この実行で，`cadl` 0.3.20のRegoの方針に欠陥が見つかった。契約インスタンスが添字を
束縛しない参照 `A[i]` を，不明（G.4）ではなく不一致として扱っていたため，そのような負担者を持つ
禁止が適用されず，`default: allow` の契約ではメッセージが許可された。`cadl` 0.3.21はこれを
修正する。0.3.20で生成した方針は，生成し直すことが望ましい。

## G.14 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。
`norms: 0.1` だけを宣言するファイルも同じである。キー `enforcement:` を持たない契約は
強制されず，その規範は[付録F](./appendix-f-norms.md)の意味をそのまま保つ。
強制される契約について，本付録はF.5に次の追加を行い，それ以外の変更は行わない。
ホストのない契約のインスタンスは，判定点の開始時から存在する。拒否または保留された
メッセージは観測にならない。強制される契約のインスタンスは，その契約が統治するメッセージだけを
観測し，束縛されていない添字に依存する発生は不明である。効力のフラグは，それが依存する量が
値を持たない間，不明である。F.5の状態は変えない。決定の時刻は，メッセージを決定する前に観測する。許可と禁止は，効力を持つかどうかのフラグを持つ。
内容を契約自身が拒否または保留した義務は `excused` になる（以上はすべてG.5）。
`approval` と `rejection` は保留のidを持ち，段階の順序を拡張し，解放されたメッセージは
その根拠に違反しない（G.6）。許可は派生インスタンスを持つ（G.7）。

`agents: 0.1` を宣言せずに `agent:`，`enforcement:`，`delegations:`，または `on_denied:` を
用いるファイルは，本付録に適合しない。エージェント統治拡張を扱う処理系は，そのような
ファイルではこれらのキーを解釈せず（検査もIRへの変換もしない），用いられているキーを
名指す警告をファイルごとに1つ出すことが望ましい。`norms: 0.1` なしに `agents: 0.1` を
宣言するファイルは，G-1のエラーになる。
本拡張を実装していない処理系は，本拡張を用いるファイルを拒否してはならない。
ファイルごとに1つの情報レベルの診断を出すことが望ましい。

# 付録G. エージェント統治拡張（agents 0.1）

本付録は，CADLの**エージェント統治拡張**を規定する。この拡張は，
規範拡張（[付録F](./appendix-f-norms.md)）の上に作られ，
`actor_def`（[A.3](./appendix-a-syntax.md#a3-context-actors-metrics)）にキー `agent:` を，
`contract_def`（[A.4](./appendix-a-syntax.md#a4-contracts-institution-layer)）に
キー `enforcement:` と `delegations:` を，`norm_def`（F.3）にキー `on_denied:` を追加する。
これにより，契約の許可と禁止は，判定点（enforcement point）に届くすべてのメッセージについて，
`allow`，`deny`，`escalate` の3つの**決定**のいずれかを定める。
決定はメッセージが効果を生じる前に行い，メッセージと規範インスタンスの状態の関数である。
そのどの部分も，エージェントの判断には委ねない。

コア言語は，これらのブロックを必須と**しない**。
本拡張を実装していないCADL準拠の処理系は，新しいキーを理由にファイルを
拒否してはならない。新しいキーを構文上は受理し，*情報レベル*の診断を出すことが望ましい。

拡張の名前は `agents` であり，本付録はバージョン `0.1` を記述する。
本拡張は `norms: 0.1` を**必要とする**。強制されるのは規範だからである。
本拡張を用いるファイルは，`extensions:`
（[A.2](./appendix-a-syntax.md#a2-top-level-structure)）で両方を宣言しなければならない。
宣言せずに用いた場合に処理系がどう扱うかはG.14で述べる。

```yaml
sos:
  ...
  extensions:
    - norms: 0.1
    - agents: 0.1
```

## G.1 動機

LLMに基づくエージェントはSoSの構成システムになりつつあり，それらをつなぐプロトコルの
標準化が進んでいる
[[MCP, 2026-07-28]](./appendix-b-references.md)
[[Linux Foundation, A2A 2025]](./appendix-b-references.md)。
強制の方法は，ツール呼び出しの境界での決定的な検査に収束しつつある。
たとえば，Amazon Bedrock AgentCore Policyは，Cedarの方針でツール呼び出しを認可し，
既定で拒否する
[[AWS, AgentCore Policy]](./appendix-b-references.md)。
欠けているのは，組織の契約（誰が，誰の権限で，何をしてよいか）からそのような検査に至る
段階である。バージョン0.1は，[9.8節](./09-research.md)の4つの研究方向への最初の一歩である。

1. **RD-8.1，契約から境界方針へのコンパイル。** CADLのファイルには，どのアクターが
   エージェントであるか，どのメッセージがツール呼び出しであるか，生成した方針が何を
   決定しなければならないかを述べるものがない（G.4，G.5，G.10）。
2. **RD-8.2，委任された権限の来歴。** 局所的な状態だけを見る検査では，ある行為が，
   元の権限者に認められていない委任を経て呼び出し元に届いたものかどうかが分からない。
   G.7は，委任された許可に来歴連鎖（provenance chain）を与える。
3. **RD-8.3，阻止された行為の後の回復。** あるプレプリントのレビューは，安全でない行為の
   94%を阻止しても，安全かつ正しく完了したタスクが5%未満にとどまったという研究を報告している
   [[Dantas+, arXiv 2026]](./appendix-b-references.md)。G.6は，名指したアクターへの
   エスカレーションと，代替のメッセージを定義する。
4. **RD-8.4の一部，監査。** コミュニティの統治は，プロトコルの上に欠けている層であることが
   指摘されている
   [[Kang & Diponegoro, arXiv 2026]](./appendix-b-references.md)。また，追記専用の監査ログを
   伴って強制される統治グラフは，プロンプトだけの「憲法」ではできなかったLLMエージェントの
   制約を実現した
   [[Bracale Syrnikov+, arXiv 2026]](./appendix-b-references.md)。G.8は，監査記録の形式を
   定める。

**バージョン0.1の範囲。** 本拡張は意図して小さく保つ。構成員資格，投票，異議の保存のための
基本要素を持たない（RD-8.4のそれ以外の部分は，後の版のために未解決のまま残る）。
計画や複数のエージェントの相互作用を検証しない（RD-8.5）。どの決定も1つのメッセージに
関するものだからである。いかなる規制の条項もCADLに対応付けない。認証を扱わない。
メッセージの送信者と受信者は与えられたものとする。境界では，内容がメッセージである規範だけを
考慮し，メッセージの送信者，受信者，名前だけを考慮して，引数は考慮しない。

## G.2 概念

| 概念 | agents 0.1での意味 |
| --- | --- |
| **ツール呼び出し（tool call）** | 受信者が種別 `tool_server` のアクターであり，名前がそのアクターの `tools:` の1つであるメッセージ。 |
| **強制される契約（enforced contract）** | キー `enforcement:` を持つ契約。強制される契約だけが決定に加わる。 |
| **判定点（enforcement point）** | ファイルのすべての強制される契約にわたって，メッセージに対する決定を行う1つの論理的な場所。 |
| **決定（decision）** | `allow`，`deny`，`escalate` のいずれか。メッセージが効果を生じる前に，G.5の決定関数が1つのメッセージについて計算する。 |
| **根拠（ground）** | 決定関数において，メッセージに適用される禁止。 |
| **保留（hold）** | 決定が `escalate` であるメッセージの記録。メッセージは，保留が最終状態に達するまで留め置かれる（G.6）。 |
| **派生インスタンス（derived instance）** | 被委任者が保持する許可（G.7）。**来歴連鎖**を伴う。来歴連鎖は，元の許可の負担者から保持者までのアクターの列であり，委任1回につき1つのリンクを持つ。 |
| **監査記録（audit record）** | 判定点が1つの決定について記録するもの（G.8）。 |

規範，規範インスタンス，契約インスタンス，制度的事象，観測は，
[付録F](./appendix-f-norms.md)の意味で用いる。

## G.3 構文（A.3，A.4，F.3へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`hyphen_name`，
`actor_ref`，`int_literal`，`duration_lit` は付録Aで，`message_event` は
[E.3](./appendix-e-sos-dsl.md)で，`norm_event` は
[F.3](./appendix-f-norms.md)で定義している。

```ebnf
actor_def         = ... , [ "agent:" , agent_binding ] ;
agent_binding     = "kind:" , agent_kind ,
                    [ "protocol:" , hyphen_name ] ,
                    [ "tools:"    , { "-" , identifier } ] ;
agent_kind        = "llm_agent" | "tool_server" | "human" | "service" ;

contract_def      = ... ,
                    [ "enforcement:" , enforcement_block ] ,
                    [ "delegations:" , { "-" , delegation_def } ] ;
enforcement_block = [ "default:" , ( "deny" | "allow" ) ] ,
                    [ "point:"   , ( "caller" | "receiver" | "gateway" ) ] ;

norm_def          = ... , [ "on_denied:" , denial_recovery ] ;
denial_recovery   = [ "escalate_to:" , actor_ref ] ,
                    [ "timeout:"     , duration_lit ] ,
                    [ "fallback:"    , message_event ] ,   (* string *)
                    [ "notify:"      , actor_ref ] ;

delegation_def    = "norm:"  , identifier ,
                    "to:"    , { "-" , actor_ref } ,
                    "grant:" , identifier ,
                    [ "revoke:"    , identifier ] ,
                    [ "max_depth:" , int_literal ] ,
                    [ "until:"     , norm_event ] ;        (* string *)
```

- `agent:` を持たないアクターには，エージェントの種別がない。種別 `tool_server` は
  ツール呼び出しを定義する（G.4）。`llm_agent`，`human`，`service` は，そのうちの1つを
  名指す静的な規則（G-8）と，ジェネレータによる利用のほかには意味を持たない。
  `protocol:`（`mcp`，`a2a`，またはその他の名前）には既定値がなく，決定に影響しない。
  範囲付きで宣言したアクターの `agent:` は，その集合のすべてのアクターに適用される。
- ツールの名前は `identifier` である。`message_event` のメッセージ名だからである。
  プロトコル上の名前が識別子でない場合は，`codegen:` の項目の `mappings:`（A.9）が
  両者を関係付ける。
- 契約は，キー `enforcement:` を持つときに**強制される**。空のマッピングまたはnull値
  （`enforcement: {}`，またはキーだけ）は，「すべて既定値で強制される」ことを意味する。
  `default:` を省略したとき，既定の決定は，ツール呼び出しについては `deny`，それ以外の
  すべてのメッセージについては `allow` である。`default:` を与えたときは，その値を両方に
  適用する（G.5）。
- `point:`（既定値 `gateway`）は，ジェネレータのための配備上のヒントであり，決定に影響しない。
  配備がどうであれ，論理的な判定点は1つである。統治されるすべてのメッセージは，
  すべての強制される契約にわたって，1つの状態の上で，1回決定される。
- `on_denied:` は禁止にだけ書ける。`timeout:` には既定値がない。`fallback:` と `notify:` は
  データである。決定の結果（G.10）に写されるだけで，それ以外の効果を持たない。
- `max_depth:` の既定値は `1` である。`revoke:` がなければ，委任をメッセージによって
  取り消すことはできない。`until:` がなければ，委任はそれ自身の終わりを持たない。

追加するキーをブロックごとに示す。アクター — `agent`（`kind` `protocol` `tools`）。
契約 — `enforcement`（`default` `point`），`delegations`（`norm`
`to` `grant` `revoke` `max_depth` `until`）。規範 — `on_denied`
（`escalate_to` `timeout` `fallback` `notify`）。強制される契約では，
名前 `approval` と `rejection` をG.6の制度的事象のために予約する。

## G.4 メッセージとツール呼び出し

**メッセージ**は，それぞれ1つの具体的なアクターである送信者と受信者，名前，引数を持つ。
受信者が `agent.kind: tool_server` を持ち，名前がそのアクターの `tools:` の1つであるとき，
メッセージは**ツール呼び出し**である。ツールサーバへの，それ以外の名前を持つメッセージは，
**未宣言のツール**の呼び出しである。それ以外のすべてのメッセージは**通常のメッセージ**である。
バージョン0.1では，ツールサーバが返す結果は別個のメッセージではない。

境界では，`message_event` `S -> R : e` を，送信者，受信者，メッセージ名（`e` の識別子，
または呼び出しの名前）の3つの成分についてメッセージと**照合**する。
バージョン0.1では，**`e` に書いた引数は考慮しない**。
`delete_file` と `delete_file(path)` は同じメッセージに一致する。各成分は，真，偽，
**不明**のいずれかであり，照合の結果はそれらのクリーネの連言である。いずれかの成分が偽で
あれば偽，そうでなく，いずれかが不明であれば不明，それ以外は真である。アクター参照は，
次のように具体的なアクターに一致する。

| 参照 | 一致するもの |
| --- | --- |
| `A` | 添字なしで宣言したアクター `A`。添字付きの要素 `A[k]` には一致しない |
| `A[3]`，`A[*]`，`A[1..3]` | `A[3]`。集合 `A` のすべての要素。`A[1]` から `A[3]` まで |
| `A[1..N]`（記号の上限） | 集合 `A` のすべての要素。上下限は比較しない |
| `A[i]` | 具体的なアクターが `A` の要素でないときは偽。そうでないとき，契約インスタンスが `i` を `v` に束縛していればちょうど `A[v]` に一致し，`i` に値を束縛していなければ**不明**である。 |

この表は[F.3](./appendix-f-norms.md)の表と同じである。F.3の表は，規範エンジンが
トレースの事象に用いる。違いは1つである。契約インスタンスが `i` に値を束縛していないとき，
F.3では `A[i]` はすべての要素に一致するが，境界ではその一致を不明とし，フェイルクローズで
解決する（G.5）。

`A` を範囲付きで宣言しており，`k` がその整数の上下限の内にあるとき，`A[k]` は集合 `A` の
**要素**である（`A[1..3]` と宣言した集合は `A[7]` を含まない）。宣言した上限が記号であるときは，
下限以上のすべての添字が要素である。

## G.5 境界での規範の強制

### インスタンス，統治されるメッセージ，決定に加わる規範

ホストが生成するインスタンスを持たない強制される契約では，F.5の単一のインスタンスは，
最初の観測からではなく，**判定点の開始時から**存在する。F.5へのこの追加によって，
最初のメッセージを決定できる。ホストアプリケーションがインスタンスを生成し，終わらせる場合，
動作中のインスタンスは，ホストアプリケーションが生成し，まだ終わらせていないものである。

強制される契約がメッセージ `m` を**統治する**かどうかは，どのインスタンスを考慮するよりも前に
決める。したがって，`parties:` には束縛を適用しない。当事者 `A[i]` または `A[*]` は，
`A` のすべての要素に一致する。

- 受信者がツールサーバであるメッセージ（ツール呼び出し，または未宣言のツールの呼び出し）は，
  そのツールサーバを当事者とするすべての強制される契約が統治する。
  **送信者が何であるかを問わない**。当事者でも，当事者でない宣言済みのアクターでも，
  未宣言のアクターでもよい。したがって，以下の段階2から4は部外者にも適用される。
  ツールサーバが複数の強制される契約の当事者である場合，そのそれぞれがそのサーバへのすべての呼び出しを
  統治し，そのうちの1つが許さない呼び出しは拒否される（段階4）。ツールサーバを共有する契約は，
  意図する呼び出しをそれぞれが許可する必要がある。
- 通常のメッセージは，その送信者と受信者がそれぞれ当事者に一致するとき，
  強制される契約が統治する。

その場合も，規範は，その負担者または有効な保持者（後述）にだけ適用される。
判定点は，メッセージを届いた順に1つずつ，それぞれ，それより前のすべての観測が残した状態の
上で決定する。決定は決定的でなければならない。

`content:` が `message_event` である許可または禁止だけが，決定に加わる。
内容が，述語，時相演算子を含む `tpredicate`，または制度的事象である許可または禁止は，
バージョン0.1では**境界で効果を持たず**，付録Fのもとで監視されるだけである。
義務と権能は決定に加わらない。義務が求めるメッセージや，権能を行使するメッセージは，
他のメッセージと同じように決定され，F.5の7は変わらない。

規範インスタンスは，**境界で効力を持つ**（in force at the boundary）間，決定に加わる。
このフラグはF.5への追加である。F.5の状態と判定は変わらない。

- 許可は，そのインスタンスが `active` である間，効力を持つ。
- 禁止は，そのインスタンスが `active` である間，効力を持つ。インスタンスが `violated` に
  なっても，禁止は**効力を持ち続ける**。違反は1回報告されるが（F.5），禁止を解くことはない。
  その後は，次のうち最初のものまで効力を持ち続ける。その `deadline:` の期間が閉じたはずの
  時刻。その `until:` が起こること。それを名指す権能の `discharge` の効果。
  それが引き継がれない改正（F.6）。契約インスタンスの終了。それを名指す `suspend` と
  `resume` の効果は，違反の後であっても，禁止の効力を失わせ，また戻す。

効力を持つ規範インスタンスは，その内容が `m` に一致し（G.4），`m` の送信者がその負担者で
あるとき，`m` に**適用される**。許可の派生インスタンス（G.7）は，それが有効であり，
保持者を送信者として内容が一致するとき，適用される。照合の結果が不明であるとき，または
判定点がフラグを持たないとき，結果は不明である。不明は**フェイルクローズ**（fail-closed）で
解決する。不明の禁止は適用され，不明の許可は適用されない。

### 決定関数

メッセージ `m` について，次の段階が，この順に**結果**（フィールドはG.10）を与える。

1. **統治されない。** `m` を統治する強制される契約がなければ，`allow`，理由 `ungoverned`。
   本付録は，そのようなメッセージを制限しない。
2. **未宣言のツール。** `m` が未宣言のツールの呼び出しであれば，`deny`，
   理由 `undeclared_tool`。
3. **契約ごと。** 統治する各契約 *C* は，その動作中のすべてのインスタンスにわたって
   決定する。
   1. *C* に動作中のインスタンスがなければ，`m` がツール呼び出しであるときは `deny`，
      理由 `no_instance`。そうでないときは段階3.4のとおり。
   2. *C* の禁止が `m` に適用されれば，それらが**根拠**であり，理由は `prohibition` である。
      すべての根拠が `on_denied.escalate_to` を持ち，すべてが同じアクターを名指し，
      そのアクターが `m` の送信者でないとき，*C* は `escalate` と決定する。
      そうでなければ `deny` と決定する。`escalate_to: A[i]` は，根拠が適用される
      各インスタンスの束縛で解決する。束縛されていない添字，またはインスタンスによって
      異なるアクターは，`deny` を与える。
   3. そうでなく，*C* の許可が，元のものであれ派生したものであれ，`m` に適用されれば，
      `allow`，理由 `permission`。
   4. そうでなければ，*C* の `default:`，またはそれを省略したときは，`m` がツール呼び出しで
      あれば `deny`，そうでなければ `allow`。理由 `default`。
4. **結合（拒否優先，deny overrides）。** いずれかの契約が `deny` と決定すれば，
   決定は `deny` である。そうでなく，いずれかの契約が `escalate` と決定すれば，
   `escalate` と決定したすべての契約が同じアクターを名指すときは決定は `escalate` であり，
   そうでないときは `deny` である（保留の承認者は1人である）。それ以外は `allow` である。

**決定契約**（determining contracts）は，`deny` と決定した契約である。それがなければ
`escalate` と決定した契約であり，それもなければ統治するすべての契約である。
結果の理由は，`deny` と `escalate` については，`no_instance`，`prohibition`，`default` の
うち，決定契約が持つ最初のものである。`allow` については，いずれかの契約が `permission` を
持てば `permission`，そうでなければ `default` である。
結果は，決定契約の根拠または適用される許可を列挙する。また，理由が `prohibition` で
あるときは常に（`escalate` だけでなく `deny` についても），それらの根拠の `fallback` と
`notify`，およびそれらのうち最小の `timeout:` を列挙する。

以上から，次のことが従う。1つの契約の中では禁止が許可に優先する（N-12は引き続き警告する）。
2つの強制される契約が統治するメッセージは，両方に許されなければならない。
`escalate_to:` のない禁止は決してエスカレーションされない。アクターは自分自身のメッセージを
承認できない。

既定値がメッセージの種類によって異なるのには理由がある。ツールは列挙されており，
ツール呼び出しは契約の外に作用する。そのため，閉じた方針をツールごとにレビューできる。
これはG.1に挙げた強制の既定値でもある。通常のメッセージには，プロトコル，ライフサイクル，
発動条件が依存する調整のメッセージが含まれる。norms 0.1のために書いた契約は，それらに対する
許可を持たないため，`deny` ではそれらがすべて止まってしまう。`default: deny` は，
それらについても方針を閉じる。

### 決定がトレースに与える効果

- **`allow`。** メッセージは効果を生じ，それを統治する強制される契約のインスタンスにとって，
  決定の時刻を時刻印とする観測になる。強制される契約のインスタンスは，その契約が統治する
  メッセージだけを観測する。どの強制される契約も統治しないメッセージ（段階1）は，
  どの強制される契約の観測にもならず，ある強制される契約が統治するメッセージは，
  それを統治しない別の強制される契約の観測にならない。したがって，メッセージは，
  強制される契約によって決定されることなしに，その契約の規範を発動させることも，
  終わらせることも，履行させることもなく，その契約の中に制度的事象を作ることもない。
  強制されない契約については，F.5をそのまま適用する。
- **`deny`。** メッセージは効果を生じず，**観測にならない**。規範を発動させず，
  制度的事象を作らず，ライフサイクル遷移を起こさず，義務を履行させず，禁止に違反しない。
  判定点は，結果を送信者に返すことが望ましい。
- **`escalate`。** メッセージは保留される（G.6）。保留されている間は観測にならない。

付録Fの期限は，メッセージが拒否または保留されている間も進み続ける。
判定点は，メッセージを決定する前に，決定の時刻を観測する。これはメッセージを運ばない観測であり，
F.5は，この観測で，過ぎたすべての期限と期間を確定させる。したがって，決定が，決定の時刻より前に
期間が閉じた禁止や，期限が過ぎた義務に基づくことはない。
拒否された `trigger:` のメッセージは，その規範を発動させない。F.5の判定への追加として，
`violated` になった義務は，その発動から違反までの間に，その内容に一致する負担者の
メッセージが，義務自身の契約を決定契約に含んで拒否されたか，またはその契約の根拠によって
保留され，違反より前に解放されなかったとき，判定 **`excused`** を持つ。
契約自身が履行を妨げたからである。その `on_violation:` は，`excused` となったすべての規範と
同じく，適用される。

## G.6 拒否の後のエスカレーション

禁止の `on_denied:` は，その禁止が根拠であるときに何が続くかを述べる。
`fallback:` は送信者が代わりに送ることのできるメッセージを名指し，`notify:` は
知らせるべきアクターを名指す。どちらも結果に写されるだけである。
代替のメッセージは許可を与えない。送られたときは，他のメッセージと同じように決定される。
`escalate_to:` と `timeout:` は保留を定義する。

決定が `escalate` であるとき，判定点は**保留**を作る。保留は，判定点の中で一意な
`hold_id`，メッセージ，決定の時刻，根拠，承認者，期限（決定の時刻に結果の `timeout` を
加えたもの，またはなし）を持つ。**保留の根拠**は，ある禁止がメッセージに適用される
1つの契約インスタンスにおける，その禁止である。保留の根拠は，統治するすべての契約にわたる
そのすべてであり，それらの契約インスタンスを*根拠の契約インスタンス*と呼ぶ。
2つの契約インスタンスで適用される禁止は，2つの根拠である。
決して終わらない契約インスタンスにおける期限のない保留は，
いつまでも保留される。保留のidが承認者にどのように届くかは，プロトコルに依存する。

| 状態 | その状態になるとき | 終結記録（G.8） |
| --- | --- | --- |
| `held` | 保留が作られたとき。最終状態でない唯一の状態 | — |
| `approved` | 承認者が承認したとき。メッセージは解放される | `allow`，理由 `approved`（または解放の拒否） |
| `rejected` | 承認者が却下したとき | `deny`，理由 `rejected` |
| `expired` | 期限が過ぎたとき | `deny`，理由 `expired`。`time` は期限 |
| `cancelled` | 根拠の契約インスタンスが終わったとき，または根拠の契約が改正されたとき | `deny`，理由 `cancelled` |

承認者は，`approval` と `rejection` の2つの制度的事象を通じて行為する。それぞれは，
承認者のメッセージから `counts_as:` 規則が作る（G-9）。たとえば
`when: "OPERATOR -> PLANNER : approve"`，`creates: approval` である。
F.5では制度的事象は「事象としてのみ存在」するが，その拡張として，この2つの事象は
1つの値，すなわち**保留のid**を運ぶ。それは，事象を作ったメッセージの最初の引数である。
これは，バージョン0.1でメッセージの引数を用いる唯一の箇所である。
承認者のメッセージそのものも統治され，G.5によって決定される。

1つの観測の中での段階の順序（F.5）を，次のように拡張する。

- **段階1の後。** `approval`（`rejection`）のうち，その保留のidが `held` の保留を名指し，
  その行為者（F.5の7）がその保留の承認者であり，その保留の根拠の契約インスタンスで
  作られたものは，その保留を `approved`（`rejected`）にする。保留が複数の根拠の
  契約インスタンスを持つときは，そのような事象が1つあれば足りる。1つのメッセージが複数の契約インスタンスで作る事象は，
  1つの事象である。それ以外の `approval` または `rejection` はどの保留も変えず，
  権限のない行為として記録することが望ましい。次に，G.7の付与，取消し，`until:` の事象を
  適用する。
- **段階6の中。** 契約インスタンスが終わると，その中に根拠を持つ `held` の保留は，
  その規範を確定させる前に，`cancelled` になる。
- **段階6の後。** この観測で `approved` になった各保留を，作られた順に解放する。

**解放。** メッセージを，現在の状態の上で，承認した観測の時刻に，もう一度決定する。
承認は，許可と根拠の代わりになり，それ以外の代わりにはならない。

1. メッセージが今は未宣言のツールの呼び出しであれば，`deny`，理由 `undeclared_tool` とする。
2. 保留の根拠を持つ統治契約は，その根拠の契約インスタンスのいずれかがもはや動作して
   いなければ理由 `no_instance` で，その契約の禁止が，保留の根拠になっていない
   契約インスタンスで適用されれば理由 `prohibition` で，拒否する（`norms` にそれらの禁止を
   並べる）。根拠である禁止が，たとえば保留の後に作られた別の契約インスタンスで今は
   適用される場合も，これに含まれる。そうでなければ，その契約は許す。許可も既定値も調べない。
3. それ以外の統治契約は，G.5の段階3によって完全に決定し，許さなければならない。許すのは，
   元の許可，今も有効な派生した許可，または既定値による。`escalate` と決定するはずの契約は，
   理由 `prohibition` で拒否する。
4. どの契約も拒否しなければ，メッセージを解放する。そうでなければ，解放を拒否する。
   その結果は，拒否する契約から，G.5の段階4と同じように作る。`contracts` はそれらの契約を
   並べ，理由は，それらのうち `no_instance`，`prohibition`，`default` の順で最初のものであり，
   `prohibition` では `norms`，`timeout`，`fallback`，`notify` をG.10のとおりに埋める。
   `escalate_to` は `null` である。

解放の拒否は最終的である。保留を作らず，保留は `approved` のままである。これらの規則により，
解放についても，G.5とG.7が他のすべてのメッセージについて述べることが成り立つ。すなわち，
2つの強制される契約が統治するメッセージは両方によって許され，どのアクターも，元の権限者が
もはや持たない権限によって行為することはない。したがって，根拠を持たない契約において，
保留から承認までの間に委任が取り消されたとき，契約インスタンスが終わったとき，または契約が
改正されたときは，解放が拒否される。メッセージを解放するとき，メッセージは，
他のどのメッセージが決定されるよりも前に，
**承認した観測の時刻印を持つ，直後の観測**として効果を生じる。F.5の3への追加として，
このメッセージは，ある禁止が保留の根拠になっている契約インスタンスでは，その禁止の内容が
起こったことにはならない。承認された例外は，その根拠に違反しない。承認は1つのメッセージを
解放する。送信者，受信者，名前が同じ後のメッセージは，改めて決定される。

**期限切れ。** `held` の保留の期限より後の時刻を持つ各決定と各観測の前に，その保留は
`expired` になる。同時に期限切れになる保留は，期限の順に，期限が等しければ作られた順に，
`expired` になる。ちょうど期限の時刻の承認は期限内とする。

## G.7 来歴を伴う委任

`delegations:` の項目は，1つの許可を**委任可能**にする。`norm:` はその許可を名指し，
`to:` は任意の深さで派生インスタンスを保持してよいアクターを列挙し，`grant:` と `revoke:` は
委任するメッセージと取り消すメッセージを名指し，`max_depth:` は連鎖のリンクの最大数であり，
`until:` はその項目のすべての派生インスタンスを終わらせる事象である。
バージョン0.1では，内容が `message_event` である許可だけを委任できる。権能は委任できない。

**派生インスタンス**は，1つの契約インスタンスにおける，同じ内容を持つ許可であり，
その内容は**保持者**を送信者として読む。その**来歴連鎖**は
*a*<sub>0</sub>, …, *a*<sub>n</sub> である。*a*<sub>0</sub> は元の許可の負担者，
*a*<sub>n</sub> は保持者であり，隣り合う各対は，1回の付与が作る**リンク**である。
負担者の連鎖は *a*<sub>0</sub> だけである。派生インスタンスは `active` または
`discharged`（最終状態）である。派生インスタンスは付録Fへの追加である。付録Fでは
規範ごとに1つのインスタンスがある。**規範，保持者，契約インスタンスの組ごとに，
`active` の派生インスタンスは高々1つ**であり，したがって，どの保持者も1つの連鎖を持つ。

派生インスタンスは，元の許可が効力を持ち（G.5），派生インスタンスが `active` であり，
その連鎖のリンクが `max_depth` 以下であり，連鎖の最初より後のすべてのアクターが `to:` の
参照に一致するとき，**有効**である。元の許可が停止されている間，その派生インスタンスは
有効でない。

**付与。** メッセージ `X -> Y : g` は，`g` が，それを統治する契約の項目の `grant:` の
名前であるとき，他のメッセージと同じようにG.5によって決定される。それが観測されると，
その契約の動作中の各インスタンスで，次の条件を調べる。

1. `X` が負担者であり，許可が効力を持つ。または，`X` が有効な派生インスタンスを保持する。
2. `Y` が `to:` の参照に一致する。
3. `Y` が `X` の連鎖に現れない。
4. `X` の連鎖のリンクが `max_depth` より少ない。
5. `Y` がその許可の `active` の派生インスタンスを保持していない。

すべてが成り立てば，`Y` のために，`X` の連鎖に `Y` を続けた連鎖を持つ派生インスタンスを作る。
1から4が成り立ち，5が成り立たなければ，付与は何もしない。
1から4のいずれかが成り立たなければ，付与は効果を持たず，権限のない行為として記録することが
望ましい。付与者は自分のインスタンスを保つ。委任は権限を共有するのであり，移転するのではない。

**終了。** 派生インスタンスは，次のときに `discharged` になる。(a) その項目の `revoke:` の
名前を持つメッセージ `X -> Y : r` が観測され，`Y` の連鎖の中で `X` が `Y` より前に現れるとき。
このとき，`Y` のインスタンスと，連鎖に `Y` が現れるすべての派生インスタンスが解除される。
(b) その項目の `until:` が，規範の `until:` と同じように起こったとき。このとき，その観測で
`active` である派生インスタンスが解除され，項目は委任可能なままである。(c) 元の許可が
`discharged` になったとき，または契約インスタンスが終わったとき。
(a) を満たさない取消しのメッセージは効果を持たない。解除されたインスタンスは復活しない。
新しい付与は新しいインスタンスを作る。

有効性は連鎖の全体から計算するため，アクターは，元の権限者が持っていなかった権限や，
もはや持っていない権限を，仲介者を通じて得ることができない。有効なインスタンスを持たない
アクターによる付与は何も作らず，連鎖は契約が許すより長くならず，1つのリンクを取り消すと，
それを通じて派生したすべてが終わる。

**改正。** 改正された契約の規範インスタンスは，F.6が定める。
本付録は2つの規則を追加する。強制される契約の新しい版が発効するとき，
(1) その契約に根拠を持つすべての `held` の保留は `cancelled` になり，
(2) すべての派生インスタンスの有効性を新しい版に対して調べる。新しい版でその許可が
`delegations:` の項目を持たないインスタンス，または元の許可が改正によって解除された
インスタンスは，`discharged` になる。

## G.8 監査記録

判定点は，すべての決定を記録することが望ましく，記録を追記専用で保つことが望ましい。
記録することは推奨であり，形式は規範的である。**監査記録**は，決定の結果（G.10）に
次の5つのフィールドを加えたものである。

| フィールド | 内容 |
| --- | --- |
| `time` | 決定の時刻。トレースの時計による。 |
| `message` | `from`，`to`，`name`。方針の入力と同じ。 |
| `instances` | 統治する契約の動作中のインスタンス。契約の `id` とインスタンスの識別子。終結記録では，動作中かどうかにかかわらず，保留の根拠の契約インスタンス。 |
| `hold_id` | `escalate` の決定と，その保留を閉じる記録で値を持つ。それ以外は `null`。 |
| `outcome` | 保留を閉じる記録では，その最終状態。それ以外は `null`。 |

`escalate` の決定は，同じ `hold_id` を持つ2つの記録を与える。1つは保留が作られたときの
記録であり，もう1つは保留が最終状態に達したときの**終結記録**（closing record）である
（G.6の表）。終結記録は，保留の `contracts`，`norms`，`escalate_to` を保つ。理由が
`rejected`，`expired`，`cancelled` のいずれかであるときは，保留の `fallback` と `notify` も保つ。
送信者が，拒否の中にそれらを見いだせるようにするためである。終結記録の `timeout` は `null` である。
解放が拒否されるとき（G.6），終結記録は，これらの代わりにその拒否の結果を持ち，`outcome` は
`approved` である。終結記録の `time` は，保留を閉じた観測の時刻である。ただし `expired` では
期限である。`expired` の記録は，期限切れが見つかったとき，すなわち次の決定または観測の前に書く。
したがって，ログの時刻が逆戻りすることはない。

付与，取消し，および権限のない行為として記録した行為は，**事象記録**（event record）として，
同じログに書くことが望ましい。後の決定が基づく状態のそれ以外の変化，すなわち，原因を問わない
派生インスタンスの終了，契約インスタンスの開始と終了，改正も，同じように書くことが望ましい。
事象記録は結果を持たない。`decision` の代わりにフィールド `event` を
持ち，次のフィールドを持つ。

| フィールド | 内容 |
| --- | --- |
| `time`，`message` | 監査記録と同じ。その事象のもとになった観測とメッセージ。メッセージがないときは，`message` は `null`。 |
| `event` | `grant`，`revoke`，`delegation_end`（派生インスタンスが取消しのメッセージ以外の原因で終わった。派生インスタンスごとに1つの記録），`instance_start`，`instance_end`，`amendment`，`unauthorised_grant`，`unauthorised_approval`，`unauthorised_rejection`，`unauthorised_act`（F.5の7が権限のない行為として記録する行為）のいずれか。 |
| `instances` | その事象が起こった契約インスタンス。`amendment` では，改正された契約の動作中のインスタンス。 |
| `norm` | 付与，取消し，または `delegation_end` では，委任可能な許可。`<contract id>.<norm id>` の形で表す。それ以外は `null`。 |
| `chain` | `grant` では，受信者の派生インスタンスの連鎖。効果を持つ `revoke` では，取り消されたインスタンスの連鎖。`delegation_end` では，終わったインスタンスの連鎖。それ以外は `null`。 |
| `holders` | その事象が派生インスタンスを作った，または解除した保持者。作られた順に並べる。それ以外は空。 |
| `hold_id` | 権限のない承認または却下では，それが運んでいた保留のid。なければ `null`。それ以外は `null`。 |
| `reason` | 効果を持つ付与または取消しでは `null`。何もしない付与（G.7の条件5）では `holder_exists`。(a) を満たさない取消しのメッセージでは `no_effect`。`unauthorised_grant` では，最初に成り立たない条件：`no_authority`（1），`not_in_to`（2），`in_chain`（3），`max_depth`（4）。権限のない承認または却下では，`unknown_hold`，`not_held`，`not_approver`，`other_instance`（根拠の契約インスタンスで作られていない）のいずれか。`unauthorised_act` では `no_power`。`delegation_end` では，その原因：`until`，`original_discharged`，`instance_end`，`amendment`。`instance_end` では `end` または `terminal_state`。`amendment` では新しい版の名前。`instance_start` では `null`。 |

記録は，判定点がそれを作る順に書く。決定の記録，次にそのメッセージがなる観測の事象記録，
次にその観測が承認または却下した保留の終結記録である。規範の効力のフラグの変化には，
それ自体の記録はない。それは，記録されたメッセージ，時刻，および契約の述語が読む値から導かれる。
本付録は，ハッシュの連鎖や署名のような，
ログの完全性の保護を定めない。それを必要とする配備は，記録の外でそれを追加する。

## G.9 静的意味論 {/* #g9-static-semantics */}

エージェント統治拡張を扱う処理系は，[付録F](./appendix-f-norms.md)の検査に加えて，
次の検査をしなければならない。

- **G-1.** `agents: 0.1` を宣言するファイルは，`norms: 0.1` も宣言しなければならない。
  そうでなければ，処理系はエラーを報告し，本拡張のキーを解釈しない。
- **G-2.** `agent:` のマッピングは `kind:` を持たなければならず，その値は `llm_agent`，
  `tool_server`，`human`，`service` のいずれかである。`protocol:` は `hyphen_name` で
  なければならない。
- **G-3.** `tools:` は `tool_server` にだけ書け，`tool_server` は少なくとも1つのツールを
  列挙しなければならない。ツールの名前は識別子でなければならず，予約語であってはならず，
  そのアクターの中で一意でなければならない（YAML 1.1のローダーでは，引用符のない `yes`，
  `no`，`on`，`off`，`true`，`false`，`null` は名前にならない。
  [A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)を参照）。
- **G-4.** `message_event` の受信者がツールサーバであるとき，メッセージ名はその `tools:` の
  1つでなければならない。これは，規範の `trigger:`，`until:`，`content:`，`counts_as:` 規則の
  `when:`，ライフサイクル遷移の `on:`，および `fallback:` に適用される。
  処理系は，これを満たさないプロトコル（A.5）のメッセージのステップについて警告することが
  望ましい。
- **G-5.** `enforcement.default` は `deny` または `allow` でなければならず，
  `enforcement.point` は `caller`，`receiver`，`gateway` のいずれかでなければならない。
  nullまたは空の `enforcement:` は有効である。
- **G-6.** 強制される契約では，許可または禁止の内容である `message_event` の送信者は，
  その `bearer:` とテキストとして等しくなければならない。
- **G-7.** `on_denied:` は，強制される契約の，内容が `message_event` である禁止にだけ書け，
  少なくとも1つのキーを持たなければならない。`timeout:` は0より大きい `duration_lit` で
  なければならず，`escalate_to:` を必要とする。処理系は，`timeout:` のない `escalate_to:` に
  ついて警告することが望ましい。
- **G-8.** `escalate_to:` と `notify:` は，宣言済みの1つのアクターを名指さなければならない
  （N-3と同じ）。`escalate_to:` は，そのメッセージが統治されるように，契約の当事者を
  名指さなければならず，その禁止の `bearer:` とテキストとして等しくてはならず，
  `agent.kind: human` を持つことが望ましい。
- **G-9.** `escalate_to: A` を持つ契約は，送信者が `A` である `message_event` から
  `approval` を作る `counts_as:` 規則を持たなければならず，`rejection` についても
  そのような規則を持つことが望ましい。強制される契約では，`approval` または `rejection` を
  作るすべての規則は，送信者がその契約の禁止の `escalate_to:` である `message_event` を
  `when:` として持たなければならず，どの規範の `id` もこの2つの名前のいずれとも等しくては
  ならない。その `message_event` の送信者と受信者は，契約の当事者でなければならない
  （その参照が名指しうるすべてのアクターが当事者に一致する）。契約が承認者のメッセージを
  統治し，そのインスタンスがそれを観測するためである。エラーになる使い方はこれらだけである。`trigger:`，`until:`，`content:` での
  この2つの事象への参照は許される。
- **G-10.** `fallback:` は，送信者がその禁止の `bearer:` とテキストとして等しく，
  受信者が宣言済みのアクターである `message_event` でなければならず，受信者または
  メッセージ名において禁止の内容と異ならなければならない。
- **G-11.** `delegations:` は強制される契約にだけ書ける。`norm:` は，その契約の，内容が
  `message_event` である許可の `id` でなければならない。1つの規範を名指してよい項目は
  高々1つである。その許可の `bearer:` は，契約インスタンスが束縛する添字（`ROBOT[i]`）を
  持ってはならない。すべての連鎖の最初のアクターをファイルから読み取れるようにするためである。
- **G-12.** `to:` は少なくとも1つの参照を列挙しなければならず，それぞれが宣言済みの
  アクターを名指さなければならない。ワイルドカードや範囲は許されるが，契約インスタンスが
  束縛する添字は許されない。`to:` はツールサーバを名指してはならず，負担者を含まないことが
  望ましい。`max_depth:` は1以上の整数でなければならない。`until:` は，規範の `until:` に
  ついての付録Fの規則（N-9，N-10）を満たさなければならない。
- **G-13.** `grant:` と `revoke:` は識別子でなければならず，予約語であってはならない。
  1つの契約の中で，すべての `grant:` と `revoke:` の名前は，互いに異なり，`approval` および
  `rejection` とも異ならなければならず，いずれも，当事者であるツールサーバのツールであっては
  ならない（G-3のYAML 1.1についての注記が当てはまる）。
- **G-14.** 処理系は，強制される契約の許可または禁止のうち，(a) 内容が `message_event` で
  ないもの（境界で効果を持たないため），または (b) 内容の `message_event` が引数を持つもの
  （引数は考慮されないため）について警告することが望ましい。
- **G-15.** 処理系は，(a) `default: allow` を持つ強制される契約の当事者のツールのうち，
  その契約のどの許可も禁止も覆わないもの，および (b) どの強制される契約の当事者でもなく，
  そのツール呼び出しが統治されないツールサーバについて警告することが望ましい。
  規範は，その内容の `message_event` がその受信者とメッセージ名を持つとき，メッセージを
  *覆う*という。
- **G-16.** 処理系は，契約が必要とし，かつ契約自身が拒否することになるメッセージについて
  警告することが望ましい。(a) 義務の内容または `fallback:` であって，そのメッセージの
  送信者を負担者とする `trigger:` のない禁止が覆うもの，または，ツール呼び出しの既定値が
  `deny` であるのに，その送信者のどの許可にも覆われないツール呼び出しであるもの。
  送信者が派生した許可を通じてのみ送ることのできるメッセージにも，この警告を出す。
  委任は実行時の状態だからである。(b) `default: deny` のもとで，どの許可も覆わない
  `grant:` または `revoke:` の名前，あるいは `approval` または `rejection` を作る規則の
  `when:` のメッセージ。

「しなければならない」の規則はエラーであり，「望ましい」の規則は警告であって，ファイルは
有効のままである。付録FのN-1からN-12は変わらず適用される。

## G.10 コード生成

2つのコードターゲットが，ファイルの強制される契約から境界方針を生成する。
これらは[付録D](./appendix-d-codegen.md)のカテゴリ*境界方針*に挙げている。
`agent-rego` はRego
[[Open Policy Agent]](./appendix-b-references.md)を出力する。これは，契約の他の部分から
契約ごとに1つの方針を出力する `opa` ターゲットとは独立である。`agent-cedar` はCedarの方針
[[AWS, AgentCore Policy]](./appendix-b-references.md)を出力する。方針の構文とファイルの
配置は，ターゲットが定める。

```jsonc
// policy input
{ "message": { "from": "SUMMARIZER", "to": "FILES", "name": "read_file" },
  "now": "2026-11-10T09:00:05Z",
  "instances": [
    { "contract": "ASSISTED_REPORTING", "instance": "default",
      "bindings": {},
      "in_force": {},
      "derived": [ { "norm": "may_read", "holder": "SUMMARIZER",
                     "chain": ["OPERATOR", "PLANNER", "SUMMARIZER"] } ] } ] }

// result
{ "decision": "allow", "reason": "permission",
  "contracts": ["ASSISTED_REPORTING"],
  "norms": ["ASSISTED_REPORTING.may_read"],
  "provenance": [["OPERATOR", "PLANNER", "SUMMARIZER"]],
  "escalate_to": null, "timeout": null, "fallback": [], "notify": [] }
```

入力は次のとおりである。

- `message`（必須）: `from` と `to` は，ファイルに書くとおりの具体的なアクター
  （`PLANNER`，`ROBOT[2]`）であり，`name` はメッセージ名である。
  引数は入力に含まれない。
- `now`（省略可能）: 決定の時刻。決定には影響しない。
- `instances`（省略可能）: すべての強制される契約の，動作中の**すべての**インスタンス。
  項目のない契約には，動作中のインスタンスがない。このフィールドがないとき，方針は，
  各強制される契約に，束縛された添字も派生インスタンスもない動作中のインスタンスが1つあると
  仮定する。インスタンスごとに，`bindings` は添字の名前を整数に対応付ける。`in_force` は，
  静的（後述）でない各規範の `id` を `true` または `false` に対応付け，項目がなければ
  不明である。`derived` は，ランタイムがG.7によって有効と認めた派生インスタンスを，
  その連鎖とともに列挙する。
- `derived` の項目は，フェイルクローズで再検査する。項目が適用されるのは，その規範が
  その契約の委任可能な許可であり，保持者がメッセージの送信者であって連鎖の最後の要素であり，
  連鎖のリンクが `max_depth` 以下であり，連鎖の最初の要素が負担者に一致し，それより後の
  各要素が `to:` の参照に一致し，元の許可が効力を持つ（静的であるか，フラグが `true` である。
  フラグがないものは数えない）ときだけである。それ以外の項目は無視する。

この形式でない入力については，決定を定義しない。処理系はエラーを報告し，生成した方針は
拒否する。

結果は次のとおりである。

- `decision`: `allow`，`deny`，`escalate` のいずれか。
- `reason`: `ungoverned`，`undeclared_tool`，`no_instance`，
  `prohibition`，`permission`，`default` のいずれか。終結記録（G.6）では，
  `approved`，`rejected`，`expired`，`cancelled` もある。
- `contracts`: 決定契約（G.5）の `id`。`ungoverned` と `undeclared_tool` では空である。
- `norms`: 決定契約の根拠（理由 `prohibition`）または適用される許可（理由 `permission`）。
  それぞれ `<contract id>.<norm id>` の形で，1回ずつ，宣言の順に並べる。
  それ以外の理由では空である。
- `provenance`: 適用される派生インスタンスの連鎖。その規範の順，次に入力の順に，
  重複なしで並べる。元の許可だけが適用されたときは空である。
- `escalate_to`: `escalate` の場合と，それを保つ終結記録（G.8）の場合の承認者。
  具体的なアクターで表す。それ以外は `null`。
- `timeout`（ミリ秒），`fallback`（テキストとしてのメッセージ事象），
  `notify`（アクター参照）は，理由が `prohibition` であるときは常に，`escalate` だけでなく
  `deny` についても，根拠から，重複なしで，宣言の順に埋める。それ以外のすべての理由では，
  `null`，`[]`，`[]` である。ただし，理由が `rejected`，`expired`，`cancelled` のいずれかである
  終結記録は，その保留の `fallback` と `notify` を保つ（G.8）。

規範は，次のとき**静的**である。内容が `message_event` である許可または禁止であり，
`trigger:`，`until:`，`deadline:` を持たず，どの権能も `effects:` でそれを名指さず，
どの規範も `reparation:` としてそれを名指さず，その規範のどのアクター参照も契約インスタンスが
束縛する添字を持たない。アクター参照とは，その負担者，相手方，内容，その `escalate_to` と
`notify`，およびその `fallback` の送信者と受信者である。G.5により，静的な規範は，
動作中のすべてのインスタンスで，その開始から終了まで効力を持つ。そのため，入力は
静的な規範のフラグを運ばない。方針は契約の1つの版に対して生成する。改正には新しい方針が
必要である。

生成した方針は，すべての入力について，G.5の決定関数と同じ `decision` を返さなければならない。
このとき，静的な規範は効力を持つものとし，その他のフラグと派生インスタンスは入力から取り，
入力が与えないものはすべて不明とする。方針言語が2つの結果しか持たないターゲットは，
G.5が `escalate` を与えるところで `deny` を返す。結果のその他のフィールドは，方針が
作ってもよく，ジェネレータが方針とともに出力する表（禁止ごとの `escalate_to`，`timeout`，
`fallback`，`notify`）からランタイムが作ってもよい。ジェネレータは，生成物の中に，
メッセージを内容とする許可または禁止のうち静的でないものをそれぞれ，実行時の状態を
必要とするものとして列挙し，それとは別に，他の内容を持つ許可または禁止をそれぞれ，
境界で効果を持たないものとして列挙しなければならない。他の種類の規範は列挙しない。
保留，解放，委任の管理（G.6，G.7）は，方針ではなくランタイムに属する。

入力に `message` だけを与えたときのG.12の例（参考）。

| `message` | 結果 |
| --- | --- |
| `PLANNER -> TICKETS : search_tickets` | `allow`，`permission`，`may_search`（静的な許可） |
| `PLANNER -> FILES : delete_file` | `OPERATOR` への `escalate`，`prohibition`，`no_delete` |
| `PLANNER -> FILES : format_disk` | `deny`，`undeclared_tool` |
| `SUMMARIZER -> FILES : read_file` | `deny`，`default`。上に示した `derived` の項目があれば，`allow`，`permission` |

**Cedarへの対応（参考）。** Cedar
[[Cutler+, OOPSLA 2024]](./appendix-b-references.md)では，`permit` の方針が満たされない限り
要求は拒否され，満たされた `forbid` の方針はすべての `permit` に優先し，評価がエラーを
起こした方針は飛ばされる。したがって，未宣言のツールと禁止は `forbid` の方針になり，
許可は `permit` の方針になり，ツール呼び出しの既定値は言語の既定の拒否である。
`escalate` は拒否として返され，出力した表からランタイムが解決する。
エラーを起こした `forbid` の方針は飛ばされ，拒否しないことになるため，生成した方針は，
上のスキーマのどの入力に対してもエラーを起こさないようにする必要がある。すなわち，
省略可能なすべての属性について，読む前にその存在を調べる。G.5が許可なしに許すメッセージ
（統治されないメッセージ，既定値が `allow` である契約）には，明示的な `permit` の方針が
必要である。また，強制される契約が2つ以上あるとき，契約をまたぐ拒否優先には，
契約ごとに，その契約が許さないものに対する追加の `forbid` の方針が必要である。
Cedarの答えだけからは，そのような方針による拒否や言語の既定値による拒否を，
「静的でない許可または派生した許可が許すかもしれない」場合と区別できない。
そのため，Cedarターゲットは静的な規範だけを扱い，残りはランタイムが決定する。

## G.12 例

人のオペレータが，LLMのプランナーに報告書の作成を依頼する。プランナーは2つのツールサーバの
ツールを呼び出し，ファイルの要約にサブエージェントを使う。このファイルは，本付録の
すべての規則と，[付録F](./appendix-f-norms.md)のN-1からN-12を満たす。

```yaml
sos:
  name: "AssistedReporting"
  extensions:
    - norms: 0.1
    - agents: 0.1

  actors:
    - id: OPERATOR
      role: "Human operator who owns the task and the files"
      agent: { kind: human }
    - id: PLANNER
      role: "LLM agent that plans the report and calls tools"
      agent: { kind: llm_agent, protocol: a2a }
    - id: SUMMARIZER
      role: "LLM sub-agent that summarises files for the planner"
      agent: { kind: llm_agent, protocol: a2a }
    - id: FILES
      role: "File store"
      agent: { kind: tool_server, protocol: mcp, tools: [read_file, delete_file] }
    - id: TICKETS
      role: "Issue tracker"
      agent: { kind: tool_server, protocol: mcp, tools: [search_tickets, create_ticket] }

  contracts:
    - id: ASSISTED_REPORTING
      parties: [OPERATOR, PLANNER, SUMMARIZER, FILES, TICKETS]
      enforcement:
        point: gateway      # default: を省略 -> ツール呼び出しは deny，他のメッセージは allow
      counts_as:
        - { when: "OPERATOR -> PLANNER : approve", creates: approval }
        - { when: "OPERATOR -> PLANNER : reject",  creates: rejection }
      norms:
        - id: may_read
          kind: permission
          bearer: OPERATOR
          content: "OPERATOR -> FILES : read_file"
        - id: may_search
          kind: permission
          bearer: PLANNER
          content: "PLANNER -> TICKETS : search_tickets"
        - id: may_file_ticket
          kind: permission
          bearer: PLANNER
          content: "PLANNER -> TICKETS : create_ticket"
        - id: no_delete
          kind: prohibition
          bearer: PLANNER
          content: "PLANNER -> FILES : delete_file"
          on_denied:
            escalate_to: OPERATOR
            timeout: 10min
            fallback: "PLANNER -> TICKETS : create_ticket"
            notify: OPERATOR
      delegations:
        - norm: may_read
          to: [PLANNER, SUMMARIZER]
          grant: grant_read
          revoke: revoke_read
          max_depth: 2
```

この契約は `lifecycle:` ブロックを持たず，インスタンスを生成するホストもない。
そのため，その単一のインスタンス（ここでは `default` と呼ぶ）は，判定点の開始時から存在する。
4つの規範は発動条件を持たない。開始時から効力を持ち，4つとも静的である（G.10）。
読み取りの許可はオペレータのものである。プランナーとサブエージェントは，高々2つのリンクに
わたる委任を通じてのみ読み取る。

09:00:00にオペレータが `OPERATOR -> PLANNER : grant_read` を送り，09:00:02にプランナーが
`PLANNER -> SUMMARIZER : grant_read` を送る。どちらも，どの規範も適用されない
通常のメッセージであるため，既定値によって許される。1つ目は，連鎖 OPERATOR → PLANNER を持つ
`may_read` の派生インスタンスを `PLANNER` のために作り，2つ目は，連鎖
OPERATOR → PLANNER → SUMMARIZER を持つ派生インスタンスを `SUMMARIZER` のために作る。
さらに `SUMMARIZER -> PLANNER : grant_read` が送られたとすれば，権限のない行為として
記録される。`PLANNER` は `SUMMARIZER` の連鎖に現れ（条件3），その連鎖はすでに2つのリンクを
持つ（条件4）からである。

**呼び出し1 — 連鎖を通じて許される。** 09:00:05にサブエージェントが
`SUMMARIZER -> FILES : read_file` を送る。このメッセージは統治され，ツールは宣言されている。
禁止は適用されない。送信者が `no_delete` の負担者でないからである。`SUMMARIZER` の
派生インスタンスは有効であり（`may_read` は効力を持ち，連鎖は2つのリンクを持ち，
そのアクターは `to:` にある），保持者を送信者として読んだその内容は一致する。
決定は `allow` である。

**呼び出し2 — エスカレーションされ，承認される。** 09:03:00にプランナーが
`PLANNER -> FILES : delete_file` を送る。`no_delete` は効力を持ち，適用される。
それは唯一の根拠であり，その `escalate_to:` は送信者でないため，決定は `escalate` である。
承認者 `OPERATOR` と期限09:13:00を持つ保留 `h-1` が作られる。09:03:40にオペレータが
`OPERATOR -> PLANNER : approve("h-1")` を送る。これは，既定値によって許される
通常のメッセージである。その観測の段階1の後，`OPERATOR` が行った事象 `approval` が
保留のid `h-1` を運び，保留は `approved` になる。段階6の後，メッセージをもう一度決定する。
ツールは宣言されており，根拠のインスタンスは動作中であり，根拠以外に適用される禁止はなく，
この呼び出しを統治する他の強制される契約もない。そのため，保留された
メッセージは，時刻印09:03:40を持つ次の観測になる。これは `no_delete` の内容が
起こったことにはならず，`no_delete` は `active` のままである。オペレータが `reject("h-1")` を
送った場合，または09:13:00まで何も送らなかった場合，終結記録は，理由 `rejected` の `deny`，
または時刻09:13:00を持つ `expired` の `deny` になる。プランナーは結果の中に代替のメッセージを
見いだし，`may_file_ticket` がその呼び出しを許す。

**呼び出し3 — 取消しの後に拒否される。** 09:10:00にオペレータが
`OPERATOR -> PLANNER : revoke_read` を送る。`PLANNER` の連鎖の中で `OPERATOR` は `PLANNER` より
前に現れるため，`PLANNER` のインスタンスは解除され，それとともに，連鎖に `PLANNER` が現れる
`SUMMARIZER` のインスタンスも解除される。09:10:30にサブエージェントが
`SUMMARIZER -> FILES : read_file` を送る。禁止は適用されない。`SUMMARIZER` は有効な許可を
保持しておらず，元の `may_read` は，送信者がその負担者でないため適用されない。
このメッセージはツール呼び出しであり，`default:` は省略されているため，契約は拒否する。
サブエージェントは，プランナーがもはや持っていない権限を保つことができない。

## G.13 IRへの追加とリファレンス実装の状況

シミュレータIR（E.7，F.9）を3か所で拡張する。そこと同じく，IRはデータクラスを
そのまま直列化したものであり，入れ子のブロックを平らにする。

```jsonc
// each actor under institution.actors
{ "id": "FILES",
  "agent_kind": "tool_server",          // null for an actor without agent:
  "agent_protocol": "mcp",
  "agent_tools": ["read_file", "delete_file"] }

// each contract under institution.contracts
{ "enforced": true,
  "enforcement_default": null,
  "enforcement_point": "gateway",
  "norms": [
    { "id": "no_delete",                // ... and the fields of F.9
      "on_denied_escalate_to": "OPERATOR",
      "on_denied_timeout_ms": 600000,
      "on_denied_fallback": "PLANNER -> TICKETS : create_ticket",
      "on_denied_notify": "OPERATOR" } ],
  "delegations": [
    { "norm": "may_read", "to": ["PLANNER", "SUMMARIZER"],
      "grant": "grant_read", "revoke": "revoke_read",
      "max_depth": 2, "until": null } ] }
```

`enforced` は，契約がキー `enforcement:` を持つとき，値がnullまたは空であっても，
`true` である。`enforcement_default` は，`default:` を省略したときは `null` である。
そのときの既定値はメッセージの種類に依存するからであり，それを適用することは利用側に委ねる。
`enforcement_point` は，強制される契約では値を持ち（`gateway`），それ以外では `null` である。
`max_depth` は常に値を持つ（`1`）。`fallback` と `until` はテキストのまま保持する。
`agent_tools` と `delegations` は，列挙するものがないときは空のリストであり，4つの
`on_denied_*` フィールドは，`on_denied:` を持たない規範では `null` である。
ここに示したすべてのフィールド（`agent_*`，`enforced`，`enforcement_*`，`delegations`，
`on_denied_*`）は，ファイルが `agents: 0.1` を宣言するときにだけ存在する。
`norms: 0.1` だけを宣言するファイルは，F.9のIRとちょうど同じIRを持つ。

**リファレンス実装。** `cadl` 0.3.20は，agents 0.1を次のように実装する。
4つの新しいキーを構文解析し，`cadl check` でG-1からG-16を適用し（「望ましい」は警告とする），
各ブロックを上のIRへ変換する。単なる数値で与えた `timeout:` は秒として読む。これは，
[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)が
期限について述べる寛容な形式である。`cadl agents-decide` は，G.10の方針の入力に対して
G.5の決定関数を実装する。これは状態を持たない。効力のフラグと有効な派生インスタンスは，
入力を通じて与える。
`cadl codegen -t agent-rego` は，完全な結果を返すRegoの方針を出力し，
`-t agent-cedar` は，静的な規範に対するCedarの方針を，付随する表とともに出力する。

**ランタイム。** `cadl` 0.3.21の次のリリースは，G.5からG.8のリファレンスランタイムである
`cadl agents-run FILE --trace TRACE [--audit OUT.jsonl]` を追加する。これは決定的で
オフラインである。記録済みのメッセージの列を，ファイルのすべての強制される契約にわたる
1つの判定点に通して再生する。時計はトレースの時刻だけである。メッセージごとに，効力のフラグを
`cadl norms-eval` の判定エンジン（F.10）から，有効な派生インスタンスをそれまでに観測した
付与と取消しから，動作中の契約インスタンスをトレースから得る。それらからG.10の方針の入力を
組み立て，`cadl agents-decide` の決定関数を呼ぶ。次に，G.5のとおりに決定を適用し，保留と
派生インスタンスを保持し（G.6，G.7），承認されたメッセージを解放する前にもう一度決定し，
G.8の監査記録と事象記録を書く。`--audit` を与えたときは，
記録をJSON Linesとして出力する。保留のidは，作られた順に `h-1`，`h-2`，…である。

トレースは `cadl norms-eval` のトレース（`t`，`bindings`，`request`，`values`，`messages`，
`state`，`amend`，`end` を持つJSON Lines）であり，判定点の全体について読む。キーを2つ追加する。
`epoch` は，`t = 0` の時刻をISO 8601の時刻印で与え，記録の時刻を時刻印にする。`instances` は，
ホストが作り，終わらせる契約インスタンスを，その束縛とともに与える。1つの行は次の順に処理する。
期限がその行の時刻より前の保留が期限切れになる。インスタンスを作る。行の時刻と値を，
メッセージなしで，改正とともに観測する（G.5）。各メッセージを決定し，許可されたメッセージは
1つの観測になる。ライフサイクル状態の変更とインスタンスの終了は，最後の観測になる。
インスタンスの終了より後のメッセージも，決定し，記録する。

次の3点は実装の読み方であり，本付録の規則ではない。改正は，2つの版で定義が異なる
強制される契約に適用し，強制される契約を追加することも削除することもできない。違反の後も，
禁止の期間の時計は，違反の前と同じく（F.5），禁止が停止されている間は止まる。判定 `excused` に
関して，メッセージが義務の内容に一致するかどうかは，境界と同じく，送信者，受信者，名前で調べる。

既知の限界。ランタイムはプロトコルに接続していない。トレースを再生するだけで，エージェントも
ツールも実行しない。ログを後からの変更に対して保護しない。ログは，規範の効力のフラグの変化の
記録を持たない（G.8）。トレースの時刻は，絶対値が10<sup>10</sup>以下の秒数で与える。
監査ファイルは，トレースの全体を再生したときにだけ書く。

テストは，ランタイムの各段階を，ランタイムが計算した状態を与えて決定関数で再実行し，
OPA 1.22.3のもとで生成したRegoの方針でも再実行する。手で書いた9つのシナリオの81個の決定
（G.12の3つの呼び出し，却下，タイムアウト，トリガから `until:` までの間の禁止，深さの制限を
持つ委任，束縛された添字とホストが作るインスタンスを持つ2つの契約）と，11個のファイルに対して
生成した26個のトレースの7 800個の決定について，両者の結果は一致した。生成したトレースは，
束縛の異なるホストが作るインスタンス，宣言された集合の外の送信者と未宣言の送信者，
2つの契約の一方だけに根拠を持つ保留，保留から承認までの間の取消し，インスタンスの終了，
改正を含む。それらのトレースの中のすべての解放（176件，うち拒否15件。無作為な改正のもとで
さらに13件，うち拒否8件）を，記録した方針の入力から，G.6の規則に照らして検査した。
リファレンス実装のコードを使わずに本付録の文面から書いた，G.4からG.7の第2のモデルは，
さらに32個のトレースについて，同じ5 101個の決定の記録と終結記録を与えた。シナリオのテストが
期待する記録は，ランタイムを実行する前に本付録の文面から導いたものであり，ランタイムは
そのとおりの記録を出力した。

ランタイムの最初の版の独立したレビューは，これらのテストが示さなかった欠陥を，実装と文面の
両方に見つけた。そのすべてが，効果を生じるべきでないメッセージに効果を生じさせるものであり，
すべて修正した。保留の根拠を，契約インスタンスごとではなく契約ごとに保持していたため，
承認が，後から作られたインスタンスにおける同じ禁止にも及んでいた（G.6）。解放される
メッセージの再検査が新しい禁止だけを調べていたため，たとえば取消しの後で，統治する別の契約が
もはや許さないメッセージが解放されていた（G.6。文面は「それ以外は再検査しない」としていた）。
`trigger:`，`until:`，`counts_as:` 規則の中の範囲付きのアクター参照が，その名前のすべての
アクターに一致し，`A[*]` が宣言された集合の外のアクターに一致していた。これは，0.3.20以来の
`cadl norms-eval` の欠陥である（F.3，F.10）。インスタンスが，その契約が統治しないメッセージを
観測していた（G.5）。生成したトレースも，欠陥を1つ示していた。同時に期限切れになる保留を，
期限の順ではなく作られた順に閉じていた。

ランタイムを書き，レビューする過程で，agents 0.1の文面に次の不足が見つかった。本付録の
この改訂は，これらを補う。メッセージを決定する状態が，最後の観測より後に過ぎた期限を
含んでおらず，許可されたメッセージをどの契約インスタンスが観測するかを述べていなかった
（G.5）。保留の根拠，`approval` を作る必要のある契約インスタンス，解放のときの決定，
同時に期限切れになる保留の順序を，述べていなかったか，述べ方が弱すぎた（G.6）。
委任の `until:` が項目を終わらせるのか，そのインスタンスを終わらせるのかが定まっていなかった
（G.7）。G.12が終結記録の中に送信者が見いだすとする `fallback` を，G.10が除外していた。
付与，取消し，権限のない行為，その他の状態の変化の記録には形式がなかった（G.8）。
契約が承認者のメッセージを統治することを求める規則がなかった（G-9。G.9の規則のうち，
変更するのはこれだけである）。

生成した方針は，OPA 1.22.3とCedar CLI 4.14.1で実行し，`cadl agents-decide` と比較した。
OPAでは，20 400個の入力について，結果の全体が一致した（強制される2つの契約，アクターの集合，
契約インスタンス，有効フラグ，委任の連鎖を持つファイルの3つの変種）。Cedarでは，5 640個の
要求について結果が一致した。ここで，Denyは拒否とエスカレーションの両方に対応する。
ただし，G.10が挙げる場合は除く。すなわち，静的でない禁止は，Cedarの方針では強制されない。
リファレンス実装のテストは，`opa` または `cedar` がインストールされているときに，両方の比較を
繰り返す。この実行で，`cadl` 0.3.20のRegoの方針に欠陥が見つかった。契約インスタンスが添字を
束縛しない参照 `A[i]` を，不明（G.4）ではなく不一致として扱っていたため，そのような担い手を持つ
禁止が適用されず，`default: allow` の契約ではメッセージが許可された。`cadl` 0.3.21はこれを
修正する。0.3.20で生成した方針は，生成し直すことが望ましい。

## G.14 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。
`norms: 0.1` だけを宣言するファイルも同じである。キー `enforcement:` を持たない契約は
強制されず，その規範は[付録F](./appendix-f-norms.md)の意味をそのまま保つ。
強制される契約について，本付録はF.5に次の追加を行い，それ以外の変更は行わない。
ホストのない契約のインスタンスは，判定点の開始時から存在する。拒否または保留された
メッセージは観測にならない。強制される契約のインスタンスは，その契約が統治するメッセージだけを
観測する。決定の時刻は，メッセージを決定する前に観測する。許可と禁止は，効力を持つかどうかのフラグを持つ。
内容を契約自身が拒否または保留した義務は `excused` になる（以上はすべてG.5）。
`approval` と `rejection` は保留のidを運び，段階の順序を拡張し，解放されたメッセージは
その根拠に違反しない（G.6）。許可は派生インスタンスを持つ（G.7）。

`agents: 0.1` を宣言せずに `agent:`，`enforcement:`，`delegations:`，または `on_denied:` を
用いるファイルは，本付録に適合しない。エージェント統治拡張を扱う処理系は，そのような
ファイルではこれらのキーを解釈せず（検査もIRへの変換もしない），用いられているキーを
名指す警告をファイルごとに1つ出すことが望ましい。`norms: 0.1` なしに `agents: 0.1` を
宣言するファイルは，G-1のエラーになる。
本拡張を実装していない処理系は，本拡張を用いるファイルを拒否してはならない。
ファイルごとに1つの情報レベルの診断を出すことが望ましい。

# 6. 設計

## 6.1 アーキテクチャ

CADL処理系は以下の4つの主要コンポーネントから構成される。

**パーサ・型検査器 (Frontend):**
CADL記述を解析し，抽象構文木（AST）を生成する。静的型検査により，アクター参照の解決，契約当事者の整合性，型の一致を検査する。

**検証エンジン (Verifier):**
AST上で形式検証を実行する。無矛盾性検証（SMTソルバ），デッドロック検出（モデル検査），安全性検証（到達可能性解析）を統合する。

**コード生成器 (Code Generator):**
CADL記述からターゲット言語（Python/TypeScript/Solidity）のランタイムコードを生成する。SysMLv2やAADLへの変換もサポートする。

**ランタイム監視器 (Runtime Monitor):**
配備された制度の実行を監視し，契約違反の検出，制度遷移の実行，ログ記録を行う。

```
処理パイプライン:

CADL記述 (.cadl)
  │
  ▼
┌──────────────┐
│ パーサ       │ ─── 構文エラー報告
│ 型検査器     │ ─── 型エラー報告
└──────┬───────┘
       │ AST
       ▼
┌──────────────┐
│ 検証エンジン │ ─── 検証結果（OK / 反例）
│  - SMT       │
│  - モデル検査│
│  - 到達可能性│
└──────┬───────┘
       │ 検証済AST
       ▼
┌──────────────┐    ┌─────────────┐
│ コード生成器 │───▶│ ランタイム   │
│  - Python    │    │ 監視器       │

│  - SysMLv2   │    │  - 遷移制御  │
└──────────────┘    └─────────────┘
```

## 6.2 処理系の構成

### 6.2.1 パーサ

YAMLベースの構文を解析し，CADL固有の型注釈・制約式・プロトコルステップを追加的に解析する。パーサはPEGパーサジェネレータを利用し，エラー回復機能を持つ。パース結果は型付きASTとして出力される。

### 6.2.2 型検査器

型検査は以下の項目を検査する: (1) アクター参照の存在確認, (2) 契約当事者の重複・不在検出, (3) プロトコルステップの送受信者がアクター定義に一致すること, (4) 情報共有宣言と実際のメッセージ交換の整合性, (5) 制度パラメータの値域制約（0 ≤ α, β, λ ≤ 1）。

## 6.3 検証エンジン

検証エンジンは3つの検証手法を統合する。

| **検証手法** | **検証対象** | **ツール基盤** |
|---|---|---|
| SMTベース検証 | 契約間の無矛盾性。guaranteeの論理的整合性。 | Z3, CVC5 |
| モデル検査 | プロトコルのデッドロック，ライブロック検出。到達可能状態の網羅的探索。 | UPPAAL, NuSMV |
| 到達可能性解析 | 制度遷移時の安全性不変条件の保持。Hamilton-Jacobi到達可能性解析。 | hj_reachability |
| 構成的検証 | アクター追加・離脱時の差分検証。既存契約への影響分析。 | 独自実装 |

## 6.4 ランタイムシステム

ランタイムシステムは，CADL記述から生成されたランタイムコードを実行環境上で監視・制御する。主な機能は以下のとおりである。

**契約監視:**
各契約のassume/guaranteeの充足を実行時に監視し，違反を検出した場合は定義されたviolationアクションを実行する。

**制度遷移制御:**
モードマップに基づき，環境パラメータの変化に応じた制度遷移を安全に実行する。遷移プロトコルの各ステップを管理し，ロールバック機能を提供する。

**メトリクス収集:**
定義された評価指標（パフォーマンス，公平性，レジリエンス等）をリアルタイムで計算し，ダッシュボードに表示する。

**ログ・監査:**
全てのプロトコル実行，契約違反，制度遷移をタイムスタンプ付きで記録し，事後分析・説明責任の履行に資する。IEC 62853の合意記述データベースとの連携を想定する。

# 付録F. 規範拡張（norms 0.1）

本付録は，CADLの**規範拡張**を規定する。この拡張は，
[付録A.4](./appendix-a-syntax.md#a4-contracts-institution-layer)の生成規則
`contract_def` に2つのキー `norms:` と `counts_as:` を追加し，契約の一部の述語に
有界の時相演算子を追加する。これにより，コア言語では `assume:`，`guarantee:`，
`responsibilities:` のテキストとして書くしかなかった義務・許可・禁止・権能を，負担者，期限，
時間に沿った状態，違反時の帰結を持つ対象として書けるようになる。

コア言語（[第5章](./05-language-spec.md)，[付録A](./appendix-a-syntax.md)）は，
これらのブロックを必須としない。
本拡張を実装していないCADL準拠の処理系は，新しいキーを理由にファイルを
拒否してはならない。新しいキーを構文上は受理し，*情報レベル*の診断を出すことが望ましい。

本拡張のバージョンは，コア言語とは独立に管理する。拡張の名前は `norms` であり，
本付録はバージョン `0.1` を記述する。F.4の時相演算子は一部の述語の読み方を変えるため，
本拡張を用いるファイルは，[付録A.2](./appendix-a-syntax.md#a2-top-level-structure)の
`extensions:` キーでそのことを宣言しなければならない。宣言せずに用いた場合に処理系がどう扱うかは
F.11で述べる。

```yaml
sos:
  ...
  extensions:
    - norms: 0.1
```

本拡張は，SoS-DSL拡張（[付録E](./appendix-e-sos-dsl.md)）と併用しても，単独で用いてもよい。
契約が `lifecycle:` ブロックも持つ場合，規範は違反時に契約インスタンスをライフサイクルの状態へ
移すことができる（F.3）。

## F.1 動機

[9.6節](./09-research.md)の研究方向は，コア言語に欠けている次の4点を挙げている。本拡張のバージョン0.1は，
そのそれぞれに対応する最小限の機能を定める。

1. **規範が第一級でない。** `"delivery_time <= 300s"` のような保証は，何が成り立つべきかを述べるが，
   誰がそれを成り立たせるのか，いつからいつまでか，成り立たなかったときにどうなるかを述べない。
   Symboleoのような義務論理に基づく契約言語は，義務と権能をライフサイクルを持つ対象として扱う
   [[Sharifi+, 2020]](./appendix-b-references.md)。CADLの契約はそうではなかった。
2. **述語に時間がない。** `assume:` と `guarantee:` は状態述語である。期限は，SoS-DSL拡張の
   ライフサイクル遷移にしかない。
3. **プロトコルと契約がつながっていない。** プロトコルのメッセージが契約上の行為と*みなされる*
   （counts as）ことを述べる手段がない。制度は，このようにして他の事実から制度的事実を作り出す
   [[Boella & van der Torre, KR 2004]](./appendix-b-references.md)。
4. **改正が動作中の規範に及ばない。** SoSの運用中に契約を改正する場合（ハンズオン教材の
   [Course D](../handson/robot-town-tutorial.md) のように），すでに発効している義務がどうなるかを
   述べる手段がない。

norms 0.1が定める範囲は意図して小さくしている。語彙と静的・動的意味論を定めることで，設計時の検査
（モデル検査器への変換。F.12）と実行時の監視を，言語を変えずに処理系が追加できるようにする。
制度パラメータα，β，λには，規範に関する形式的な意味を与えない（F.7）。契約の規範とパラメータを
結び付ける最初の定めは，根拠付け拡張（[付録J](./appendix-j-grounding.md)）が与える。

## F.2 概念

| 概念 | norms 0.1での意味 |
| --- | --- |
| **規範（norm）** | 契約に宣言する，1人の負担者の義務・許可・禁止・権能。 |
| **義務（obligation）** | 負担者は，その `content` を実現しなければならない（述語を真にする，または事象を起こす）。`deadline:` があればその期限までに。 |
| **禁止（prohibition）** | 負担者は，規範が発効している間（`deadline:` があればその期間内），その `content` を実現してはならない。 |
| **許可（permission）** | 負担者は，その `content` を実現してよい。許可は違反されることがなく，許されていることを記録する。 |
| **権能（power）** | 負担者は，契約の他の規範の状態を変える制度上の行為（その `content`）を行うことができる（`effects:`）。権能は履行も違反もされない。 |
| **制度的事象（institutional event）** | `counts_as:` 規則がメッセージや条件から作る，契約の名前付きの事象。たとえば「このメッセージは再割当てとみなす」。 |
| **契約インスタンス** | [付録E](./appendix-e-sos-dsl.md)と同じく，契約の1回の実行。いつ始まりいつ終わるかはF.5で述べる。 |
| **規範インスタンス** | 1つの契約インスタンスにおける規範。バージョン0.1では，各規範は1つの契約インスタンスにつきちょうど1つのインスタンスを持つ。`ROBOT[i]` の `i` のような添字は契約インスタンスが束縛する。 |
| **判定（verdict）** | これまでに観測したトレース上での，規範インスタンスまたは時相的な保証の値。`pending`，`fulfilled`，`violated`，`excused` のいずれか（F.5）。 |

## F.3 構文（A.4へのEBNFの追加）

文法は[付録A](./appendix-a-syntax.md)の記法に従う。`identifier`，`actor_ref`，
`duration_lit`，`predicate`，`text` は付録Aで，`message_event` と `severity` は
[付録EのE.3節](./appendix-e-sos-dsl.md)で定義している。`contract_def` に2つの省略可能なキーを追加する。

```ebnf
contract_def    = ... ,
                  [ "norms:"     , { "-" , norm_def } ] ,
                  [ "counts_as:" , { "-" , counts_as_def } ] ;

norm_def        = "id:"           , identifier ,
                  "kind:"         , norm_kind ,
                  "bearer:"       , actor_ref ,
                  [ "counterparty:" , actor_ref ] ,
                  [ "trigger:"      , norm_event ] ,
                  [ "until:"        , norm_event ] ,
                  "content:"      , norm_content ,
                  [ "deadline:"     , duration_lit ] ,
                  [ "on_violation:" , norm_violation ] ,
                  [ "effects:"      , power_effects ] ,
                  [ "on_amendment:" , amendment_policy ] ;
norm_kind       = "obligation" | "permission" | "prohibition" | "power" ;

norm_event      = message_event | identifier | predicate ;    (* string *)
norm_content    = message_event | identifier | tpredicate ;   (* string *)

norm_violation  = [ "severity:"   , severity ] ,
                  [ "sanction:"   , text ] ,
                  [ "reparation:" , identifier ] ,
                  [ "transition:" , identifier ] ;

power_effects   = [ "activate:"  , { "-" , identifier } ] ,
                  [ "suspend:"   , { "-" , identifier } ] ,
                  [ "resume:"    , { "-" , identifier } ] ,
                  [ "discharge:" , { "-" , identifier } ] ;

amendment_policy = "carry_over" | "discharge"
                 | ( "transform:" , identifier ) ;

counts_as_def   = "when:"    , ( message_event | predicate ) ,
                  "creates:" , identifier ,
                  [ "if:"      , predicate ] ;
```

`norm_event` と `norm_content` は次のように読む。`A -> B : m` の形の文字列は `message_event` である。
1つの識別子だけからなる文字列は，契約が `counts_as:` でその名前の制度的事象を宣言していれば
その事象を名指し，そうでなければ述語（状態変数，N-8）である。それ以外の文字列は述語
（`norm_event`）または `tpredicate`（`norm_content`）である。より大きな述語の中に現れる
制度的事象の名前（`reassignment AND x > 0`）は，事象ではなく状態変数である。`[`，`]`，`*`，`->`，
`": "` を含む値は，[付録A](./appendix-a-syntax.md)のすべてのスカラーと同じく，引用符で囲むことが
望ましく，フロー形式のシーケンスの中では囲まなければならない。

`message_event` `S -> R : m` は，名前 `m` を持ち，送信者が `S` に一致し，受信者が `R` に
一致するメッセージを含む観測で**起こる**。`m` を引数付きで書いたときは，それらがメッセージの
引数と等しくなければならない。アクター参照は，`message_event` が現れるどの場所でも，すなわち
`trigger:`，`until:`，`content:`，`counts_as:` 規則の `when:` で，メッセージの具体的な
アクターに次のように一致する。

| 参照 | 一致するもの |
| --- | --- |
| `A` | 添字なしで宣言したアクター `A`。添字付きの要素 `A[k]` には一致しない |
| `A[3]` | 要素 `A[3]` |
| `A[*]` | 宣言した集合 `A` のすべての要素 |
| `A[1..3]` | 要素 `A[1]` から `A[3]` まで。上限が記号であるとき（`A[1..N]`）は，集合のすべての要素 |
| `A[i]` | 契約インスタンスが `i` を `v` に束縛しているときは，要素 `A[v]`。`i` に値を束縛していないときは，集合のすべての要素（処理系は警告することが望ましい） |

`A` を範囲付きで宣言しており，`k` がその整数の上下限の内にあるとき，`A[k]` は集合 `A` の
**要素**である。`A[1..3]` と宣言した集合は `A[7]` を含まない。宣言した上限が記号であるとき
（`A[1..N]`）は，下限以上のすべての添字が要素であり，`A[0]` は要素でない。宣言していないアクター，
または集合の上下限の外にあるアクターは，どの参照にも一致しない。

これらの述語では，[付録EのE.4節](./appendix-e-sos-dsl.md#e4-static-semantics)の予約識別子を
`rule` と同じく用いることができる。`now`，`request`，および契約が `lifecycle:` ブロックを持つ場合の
`state` である。E.3の所属判定 `x IN [a, b]` も用いることができる。

`on_violation:` の `reparation:` は，この規範が違反されたときに発効する同じ契約の別の規範
（反義務（contrary-to-duty）の規範）を名指し，`sanction:` は制裁をテキストで述べ，
`transition:` は契約の `lifecycle:` ブロック（[付録E](./appendix-e-sos-dsl.md)）の状態を名指す。
契約インスタンスは，ライフサイクル遷移の `on_violation.transition` と同じく，その状態へ移る。
`severity:` の既定値は `Major`，`on_amendment:` の既定値は `carry_over` である。
`counterparty:` は規範の相手方となる当事者を名指す。バージョン0.1では参考情報であり，
意味論には影響しない。

キー `until:` と，F.4の時相演算子 `until(...)` は別のものであり，同じ規範の中に両方現れてよい。

## F.4 時相述語

`tpredicate` は，[付録AのA.10節](./appendix-a-syntax.md#a10-expressions)の `predicate` のうち，
`function_call` が書ける位置に次の3つの有界の時相演算子を書けるものである。
演算子は関数呼び出しの形で書くため，A.10の式の文法は変わらない。本拡張はこの3つの名前に意味を与える。

```ebnf
tpredicate      = predicate ;     (* 以下の呼び出しが時相的な意味を持つ *)
temporal_call   = "within"     , "(" , duration_lit , "," , tpredicate , ")"
                | "throughout" , "(" , duration_lit , "," , tpredicate , ")"
                | "until"      , "(" , tpredicate , "," , tpredicate , "," , duration_lit , ")" ;
```

| 演算子 | 時刻 t で成り立つ条件 | 計量時相論理 |
| --- | --- | --- |
| `within(d, p)` | `[t, t + d]` のある時刻で `p` が成り立つ | F<sub>[0,d]</sub> p |
| `throughout(d, p)` | `[t, t + d]` のすべての時刻で `p` が成り立つ | G<sub>[0,d]</sub> p |
| `until(p, q, d)` | `[t, t + d]` のある時刻 t′ で `q` が成り立ち，`[t, t′)` のすべての時刻で `p` が成り立つ | p U<sub>[0,d]</sub> q |

演算子は**時刻付きトレース**の上で評価する。これは観測の列であり，各観測は観測量のスナップショットと
単調非減少の時刻印からなる。[付録E](./appendix-e-sos-dsl.md)のモニターに渡されるものと同じである。
「ある時刻」「すべての時刻」は，時刻印がその区間に入る観測の上を動く（点ごとの意味論）。
観測を1つも含まない区間では，`within` は偽，`throughout` は真になる。`d` は0より大きい
`duration_lit` でなければならない。演算子は入れ子にしてよい。

**書ける位置。** 本拡張を宣言すると，時相演算子は，契約の `assume:` と `guarantee:` の項目，
および規範の `content:` にだけ書ける。バージョン0.1では，ファイルのそれ以外の述語や条件には
書いてはならない（N-10）。たとえば，規範の `trigger:` と `until:`，`counts_as:` 規則の `when:` と
`if:`，モニターの `rule:`，ライフサイクルの `when:` と `on:`，`condition:`，`safety_invariant:`，
`formula:`，`expr:`，プロトコルの条件である。事象と条件は1つの観測の時点で評価するため，そこに未来を参照する演算子を
書くと，後になるまで真偽が決まらないからである。

**評価する時点。** `assume:` または `guarantee:` の `tpredicate` は，契約インスタンスが始まる時刻に
評価する。そこでの `within(300s, p)` は「契約インスタンスの開始から300秒以内に `p`」を意味する。
不変条件を述べるには `throughout` を用いて書く。`content:` の `tpredicate` は，規範の発動後の
観測の時刻に評価する（F.5）。時相演算子を含まない述語は，コア言語での意味を保つ。

**値が分かる時点。** 時刻 t での演算子の値は，t より後の観測に依存することがある。値は，それを
定める最初の観測で**決まる**。それまで値は決まらず，決まった値は変わらない。

被演算子が時相演算子を含まない演算子については，規則は次のとおりである。`within(d, p)` が真に，
`throughout(d, p)` が偽に決まるのは，`[t, t + d]` の中のそれを示す観測である。`until(p, q, d)` は，
`q` が成り立つ観測で真に決まり，`q` が成り立つより前に `p` が成り立たなくなった観測で偽に決まる。
それ以外の場合，値は，時刻印が `t + d` より後である最初の観測で決まる。このとき区間は終わっており，
`within` と `until` は偽，`throughout` は真である。ただし，区間の中の観測で被演算子が未定義（F.5）で
あり，その被演算子に値があれば結果が変わりえた場合，値は未定義である。`until(p, q, d)` では，
これに当たるのは，`q` が未定義であった場合と，`q` が成り立った観測より前の観測で `p` が未定義で
あった場合だけである。`q` が一度も成り立たなかったときは，`p` が未定義であっても関係がなく，
値は偽である。同様に，`q` が未定義であった観測より後に `p` が成り立たなくなっても，`until` は
偽とは決まらず，値は未定義である。したがって，
区間の終わりは，時刻 `t + d` そのものではなく，その後の最初の観測で分かる。その観測は，どの量も
変えなくてよい（F.5）。

被演算子が時相演算子を含む演算子は，それが依存する被演算子の値が決まったときに決まる。被演算子の
値は，それぞれの観測で，同じ規則によって決まる。これは `t + d` より後になることがある。時刻 t での
`within(2s, throughout(5s, p))` は，`[t, t + 2s]` の観測での `throughout(5s, p)` の値を必要とする。
`p` が成り立ち続ける場合，その値は5秒より後の観測で初めて決まる。したがって，この演算子は，
`t + 7s` より後の観測まで決まらないことがある。一般に，時刻 t での `tpredicate` の値は，
遅くとも，入れ子になった演算子の時間の和の最大値を t に加えた時刻より後の最初の観測で決まる。

`norms: 0.1` を宣言していないファイルは，コア言語と同じく，`within`，`throughout`，`until` を
ふつうの関数名として読む。

## F.5 動的意味論

### 契約インスタンス

規範は契約インスタンスごとに判定する。契約が `lifecycle:` ブロックを持つ場合，契約インスタンスは
[付録EのE.5節](./appendix-e-sos-dsl.md)のものである。ホストアプリケーションがインスタンスを生成し，
インスタンスは終端状態に達したときに**終わる**。契約が `lifecycle:` ブロックを持たない場合，
ホストアプリケーションは同じようにして，状態を持たない契約インスタンスを生成し，終わらせる。
ホストがない場合は，1つのインスタンスが最初の観測で始まり，最後の観測で終わる。
契約インスタンスがまだ動作している間に止まったトレースは*前半部分*であり，インスタンスは終わっておらず，
何も確定させない。

システムの動作中に観測を1つずつ受け取る処理系は，ある観測を処理する時点では，それが最後の観測で
あるかどうかを判断できない。そのような処理系には，インスタンスの終了を，その観測の後に別に通知する。
規範は，そのとき，最後に受け取った観測で，その時刻印を用いて，その観測の段階6と同じように
確定させる（下の6）。契約インスタンスが終わった後に届いた観測は，そのインスタンスの一部ではなく，
インスタンスに影響しない。

観測は，何も変えなくてよい。時刻印だけを含む観測も，他の観測と同じ観測であり，その時点で述語を評価し，
期限を調べる。過ぎた期限と区間の終わりは，観測と観測の間ではなく，観測の時点で検出する（下の2と3，F.4）。
したがって，動作中のシステムを監視する処理系は，発効中の規範の期限が過ぎた後，早いうちに観測を
行うことが望ましい。観測がなければ，違反は次の観測まで起こらず，`violated` か `excused` かも
そのときまで決まらない。

述語は，各観測で，真，偽，**未定義**の3つの値のいずれかを取る。未定義とは，まだ値を持たない量を
参照している場合である。`AND`，`OR`，`NOT` はクリーネの3値論理に従う。未定義の述語は，成り立ちも
破れもしない。事象や条件はそれによって起こらず，仮定や保証はそれによって決まらない。
「真になる」とは，現在の観測で真であり，かつインスタンスの直前の観測で真でなかった（または直前の
観測がない）ことをいう。`lifecycle:` ブロックを持つ契約では，述語の中の `state` は，現在の観測の
遷移が起こる前のライフサイクルの状態である。

`load > 5` の `load` や `ROBOT[i].status == Delivered` の `Delivered` のように，述語の中に単独で
書かれた名前は，観測量か記号値のいずれかである。観測量である名前の集合は，契約インスタンスごとに
固定する。この集合は，インスタンスの開始時に処理系に与える。記録したトレースについては，
インスタンスのいずれかの観測で値を持つ名前の集合である。この集合に属する名前は，インスタンスの
すべての観測で量であり，最初の値より前の観測では未定義であって，記号値ではない。単独で書かれた
それ以外の名前は，すべて記号値である。記号値は，`==`，`!=`，`IN` によって文字列の値と比べることだけが
できる。それ以外の使い方をする述語は未定義である。

### 限量子と集約

限量述語 `exists x in D: p` と `for all x in D: p`，および集約関数の引数である内包表記
`f(e for x in D)`（[付録AのA.10節](./appendix-a-syntax.md#a10-expressions)）は，
観測の時点で**定義域** `D` の上で評価する。定義域は，宣言したアクターの集合を `A`，`A[*]`，
`A[lo..hi]` のいずれかで名指す。内包表記の定義域は，整数の範囲 `lo..hi` でもよい。
それ以外の定義域を持つ述語は評価しない（F.10）。

変数 `x` は，定義域のメンバーの添字を値に取る。`p` または `e` の中では，`x` で添字付けした
アクター参照（`A[x]`。`A[x+1]` のような添字式の中も含む）はその添字のメンバーを表す。
`A` のメンバー（F.3）でない添字はどのメンバーも表さず，その量は，トレースが何を与えても
未定義である。`x.q` はそのメンバーの量 `q` を表す（`sum(r.load for r in ROBOT[*])` の `r.load`）。
単独の `x` は整数の添字であり，`j != k` は `j` と `k` が異なるメンバーであることをいう。
`p` または `e` の中では，`x` は，契約インスタンスが束縛する同名の添字，同名の観測量，
および外側の限量子や内包表記の同名の変数を隠す。集合の宣言の記号の境界は隠さない。
`A[1..N]` と宣言した集合の境界 `N` は，限量子や内包表記が `N` という名前の変数を持つときも，
すべての限量子と内包表記の外側で読む（N-14）。

**閉じた定義域と開いた定義域。** 集合のメンバーはF.3のとおりであり，範囲 `A[lo..hi]` は
その境界の内側のメンバーだけを残す。すべての境界が整数であれば，定義域は**閉じて**おり，
ちょうどそれらのメンバーからなる。記号の境界（`A[1..N]` と宣言した集合，`A[2..N]`，`1..N` の
`N`）は，契約インスタンスがその名前を整数に束縛するとき，またはその名前が観測量であって
その観測での値が整数であるとき，その観測で値を持つ。記号の境界を持つ定義域も，そのような
境界がすべて値を持ち，かつ，集合の宣言の記号の境界については，その値を超える添字のメンバーが
その観測またはそれより前に名指されていないときは，閉じている。F.3は，境界がどんな値を持っても，
下限以上のすべての添字をメンバーとするので，値を超えて名指されたメンバーがあれば定義域は
開いたままである。そのとき処理系は警告することが望ましい。そうでなければ定義域は**開いて**おり，
メンバーの数はわからない。開いた定義域の，ある観測での
**既知のメンバー**とは，集合のメンバーのうち整数の境界の内側にあり，契約インスタンスが
その観測またはそれより前に名指したものである。名指すとは，値の名前に現れること
（`A[3].delivery`），メッセージの送信者または受信者であること，および，契約の規範か
`counts_as:` 規則が `A[i]` と書く添字 `i` を `k` に束縛することである。現在より後の観測は
決して用いない。したがって，開いた定義域が，後で観測したものによって閉じることはない。

トレースが与える境界はいくらでも大きくなりうるので，処理系は，閉じた定義域について列挙する
メンバーの数を制限してよい。そのとき，制限より多くのメンバーを持つ閉じた定義域は，その既知の
メンバーによって，開いた定義域として評価する。下の議論によりこれは健全であり，閉じた定義域が
決めるはずの値が未定義になりうるだけである。そうする処理系は，集合と大きさを示して警告する
ことが望ましい。

**値。** 閉じた定義域では，限量子はクリーネの3値論理に従う。`exists x in D: p` は，
あるメンバーで `p` が真なら真，すべてのメンバーで `p` が偽なら偽，それ以外は未定義である。
`for all x in D: p` は，あるメンバーで `p` が偽なら偽，すべてのメンバーで `p` が真なら真，
それ以外は未定義である。空の定義域では，`exists` は偽，`for all` は真である。開いた定義域では，
既知のメンバーだけが値を決める。`exists` は，既知のあるメンバーで `p` が真なら真であり，
`for all` は，既知のあるメンバーで `p` が偽なら偽である。それ以外の値は未定義である。
既知のすべてのメンバーで `p` が同じ値を持つときも，既知のメンバーがないときも同じである。
`p` が時相演算子（F.4）を含むときは，まだ値を決めうるメンバーについて `p` が決まっていない間，
値は決まらない。

開いた定義域についてのこの規則は健全である。既知のメンバーをその観測での値のまま含み，
さらに任意のメンバーを任意の値（未定義でもよい）で含む閉じた定義域を考える。そのような定義域は，
それまでに名指されたすべてのメンバーを含むので，境界が後にどんな値を取っても，開いた定義域の
あり得る完成形である。`p` が真となる
メンバーはその定義域でも `exists` を真にし，`p` が偽となるメンバーは `for all` を偽にする。
クリーネの論理では，真の被演算子を持つ選言は真であり，偽の被演算子を持つ連言は偽であって，
ほかの被演算子によらないからである。したがって，開いた定義域で真または偽である値は，
そのようなすべての閉じた定義域での値である。この規則はまた最も強い。既知のメンバーが
値を決めないとき，`p` が真となる（または偽となる）メンバーを加えると値が変わる。未定義は，
F.5が値を持たない量を参照する述語に与える値である。特に，開いた定義域の上の `exists` は
決して偽にならず，`for all` は決して真にならない。`content:` がそのような `exists` である禁止は，
既知のメンバーがそれを示したときに違反となり，そうでなければ，未定義の内容一般と同じく，
違反とならない。

**集約。** 内包表記の集約関数のうち，規範拡張は `sum`，`count`，`min`，`max`，`avg` を
評価する。`count(p for x in D)` は `p` が真となるメンバーの数である。`p` の値は，真であるか0以外の数で
あるときに真と数え，文字列の値や記号値はその数を未定義にする。ほかの関数は `e` の値を
取り，その値は数である。空の定義域の `sum` と `count` は0である。集約は，開いた定義域の上で，
あるメンバーで `e`（`count` では `p`）が未定義であるとき，`e` の値が数でないとき，
および空の定義域の上の `min`，`max`，`avg` では未定義である。そのような値を比べる述語は
未定義である。ほかの関数と，内包表記の中の時相演算子は評価しない（F.10）。

`ROBOT[*].battery > 10` や `count(ROBOT[*].status == Collision)` のような，定義域の外の
ワイルドカード参照や範囲参照には，述語の中で付録Aが定める値がなく，それを含む述語は
評価しない（F.10）。意味は限量子の形で書ける。`for all j in ROBOT: ROBOT[j].battery > 10` と
`count(ROBOT[j].status == Collision for j in ROBOT)` である。

ある観測での定義域とその既知のメンバーは，その観測までの観測だけによる。したがって，
限量述語と集約の値についても，下の判定の性質が保たれる。ある観測の後の判定は，その観測までの
トレースの判定である。定義域が開いているためにある観測で未定義である述語は，メンバーが
名指されるか境界が値を持つと，後の観測で値を持つことがある。前の観測での値は未定義のまま
である。

### 規範インスタンス

規範インスタンスは，次の6つの状態のいずれかにある。

| 状態 | 意味 |
| --- | --- |
| `inactive` | まだ発効していない。 |
| `active` | 発効中。義務または禁止が判定されている。 |
| `suspended` | 一時的に発効していない（権能による）。期限と期間の時計は止まる。 |
| `fulfilled` | 内容が期限内に実現された義務，または内容が起こらないまま期間が終わった禁止。 |
| `violated` | 内容が実現されないまま期限が過ぎた義務，または内容が起こった禁止。 |
| `discharged` | 履行も違反もされずに終わった。`until:`，権能，契約インスタンスの終了，または改正（F.6）による。 |

`fulfilled`，`violated`，`discharged` は最終状態である。バージョン0.1では，規範インスタンスは
1つの契約インスタンスにつき高々1回判定される。規範インスタンスが `inactive` でないときに
起こった発動条件は無視し，禁止は最初の違反だけを報告する。

1. **発動。** 規範インスタンスは `inactive` で始まり，次のときに `active` になる。
   - その `trigger:` が起こったとき（メッセージが送られる，制度的事象が作られる，または述語が真になる）。
   - `trigger:` を持たず，他の規範の `reparation:` にも権能の `activate:` の効果にも名指されていない
     規範については，契約インスタンスが始まったとき。
   - それが修復する規範が違反されたとき（`reparation:`），または権能がそれを発効させたとき（`activate:`）。

   **発動時刻**は，規範が発効した観測の時刻印である。
2. **義務。** 発効中の義務は，発動時刻以降の観測のうち，その `content` が起こる（メッセージまたは
   制度的事象）か成り立つ（その観測の時点で評価した `tpredicate`）最初の観測で `fulfilled` になる。
   発動時刻から `suspended` の間の時間を除いて測った `deadline:` が，そうならないまま過ぎると
   `violated` になる。ちょうど期限の時刻の内容は期限内とし，義務が `suspended` である間の内容は数えない。
違反は，期限の後の最初の観測で起こる。内容が時相演算子を含む `tpredicate`
   である場合，ある観測での値は後になって決まることがある。義務は値が決まるまで `pending` にとどまり，
   期限までの観測だけを数える。
3. **禁止。** 発効中の禁止は，その `content` が起こるか成り立つ最初の観測で `violated` になる。
   発動時刻から `suspended` の間の時間を除いて測った `deadline:` の期間が終わると `fulfilled` になる。
   ちょうど期間の終わりの時刻の内容は違反とする。停止中の禁止は判定しない。
4. **許可と権能。** 解除されるまで `active` にとどまる。
5. **解除。** `active` または `suspended` の規範インスタンスは，期限にかかわらず，その `until:` が
   起こったとき，または権能がそれを解除したときに `discharged` になる。
6. **契約インスタンスの終了。** 契約インスタンスが終わると，最終状態でないすべての規範インスタンスを
   確定させる。`deadline:` のない発効中または停止中の義務は `violated` に，期限がまだ過ぎていない
   義務は `discharged` に，禁止は `fulfilled` に，`inactive` のものを含むそれ以外の規範インスタンスは
   `discharged` になる。例外が2つある。インスタンスが終わる観測で発効し，その観測の段階4で
   最終状態にならなかった規範インスタンスは，発効の後に観測がないため `discharged` になる。
   内容の `tpredicate` の値がまだ決まっていない
   義務または禁止は，そのままの状態にとどまり，判定は `pending` である。この確定によって生じた違反は，
   その重大度とともに報告するが，インスタンスが終わっているため，`reparation:` と `transition:` は
   適用しない。
7. **権能。** メッセージから作られた制度的事象は，そのメッセージの送信者が*行った*ものとする。
   述語から作られた制度的事象には行為者がいない。発効中の権能の負担者がその `content`（制度的事象，
   または負担者が送るメッセージ）を行うと，`effects:` が同じ契約インスタンスの規範インスタンスに
   適用される。`activate` は未発効の規範を発効させ，`suspend` は発効中の規範を停止し，`resume` は
   停止中の規範を発効に戻し，`discharge` は発効中または停止中の規範を `discharged` にする。
   他の状態にある規範への効果は何もしない。行為者の対応する権能が発効していないときにその行為が
   行われた場合，効果は適用されない（制度的事象そのものは他の規範に対して存在する）。規範を監視する
   処理系は，その行為を権限のない行為として記録することが望ましい。
8. **違反。** 規範インスタンスが `violated` になると，その `on_violation:` が適用される。
   指定の `severity:`（既定値 `Major`）で，規範の `id` をラベルとする違反が報告され，
   `reparation:` の規範が発動し，`transition:` があり，かつ契約インスタンスがまだ終端状態に
   なければ，契約インスタンスはその状態へ移る。

### Counts-as

`counts_as:` 規則は，その `when:` が起こり（メッセージが送られるか，述語が真になる），
その観測で `if:` の条件（あれば）が成り立つと，契約インスタンスにその制度的事象を作る。
制度的事象は契約インスタンスに局所的である。制度的事象は事象としてのみ存在し，規範を発動させ，
終わらせ，履行させることができ，権能の内容になる。

### 1つの観測の中での順序

1つの観測に含まれる1つのメッセージが，制度的事象を作り，ある規範を発動させ，別の規範を履行させ，
ライフサイクル遷移を起こすことがある。処理系は次の順に，それぞれ直前の段階が残した状態に対して適用する。
段階1の前に，契約の `assume:` の項目，次に `guarantee:` の項目を評価する。したがって，ある観測で
破れた仮定は，その観測での違反を免責する。また，インスタンスの最初の観測では，それより前に，
インスタンスの開始時に発効する規範を発効させる。

1. `counts_as:` 規則の制度的事象を作る。
2. 権能の効果を適用する（7）。権能は宣言の順に，1つの権能の中では `activate`，`suspend`，`resume`，
   `discharge` の順に適用する。権能が発効しているかどうかは，この段階の初めに決める。
3. 発動条件が起こった規範を発動させる（1）。
4. 発効中の規範を判定する。各規範について，過ぎた期限，内容，`until:` の順に調べる（2，3，5）。
   したがって，同じ観測では，期限切れによる違反が解除より先になり，内容が `until:` より先になる。
   段階3で発動した規範もこの段階で判定するため，発動時刻の内容も数える。
5. `on_violation:` を適用する（8）。ここで発動した修復の規範は，次の観測で初めて判定する。
6. [付録E](./appendix-e-sos-dsl.md)のライフサイクル遷移を起こし，契約インスタンスが終わっていれば
   その規範を確定させる（6）。

### 判定

これまでに観測した有限のトレース上での，規範インスタンス，または時相演算子を含む保証の**判定**は，
次の4つの値のいずれかである。

| 判定 | 規範インスタンス | 契約の保証 |
| --- | --- | --- |
| `pending` | `inactive`，`active`，`suspended` | 観測した前半部分では決まらない |
| `fulfilled` | `fulfilled` または `discharged` | 前半部分のどの続きでも成り立つ |
| `violated` | 契約の仮定が1つも破れていない間に `violated` になった | どの続きでも成り立たず，その時点で仮定が1つも破れていなかった |
| `excused` | 契約の仮定が破れた観測以降に `violated` になった | 仮定が破れた観測以降に成り立たなくなった |

仮定は，その値が偽になる最初の観測で**破れる**（時相演算子を含む項目では，値が偽に決まる観測である。F.4）。
値がまだ決まらない仮定や，値が未定義の仮定は破れていない。時相演算子を含まない `assume:` または `guarantee:` の項目は状態述語であり，すべての観測で
評価する。偽である最初の観測で破れ，契約インスタンスが終わるまで破れなかった保証は `fulfilled` になる。
状態述語と時相演算子が混ざった項目は `tpredicate` であり，インスタンスの開始時に1回評価する。
仮定がいったん破れると，同じ契約インスタンスの以後の違反はすべて `excused` になる。保証や規範が
`excused` になるのは，仮定が破れたときではなく，それ自身が破れたときである。解除された許可や
権能の判定は `fulfilled` とする。F.2の意味で履行されたわけではない。期限切れによる違反が
`violated` か `excused` かは，期限の時刻ではなく，違反が起こる観測で判定する。トレースが終わっても，
`pending` の判定は `pending` のままである。期限や区間の終わりより前に止まったトレースは，
それを決めない。区間がまだ終わっていない時相的な項目は，契約インスタンスが終わっても決まらない。

観測量の集合を契約インスタンスごとに固定すれば（上の「契約インスタンス」を参照），ある観測の後の
判定は，その観測までのトレースを，同じ集合のもとで前半部分として読んだときの判定である。判定は
それより後の観測に依存せず，`pending` 以外の判定は後から変わらない。したがって，処理系は，
システムの動作中に観測ごとに判定を計算してよい。量の集合が同じであれば，その判定は，記録した
トレースを読む処理系の判定と同じである。

量の名前を与えられず，観測から名前を得る処理系は，名前を，最初の値が届くまで記号値として読む。
そのような名前を最初の値より前に使う述語については，この処理系は上と異なる判定を与えてよい。
許される違いはこれだけである。このような処理系には，名前を与えることが望ましい。違いが生じるのは，
その名前を文字列の値と比べる場合だけである。記号値のそれ以外の使い方は未定義であり，値のない量も
未定義だからである。

`excused` は，「負担者が果たさなかった」ことと「契約が仮定するものを負担者が与えられなかった」ことを
区別する。これは，義務論理に基づく実行時検証で責任を割り当てる基礎である
[[Kharraz+, ICTAC 2023]](./appendix-b-references.md)。仮定を考慮することで，監視できる性質も増える
[[Henzinger & Saraç, RV 2020]](./appendix-b-references.md)。バージョン0.1は，仮定のこの弱い読み方を
用いる。仮定が成り立たなくなった後もしばらく保証が成り立たなければならないという
[5.4.1節](./05-language-spec.md)の強い読み方は，バージョン0.1の判定では表さない。
`excused` となった規範も，その `on_violation:` は発動する。契約インスタンスへの帰結は
責任の所在に依存しないためである。報告される違反は，判定 `excused` を伴う。

## F.6 改正

**改正**とは，契約インスタンスの動作中に，契約の定義を同じ `id` を持つ新しいバージョンで置き換えることである。
バージョンをどう作り，承認し，発効させるかはnorms 0.1の範囲外である。ハンズオン教材の
[Course D](../handson/robot-town-tutorial.md) はその手続きの1つを示している。新しいバージョンは，ある観測で，
その観測で他の何を評価するよりも前に発効する（仮定と保証の評価，およびF.5の段階1よりも前）。
したがって，改正によって発効した規範は，その同じ観測で判定する。規範インスタンスは次のように扱う。

`active` または `suspended` の規範インスタンスは，**古い**バージョンの規範の `on_amendment:` に従う。

| `on_amendment:` | 効果 |
| --- | --- |
| `carry_over`（既定値） | インスタンスは，新しいバージョンの同じ `id` の規範のもとで続く。状態と，期限に対してすでに経過した時間を保つ。新しいバージョンにその `id` の規範がない場合，またはその規範の `kind` が異なる場合は，代わりに `discharged` になる。内容が変わる場合，インスタンスはこの観測以降，新しい内容で判定する。経過した時間がすでに新しい期限を超えている場合（ちょうど等しい場合は超えていない），義務は，停止中のものも含めて，新しいバージョンの発効時に `violated` になる。禁止は期間が終わったことになり，`fulfilled` になる。 |
| `discharge` | インスタンスは `discharged` になる。 |
| `transform: X` | インスタンスは `discharged` になり，新しいバージョンの規範 `X` が `inactive` であればそれを発動させる。経過した時間は期限に算入する（義務と禁止の場合。許可と権能では時間は影響しない）。`X` が `inactive` でなければ，それ以上は何もしない。 |

表の各項目は，古いバージョンが規範を宣言している順に，新しい規範を発効させる前に適用する。
`transform:` の対象 `X` が新しいバージョンにない場合，インスタンスは `discharged` になるだけである。

`inactive` の規範インスタンスは，新しいバージョンの同じ `id` の規範の定義を引き継ぎ，新しいバージョンにその規範が
なければ取り除かれる。新しい定義が `trigger:` を持たなくても，改正によって発効することはない。
古いバージョンにその `id` の規範がないものを*新しい*規範という。新しい規範は `inactive` から始まり，
`trigger:` を持たず，修復や発動の対象でもなければ，ただちに発効する（F.5の1）。最終状態のインスタンス
（`fulfilled`，`violated`，`discharged`）は影響を受けず，その `id` は同じ契約インスタンスの中で
再び使わない。最終状態のインスタンスと同じ `id` を持つ新しいバージョンの規範には，新しいインスタンスを
作らない。特に，違反は，それが起きたバージョンのもとでの違反のままである。改正の後に起きた違反には，
新しいバージョンの `on_violation:` を用いる。

新しいバージョンの `counts_as:` 規則は，その発効時から適用する。両方のバージョンでテキストが同じ `assume:` または
`guarantee:` の項目は，その値を保って続く。新しい項目はこの観測から評価する（`tpredicate` はこの観測で
評価する）。取り除かれた項目は，それまでの判定を保つ。改正の前に破れた仮定は，以後の違反を
引き続き免責する。契約が `lifecycle:` ブロックを持つ場合，インスタンスの現在の状態は新しいバージョンの状態で
なければならない。そうでなければ，そのインスタンスに改正を適用できない。バージョン0.1では，
モード遷移（A.7）は規範インスタンスに影響しない。

改正を適用する処理系は，新しいバージョンが発効する前に，引き継がれる規範のうち `content` または
`deadline:` が変わるものをすべて報告することが望ましい。

## F.7 静的意味論 {/* #f7-static-semantics */}

規範拡張を扱う処理系は，既存の検査に加えて，次の検査をしなければならない。

- **N-1.** 規範の `id` は識別子でなければならず，予約語（[付録E](./appendix-e-sos-dsl.md)の `IN` を
  含む）であってはならず，契約の中で一意でなければならない。`creates:` の名前は識別子でなければならず，
  同じ契約の規範の `id` と同じであってはならない（YAML 1.1のローダーでは，引用符のない `yes`，`no`，
  `on`，`off` は名前ではなく真偽値になる。[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)を参照）。
- **N-2.** `kind:` は `obligation`，`permission`，`prohibition`，`power` のいずれかでなければならない。
- **N-3.** `bearer:` と `counterparty:` は，宣言済みの1つのアクターを，添字なしで，整数の添字付きで
  （`ROBOT[1]`），または契約インスタンスが束縛する添字付きで（`ROBOT[i]`）名指さなければならない。ワイルドカードや範囲（`ROBOT[*]`，
  `ROBOT[1..3]`）は許されない。契約の当事者を名指すことが望ましい。
- **N-4.** `deadline:` は `duration_lit` でなければならず，義務または禁止にだけ書ける。
  `on_violation:` も義務または禁止にだけ書ける。
- **N-5.** `effects:` は権能にだけ書け，権能は少なくとも1つの効果を持たなければならない。
  `effects:` の各名前は，権能自身以外の，同じ契約の規範の `id` でなければならない。
- **N-6.** `on_violation.reparation` は，`trigger:` を持たない，同じ契約の義務または禁止を
  名指さなければならない。どの規範から `reparation:` をたどっても，その規範に戻ってはならない。
- **N-7.** `on_violation.transition` は，同じ契約の `lifecycle.states` にある状態を名指さなければ
  ならない。したがって，その契約は `lifecycle:` ブロック（[付録E](./appendix-e-sos-dsl.md)）を
  持たなければならない。
- **N-8.** `trigger:`，`until:`，`content:` の全体として用いた識別子が，契約の制度的事象ではなく
  規範の `id` であるときは，誤りの可能性が高いため，処理系は警告することが望ましい。
- **N-9.** 規範または `counts_as:` 規則の `message_event` では，送信者と受信者は宣言済みのアクターを
  名指さなければならない。権能の内容は，それを作るすべての `counts_as:` 規則が `message_event` から
  作る制度的事象，または送信者が負担者である `message_event` でなければならない。内容が `message_event` である義務または禁止では，
  送信者は負担者であることが望ましい。
- **N-10.** 時相演算子はF.4の引数を持たなければならず，その期間は0より大きい `duration_lit`
  でなければならず，F.4が許す位置の外に現れてはならない。
- **N-11.** `on_amendment:` は，`carry_over`，`discharge`，または識別子 `X` を持つ
  `{ transform: X }` でなければならない（`X` が新しいバージョンに存在するかは，そのバージョンに対してしか検査できない）。
- **N-12.** 同じ契約の許可と禁止が，同じ `bearer:` と，テキストとして同一の `content:` を持つ
  ときは，両者が衝突するため，処理系は警告することが望ましい。
- **N-13.** 禁止の `trigger:` が `message_event` であり，トリガのすべての発生が内容の発生でも
  あるとき，処理系は警告することが望ましい。内容が，同じメッセージ名を持ち，内容が引数を持つ
  ときは同じ値の引数を持ち，トリガのアクター参照が一致するすべてのアクターに一致するアクター参照を
  持つ `message_event` である場合（`R[1..3]` と宣言した集合についての `D -> R[i] : go` と
  `D -> R[1..3] : go`），または，内容が，`if:` のない `counts_as:` 規則がそのようなメッセージから
  作る制度的事象である場合である。この検査は最善の努力であり，そのような禁止をすべて見つける
  わけではない（たとえば，トリガのメッセージが真にする述語を内容とするもの）。そのような禁止は，それを発効させる観測で違反となる
  （F.5の段階4）。これが意図であることはまれである。2回目の発生の禁止は，状態についての
  限量述語（F.5の「限量子と集約」）か，それより前の事象をトリガとし `until:` で区切った禁止で
  書く。
- **N-14.** 限量子または内包表記の変数が，宣言した集合の記号の境界の名前を持つとき
  （`S[1..N]` についての `for all N in S: ...`），処理系は警告することが望ましい。境界は
  限量子の中でも自分の値を保つ（F.5）が，読み手はそれを予期しないかもしれない。

### コアの検査との関係

[6.3節](./06-design.md)の無矛盾性検査（SMTソルバーによる `assume:` と `guarantee:` の
充足可能性の検査）は状態述語に適用する。時相演算子を含む `assume:` または `guarantee:` の項目は
状態述語ではない。規範拡張を扱う処理系のうち時相述語を変換しないものは，そのような項目をSMT検査から外し，
外したことを報告しなければならない。演算子を解釈されない関数として扱ってはならない。

### 制度パラメータとの関係（参考）

[5.4.2節](./05-language-spec.md)のパラメータには，バージョン0.1では規範に関する形式的な意味を
与えない。後のバージョンで明確にする予定の読み方（[9.6節](./09-research.md)のRD-6.1）は次のとおりである。
意思決定の集中度βは，契約の権能を誰が持つかを表す。情報共有度αは，他の当事者がどの発動条件と
内容を観測できるかを表す。インセンティブ強度λは，違反された規範の制裁の大きさを調整する。

根拠付け拡張（[付録J](./appendix-j-grounding.md)，`grounding` 0.1）は，本付録を変えずに，
この読み方に関係する指標を定義する。βについては，契約の権能の集中である。αについては，宣言した
情報項目の共有である（発動条件と内容の観測可能性ではない）。λについては，戦略モデルがλを掛ける
制裁の数値の大きさと，制裁または報酬を伴う規範の数である。

## F.8 例

次の契約は，[付録EのE.6節](./appendix-e-sos-dsl.md)の配送契約を簡略にし，規範を加えたものである。
[`cadl`](https://github.com/ertlnagoya/cadl) リポジトリの `examples/norms_robot_delivery.cadl`
から取り，一部を省略している。

```yaml
sos:
  name: "RobotDeliveryNorms"
  extensions:
    - sos-dsl: 0.1
    - norms: 0.1
  # アクター DISPATCHER，ROBOT[1..N]，CUSTOMER[1..M] は付録Eと同じ

  contracts:
    - id: DELIVERY_SLA
      parties: [DISPATCHER, "ROBOT[*]", "CUSTOMER[*]"]
      assume:
        - "throughout(300s, DISPATCHER.is_operational == true)"
      guarantee:
        - "within(300s, ROBOT[i].status == Delivered)"

      lifecycle:
        states:   [Proposed, Assigned, Delivering, Completed, Violated]
        initial:  Proposed
        terminal: [Completed, Violated]
        transitions:
          - { id: assign,   from: Proposed,   to: Assigned,   on: "DISPATCHER -> ROBOT[i] : route_assignment" }
          - { id: start,    from: Assigned,   to: Delivering, on: "ROBOT[i].status == InTransit" }
          - { id: complete, from: Delivering, to: Completed,  on: "ROBOT[i].status == Delivered" }

      counts_as:
        - when: "DISPATCHER -> ROBOT[i] : replan_command"
          creates: reassignment

      norms:
        - id: acknowledge
          kind: obligation
          bearer: "ROBOT[i]"
          counterparty: DISPATCHER
          trigger: "DISPATCHER -> ROBOT[i] : route_assignment"
          content: "ROBOT[i] -> DISPATCHER : ack(accepted)"
          deadline: 5s
          on_violation:
            severity: Major
            reparation: report_failure
        - id: report_failure
          kind: obligation
          bearer: "ROBOT[i]"
          counterparty: DISPATCHER
          content: "ROBOT[i] -> DISPATCHER : failure_report"
          deadline: 2s
          on_violation:
            severity: Critical
            transition: Violated
        - id: no_low_battery_driving
          kind: prohibition
          bearer: "ROBOT[i]"
          content: "ROBOT[i].battery < 10 AND ROBOT[i].status == InTransit"
          on_violation:
            severity: Critical
            sanction: "removed from the dispatch pool for one period"
        - id: may_return_to_charge
          kind: permission
          bearer: "ROBOT[i]"
          content: "ROBOT[i] -> DISPATCHER : charging_request"
        - id: reassign
          kind: power
          bearer: DISPATCHER
          content: reassignment
          effects:
            discharge: [acknowledge, report_failure]
          on_amendment: discharge
```

`acknowledge` は経路の割当てで発動し，5秒以内に果たさなければならない。これが違反されると，
ロボットは2秒以内に故障を報告しなければならない（反義務の義務 `report_failure`。それまでは
`inactive` のままである）。これも果たせないと，契約インスタンスは `Violated` へ移る。
`no_low_battery_driving`，`may_return_to_charge`，`reassign` は発動条件を持たず，契約インスタンスの
開始時から発効している。配車係の `replan_command` は配車係が行う `reassignment` とみなされ，
権能 `reassign` が発効している間は，2つの義務をどちらも解除する。各規範は契約インスタンスごとに
1回しか判定されないため，同じインスタンスで後から経路の割当てがあっても新しい義務は生じない。
保証は，ロボットが契約インスタンスの開始から300秒以内に配送することを述べる。遅れた配送より前に
配車係が動作を止めた場合，その配送は `violated` ではなく `excused` になる。

## F.9 中間表現（IR）への追加

シミュレータIR（E.7）の `institution.contracts` の各契約に，`norms` と `counts_as` の
2つのフィールドを追加する。E.7と同じく，IRはデータクラスをそのまま直列化したものであり，
入れ子のブロックを平らにする。

```jsonc
{
  "norms": [
    { "id": "acknowledge",
      "kind": "obligation",
      "bearer": "ROBOT[i]",
      "counterparty": "DISPATCHER",
      "trigger": "DISPATCHER -> ROBOT[i] : route_assignment",
      "until": null,
      "content": "ROBOT[i] -> DISPATCHER : ack(accepted)",
      "deadline_ms": 5000,
      "on_violation_severity": "Major",
      "on_violation_sanction": null,
      "on_violation_reparation": "report_failure",
      "on_violation_transition": null,
      "effects_activate": [],
      "effects_suspend": [],
      "effects_resume": [],
      "effects_discharge": [],
      "on_amendment": "carry_over",
      "transform_to": null }
  ],
  "counts_as": [
    { "when": "DISPATCHER -> ROBOT[i] : replan_command",
      "creates": "reassignment",
      "if": null }
  ]
}
```

`trigger`，`until`，`content`，`when`，`if` は，E.7の規則と同じくテキストのまま保持する。
キー `if` は，直列化したIRでは `if` と書く。ホスト言語によっては，データクラスのフィールドにこの名前を付けられない。
`on_violation_severity` は，`on_violation:` ブロック全体を省略したときは `null`，
`severity:` なしでブロックがあるときは `Major` である。`on_amendment` は常に値を持ち，`carry_over`，`discharge`，
`transform` のいずれかである。`transform_to` は `transform:` の対象であり，それ以外のときは `null` である。
`norms` と `counts_as` は，それらを持たない契約では空のリストである。

## F.10 リファレンス実装の状況 {/* #f10-reference-implementation-status */}

リファレンス実装（`cadl` 0.3）は，`cadl` 0.3.19からnorms 0.1を次のように実装する。

- `cadl` は `norms:`，`counts_as:`，およびF.4の時相演算子を構文解析し，`cadl check` で
  規則N-1からN-14を適用し（N-8，N-12，N-13，N-14，およびN-3とN-9の「望ましい」は警告とする。
  N-13とN-14は `cadl` 0.3.23から），両ブロックをF.9のIRへ変換する。
- `cadl verify` のSMT検査は，時相演算子を含む `assume:` と `guarantee:` の項目を外し，
  それぞれを検査しなかったものとして報告する（F.7）。`cadl codegen` は，同じ項目をすべてのターゲットの
  契約のコードから外し，コードにコメントを残して警告を出す。時相演算子はターゲットの言語へ変換しない。
  Pythonターゲットは，これらの項目を別のモジュールで監視する（下記）。
- 規範の数値の `deadline:` は秒として読む。これは，[A.12](./appendix-a-syntax.md#a12-reference-implementation-status-v03)が
  ライフサイクルの期限について述べる寛容な形式である。`cadl check` は，F.4に挙げた位置で時相演算子を探す。
  テキストである `violation.detect`，`incentives.rules`，プロトコルの `trigger:`，`context.assumptions` の中は探さない。
- `cadl` 0.3.20からは，`cadl norms-eval` が，記録したトレース（JSON Lines。1行に1つの観測。形式は
  `cadl` リポジトリのREADMEに示す）から，1つの契約インスタンスについて，F.5の規範の状態，判定，違反，
  制度的事象，権限のない行為を計算し，トレースが名指すF.6の改正を適用する。ライフサイクルの状態は
  トレースから取り，ライフサイクルの状態機械は実行しない。違反が求める `transition:` は報告するだけで，
  適用しない。`cadl` 0.3.21までは，メッセージ事象のアクター参照を広く一致させすぎていた。
  `A[1..2]` のような範囲が `A[k]` という名前のすべてのアクターに一致し，`A[*]` と束縛のない
  `A[i]` が，宣言した集合の外のアクターにも一致していた。`cadl` 0.3.22は，F.3の表に
  従って一致させる。`trigger:`，`until:`，`content:`，`counts_as:` 規則でそのような参照を用いる
  ファイルについて計算した判定は，計算し直すことが望ましい。このリリースは，上限が記号である
  集合の下限も調べる。トレースの時刻は，絶対値が2<sup>53</sup>以下の有限の数であり，エポック秒も
  エポックミリ秒も受け付ける。トレースのメッセージのアクターと名前は，書かれたとおりに読む。
  0.3.21が `ROBOT[2]` と読んでいた `ROBOT[ 2 ]` は，トレースの誤りである。これは意図した変更である。
  記録したトレースの中で1つのアクターに2つの綴りがあると，名前を比較する検査が無効になるからである。また，契約インスタンスの
  終了後の観測を完全に無視する。0.3.21までは，観測量の名前（F.5）をそれらの観測からも取っていたため，
  終了後の観測が判定を変えることがあった。`cadl` 0.3.22までは，限量子または集約を含む規範や
  項目を評価しなかった。`cadl` 0.3.23からは，F.5（「限量子と集約」）の定めるとおりに評価する。閉じた定義域の
  メンバーは10 000個まで列挙し，それより大きい定義域は警告を出して開いた定義域として評価する。
  時相演算子と内包表記の `sum`，`count`，`min`，`max`，`avg` 以外の関数呼び出し，限量子や
  内包表記の定義域の外のワイルドカード参照や範囲参照（`ROBOT[*].battery`），定義域がアクターの
  集合でも範囲でもない限量子や内包表記，整数の範囲を動く変数 `x` についての `x.q`，内包表記の
  中の時相演算子のいずれかを含む規範や項目は評価せず，`pending` のままにし，その理由を
  報告に示す。`cadl norms-diff` は，ファイルの2つのバージョンを比べ，F.6が各契約の規範に
  何をするかを報告する。引き継がれる規範のうち `content` または `deadline:` が変わるものと，新しいバージョンに
  ない `transform:` の対象を含む。
- `cadl` 0.3.22からは，`cadl codegen -t python` が，`norms: 0.1` を宣言したファイルに対して，
  生成するパッケージにモジュール `norms_monitor.py` を出力する
  （[付録DのD.1節](./appendix-d-codegen.md)）。このモジュールは，システムの動作中に
  1つの契約インスタンスを監視する。ホストはインスタンスに対してモニターを作り，観測を1つずつ渡す。
  モニターは，その観測で状態または判定が変わった規範インスタンス，保証，仮定を，時刻と理由とともに返す。
  ホストはインスタンスの終了を通知し，現在の判定を問い合わせることができる。モジュールは，
  `cadl norms-eval` の評価コードをそのまま写したものと，ファイルの契約をデータにしたものを含む。
  実行時に `cadl` を必要とせず，記録したトレースに対しては `cadl norms-eval` と同じ結果を与える。
  このコマンドと同じく，ライフサイクルの状態は観測から取り，`transition:` は報告するだけで適用しない。
  観測を1つずつ受け取る処理系についてF.4とF.5が述べる点は，次のように扱う。過ぎた期限と区間の
  終わりは，次の観測で検出する。モニターは，時間が経過するだけで決まるものについて，それが確実に決まる最も早い
  時刻印をホストに知らせる（期限の時刻ちょうどの内容は期限内であるため，期限または区間の終わりより
  わずかに後である。時刻は10<sup>-9</sup>秒の許容誤差で比べる）。アクターを付けずに書かれた量の名前は
  ホストが指定する。指定のない名前は，最初の値が届くまで記号値として読む。これはF.5が許す違いである
  （`cadl norms-eval` は，名前を，トレースの中のインスタンスの観測から取る）。インスタンスの終了後の
  観測は何の効果も持たず，その数を警告に示す。形式の誤った観測と，改正を適用できない観測は拒否し，
  モニターは元のままである。インスタンスの観測は，モニターを捨てるまで保持する。改正（F.6）は，
  新しいバージョンから生成したモニターのデータをホストが与えた場合に適用する。モニターはCADLファイルを読めない。
  `cadl codegen` は，モジュールを書き出す前に，それがコンパイルできること，および使う名前がすべて
  その中で定義されていることを検査し，そうでなければ生成を拒否する。
- Solidity，OPA，Unity C#のターゲットは規範を監視しない。
- `cadl` 0.3.25からは，`cadl norms-check` がF.12を実装する。1つの契約インスタンスのモデルを作り
  （`--bindings`，`--members`，`--step`，`--horizon`），PRISM 4.11（PATH上の `prism`。明示的エンジンで，
  戦略を出力させる）で問いを実行し，すべての証拠を `cadl norms-eval` のエンジンで評価する。
  `--timeout` は，PRISMのすべての実行に使う時間の合計を制限する（既定は600秒）。PRISMがなければ，
  何も検査しなかったことを報告して終了ステータス0で終わり，モデルと性質は書き出せる（`--export`）。
  `--require-checker` を指定すると，PRISMがないことを誤りとする。Stormは使わない。変換は，
  生成したPRISMのテキストを，それが使う部分を読む解釈器で実行し，`cadl norms-eval` と照合して試験している。
  実行する経路は，環境の選択のランダムな経路と，1つの契約について観測が2個以下のすべての経路である。
  比べるのは，各観測での各規範の状態である。解釈器はPRISMのシミュレータが生成した経路と比べ，
  PRISMの答えは到達可能な状態についての明示的な不動点計算と比べている。

## F.11 後方互換性

本拡張を用いないCADL v0.3のファイルは引き続き有効であり，同じように読まれる。
`norms: 0.1` を宣言せずに `norms:`，`counts_as:`，または時相演算子を用いるファイルは，
本付録に適合しない。規範拡張を扱う処理系は，そのようなファイルでは `within`，`throughout`，`until` を
ふつうの関数名として読み，`norms:` と `counts_as:` のブロックを解釈せず（検査もIRへの変換もしない），
宣言されていない拡張のキーとして報告することが望ましい。本拡張を実装していない処理系は，
そのようなファイルを拒否してはならない。ファイルごとに1つの情報レベルの診断を出すことが望ましい。

## F.12 モデル検査器による設計時の検査 {/* #f12-design-time-checking */}

F.5は，1つの契約インスタンスの規範を1つのトレースについて判定する。本節は，1つの契約インスタンスの
規範を，PRISM言語 [[Kwiatkowska+, CAV 2011]](./appendix-b-references.md) の有限のマルコフ決定過程（MDP）に
変換する方法を定める。このMDPの経路は，長さが上限以下であるそのインスタンスのトレースのすべてである。
モデル検査器は，トレースがまだない設計の段階で，すべての振る舞いについて次の問いに答える。規範はそもそも
違反されうるか。義務が発効するたびに，それを守る続きがあるか。2つの規範は衝突するか。権能は一度でも
行使されうるか。モデルは確率を持たない。選択はすべて環境の非決定的な選択であり，問いは定性的である。
同じ行為を義務づけ，かつ禁止する規範の検出は，規範的なマルチエージェントシステムで知られた問題である
[[Vasconcelos+, JAAMAS 2009]](./appendix-b-references.md)。SymboleoPCは，法的な契約の性質をモデル検査器
nuXmvで検査する [[Parvizimosaed+, SoSyM 2025]](./appendix-b-references.md)。本節は，このような検査を
提供する処理系のためのものであり，F.1からF.11を変えない。

### 契約インスタンス

モデルは，1つの契約と1つの契約インスタンスについて作る。契約の添字変数（`ROBOT[i]` の `i`）は
固定した値を持ち，アクターの集合はそれぞれ固定した数nの要素 `A[lo]` から `A[lo+n-1]` を持つ。上限が
整数である集合では，nは宣言した大きさ以下である。メッセージ事象の中の `A[*]`，`A[lo..hi]`，束縛の
ない `A[i]` は，F.3の表で一致するインスタンスの要素を表す。

### 環境が選ぶもの

環境は，各観測で次の3つを選ぶ。

1. メッセージ。モデルのメッセージ事象は，変換した `trigger:`，`until:`，義務・禁止・権能の内容，
   counts-as規則の `when:` に含まれるメッセージ事象が，インスタンスの中で表す具体的なメッセージ
   （送信者，受信者，名前，引数）である。これらのどれにも一致しないメッセージは，変換した規範の状態を
   変えないので，モデルに含めない。環境はメッセージ事象の部分集合を選ぶ。1つの観測で，各メッセージ事象は
   高々1回，決まった順序（モデルの順序）で起こる。
2. 値。v0.1の述語は，1つの量をリテラルと比べる。ある量と比べるリテラルは，その量の定義域を，そのような
   比較がすべて同じ値を持つクラスに分ける。数 c<sub>1</sub> < … < c<sub>k</sub> では，c<sub>1</sub>より
   小さい値，各c<sub>j</sub>，隣り合う2つの間の開区間，c<sub>k</sub>より大きい値がクラスである。記号値と
   テキストの値では，各リテラルとそれ以外の1つの値がクラスである。真理値の量では，真と偽がクラスである。
   各クラスは1つの代表値で表す。どの量についても「値なし」もクラスであり，その量を使う述語はそこで
   未定義（F.5）になる。環境は量ごとに1つのクラスを選ぶ。ただし，量のクラスの組合せのうち，すべての
   述語に同じ3値の値を与えるものは区別しない。モデルは，そのような組合せの1つだけを選択として持つ。
   クラスは，量の値が，その量と比べるリテラルと同じ型（数，真理値，または記号値とテキスト）であるか，
   値がないことを前提とする。数と比べる量にテキストを与えるなど，ほかの型の値を持つトレースでは，
   どのクラスでも真になる述語が偽または未定義になりうる。答えはそのようなトレースを扱わない。
3. 終了。インスタンスがこの観測で終わるかどうか（F.5の手順6）。`lifecycle:` のない契約で通知される
   終了と，ライフサイクルの終端状態の両方を表す。

### 時間

観測は，ステップΔの倍数の時刻に起こる。観測nの時刻はnΔである。Δは，与えられるか，または変換した
期限，時相演算子，仮定の時間の最大公約数とする（どれもなければ1秒）。与えるΔは，それらのそれぞれを
割り切らなければならない。期限dはd/Δステップに，`within`，`throughout`，`until` の区間wはw/Δ
ステップになる。

観測がΔの倍数の時刻に，0からインスタンスの終了まで並ぶトレースについて，モデルは厳密である。
F.5が比べる時間（規範の発効中の時間と期限，観測と区間の終わり）はそのとき整数個のステップであり，
ステップで比べた結果は秒で比べた結果と同じである。何も含まない観測も，ほかの観測と同じ観測である（F.5）。
モデルは，Δの2つの倍数の間の観測と，倍数を飛ばすトレースを扱わない。Δの倍数の時刻の間にある観測は，
過ぎた期限を早く検出しうる。また，その間だけ成り立つ値を見うる。そのようなトレースの性質を検査するには，
より小さいΔが要る。

上限Hは，インスタンスの長さを制限する。インスタンスは遅くとも観測Hで終わる。既定では，変換した義務と
禁止についての和 H = 2 + Σ (d + w + 2) とする。dとwは，期限と内容の区間のステップ数（なければ0）である。
この値は，各規範を順に発効させ，判定し，その修復を発効させるのに足りる観測の数である。答えは，観測が
H + 1個以下のインスタンスについてのものである。より大きいHは，より長いインスタンスを扱う。

### 状態と遷移

ある観測の後のモデルの状態は，次のものからなる。

- ステップの番号と，インスタンスが終わったかどうか。
- 変換した規範ごとに，その状態（F.5）。`discharged` は，発効していた規範と，インスタンスの終了時に
  `inactive` だった規範に分ける。`violated` は，判定 `violated` と `excused` に分ける。
- 変換した義務と禁止ごとに，その観測で発効したかどうかと，発効中の時間のステップ数（期限 + 1まで数える）。
- 内容が時相演算子である義務と禁止ごとに，判定を待つ候補。候補は経過ステップ数ごとに持ち，F.4がそれを
  決めるのに必要な情報（未定義の値を見たか。`until` では，前の部分が未定義だったかも）を伴う。また，
  真または真でないと決まった候補が，規範の判定を待っているかどうか（`suspended` の間は判定しない）。
- 真になることが事象である述語ごとに，前の観測でのその値。
- 時相演算子を含む仮定ごとにその状態と，仮定が破れたかどうか。
- 権能ごとに行使されたかどうかと，修復を持つ義務と禁止ごとに，修復が発効したかどうか。

モデルの1つの遷移は1つの観測である。F.5の手順を，その順序（「1つの観測の中での順序」）で，環境の選択に
ついて，それぞれ前の手順の残した状態に適用する。インスタンスが終わった後，状態は変わらない。

### 変換するもの

変換のバージョン0.1は，次のものを変換する。メッセージ事象（引数はリテラルまたは名前），counts-as規則の
制度的事象，量（`A.q`，`A[k].q`，`i` を束縛した `A[i].q`）とリテラルの比較（`==`，`!=`，`<`，`<=`，
`>`，`>=`，`IN`），条件として使う真理値の量，`AND`，`OR`，`NOT` からなる述語，そのような述語の上の
有界の時相演算子1つからなる内容，期限，`until:`，`if:` を持つcounts-as規則，権能とその効果，修復，
これらの形の `assume:` の項目（判定 `excused` のため）。限量子，集約，述語の中のワイルドカード参照，
算術，2つの量の比較，`request` のフィールド，`now`，`state`，ほかの演算子と組み合わせた時相演算子，
入れ子の時相演算子，改正（F.6）は変換しない。そのような部分を持つ規範は，理由とともに「変換しない」と
報告する。そのような規範に振る舞いが依存する規範も同じである。変換しない規範の修復，変換しない権能の
効果の対象，変換しないcounts-as規則の事象を `trigger:`，内容，`until:` とする規範がこれに当たる。
`assume:` の項目を変換しないとき，トレースでは違反が `excused` になりうるが，モデルはそれを区別しない。
F.10が判定しない（評価できない）規範は，トレースと同じく，モデルでも `inactive` のままである。
`guarantee:` の項目は規範の状態を変えないので，変換しない。

### 問い

問いは，モデルのラベルについてのPRISMの性質である。終了について2つの読み方を使う。「任意の終了」
（`early_end=true`）では，インスタンスはどの観測でも終わりうる。これを可能性の問いに使う。「上限まで続く
読み方」（`early_end=false`）では，インスタンスは上限まで続く。これを必然性の問いに使う。インスタンスを
早く終えると，義務は期限の前に解除される。そのため，任意の終了では，必然性の問いの答えが自明になる。

| 問い | 読み方 | 性質 | 答え |
| --- | --- | --- | --- |
| 規範nは発効しうるか | 任意の終了 | `Pmax=? [ F "a_n" ]` | 0より大きければ「はい」 |
| 違反されうるか | 任意の終了 | `Pmax=? [ F "v_n" ]` | 0より大きければ「はい」 |
| 履行されうるか | 任意の終了 | `Pmax=? [ F "f_n" ]` | 0より大きければ「はい」 |
| どのインスタンスでも違反されるか | 上限まで続く | `Pmin=? [ F "v_n" ]` | 1であれば「はい」 |
| 発効するたびに守れるか | 上限まで続く | `Pmax=? [ F (!"end" & !(P<=0 [ X "j_n" ]) & P<=0 [ X ("j_n" & !"v_n" & !(P>=1 [ F "v_n" ])) ]) ]` | 0より大きければ「いいえ」 |
| nとmは衝突するか | 上限まで続く | `Pmax=? [ F (!"v_n" & !"v_m" & !(P<1 [ G !"v_n" ]) & !(P<1 [ G !"v_m" ]) & P>=1 [ F ("v_n" \| "v_m") ]) ]` | 0より大きければ「はい」 |
| 権能pは行使されうるか | 任意の終了 | `Pmax=? [ F "x_p" ]` | 0より大きければ「はい」 |
| nの修復は発効しうるか | 任意の終了 | `Pmax=? [ F "r_n" ]` | 0より大きければ「はい」 |

`"a_n"` はnが発効した後で成り立つ。`"v_n"` はnが違反されているとき（どちらの判定でも），`"f_n"` は
履行されているときに成り立つ。`"j_n"` は，nが発効した観測の後の状態で成り立つ（その観測の後のnの状態は
問わない）。`"x_p"` はpが行使された後で，`"r_n"` はnの修復が発効した後で，`"end"` はインスタンスが
終わった後で成り立つ。MDPでは，`P>=1 [ F φ ]` は選択のどの解決もφに到達することを，
`!(P<1 [ G !φ ])` は選択のある解決がφを避け続けることを表す。`P<=0 [ X φ ]` は次の観測のどの選択も
φに至らないことを，`!(P<=0 [ X φ ])` はある選択がφに至ることを表す。

ある観測の前の状態で，環境のある選択が規範を発効させ，規範を発効させる選択がどれも，その後のどの続きも
規範に違反する状態に至るとき，その発効は守れない。この問いは，発効させる観測の前の状態について問う。
その観測が環境の選択を含むからである。メッセージを発動条件とする期限0秒の義務は，同じ観測で内容が
起こりうるので守れる。期限0秒の修復は，次の観測で初めて判定される（F.5の手順5）ので守れない。
この問いを発効について問うのは，期限を持つ義務はどれも，担い手が何もしなければ，その後に何が起きても
違反される状態に至るからである。

2つの義務または禁止nとmは，次の状態に到達できるとき，衝突する。どちらも違反されておらず，それぞれ単独では
まだ守れ，どの続きもどちらかに違反する状態である。たとえば，ある義務の内容をある禁止が禁じていて，両方が
発効しているとき，その義務と禁止は衝突する。衝突は修復を通じても生じうる。nを守ると第3の規範に違反し，
その修復がmである場合である。

### 証拠

何かが可能であるという答えには，必ず証拠が付く。証拠は，リファレンス実装の形式のトレースであり，
Δの倍数ごとに1つの観測を持ち，F.5で評価すると主張どおりの判定になる。証拠は，`Pmax` の性質について
モデル検査器が与える戦略の経路であり，目標に達した後は，インスタンスが終わるまでメッセージも値もない
観測が続く。守れない発効の証拠は，発効させる観測の前の状態に達する。処理系は，その観測での環境の
選択のそれぞれについて，規範を発効させるかどうかをF.5で評価し，モデルと一致することを確かめる。
また，規範を発効させる選択のそれぞれについて，その後に上限までメッセージも値もない観測を続けると規範に
違反することを確かめる。発効させる選択のほかの続きもすべて規範に違反することは，モデル検査器の答えに
よる。証拠のトレースは，発効させる選択の1つを含む。衝突には，衝突の状態から始まる2つの証拠がある。
一方はnを守ってmに違反し，他方はmを守ってnに違反する。どのインスタンスでも違反される規範については，
メッセージも値もないインスタンスを例として示す。処理系は，すべての証拠をF.5で評価し，主張どおりの判定に
ならない証拠を自らの誤りとして報告することが望ましい。

### 制限

バージョン0.1は，1000を超える観測の上限，16を超えるメッセージ事象，1つの観測について8192を超える
環境の選択，および述語の1つのまとまりについて20000を超えるクラスの組合せを持つ量を拒否する。
モデル検査器は到達可能な状態を明示的に調べる。遷移の数は，到達可能な状態の数と選択の数の積であり，
メッセージ事象と値のクラスとともに増える。検査の時間は，モデルのコマンドの数（選択と終了の組ごとに2つ）と
到達可能な状態の数とともに増える。メッセージ事象が12個（選択が4096，コマンドが16384）のインスタンスでは，
10分を超えた。処理系は，モデル検査器の時間を制限し，制限を超えたときはそれを報告することが望ましい。

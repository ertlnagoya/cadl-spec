# 付録D. コード生成ターゲット一覧

本付録は CADL v0.3 が規定するコード生成ターゲットを列挙し，
リファレンス実装のディレクトリ構成との対応を示す。
[付録A §A.9](./appendix-a-syntax.md#a9-codegen-block) が `codegen:` の項目の EBNF を定義する。
本付録では，各ターゲット名を**カテゴリ**・**生成物**・
**リファレンス実装（[`cadl`](https://github.com/ertlnagoya/cadl) 0.3）内の
モジュール**と対応づける。

## D.1 ターゲット一覧

| ターゲット名 | カテゴリ | 生成物 | リファレンス実装モジュール | コマンド |
|-------------|---------|--------|-------------------|---------|
| `python` | ランタイムコード | Python パッケージ（アクター，契約モニター，プロトコル，モードコントローラ，メトリクス，ランタイム。`norms: 0.1` を宣言したファイルでは，[付録F](./appendix-f-norms.md)の規範のモニターも含む） | `cadl.codegen` | `cadl codegen -t python` |
| `solidity` | 制度契約 | Solidity [[Solidity Documentation]](./appendix-b-references.md) スマートコントラクト（契約ごとに 1 つ）。`norms: 0.1` を宣言したファイルでは，契約ごとの規範のモニターも含む（D.5） | `cadl.codegen.solidity` | `cadl codegen -t solidity` |

`codegen:` の項目では，名前 `python` はランタイムコードのターゲットを指す。
同名のシミュレータ設定は `cadl sim-gen` で生成する。したがって，v0.3 では
Python のシミュレータ設定を `codegen:` の項目から要求することはできず，
`cadl sim-gen -t python` を用いる。リファレンス実装（`cadl` 0.3）では，
最右列に示すとおりコマンドラインでターゲットを選択する。ファイル中の
`codegen:` の項目は構文解析されるだけで，この項目に基づく生成はまだ行わない。`cadl` 0.3.9 からは，
実装が出力できないターゲットを指定した項目に警告が出る（D.4）。

規範拡張（[付録F](./appendix-f-norms.md)）を宣言したファイルに対しては，`python` ターゲットは
モジュール `norms_monitor.py` も出力する（`cadl` 0.3.22 から）。このモジュールは，
各契約の `norms:` と `counts_as:` のブロック，および `assume:` と `guarantee:` の項目を，
時相演算子を含む項目も含めて，システムの動作中に 1 つの契約インスタンスについて監視する。
観測を 1 つずつ受け取り，状態または判定（`pending`，`fulfilled`，`violated`，`excused`）が
変わった規範インスタンスと項目を返す。パッケージの他のモジュールと違い，`cadl` をインポートしない。
宣言されたアクターと契約をデータ（1 つの JSON テキスト）として持ち，`cadl norms-eval` の
評価コードを含み，Python の標準ライブラリだけを用いる。生成器は，モジュールを書き出す前に検査し，
検査に失敗した場合は何も書き出さない。
詳細は [F.10](./appendix-f-norms.md#f10-reference-implementation-status) に示す。
`solidity` と `opa` のターゲットは，時相演算子を含む項目を契約のポリシーから外してコメントを残し，
それらを規範とともに契約ごとの別のファイルで監視する（`cadl` 0.3.25 から。D.5）。
`unity-csharp` のターゲットは規範を監視しない。

## D.2 二層ジェネレータ構成

リファレンス実装は，出力が**契約を強制または実行するコード**であるか，
**シミュレータの設定**であるかに応じて codegen を二層に分割している：

```
src/cadl/
├── codegen/            ← コード層（cadl codegen）
│   ├── *_gen.py        ← Python ランタイムパッケージ
│   ├── solidity/       ← 契約のスマートコントラクト強制
│   ├── opa/            ← 契約のポリシー強制（Rego）
│   └── unity_csharp/   ← Unity C# のライフサイクル／モニター実行系
└── sim/                ← シミュレータ層（cadl sim-gen）
    ├── ir.py           ← 三層シミュレータ IR
    ├── gen_unity.py
    ├── gen_go.py
    └── gen_python.py
```

単一の CADL ソースファイルは，両層のターゲットを同じ `codegen:`
ブロック内で宣言してよい。処理系は，各ターゲットを，対応する層で
独立に処理することが望ましい。

## D.3 選択指針

- **`unity`**: 多エージェントシミュレーションを視覚的に観察する場合。
  契約のライフサイクルとモニター（[付録E](./appendix-e-sos-dsl.md)）をそのシミュレーションの
  中で実行する場合は **`unity-csharp`**。
- **`python`**: アクター，契約モニター，プロトコルの実行可能な
  ランタイムの基本のコードが必要な場合，または[付録F](./appendix-f-norms.md)の規範を
  システムの動作中に監視する場合。**`ros2`** は実ロボットの駆動のために
  予約されており，`cadl` 0.3 では未実装である。
- **`solidity`**: Institution 層契約をオンチェーン（ブロックチェーン）
  で強制する場合。
- **`opa`**: 契約を API／サービス境界のポリシー（policy-as-code）
  として強制する場合。

同一ファイルで複数のターゲットを指定してよいが，
生成される成果物は互いに独立である。たとえば同一ソースから生成された
Unity のシミュレータ設定と Solidity 契約のランタイム相互運用性は，CADL ツール
チェーンでは保証しない。

## D.4 準拠性

処理系は，各層から少なくとも 1 ターゲット
（たとえば `unity` と，`solidity` または `opa`）を
サポートするとき，**codegen コア準拠**である。

要求されたターゲットを生成できない場合，処理系は明確な診断
（例: 「codegen ターゲット `ros2` は本処理系で未対応」）
を出力しなければならない。診断を出さずに読み飛ばしてはならない。

## D.5 `opa` と `solidity` のターゲットの規範モニター {/* #d5-norms-monitors-of-the-opa-and-solidity-targets */}

`norms: 0.1` を宣言したファイルに対して，リファレンス実装の `opa` と `solidity` のターゲットは，
`cadl` 0.3.25 から，契約のポリシーとは別に，契約ごとに規範のモニターを 1 つ出力する。
`opa` は `norms_monitor_<contract>.rego` に Rego のパッケージ `cadl.norms_monitor.<contract>` を，
`solidity` は `<Contract>NormsMonitor.sol` にコントラクト `<Contract>NormsMonitor` を出力する。
モニターは，1 つの契約インスタンスについて `norms:` と `counts_as:` のブロック，および
`assume:` と `guarantee:` の項目を評価する。契約のポリシーが外す，時相演算子を含む項目も評価する。
1 つの観測は，`cadl norms-eval` と同じく F.5 の順序で処理する。

**扱う構文。** 両方のモニターは，メッセージ事象（F.3 のアクターの指定と引数を含む），制度的事象，
F.5 の3値論理に従う述語（比較，`IN`，`AND`，`OR`，`NOT`，算術，アクターを付けた量と付けない量，
`request` のフィールド，`now`，`state`），トリガ，`until:`，期限，`reparation:` の規範，権能の効果，
`if:` を持つ counts-as 規則，入れ子を含む F.4 の時相演算子を評価する。述語の限量子，集約，
ワイルドカード参照と範囲参照，式である添字（`A[i+1]`），改正（F.6）は評価しない。規範，counts-as 規則，
`assume:` の項目でこれらのいずれかを使う契約にはモニターを生成せず，処理系はモニターを生成できない原因の構文を報告する。
そのような `guarantee:` の項目は，ほかの判定がそれに依存しないので，警告を出してモニターから外す。
どちらも正確に計算する（F.5）。Rego のモニターは十進数で計算するので，結果が十進数になるとは限らない `/` を拒否する。
Solidity のモニターは小数点以下 6 桁の固定小数点数を用いるので，`*`，`/`，小数点以下が 6 桁を超える
リテラルも拒否する。また，時相演算子の区間を観測が届くたびに 1 回だけ走査するので，時相演算子の中の
時相演算子と，時相演算子を 3 つ以上含む規範の内容も拒否する（下記）。
デプロイ時のコード（creation code）が EIP-3860 の上限 49152 バイトを超える契約と，実行時コードが
EIP-170 の上限 24576 バイトを超える契約も拒否する（`cadl codegen` はどちらの大きさも大きめに見積もる）。`guarantee:` の項目でこれらを使う
場合は，上と同じくその項目だけを外す。`amend` を持つ観測は実行時に拒否する。

**Rego のモニター。** Rego のモニターはステップ関数である。OPA は状態を持たないので，ポリシーは直前の状態と
1 つの観測からモニターの次の状態を計算する。状態は呼び出しの間ホストが保存する。規則 `result` は
`input` として次を受け取る。

| キー | 意味 |
|-----|------|
| `state` | 直前のステップが返した状態。最初の観測の前は null または省略 |
| `observation` | `cadl norms-eval` のトレース形式による 1 つの観測（`t`，`values`，`messages`，`state`，`end`。`bindings` と `request` は最初の観測だけ） |
| `finish` | 観測の代わりに `true` を与えると，インスタンスは最後の観測で終わる（F.5 の手順 6） |
| `bindings`，`request` | 最初の観測が持たない場合の，インスタンスの束縛と request |
| `quantities` | アクターを付けずに書かれた量の名前。既知の名前（F.5）に加える |

`result` は，`state`（次の状態），`changes`（状態または判定が変わった規範インスタンスとその前の値，
および決まった項目），`violations`，`institutional_events`，`powers_exercised`，`unauthorised`，
`verdicts`（各規範の状態と判定，各仮定の状態，各保証の判定，`ok`），`ended`，`next_deadline`
（発効中の義務と禁止の最も早い期限）を持つ。形式の誤った観測に対しては，`result` は `error` と
変わらない `state` を持つ。状態は次のキーを持つ JSON オブジェクトである。

| キー | 内容 |
|-----|------|
| `format` | `"cadl-norms-monitor-state/1"` |
| `contract` | 契約の id。ほかの契約の状態は拒否する |
| `n` | これまでに処理したインスタンスの観測の数 |
| `t` | 最後の観測の時刻。終了後の観測の時刻も含む |
| `ended`，`end_index` | インスタンスが終わったかどうかと，終わった観測 |
| `ignored` | 終了後の観測の数（それらは効果を持たない） |
| `bindings`，`request` | 最初の観測とともに与えられたもの |
| `known` | 既知の量の名前（F.5）を整列したもの |
| `values` | これまでに観測した各量の現在の値 |
| `lc` | 最後の観測の後のライフサイクルの状態（`lifecycle:` がなければ null） |
| `buffer` | まだ読む観測。`i`（インスタンスの中の番号），`t`，`values`（その時点の値），`st`（その観測の前のライフサイクルの状態）を持つ。最後の観測，時相的な内容がまだ決まらない規範の最も古い候補からの観測，時相的な項目がまだ決まらない間は最初からのすべての観測を保持し，それより古い観測は捨てる |
| `norms` | 規範ごとに 1 つの記録を契約の順に持つ。`id`，`state`，`verdict`，`at` と `act`（最初に発効した時刻と番号），`since` と `before`（期限のための，現在発効している区間の始まりと，それより前に発効していた時間），`from`（`reparation:` の規範を初めて判定する観測），`cands`（時相的な内容がまだ決まらない観測の番号） |
| `items` | `assume` と `guarantee`。項目ごとに `value`（null，`true`，`false`，`"undefined"`），`seen`（状態述語がある観測で成り立ったか），`verdict`，`time` |
| `failed_at` | 最初の仮定が成り立たなくなった時刻，または null |

**Solidity のモニター。** Solidity のモニターは，1 つの契約インスタンスの状態を保持するコントラクト
である。コンストラクタは報告者のアドレスを受け取る（ゼロアドレスならデプロイした者。`reporter()`）。
`begin`，`observe`，`addQuantities`，`finish` を呼べるのは報告者だけである。報告者は変更できない。
報告者の鍵を失うと，モニターはその時点の状態のまま，それ以降の観測を記録できない。
`begin(bindings, request, quantities)` は最初の観測の前に呼べる。`observe(t, values, messages,
hasState, state, end)` は 1 つの観測を記録し，`addQuantities(names)` はアクターを付けずに書かれた
量の名前を加え，`finish()` は最後の観測でインスタンスを終える。`verdicts()` は規範の状態と判定を
`normIds()` の順に，および項目の判定を返す。そのほかの情報は `contractId()`，`ok()`，
`nextDeadline()`，`observations()`，`lastT()`（最後の観測の時刻。終了後の観測を含む），`ended()`，
`ignored()`（終了後の観測の数）で取得でき，各呼び出しによる変化はイベント `NormChanged`，
`ItemChanged`，`Violation`，`InstitutionalEvent`，`PowerExercised`，`Unauthorised` で通知される。値は，名前，種類（null，真偽値，数，
文字列），数，文字列の組である。時刻を含む数は 10<sup>6</sup> を掛けた固定小数点数である。
トレースを再生して検査できるように，時刻は `observe` の引数とする。運用では `block.timestamp` に
10<sup>6</sup> を掛けた値を渡してもよい（MAY）。形式の誤った観測は revert し，状態は元のままである。
コントラクトは CADL の契約のモデルをデータとして保存し（コンストラクタが格納する），それを解釈する。
モデルと状態はストレージの 1 つの構造体にまとめ，6 つのライブラリがそれを読み書きする。
ライブラリには，述語の評価，状態を持たない関数，時相演算子を 1 つ含む内容の判定，2 つ含む内容の判定，
項目，事象・メッセージ・counts-as 規則・権能の処理を置き，それぞれの実行時コードを EIP-170 の
大きさの上限に収める。`cadl` 0.3.28 から，コントラクトの実行時コードの見積もりは 16 840 バイトであり，
上限まで 7 × 10<sup>3</sup> バイト以上の余裕がある（0.3.27 では 24 410 バイト）。
1 つの観測にかかるガスは，それより前の観測の数とともには増えない。
時相演算子の区間は 1 回だけ走査し（各観測の値を，区間がまだ終わっていない走査に加える），値は
二分探索で探し，後のステップが読まない値は，新しい値 1 つにつき数個ずつ削除する。

*時相演算子が 1 つの内容。* 時相演算子を 1 つ含む規範の内容では，
時相演算子以外の部分の値は候補を作る観測で決まる（名前は固定される。下の違いを参照）。そのため内容は
演算子の値の関数であり，モニターはその観測で，演算子を未決，真，偽としたときの内容の値を読む。
内容は，演算子の値によらず真（候補はすぐに成り立つ），決して真にならない（候補を作らない），
演算子が真のときに限り真，演算子が偽のときに限り真，演算子が真または偽のときに真，
決して真にならないが演算子が決まるまで未決（候補は F.5 のとおり規範を未決のままにする）のいずれかになる。
演算子が未定義のときに内容が真になるのは，演算子が未決のときにも内容が真である場合に限るので，
場合はこれで尽きる。被演算子が未定義である比較，算術，`IN` の左辺は未定義であり，
`AND`，`OR`，`NOT` が未定義の被演算子に対して真または偽を返すのは，未決の被演算子に対しても
それを返す場合に限るからである。これにより，`NOT` の下の演算子，比較の中の演算子
（`within(3s, p) == flag`，`until(p, q, 3s) <= A.y`），`IN` の中の演算子を扱う。
規範は候補の列を 3 つ持ち，それぞれ古い順に並べる。演算子が真のときに成り立つ候補，偽のときに成り立つ候補，
演算子が決まるのを待つだけの候補である。真のときにも偽のときにも成り立つ候補は最初の 2 つの列に入る。
2 つ目の列は，否定した被演算子に対する双対の演算子を読む。`NOT within(d, p)` は `throughout(d, NOT p)`，
`NOT throughout(d, p)` は `within(d, NOT p)`，`NOT until(p, q, d)` は下に述べる release である。
各列は，前回の判定以後の観測での被演算子の値から，次のものを保持する。`within` では被演算子が最初に真に
なった時刻，`throughout` では最初に偽になった時刻と最初に未定義になった時刻，`until` では `q` が最初に
真になった観測と `p` が最初に真でなくなった観測，release ではこの 2 つに加えて `q` が最初に偽でなくなった
観測と `p` が最初に偽になった観測である。これらと，区間で候補が成り立たなくなる値を見た最後の候補から，
時刻の比較ですべての候補を判定する（`throughout` では，区間が最初の偽または未定義の値より前に終わった
最も新しい候補が成り立つ）。候補ごとに区間を走査せず，候補の列を数回二分探索するだけであり，規範が
停止している間も同じである。判定した候補は観測ごとに数個ずつ削除する。

*release。* 述語の観測での値を F.5 の 3 つの値（真，偽，未定義）と Kleene の論理結合子で表し，
候補 k の区間の観測の集合を W とする。F.4 により，k での `until(p, q, d)` の値は

∨<sub>j ∈ W</sub> ( q<sub>j</sub> ∧ ∧<sub>k ≤ i &lt; j</sub> p<sub>i</sub> )

であり，ある項が真になる最初の観測，`p` が偽になる最初の観測（それより後の項はすべて偽になる），
または区間が終わったときに決まり，それまでは未決である。Kleene の否定は対合であり，de Morgan の法則を
満たすので，

NOT `until(p, q, d)` = ∧<sub>j ∈ W</sub> ( ¬q<sub>j</sub> ∨ ∨<sub>k ≤ i &lt; j</sub> ¬p<sub>i</sub> )

が成り立つ。これは ¬p と ¬q の release であり，区間の観測のうち ¬p が成り立つ最初の観測までと，その観測で，
¬q が成り立つことを表す。`NOT` は未決の値を未決のままにし，決まった値をその否定にするので，release は
`until` と同じ観測で決まる。release が真になるのは，すべての項が偽のときに限る。W の中で `p` が偽になる
最初の観測を b とし，それがなければ W の最後の観測を b とする。j が b より後の項は p<sub>b</sub> により偽である。
j が b 以前の項には偽の p<sub>i</sub> がないので，その項が偽になるのは q<sub>j</sub> が偽のときに限る。
したがって release が真になるのは，W の b までのすべての観測で `q` が偽のときに限り，それ以外では
偽または未定義である。未定義の値があっても同じことが成り立つ。q<sub>j</sub> が未定義で偽の
p<sub>i</sub> がない項は偽にならないからである。そこで release の列は，区間の中で `p` が偽になり，
その観測とそれより前で `q` が偽であった候補と，区間の中で `q` が偽のまま区間が終わった候補を成り立たせる。
`p` が偽になるとすべての候補を除く（どの区間もそこで決まる）。`until` が真になった候補
（候補以後 `p` が真のままで `q` が真になったもの）と，区間が終わった候補も除く。`q` が偽でない値を見た候補は，
これらのいずれかで決まるまで，未決のまま残す。

*時相演算子が 2 つの内容。* 時相演算子を 2 つ含む内容では，モニターは候補を作る観測で内容を 1 回読み，
2 つの演算子の値（未決，真，偽，未定義）の 16 通りの組それぞれに対する内容の値を求める。
2 つの演算子の比較（`within(…) == throughout(…)`）もこれで扱う。1 つの観測は，演算子を候補の範囲ごとに
決める。区間が終わった候補は偽（`throughout` では真）になり，区間の中で被演算子が未定義になっていれば
未定義になる。`within` の被演算子が真になること，`throughout` の被演算子が偽になること，`until` の `p` が
偽になることは，終わっていないすべての区間を決める。`until` の `q` が真になることは，候補以後 `p` が真のままの
候補を決める。これらの範囲は候補の二分探索で求める。候補はストレージのセグメント木の葉である。
節点は，候補でまだ決まっていない演算子の集合と，演算子がこれから取りうる値の組との対ごとに，その下の
候補がその場合に成り立つかどうかと，未決のままかどうかを記録する（この対は 49 通りで，1 語に収まる）。
演算子をある範囲で決めると，これらの対はシフトとマスクで写り，遅延伝播で子に伝わる。そのため 1 つの観測は
少数の範囲を，候補の数の対数に比例する手数で変え，根から，成り立つ候補と未決の候補があるかどうかがわかる。
時相演算子を 3 つ以上含む内容は拒否する。その場合，候補は異なる観測で決まる複数の演算子に依存する。
`AND` で結んだ m 個の `within` では，成り立つ候補を探すことは，ある演算子が決めた候補について残りの
m − 1 個の演算子を問う検索になり，節点が記録する対は 7<sup>m</sup> 通りに増える（演算子が 3 つでは 343 通り）。
そのため，モニターが観測 1 つのコストに上限を保てるのは演算子が 2 つまでである。

*ガス。* テストでは，F.8 の例の観測 1 つにかかるガスは，1 秒に 1 つの観測を 320 個与えたとき，
仮定の 300 秒の区間が終わる前もその後も約 6.4 × 10<sup>5</sup>（最大は最初の観測の 1.2 × 10<sup>6</sup>）である。
1 秒に 1 つの観測を，どの候補も未決のままである 1000 秒の区間に与えたとき，320 個目と 1000 個目の観測に
かかるガスは，内容が `throughout(1000s, …)` では 4.4 × 10<sup>5</sup> と 4.5 × 10<sup>5</sup>，
`NOT until(…, 1000s)` では 5.2 × 10<sup>5</sup>，`throughout(1000s, …) == true` では 5.1 × 10<sup>5</sup>，
`within(1000s, …) OR throughout(1000s, …)` では 5.9 × 10<sup>5</sup>（最大 8.0 × 10<sup>5</sup>）である。
`cadl` 0.3.25 は観測のたびにすべての候補を読み，320 個目で 1.3 × 10<sup>7</sup> を使っていた。観測がブロックのガス上限を超えるモニターは，
その観測を記録できず，元に戻らない。そのため，観測 1 つのガスに上限があることが必要である。生成した
ファイルは，その先頭のコメントのとおり，solc 0.8.24 から 0.8.37（確かめた範囲。pragma は
`>=0.8.24 <=0.8.37`）と `--optimize --optimize-runs 1` でコンパイルする。オプティマイザを使わないと実行時
コードが EIP-170 の上限を超える。デプロイ時のコードと実行時コードの見積もりは，オプティマイザの runs が
1 でも 200 でも成り立つ。

**`cadl norms-eval` との違い。** モニターは，Python のモニターと同じく，それまでに受け取った観測で
各観測を判定する。過ぎた期限は次の観測で検出し，インスタンスは `finish` かインスタンスを終える観測で
終わり，アクターを付けずに書かれた量の名前は，`quantities`（または `addQuantities`）で与えた名前と
それまでに観測した名前である。`cadl norms-eval`（本付録はこれを変えない）とは次の点が違う。

- 数と時刻は，`cadl norms-eval` と同じく（F.5），どちらのモニターでも正確に扱う。Rego のモニターは
  数を書かれたとおりの十進数として読み，状態では数と時刻を `{"$q": [n, k]}`，つまり
  n / 10<sup>k</sup> として持つ。`/`（商は十進数になるとは限らない）と，正確な値が小数点以下 4095 桁を
  超えうる積（どの数も小数点以下 400 桁まで。F.5）は拒否する。どちらのモニターも，`cadl norms-eval` と
  同じく，観測，request，束縛に含まれる F.5 の範囲を超える数を拒否する。
  Solidity のモニターは小数点以下 6 桁を持ち，`*`，`/`，それより多い桁のリテラルを拒否する。
  ホストは小数点以下 6 桁までの数を渡す。これらの制限を満たす入力では，判定は `cadl norms-eval`
  と一致する。Rego のモニターの結果では，参照用に時刻を JSON の数で書く。
- モニターは，`cadl norms-eval` が受け付ける次の入力を拒否する。小数部も指数も持たない整数（`1.0` と
  `1e2` は拒否する）でも文字列でもない束縛，リストまたはオブジェクトである `values` の値
  （Rego では `request` の中のリストも），Rego では空白だけが違う `values` の 2 つのキー，`amend` を
  持つ観測である。Solidity のモニターは，request を葉の形（`"a.b"`）で，値の名前を ASCII で，
  メッセージのアクターと名前を ASCII の英字，数字，`_` で受け取る。束縛は整数か文字列として受け取る
  ので，小数部や指数を付けて書かれた束縛はホストが拒否する。
- Solidity では，時相演算子の中で読むアクターを付けない名前（`throughout(10s, A.s == flag)` の
  `flag` のように，記号値にも量にもなりうる名前）が量であるときは，`begin` か最初の観測より前の `addQuantities` で与えるか，
  最初の観測で観測しなければならない（束縛である名前はこの制限を受けない）。走査は読んだ値を保持するので，そのような名前を後から既知にする `observe`
  と `addQuantities` は拒否する（revert する）。`cadl norms-eval` と Rego のモニターは，新しい名前で
  それより前の観測を読み直す。
- Rego のモニターは与えられた状態を信頼する。状態の形式と契約は検査するが，内容は検査しない。
  ホストは保存した状態を改変されないように保ち，それぞれを次のステップにだけ渡す。
- `cadl norms-eval` の理由，警告，タイムラインは返さない。

**ファイルの文字列。** どちらのモニターでも，`.cadl` ファイルのテキストはコードにならない。Rego は
契約を 1 つの JSON テキストとして持ち，ほかのリテラルを JSON の文字列として書く。Solidity は
すべてのテキストを 16 進リテラルとして書く。`cadl codegen` の入力検査はその前に適用する。

**検証。** リファレンス実装は，観測ごとに，両方のモニターを `cadl norms-eval` と比べる。比べるのは
規範の状態と判定，項目の判定，変化，違反（重大度と制裁を含む），制度的事象，行使された権能，
権限のない行為，次の期限である。対象は，サンプルのトレース，テストのトレース，ランダムなトレース，
長いトレースである。Rego は `opa eval` で，Solidity は EVM で実行する。

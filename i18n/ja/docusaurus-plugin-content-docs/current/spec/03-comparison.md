# 3. 既存言語との比較

## 3.1 関連する言語・フレームワークの概観

**MOISE+:**
組織的マルチエージェントシステムのための構造的・機能的・義務論的記述モデル [[Hübner+, 2007]](./appendix-b-references.md)。組織の役割・グループ・ミッションを形式的に記述できるが，契約やアルゴリズムの記述は範囲外である。

**OperA:**
エージェントベースシステムのための組織モデル [[Dignum, 2004]](./appendix-b-references.md)。社会構造・相互作用構造・規範構造の3側面から組織を記述する。プロトコル記述に一定の対応があるが，SoSの制度層は扱わない。

**Symboleo:**
法的契約の形式仕様言語 [[Sharifi+, 2020]](./appendix-b-references.md)。契約の当事者・義務・権利・違反条件を厳密に記述できるが，組織構造やプロトコル，技術アーキテクチャとの統合は範囲外である。

**AADL契約拡張:** Architecture Analysis and Design Language [[Feiler & Gluch, 2012]](./appendix-b-references.md) に契約概念を導入した拡張。assume-guarantee契約をアーキテクチャ記述に統合するが，SoSの制度層は設計対象としていない。

**SysMLv2 / HAMR:**
システムモデリング言語の次世代版 [[OMG, 2025]](./appendix-b-references.md) と，AADL向けに開発されSysMLv2にも対応するモデル駆動のコード生成ツールチェーン [[Hatcliff+, 2021]](./appendix-b-references.md)。アーキテクチャ記述に優れるが，制度設計変数の記述は範囲外である。

**スマートコントラクト（Solidity等）:**
分散的な自己統治を実現する実装基盤。代表的な言語にSolidity [[Solidity Documentation]](./appendix-b-references.md) があり，有限状態機械に基づく安全なコントラクトの設計手法も提案されている [[Mavridou & Laszka, 2018]](./appendix-b-references.md)。C-SoSのガバナンス実装に有望だが，制度の設計段階での検証や3層統合記述は提供しない。

**IADフレームワーク:**
Ostromの制度分析・発展フレームワーク [[Ostrom, 2005]](./appendix-b-references.md)。共有資源のガバナンスを概念的に分析するが，形式的な記述言語ではなく，パラメータ化は限定的である。

最後の2行は，制度の改正と，改正の判断の記録についてのものである（[付録K](./appendix-k-amendment.md)，[付録L](./appendix-l-decisions.md)）。MOISE+では，再組織化は組織に対する変更の計画である。Designerの役割が計画を提案し，Selectorが一つを選び，OrgManagerがそれを実行し，Historianが各変更を記録する [[Hübner+, SBIA 2004]](./appendix-b-references.md)。JaCaMoでは，再組織化は対象のグループとスキームを止め，仕様を変え，再び開始する。エージェントへの各指示は，すぐに実行するか，エージェントが前に約束した目標を終えてから実行するかを示す [[Sorici+, ITMAS 2012]](./appendix-b-references.md)。仕様はその場で書き換えられ，バージョンは定義されず，前の仕様は残らない。OperAは，役割を取り除くなどの変更の後のモデルの検証を今後の課題とし，動いている社会が変更後のモデルにどう移るかを定義していない [[Dignum, 2004]](./appendix-b-references.md)。SysML v2は，モデルの履歴を変更できないコミットとして，ブランチとタグとともに保存する [[OMG, Systems Modeling API 2025]](./appendix-b-references.md)。これは設計のリポジトリのバージョンであり，動いているインスタンスのバージョンではない。コミットには誰が決めたかを表す属性がなく，理由は自由記述でしか書けない。CompoundのようなDAOのガバナーは，採択した提案の実行をタイムロックで遅らせ，提案，投票，委任された票を記録する [[Compound Governance]](./appendix-b-references.md)。提案の実行時に，提案に必要な票数，定足数，委任された票を検査するが，その変更がモデルの宣言で改正できるものかどうかは検査せず，バージョンも経過措置も持たない。CADLが最後の行で○なのは，付録Lが記録を事後に検査し，実行時には何も強制しないからである。

## 3.3 CADLの独自性

本仕様書で調査した範囲では，全ての要件を単独で満たす既存アプローチは見当たらない。CADLの特徴は以下の4点である。

**(1) 3層統合記述:**
制度（権限・インセンティブ・情報共有），プロトコル（協調手順・タイミング制約），アルゴリズム（計算手法の抽象参照）の3層を単一言語内で一貫して記述する。本仕様書で調査した範囲では，この3層を単一言語で扱う既存のDSLは見当たらない。

**(2) 制度のパラメトリック設計:**
意思決定の集中度β，情報共有度α，インセンティブ強度λ等の制度設計変数を数値パラメータとして定義し，モードマップの構築を直接支援する。

**(3) 記述→検証→配備→監視の一貫サイクル:**
設計段階の形式検証（無矛盾性・安全性），配備時のコード生成，運用時のランタイム監視を一貫した言語基盤の上で扱うことを目指す。

**(4) 制度についての判断を，その制度と照合する:**
改正の判断を，判断者が人・LLM・ツールのいずれでも同じ証拠とともに記録し，その記録を，モデル自身が宣言する改正可能なパラメータと決定権者に照らして検査する（[付録K](./appendix-k-amendment.md)，[付録L](./appendix-l-decisions.md)）。検査が示すのは誰がどの権限の内で判断したかであり，判断が正しかったかどうかではない。

## 3.4 判断と委任の記録

3.2節の言語は制度を記述する。それを改正する判断の記録（[付録L](./appendix-l-decisions.md)）は，言語設計の外の研究に近く，その部品にはいずれも先例がある。判断の問い・選択肢・理由・前提を記録することは，IBIS [[Kunz & Rittel, 1970]](./appendix-b-references.md) 以来の設計根拠の記録と，書き換えずに新しい記録で置き換えるアーキテクチャ決定記録 [[Nygard, 2011]](./appendix-b-references.md) の実践である。W3C PROV-DMは，人とソフトウェアを問わずあらゆる種類のエージェントについて委任（`actedOnBehalfOf`）を定義している [[W3C PROV-DM, 2013]](./appendix-b-references.md)。OAuthのトークン交換は誰が誰のために行為するかを運び [[RFC 8693]](./appendix-b-references.md)，LLMエージェントについての近年の研究は委任に範囲・期限・撤回を与える [[Tomašev+, arXiv 2026]](./appendix-b-references.md)。DAOのガバナーは提案，投票，委任された票を記録し，可決したものを実行する [[Compound Governance]](./appendix-b-references.md)。規制影響評価は，規則を採る前に，それをいつどのように評価するかを決めておく [[EC, Better Regulation 2021]](./appendix-b-references.md)。アシュアランスケースはモデルから生成され，運用中に再評価される [[Wei+, JSS 2024]](./appendix-b-references.md)。規範的なマルチエージェントシステムでは，制度の規則はそれを変える制度化された権能を持つ者が変え [[Jones & Sergot, 1996]](./appendix-b-references.md)，[[Pitt+, TAAS 2012]](./appendix-b-references.md)，実行時に追加・削除される規範を監視器が追うことができる [[Gómez-Sebastià, 2016]](./appendix-b-references.md)。LLMエージェントについての近年の研究にも，同様の問題を扱うものがある。Moghaddamの設計では，LLMが論証の一部を下書きし，その証拠の決定的な検査に通った下書きだけが判断の記録に入る。モデルが書いたものの来歴はW3C PROVで残し，論証はGSNに似た形で表示できる。人は下書きを見直し，覆すことができる [[Moghaddam, arXiv 2026]](./appendix-b-references.md)。AgentCityでは，エージェントが運用の契約を書き，基礎と手続きの契約は人が書いてエージェントは変更できず，すべてのエージェントに責任を負う人が割り当てられる [[Ruan & Zhang, arXiv 2026]](./appendix-b-references.md)。SentinelAgentは，LLMエージェントの連鎖に沿って委任される権限を狭め，期限を付け，撤回できるようにする [[Patil, arXiv 2026]](./appendix-b-references.md)。MishraとSharadは，各行為をそれが行われた委任とともに記録し，ある委任のもとで何が行われたかを後から調べられるようにする [[Mishra & Sharad, arXiv 2026]](./appendix-b-references.md)。これらは，行為が効力を持つ前に権限を検査するか，委任のもとで行われた行為を記録する。AgentCityでは，誰がどの契約を変えてよいかの規則を変更の前に強制するよう設計されており，判断の記録に照らして事後に検査するものではない。

付録Lは，これらの部品を制度のモデルの改正のためにまとめたものである。本仕様書で調査した範囲では，次のすべてを備える記録の形式は見当たらない。何をどの範囲と刻みで，誰がどの手続きで改正してよいかというモデル自身の宣言（付録K，K.3）に照らして事後に検査されること，人・LLM・ツールに同じ証拠を求めること，他の当事者に代わってなされた判断が委任された層と手続きの外にあれば指摘すること，測り直しの約束を，後の同じ条件での測定がそれを示したときにだけ果たされたと認めることである。CADLは部品を新規性として主張しない。理由の欄，ハッシュ連鎖，委任とその来歴，事後評価，GSNの生成は確立している。LLMへの委任とエージェントの監査記録の研究は急速に現れているので，この比較は2026年11月時点の文献に基づく。

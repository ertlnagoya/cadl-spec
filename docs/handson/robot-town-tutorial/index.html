Course D — Robot Town: Amending Rules Toward a KPI

⬅ Back to Course A → Course A — Robot Delivery

Audience: Students who have completed Course A (CADL/SoS-DSL basics). Course B is not required.

Time: 120–150 minutes, plus optional stretch goals.

You will leave with: KPIs written by a human in natural language, the LLM's amendment proposals and decision requests, the human's decisions with their reasons (in prose and in GSN), and the versions of the CADL rules and of the constitution that resulted, period by period.

0. What this course demonstrates​

Courses A and B write a contract once and check a simulation against it. In Course D the contract itself changes while the system runs. Three delivery companies (A, B, C; two robots each) share the 11-node road network of the Raspberry Pi Mouse simulator. After each simulated hour (one period), amendments to the rules are considered.

A human, an LLM and a set of mechanical gates share the work:

WhoDoes what
Human (the service operator)Writes the service KPIs in natural language; the KPIs may change over time. Answers the LLM's decision requests and records the reason and the outcome, in prose or in GSN
LLMTurns the KPI into measurable metrics and proposes amendments to rules, regulation and contracts toward it. When a question cannot clearly be settled, or when human stakeholders must agree, it does not decide: it asks the human and supplies what the decision needs
GatesCheck, constitution, improvement measured on the same random seeds, and the companies' vote. The LLM's own account is never trusted; only measured values count
kpi.md (written by a human in natural language; may change per period)
   │  the LLM turns it into a measure; if it can be read several ways, the human picks  ← request K<k>
   ▼
measure robot_town.cadl (version k) in this period's environment
   │  the LLM proposes amendments (rules, contract, regulation)
   │  gates: check → constitution → improvement (same seeds) → vote
   ▼
does any proposal raise agreement, contract, regulation, safety, KPI conflict or uncertainty, or did the LLM ask?
   ├ no  → adopt automatically the gate-passing proposal with the best KPI
   └ yes → the LLM writes a decision request and the human answers                 ← request D<k>
   ▼
robot_town.cadl (version k+1) and the record of decisions (decisions.md, gsn.yaml)
   │  next period, the LLM reads the human's decisions and reasons before proposing

The exercise lives in the public repository cadl-robot-town. It needs neither Unity nor SUMO: the town is a small Python simulation, and the norms are judged by the same reference runtime as Course A (contract_engine.py, copied from cadl-raspimouse-simulator).

About the recorded LLM output

§4–§8 can be followed without an API key by replaying the records in examples/steward-d-en/ (English) and examples/steward-goodhart/. They are records of real runs with Claude Opus 5.5 on 2026-10-29/30; examples/steward-d/ holds the same run in Japanese. The answers to the decision requests (answers.yaml) were written by Claude playing the human operator when the records were made; from §4 on, answer them yourself. Every number shown is measured by the gates and the simulation on replay. §10 shows how to run a real LLM with your own key.

2. Read the rules, the contract and the regulation (15 min)​

Open cadl/robot_town.cadl. The town has two contracts.

  • DELIVERY_SLA: one instance per order. Pick up within 120 s and deliver within 120 s of pickup, or the order becomes Late. This is the promise to customers.
  • ROAD_USE: one instance each time a robot stops on the road to wait for its next order.
    - id: DELIVERY_SLA
      parties: [TOWN_STEWARD, "ROBOT[*]"]
      guarantee:
        - "pickup_time <= 120s"         # @amend:pickup_deadline
        - "dropoff_time <= 120s"        # @amend:dropoff_deadline
      lifecycle:
        ...
          - id: pickup
            from: Assigned
            to:   PickedUp
            on:   "ROBOT[i].status == PickedUp"
            deadline: 120s            # @amend:pickup_deadline
            on_violation: { transition: Late, severity: Major }
        ...
    - id: ROAD_USE
      parties: [TOWN_STEWARD, "ROBOT[*]", COUNCIL]
      authority:
        decision_holder: COUNCIL
      incentives:
        type: sanction
        lambda: 0.5                   # @amend:sanction_lambda
      lifecycle:
        states: [Holding, Overstay, Released, Evicted]
        initial: Holding
        terminal: [Released, Evicted]
        transitions:
          - id: release
            from: [Holding, Overstay]
            to:   Released
            on:   "ROBOT[i] -> TOWN_STEWARD : node_released"
            deadline: 60s             # @amend:hold_limit
            on_violation: { transition: Overstay, severity: Minor }
      monitors:
        - id: blocking_guard
          observe: "ROBOT[i].blocking"
          sampling: periodic(1000ms)
          rule: "ROBOT.blocking >= 3 AND state IN [Holding, Overstay]"  # @amend:block_k
          on_match: { transition: Evicted, severity: Major }

(Excerpt, simplified.)

A line tagged # @amend:<name> holds a parameter that may be amended. When several lines carry the same name (the pickup guarantee and the pickup deadline), they must all hold the same value. Which layer a parameter belongs to and how far it may move is set by constitution.yaml:

amendable:
  hold_limit:       {layer: rule,     min: 10, max: 120, step: 10}   # seconds a robot may wait on the road
  block_k:          {layer: rule,     min: 1,  max: 4,   step: 1}    # robots waiting behind it before eviction
  sanction_lambda:  {layer: rule,     min: 0.0, max: 2.0, step: 0.5} # sanction points per violation (Minor 1, Major 3)
  to_central:       {layer: rule, safety: true, ...}                  # operating-mode switch (§9)
  pickup_deadline:  {layer: contract, min: 60, max: 180, step: 30}   # promised seconds to pickup
  dropoff_deadline: {layer: contract, min: 60, max: 180, step: 30}   # promised seconds to delivery
invariants:
  min_company_on_time_rate: 0.6
vote:
  quorum: 2
regulation:
  invariants.min_company_on_time_rate: {min: 0.5, max: 0.95, step: 0.05}
  vote.quorum:                         {min: 1,   max: 3,    step: 1}

(Excerpt, simplified.)

There are three layers of amendment:

LayerCoversWho decides
RuleROAD_USE and the operating-mode switching conditionsadopted automatically if it passes every gate; the switching conditions (safety: true) are decided by the human
ContractDELIVERY_SLA (the promise to customers)customers have no vote, so the human decides
Regulationvalues in the constitution (invariants, quorum)the human decides

The three companies behave differently (town/policies.py): A always returns to its garage; B waits on the road for its next order but leaves 5 s before hold_limit, and does not wait on the road at all if a single waiting robot triggers eviction (block_k of 1); C waits until an order comes or it is evicted, unless sanction_lambda reaches 1.5, when it behaves like B. A robot stopped at an intersection blocks everyone who wants to pass through it.

4. Write the KPI (15 min)​

The human's first job is to write the KPI. In English it goes in kpi.en.md:

## From period 1

Deliver as many orders as possible across the town within the times we promised customers
(120 seconds from order to pickup, 120 seconds from pickup to delivery). No company's customers
should be kept waiting badly.

## From period 5

The quiet season begins and orders fall. On-time delivery still matters, but to keep the
companies cooperating, no single company should gain or lose because of how the road is used.

A ## From period k heading says when a KPI takes effect (the Japanese file, kpi.md, uses ## 第 k 期から). The loop re-reads the file at the start of every period, so you may edit it between periods. --lang en makes the loop's own text and the LLM's writing English.

A natural-language KPI cannot rank proposals by itself. The LLM rewrites it as a combination of the metrics in town/kpi.py (on-time deliveries, late deliveries, unfinished orders, blocked time, the lowest company's on-time rate, the spread of the companies' utilities, total sanctions, and so on). This is the measure: a main goal (improvement is measured by it), watched goals (the human is told if they get worse by more than the noise) and conditions (which every amendment must keep).

Replay the record and run one period. Without --answers, you answer decision requests in the terminal.

python -m town.steward --lang en --mode DISTRIBUTED --rounds 1 --name try-d-en \
    --llm replay --replay-dir examples/steward-d-en
  KPI (from period 1): Deliver as many orders as possible across the town within the times we promised customers (120 seconds from order to pickup, 120 seconds from pickup to delivery). No company's customers should be kept waiting badly.
  LLM: replay: examples/steward-d-en/p1-kpi.json (claude-opus-5-5, input 2428 / output 2266 tokens)

The second part, 'no company's customers should be kept waiting badly', is a fairness floor across companies A, B and C. (…)
   [1] Maximize town-wide on-time deliveries with a floor on the worst company: main goal on_time_deliveries (increase), min_company_on_time_rate (increase), unfinished (decrease), late_deliveries (decrease); conditions min_company_on_time_rate >= 0.8, unfinished <= 3
   [2] Maximize the worst company's on-time rate (maximin fairness first): main goal min_company_on_time_rate (increase), on_time_deliveries (increase), unfinished (decrease); conditions unfinished <= 3
   [3] Maximize town-wide on-time deliveries with a cap on the inter-company gap: main goal on_time_deliveries (increase), on_time_rate_gap (decrease), min_company_on_time_rate (increase); conditions on_time_rate_gap <= 0.15
   Concern: 'Kept waiting badly' is not quantified. It could mean an absolute floor per company, a limit on the spread between companies, or no orders left undelivered. The numeric thresholds in the guards are provisional guesses and should be set from baseline measurements.
   Concern: on_time_deliveries is a proxy that ignores orders already past their deadline. Optimizing it alone could deprioritize late orders and leave them unfinished, which is exactly the badly-kept-waiting outcome the KPI forbids. (…)
   Concern: The promised times (120 s / 120 s) are part of the KPI and of DELIVERY_SLA. Raising the on-time count by loosening the SLA would game the metric, and any SLA change must be decided by humans as a contract amendment.

  → Decision request K1 (the LLM recommends 1)

This replays what Claude Opus 5.5 actually wrote on 2026-10-29. When a KPI has a single reading and no concern, the LLM uses its measure without asking. Here it found "kept waiting badly" unquantified and returned three measures with five concerns. The machine checks the metric names and the shape of every measure the LLM writes; one that uses an unknown metric is dropped from the choices.

After you pick a number you are asked for a reason and for assumptions (GSN Assumptions; any number of lines, an empty line ends). The recorded answers (examples/steward-d-en/answers.yaml) were written by Claude playing the operator when the record was made:

K1:
  choice: "1"
  reason: Follow the order of the KPI. Town-wide on-time deliveries are the main goal, and the worst company's on-time rate, unfinished orders and late deliveries are watched. The floors are provisional, as the LLM says; 0.8 keeps today's worst company (0.84) from falling further. (…)
  assumptions:
    - Customers cannot choose their delivery company

(The "watched goals and conditions" and "notes" columns are left out here; the note on R1 reads "the current rules meet the new condition".) The LLM's first proposal, block_k 3 → 2 (evict a robot as soon as two robots wait behind it), adds 9.2 on-time deliveries but is voted down by B and C. It also proposed a regulation: raising the constitution's floor on every company's on-time rate from 0.6 to 0.65. It proposed no contract change, having read at K1 that loosening the promised times does not count as improving the KPI.

The loop does not decide when a proposal raises any of the following (triage() in town/steward.py):

ReasonWhen
Agreementit improves the KPI but is voted down, and beats every proposal that could be adopted automatically
Contractit changes the promise to customers and improves the KPI
Regulationit changes a value of the constitution
Safetyit changes an operating-mode switching condition and improves the KPI
KPI conflictit improves the main goal but breaks a KPI condition or worsens a watched goal
Uncertainit passes every gate but improves on fewer than 4 of the 5 seeds
LLMthe LLM itself said a human should decide (only for proposals that keep the constitution's invariants)

Here proposal 1 raises agreement and R1 raises regulation. The LLM writes decision request D1, saved as runs/try-d-en/p1-request.md:

  → Decision request D1 (LLM: replay: examples/steward-d-en/p1-request.json (claude-opus-5-5, input 2712 / output 1957 tokens))

A request contains the question; why the LLM is not deciding; for each option what happens and who gains or loses; the LLM's recommendation; and what the LLM does not know. The options are the proposals that raised a reason, the proposal that could be adopted automatically (if any) and "keep"; the LLM cannot add options. The table of numbers is the gates' measurement, not the LLM's prose.

The recorded answer goes against the LLM's recommendation and adopts proposal 1, overturning the vote:

D1:
  choice: "1"
  reason: The intersections are a road shared by the three companies; waiting there is no company's right. Late deliveries fall from 10.4 to 1.2 and the worst company's on-time rate rises, so adopt it against B's and C's votes. Re-measure C's utility (28.8 to 19.0) and the road violations next period. The constitutional floor (R1) can wait; it changes nothing now.
  assumptions:
    - B and C keep delivering in town after the rules change

The same period in Japanese (examples/steward-d/) produced no regulation proposal, and its recommendation changed when the request was sent a second time on the same numbers (first "1", then "keep"). A recommendation is the output of one request. The LLM laid out the material and showed that both choices had reasons; the human decided.

The record of decisions​

Each decision goes into two files in runs/<name>/:

  • decisions.md: the prose record — for each decision, the measure, the LLM's assessment, why the human was asked, the LLM's recommendation and unknowns, and the human's choice and reason.
  • gsn.yaml: a GSN (Goal Structuring Notation) tree, with a Mermaid diagram in gsn.md.
GSN elementWhat goes in it
Goalthe KPI written by the human (one per version)
Strategythe decision of a period (the amendment adopted, or no change)
Solutionthe measurement on the same seeds (p<k>-evidence.md)
Contextthe measure of the KPI; the period's environment
Assumptionassumptions written by the human
Justificationthe human's reason (or, for an automatic decision, its condition)

Reasons may be written in prose or as GSN elements; in the --answers YAML, list elements (each with type: and text:) under gsn:. For example (the recorded answer to D2 gives its reason in prose):

D2:
  choice: keep
  gsn:
    - type: justification
      text: Only 2 of 5 seeds improve; do not cut C's utility by 16 for an uncertain gain
    - type: context
      text: In D1 we decided to re-measure C's utility

From the next period on, earlier decisions and the human's reasons are passed to the LLM. §6 shows how that changes its proposals and recommendations.

Things to notice:

  • Period 2: block_k 2 → 1 passes every gate, but only 2 of 5 seeds improve. The LLM also asked on its own, citing the human's promise in D1 to re-measure C's utility. 7. The KPI changes (15 min)​

From period 5, the other section of the KPI file takes effect. When the KPI changes, the LLM rewrites the measure and lists earlier decisions whose premises no longer hold:

  KPI (from period 5): The quiet season begins and orders fall. On-time delivery still matters, but to keep the companies cooperating, no single company should gain or lose because of how the road is used.
   [1] Fairness of utility first, on-time delivery watched: main goal utility_gap (decrease), on_time_deliveries (increase), on_time_rate_gap (decrease), sanction_total (decrease); conditions min_company_on_time_rate >= 0.8, unfinished <= 3
   [2] Fairness of on-time rates first: main goal on_time_rate_gap (decrease), on_time_deliveries (increase), utility_gap (decrease), min_company_on_time_rate (increase); conditions min_company_on_time_rate >= 0.8, unfinished <= 3
   [3] On-time delivery first, fairness watched: main goal on_time_deliveries (increase), utility_gap (decrease), on_time_rate_gap (decrease), late_deliveries (decrease); conditions min_company_on_time_rate >= 0.8, unfinished <= 3
   Concern: A gap metric can be improved by levelling down: making the best-off company worse instead of helping the worst-off one. (…)
   Concern: 'No company should gain or lose' may mean no company ends up worse off than under the current rules. No available metric measures each company's change against today. (…)
   (2 more)
   To review: K1 — K1 made town-wide on-time deliveries the main goal. The new KPI puts fairness between companies first and on-time delivery second, so the main goal and its guards need to be chosen again.
   To review: D1 — D1 (block_k 3 → 2) was adopted against B's and C's votes, and C's utility fell from 28.8 to 19.0. The new KPI says no company should lose because of how the road is used. (…)

Exercise 7-1​

  1. Pick measure 3 at K5 (copy answers.yaml and edit K5) and run period 5. How do the options of the decision request change? The recorded request was written for measure 1; what happens to it?
  2. Under which measure, and if the LLM had not written what, would switching off sanctions be adopted automatically without a request? Is that desirable? In a replay the KPI reading is the recorded one, so to try a rewritten KPI file you need a real LLM (§10).

8. A KPI that is a proxy (15 min)​

What happens when the KPI aims at a convenient stand-in (a proxy)? examples/steward-goodhart/kpi.en.md says:

## From period 1

Make sure the road rules are kept. Reduce road-rule violations as much as possible.
python -m town.steward --lang en --kpi examples/steward-goodhart/kpi.en.md --mode DISTRIBUTED --name goodhart-en \
    --llm replay --replay-dir examples/steward-goodhart/en --answers examples/steward-goodhart/en/answers.yaml

The LLM warned that "road_violations is defined by the rules themselves. A ROAD_USE amendment that lengthens release deadlines or weakens or removes blocking_guard would lower the count without making robots behave better", and offered only measures that also watch blocked time and service: (1) the count as main goal, watching blocked time, on-time deliveries and unfinished orders; (2) blocked time as main goal, watching the count. It offered no count-only measure at all. Its two proposals both tighten (sanction_lambda 0.5 → 1, block_k 3 → 2); neither reduces the count (+0.0 and −8.2: evicting earlier counts more evictions), so nothing is adopted.

In Japanese (examples/steward-goodhart/proxy/ and guarded/), the LLM did offer a measure of the count plus on-time deliveries only, with the same warning, and recommended the one with more watches. Even when the human chose the count-only measure, the LLM proposed no loosening, writing that loosening would cut the count but run against "make sure the rules are kept".

There is no guarantee that an LLM will read the KPI's intent as it did here. Choosing the measure is the human's job, and when a loosening is proposed, what stops it is the watches and the human's decision.

The switching conditions are written in the CADL file and evaluated every 5 minutes over the last 5 minutes:

  transitions:
    - from: DISTRIBUTED
      to: CENTRALIZED
      condition: "orders_in_window < 22"      # @amend:to_central
      protocol: SWITCH
      safety_invariant: "robots_on_road == 0"
    - from: CENTRALIZED
      to: DISTRIBUTED
      condition: "orders_in_window >= 26"     # @amend:to_distributed
      protocol: SWITCH

A switch to centralized takes effect only once no robot is waiting on the road (C stalls for 30 s; anything still there after 60 s is evicted by the steward), and the safety_invariant is checked at that moment. Compare three ways of running a period with a rush:

python -m town.compare cadl/robot_town.cadl --rush 1200 2400 25 --mode DISTRIBUTED
python -m town.compare cadl/robot_town.cadl --rush 1200 2400 25 --mode CENTRALIZED
python -m town.compare cadl/robot_town.cadl --rush 1200 2400 25 --mode adaptive

The mode switches three times in the period: to centralized after 5 minutes, to distributed for the rush, and back to centralized after it. Now make the switch take effect without waiting for the road to clear:

python -m town.period --rush 1200 2400 25 --no-quiescence

The last line reports about 1.4 safety-invariant breaches per period (安全条件の違反 1.4 回).

The two switching thresholds are marked safety: true in the constitution. With town.steward in --mode adaptive (the default), any proposal that changes them and improves the KPI is always brought to the human as safety.

10. Run with a real LLM (optional, 15 min)​

The records in §4–§8 come from real runs with Claude Opus 5.5 on 2026-10-29/30. With your own API key the LLM answers afresh each time, so you will get proposals and recommendations different from the records.

export ANTHROPIC_API_KEY=...        # type your own key; never paste it into a chat or a file
python -m town.steward --lang en --mode DISTRIBUTED --rounds 6 --name live-d-en
python -m town.steward --mode DISTRIBUTED --rounds 6 --name live-d      # Japanese; KPI in kpi.md

Each period sends up to three requests: rewriting the KPI (when it changed), proposing amendments, and writing a decision request (only when one is needed). The LLM's outputs are saved in runs/<name>/llm/. Without a terminal and without an answer, the loop writes the decision request to p<k>-request.md and stops; write your answer to a YAML file and rerun the same command with the same --name, adding --answers <YAML>, and the recorded LLM outputs are reused instead of being requested again.

The six periods of the records used about 60,600 input and 52,200 output tokens in English, and 61,600 and 52,800 in Japanese. One request took from 20 seconds to 2 minutes; once, a request had no response after 11 minutes and was retried.

What the real runs showed​

  • Recommendations vary. In Japanese, the D1 recommendation changed from "1" to "keep" when the same request was sent again; in English, the LLM recommended a regulation (R1) that the Japanese run never proposed. The value of a decision request lies less in its recommendation than in laying out the question, who gains and loses, and what is unknown.
  • The LLM's unknowns point at gaps in the tool. The first version of the table did not show the values of the watched goals; the LLM wrote that it did not know "on_time_rate_gap が具体的に どれだけ悪化したか（表には最低の定時率しか載っていません）" ("how much on_time_rate_gap worsened; the table only shows the lowest on-time rate"), so the table gained a column of watched goals and conditions. Not knowing the quorum (period 2, §6) is not fixed yet (§11).
  • Past reasons shape later recommendations. In period 2 the LLM cited D1's promise to re-measure, and in period 6 D5's reason for 70 s.

12. What the specification cannot express yet​

Building this exercise exposed these gaps in CADL 0.3 / cadl 0.3.18:

  • cadl sim-ir does not emit sos.transitions[*].safety_invariant into the IR (cadl check does check it as an expression). The exercise reads it from the checked source file.
  • An operating mode (regime) is only a name; there is no syntax to bind parameter values or contracts to it. What changes in centralized mode (bays, exclusive edges) is decided by the simulator.
  • Which layer (rule or contract) a parameter belongs to, and who decides its amendment, is written in constitution.yaml and in # @amend: comments, not in CADL.
  • A metrics target is a single expression: there is no syntax for a KPI that changes over time, or for the choice of how a KPI is measured, and none to link the record of human decisions (GSN) to a version of the rules. The exercise keeps kpi.md, decisions.md and gsn.yaml outside the rules.

Up to cadl 0.3.11, an unreadable value such as deadline: soon passed cadl check and became null in the IR; from 0.3.12 it is an error. The exercise also rejects rules whose IR lacks a value the town needs, so the check gate works even with an older compiler.

Summary​

  • The KPI is written by a human in natural language and may change over time. The LLM turns it into a measure, but when it can be read several ways or relies on a proxy, the human chooses.
  • The LLM proposes amendments to rules, regulation and contracts toward the KPI. Matters needing stakeholders' agreement, the promise to customers, regulation, safety, conflicts within the KPI and uncertain improvements it does not decide: it hands them to the human with the measurements, who gains and who loses, and what it does not know.
  • The human's decisions and reasons are kept, in prose and in GSN, alongside the versions, and change the LLM's next proposals and requests.
  • What finally backs an adoption is the gates — check, constitution, measured improvement and the parties' agreement — together with the reasons the human left.

Appendix D — Codegen Target Catalog

This appendix enumerates the code-generation targets defined by CADL v0.3 and the mapping to the reference implementation's directory layout. Appendix A §A.9 defines the EBNF for codegen: entries; this appendix pairs each target name with its category, intended artifact, and implementation location in the reference implementation (cadl 0.3).

D.1 Target catalog​

The name python denotes the runtime-code target in a codegen: entry; the simulator configuration of the same name is requested with cadl sim-gen. The Python simulator config therefore cannot be requested from a codegen: entry in v0.3; use cadl sim-gen -t python. In the reference implementation (cadl 0.3) the target is selected on the command line as shown in the last column; codegen: entries in the file are parsed but do not yet drive generation. From cadl 0.3.9, an entry that names a target the implementation cannot emit gets a warning (D.4).

For a file that declares the norms extension (Appendix F), the python target also emits the module norms_monitor.py (from cadl 0.3.22). It monitors the norms: and counts_as: blocks and the assume: and guarantee: items of each contract, including the items with temporal operators, for one contract instance while the system runs: it is given one observation at a time and returns the norm instances and items whose state or verdict (pending, fulfilled, violated, excused) changed. Unlike the other modules of the package, it does not import cadl: it carries the declared actors and the contracts as data (one JSON text) and the evaluation code of cadl norms-eval, and uses only the standard library of Python. The generator checks the module before it writes it and writes nothing when the check fails. F.10 gives the details. The solidity and opa targets leave the items with temporal operators out of the contract policy, with a comment, and monitor them, with the norms, in a separate file per contract (from cadl 0.3.25; D.5). The unity-csharp target does not monitor norms.

D.2 Two-tier generator layout​

The reference implementation splits codegen into two tiers, reflecting whether the output is code that enforces or executes the contracts or a configuration for a simulator:

src/cadl/
├── codegen/            ← code tier (cadl codegen)
│   ├── *_gen.py        ← Python runtime package
│   ├── solidity/       ← smart-contract enforcement of contracts
│   ├── opa/            ← policy enforcement (Rego) of contracts
│   └── unity_csharp/   ← Unity C# lifecycle / monitor runtime
└── sim/                ← simulator tier (cadl sim-gen)
    ├── ir.py           ← three-layer simulator IR
    ├── gen_unity.py
    ├── gen_go.py
    └── gen_python.py

A single CADL source file MAY declare targets from both tiers in one codegen: block. The processor SHOULD dispatch each target to its tier independently.

D.3 Selection guidance​

  • Pick unity when the experiment is a multi-agent simulation with graphical inspection, and unity-csharp when contract lifecycles and monitors (Appendix E) are to run inside that simulation.
  • Pick python when you want an executable runtime skeleton of the actors, contract monitors, and protocols, or when the norms of Appendix F are to be monitored while the system runs; ros2 is reserved for driving actual robots and is not implemented in cadl 0.3.
  • Pick solidity when the Institution-layer contracts must be enforced on-chain (blockchain deployment).
  • Pick opa when contracts should be enforced as policies at API / service boundaries (policy-as-code).

Multiple targets in one file are permitted but the resulting artifacts are independent — the CADL toolchain does not guarantee runtime interoperability between, e.g., a Unity simulator config and a Solidity contract generated from the same source.

D.4 Conformance​

A processor is codegen-core-conforming if it supports at least one target from each tier (for example unity together with solidity or opa).

A processor that cannot emit a requested target MUST report a clear diagnostic (for example, "codegen target ros2 is not supported by this processor") rather than silently skipping it.

D.5 Norms monitors of the opa and solidity targets​

For a file that declares norms: 0.1, the opa and solidity targets of the reference implementation emit, from cadl 0.3.25, one monitor of the norms per contract next to the contract policy: opa the Rego package cadl.norms_monitor.<contract> in norms_monitor_<contract>.rego, and solidity the contract <Contract>NormsMonitor in <Contract>NormsMonitor.sol. A monitor evaluates the norms: and counts_as: blocks and the assume: and guarantee: items of one contract instance, including the items with temporal operators, which the contract policy leaves out. One observation is processed in the order of F.5, as cadl norms-eval processes it.

Supported constructs. Both monitors evaluate message events (with the actor patterns of F.3 and arguments), institutional events, predicates with the three-valued reading of F.5 (comparisons, IN, AND, OR, NOT, arithmetic, quantities with and without an actor, fields of request, now, state), triggers, until:, deadlines, reparations, the effects of powers, counts-as rules with if:, and the temporal operators of F.4, also nested. They do not evaluate quantifiers, aggregates, wildcard or range references in predicates, an index that is an expression (A[i+1]), or amendments (F.6). A contract that uses one of these in a norm, a counts-as rule, or an assume: item gets no monitor, and the processor reports which construct prevents it; such a guarantee: item, on which no other verdict depends, is left out of the monitor with a warning. Both compute exactly (F.5): the Rego monitor with decimal numbers, so it refuses /, whose result is not always one. The Solidity monitor uses fixed-point numbers with six decimals and therefore also refuses *, /, and literals with more than six decimals; outside the content of a norm it scans the window of a temporal operator once, as the observations arrive, and therefore refuses there a temporal operator inside another one; in the content of a norm it refuses five or more temporal operators and the temporal operators inside another one whose values are not decided in the order of the observations (see below); and it refuses a contract whose creation code would exceed the 49152 bytes of EIP-3860 or whose runtime code would exceed the 24576 bytes of EIP-170 (cadl codegen estimates both sizes from above). In a guarantee: item these lead to the item being left out, as above. An observation with amend is refused at run time.

The Rego monitor. The Rego monitor is a step function. OPA keeps no state, so the policy computes the next state of the monitor from the previous state and one observation; the host stores the state between calls. The rule result takes as input:

finishtrue instead of an observation: the instance ends at its last observation (step 6 of F.5)
bindings, requestBindings and request of the instance, when the first observation does not carry them

result has state (the next state), changes (each norm instance whose state or verdict changed, with the previous ones, and each item that was decided), violations, institutional_events, powers_exercised, unauthorised, verdicts (the state and verdict of every norm, the status of every assumption, the verdict of every guarantee, and ok), ended, and next_deadline (the earliest deadline of an active obligation or prohibition). For an observation that is malformed, result has error and the unchanged state. The state is a JSON object with these keys:

The Solidity monitor. The Solidity monitor is a contract that keeps the state of one contract instance. Its constructor takes the address of the reporter (the deployer when it is the zero address, reporter()); only the reporter may call begin, observe, addQuantities, and finish. The reporter cannot be changed: if its key is lost, the monitor stays as it is and records no further observation. begin(bindings, request, quantities) may be called before the first observation, observe(t, values, messages, hasState, state, end) records one observation, addQuantities(names) adds names of quantities written without an actor, and finish() ends the instance at its last observation. verdicts() returns the states and verdicts of the norms and the marks of the items, in the order of normIds(); contractId(), ok(), nextDeadline(), observations(), lastT() (the time of the last observation, also of one after the end), ended(), and ignored() (the number of observations after the end) can be read, and the events NormChanged, ItemChanged, Violation, InstitutionalEvent, PowerExercised, and Unauthorised report the changes of each call. A value is a tuple of a name, a kind (null, boolean, number, string), a number, and a string; numbers, including the time, are fixed-point numbers times 106. The time is an argument of observe so that a trace can be replayed and tested; a deployment MAY pass block.timestamp times 106. A malformed observation reverts, which leaves the state as it was. The contract stores the model of the CADL contract as data, filled in by its constructor, and interprets it. The model and the state are one struct in storage, which six libraries read and change: they hold the evaluation of predicates, the functions without state, the judgement of contents with one temporal operator, that of contents with two to four or with one inside another, the items, and the events, messages, counts-as rules and powers, so that each runtime code stays within the size limit of EIP-170. From cadl 0.3.28 the runtime code of the contract is estimated at 16 840 bytes, which leaves more than 7 × 103 bytes below that limit (24 410 in 0.3.27); from cadl 0.3.30, without the frozen flag of a norm, which the engine no longer needs (F.7, N-16), it is estimated at 16 670 bytes, and CadlNormsActs at 12 080 bytes (12 170 before). From cadl 0.3.29 the libraries CadlNormsMulti and CadlNormsEval are estimated at 7 490 and 10 410 bytes (4 430 and 10 310 in 0.3.28), and the size of the code does not depend on the number of temporal operators. The cost of an observation does not grow with the number of earlier observations: the window of a temporal operator is scanned once (each observation adds its own value to the scans that are open), a value is found by binary search, and the values that no later step can read are deleted, a few per new value.

One temporal operator. The content of a norm with one temporal operator is decided, at the observation of a candidate, up to that operator: the rest of the content has its value there (its names are fixed, see the differences below), so the content is a function of the value of the operator, and the monitor reads it there with the operator undecided, true, and false. The content is then true whatever the operator gives (the candidate holds at once), never true (no candidate), true exactly when the operator is true, true exactly when it is false, true when it is true or false, or never true but undecided until the operator is decided (the candidate keeps the norm pending, as F.5 does). An undefined operator makes the content true only when the content is true with the operator undecided, so these cases are all: a comparison, an arithmetic operation, and the left side of IN are undefined when an operand is, and AND, OR, and NOT give a true or false result for an undefined operand only when they give it for an undecided one. This covers an operator under NOT, inside a comparison (within(3s, p) == flag, until(p, q, 3s) <= A.y), and in IN. A norm keeps three queues of candidates, oldest first: those that hold when the operator is true, those that hold when it is false, and those that only wait for it; a candidate that holds in both cases is in the first two. The second queue reads the dual operator on the negated operands: NOT within(d, p) is throughout(d, NOT p), NOT throughout(d, p) is within(d, NOT p), and NOT until(p, q, d) is the release below. Each queue keeps, with what the observations since its last judgement say about the operands: for within, the first time the operand is true; for throughout, the first time it is false and the first time it is undefined; for until, the first observation at which q is true and the first at which p is not; for the release, these two, the first observation at which q is not false, and the first at which p is false. Together with the last candidate whose window has seen an operand that rules it out, these decide every candidate by comparing times (for throughout, the newest candidate whose window ended before the first false or undefined value holds), with a few binary searches over the queue and without scanning a window per candidate; this holds also while the norm is suspended. Decided candidates are deleted a few per observation.

Release. Write the values of a predicate at an observation in the three values of F.5 (true, false, undefined) with the connectives of Kleene, and let W be the observations of the window of candidate k. By F.4, until(p, q, d) at k is

∨j ∈ W ( qj ∧ ∧k ≤ i < j pi ),

decided at the first observation at which a term is true, at the first at which p is false (every later term is false), or when the window is over, and undecided before. The negation of Kleene is an involution and satisfies the laws of De Morgan, so

NOT until(p, q, d) = ∧j ∈ W ( ¬qj ∨ ∨k ≤ i < j ¬pi ),

the release of ¬p and ¬q: ¬q holds at every observation of the window up to and including the first at which ¬p holds. NOT keeps an undecided value undecided and turns a decided value into its negation, so the release is decided at the same observations as until. It is true exactly when every term is false. Let b be the first observation of W at which p is false, or the last of W when there is none. A term with j after b is false through pb. A term with j at or before b has no false pi, so it is false exactly when qj is false. Hence the release is true exactly when q is false at every observation of W up to b, and it is false or undefined otherwise; with undefined values this is the same statement, since a term with an undefined qj and no false pi is not false. The queue of the release therefore holds a candidate when p is false inside its window with q false before and at that observation, or when its window is over with q false in it; it removes every candidate when p is false (each window is then decided), the candidates for which until becomes true (q true with p true since the candidate), and those whose window is over; a candidate that has seen q not false is kept, undecided, until it is decided in one of these ways.

Several temporal operators. For a content with m temporal operators, 2 ≤ m ≤ 4, the monitor reads the content once at the observation of a candidate and obtains its value for each of the 4m combinations of values of the operators (undecided, true, false, undefined), as bits of one 256-bit word; this covers a comparison of two operators (within(…) == throughout(…)). An observation decides an operator for a range of candidates at a time: the candidates whose window is over become false (throughout: true), or undefined when an operand was undefined in the window; an operand true for within, false for throughout, or p false for until decides every open window; q true for until decides the candidates with p true since them. Binary searches over the candidates find these ranges. The candidates are the leaves of a segment tree in storage. A node gives each operator a state: decided, or undecided and taking one of the four values in the future considered. For each of the 5m combinations of states it records whether a candidate below holds in that future and whether one is undecided in it. A decided operator leaves no value in the node: its value is already part of the values of the content that the candidate keeps for the other operators. The 2 × 5m bits fit in one word for m ≤ 3 (250 bits, with 6 bits for the tags of the lazy propagation) and in five words for m = 4 (the state of the fourth operator selects the word). Deciding operator i to the value v moves the combinations in which i is undecided and takes v to those in which it is decided, and drops the other combinations in which it is undecided: for the first three operators a shift and a mask of each word, for the fourth an OR of words. This is propagated lazily, so an observation changes a few ranges per operator, each in steps that grow with the logarithm of the number of candidates, and the root says whether a candidate holds and whether one is undecided. The cost of an observation therefore does not grow with the number of observations for any m ≤ 4, and it grows with m by a factor measured below. Five or more temporal operators in one content are refused: the 45 values of the content do not fit in one word, and a node would have 25 words. (Up to cadl 0.3.28 a node kept the values of the decided operators too, 7m pairs, which allowed two operators in one word.)

A temporal operator inside another one. In the content of a norm, the operand of within(d, …) or throughout(d, …) may be another within(e, p) or throughout(e, p), or its negation, where p has no temporal operator (within(5s, throughout(2s, p)), throughout(3s, NOT within(1s, p))). The value of the inner operator at an observation j is known only later; the outer operator reads the sequence of these values, each with the time tj of its observation. The monitor decides the inner operator for every observation from the first candidate of the activation on, with a summary of its own, and feeds the decided values to the outer operator in the order of the observations; the outer operator is one operator of the segment tree above. within(e, p) is NOT throughout(e, NOT p) (negation in Kleene's logic keeps undecided and undefined values and exchanges true and false, so both are decided at the same observations to opposite values), so let the inner operator be Xj = throughout(e, p′) and the operand of the outer one Yj = Xj or NOT Xj. Let F(n) be the first observation whose inner value is not decided at observation n (n + 1 when there is none).

  1. The inner values decided at n are those of the observations before F(n). Let Xj be decided at n and i < j. If Xj is false by a false p′ at an observation x of its window, either x is in the window of i, which makes Xi false, or the window of i ended before tx ≤ tn, which decides Xi. If the window of j is over at n, so is the window of i, which ends no later.
  2. An observation n decides at most three runs of inner values, in this order. The observations from F(n − 1) up to the first observation b with tb + e ≥ tn (a binary search over the times) have windows that end at n − 1: they were open at n − 1 and are over at n. Those up to the last observation u with p′ undefined are undefined, the others true (none of them has seen p′ false, or it would be decided already). When p′ is false at n, the observations from b to n are false. F(n) is n + 1 when p′ is false at n and b otherwise; the summary keeps F and u only.
  3. Let τ be tF(n) when F(n) ≤ n and tn otherwise. A run of fed values Ys, …, Ye with the decisive value (true for within, false for throughout) decides the candidates k ≤ e with tk + d ≥ ts, whose windows hold an observation of the run; a run of undefined values marks the candidates up to e. A candidate with tk + d < τ that is not decided becomes undefined when marked, and false for within (true for throughout) otherwise, after the runs of n are fed. A mark reaches only candidates whose window holds an undefined value. A run of undefined values starts at F(n − 1). When F(n − 1) ≤ n − 1, τ was tF(n − 1) at n − 1, so the candidates whose window ended before tF(n − 1) were decided at n − 1; a candidate up to F(n − 1) that is still undecided has that observation in its window, and a later one is itself in the run. When F(n − 1) = n, every value before n is decided, b = n, and n decides at most the run of false values from n, so there is no run of undefined values to mark.
  4. These are the values of F.5 at every observation. By 1 the values that F.5 reads in the window of candidate k at n are decided exactly when they are fed, so a decisive value decides k at the same observation. Without one, F.5 gives undecided while the window is not over or holds an undecided value. If F(n) ≤ n, XF(n) is undecided: when k ≤ F(n) and tF(n) ≤ tk + d it is in the window of k; when tF(n) > tk + d every value of the window is fed and the window is over, since tn ≥ tF(n); when k > F(n), Xk is undecided by 1 and k is in its own window, while tF(n) ≤ tk leaves the window of k open in 3. If F(n) = n + 1, every value is fed and τ = tn. In each case the monitor decides k at the observation at which F.5 does, from the same values, and so to the same value.

An observation evaluates p′ once, makes one binary search over the times, feeds at most three runs, and decides window ends once, each with a few binary searches and range updates of the tree, so its cost is bounded as above. Refused are until in a nesting, an operand of the outer operator that is more than the inner operator or its negation (within(5s, throughout(2s, p) AND r)), and three levels. In them a value of the operand can be decided before that of an earlier observation, and feeding the values in order would decide later than F.5. In within(5s, until(p, q, 3s)), with p undefined and q false at t = 0 and p and q true at t = 1, the inner value at t = 1 is true at once, so the outer operator at t = 0 is true at t = 1 in F.5, while the inner value at t = 0 stays undecided until its window ends after t = 3. In within(d, throughout(e, p) AND r) a false r decides the operand at once. Whether these contents can be monitored with bounded gas in some other way is left open.

The tree is not pruned: each activation of such a norm adds at least three storage slots per candidate (its observation, its time, its leaf, and the inner nodes above it), which stay in storage; the gas of an observation does not grow with them. Every monitor also keeps two entries per observation (its time and the lifecycle state before it), which are not deleted either.

Gas. The figures below are measured with one value per observation; with two values an observation costs about 20 % more. In the tests, an observation of the example of F.8 costs about 6.4 × 105 gas over 320 observations at one per second while the 300-second window of its assumption is open and after it (at most 1.2 × 106, at the first observation). At one observation per second into windows of 1000 seconds in which every candidate stays undecided, an observation costs, at the 320th and at the 1000th observation, 4.4 × 105 and 4.5 × 105 gas for the content throughout(1000s, …), 5.2 × 105 for NOT until(…, 1000s), 5.1 × 105 for throughout(1000s, …) == true, and 5.9 × 105 for within(1000s, …) OR throughout(1000s, …) (at most 8.0 × 105); from cadl 0.3.29 the last content costs 6.1 × 105 and 6.2 × 105, with a third operator (… OR within(1000s, …)) 8.4 × 105 and 8.5 × 105 (at most 1.1 × 106), with a fourth 1.8 × 106 and 1.9 × 106 (at most 2.6 × 106; the factors over two operators are about 1.4 for three and 3.0 for four, from the five words of a node), and the nested contents within(1000s, throughout(500s, …)) and throughout(1000s, within(10s, …)) 4.9 × 105 and 5.0 × 105, and 6.0 × 105 and 6.3 × 105 (at most 8.3 × 105; the inner values of the second are decided from the eleventh second on, and each then decides the candidates of its window false); cadl 0.3.25 read every candidate at every observation and used 1.3 × 107 gas at the 320th. A monitor whose observation would exceed the block gas limit cannot record it and does not recover, so the bound matters. The generated file is to be compiled with solc 0.8.24 to 0.8.37 (checked; its pragma is >=0.8.24 <=0.8.37) and --optimize --optimize-runs 1, as its header says: without the optimizer the runtime code exceeds the limit of EIP-170, and the estimates of the creation code and of the runtime code hold for the optimizer with 1 or 200 runs.

Differences from cadl norms-eval. The monitors decide each observation with the observations received so far, as the Python monitor does: a passed deadline is detected at the next observation, the instance ends with finish or with an observation that ends it, and the names of quantities written without an actor are those given with quantities (or addQuantities) and those observed so far. Where they differ from cadl norms-eval (which this appendix does not change):

  • Numbers and times are exact in both monitors, as in cadl norms-eval (F.5). The Rego monitor reads a number as the decimal it is written as and keeps numbers and times in its state as {"$q": [n, k]}, the number n / 10k; it refuses / (a quotient is not always a decimal number), and a product whose exact value could have more than 4095 decimals (every number has at most 400, F.5). Both monitors, like cadl norms-eval, refuse a number outside the range of F.5 in an observation, its request or its bindings. The Solidity monitor holds six decimals and refuses *, /, and literals with more decimals; its host passes numbers with at most six decimals. For the inputs that meet these limits, the verdicts agree with cadl norms-eval. The results of the Rego monitor write times as JSON numbers for reference.
  • The monitors refuse inputs that cadl norms-eval accepts: a binding that is not an integer written as one (1.0 and 1e2 are refused) or a string, a value of values that is a list or an object (in Rego a list anywhere in request too), in Rego two keys of values that differ only in whitespace, and an observation with amend. The Solidity monitor takes the request as leaves ("a.b"), the names of values in ASCII, and the actors and names of messages in ASCII letters, digits, and _. It receives bindings as integers or strings, so its host refuses a binding written with a fraction or an exponent.
  • In Solidity, a bare name read inside a temporal operator (a quantity such as flag in throughout(10s, A.s == flag), as opposed to a symbol) must be given in begin (or addQuantities before the first observation) when it is a quantity, or be observed at the first observation; a name that is a binding is not affected: the scans keep the values they have read, so an observe or addQuantities that would make such a name known later is refused (it reverts). cadl norms-eval and the Rego monitor read the earlier observations again with the new name.
  • The Rego monitor trusts the state it is given: it checks the format and the contract of the state, not its content. The host keeps the states it stores intact and passes each one to the next step only.
  • Reasons, warnings, and the timeline of cadl norms-eval are not reported.

Strings of the file. No text of the .cadl file is code in either monitor: the Rego carries the contract as one JSON text and writes the other literals as JSON strings, and the Solidity writes every text as a hex literal. The input check of cadl codegen applies first.

Verification. The reference implementation compares both monitors with cadl norms-eval after every observation: the norm states and verdicts, the item verdicts, the changes, the violations (with severity and sanction), the institutional events, the exercised powers, the unauthorised acts, and the next deadline, on the example traces, the traces of its test suite, random traces, and a long trace. The Rego runs in opa eval, the Solidity on an EVM.
